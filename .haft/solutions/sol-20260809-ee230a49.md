# Solutions for: Cursor cold-path: init'd Pysar MCP never becomes usable for end authors

Problem: prob-20260809-5a4334ac

## Variants (5)

### V1. Init rewrites Cursor mcp.json with a Cursor-visible binary path

Keep project MCP as the transport, but stop shipping bare command=pysar. At `pysar init --cursor`, resolve the running binary (or LookPath / known install locations) and write an absolute or ${userHome}/.local/bin/pysar command into .cursor/mcp.json so Dock-launched Cursor can spawn serve without shell PATH. Update goldens + docs to match.

**Strengths:**
- Small change surface (init + asset + tests)
- Matches Cursor docs (full path or PATH)
- Works with existing ps-* MCP I/O contract

**Novelty:** Fixes the host spawn contract at scaffold time inside the file Cursor already reads — no new distribution channel, no MCP bypass.

**Weakest link:** Does not by itself flip Cursor's 'disconnected/never createClient' enablement state; if Customize leaves project MCP off, a correct path still never spawns.

**Risks:**
- Machine-specific absolute paths in committed mcp.json if authors commit them
- Still depends on Cursor actually enabling the project server

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Necessary substrate for any project-mcp.json strategy; later deeplink/plugin variants still need a spawnable command.

**Diversity role:** scaffold/PATH fix

### V2. Cursor Marketplace / install-link first-class connect

Ship Pysar as a Cursor Marketplace plugin or official mcp install deeplink that registers the server into Customize's Connected surface the same way Cloudflare plugins appear — one Add to Cursor click after binary install, not buried project mcp.json archaeology.

**Strengths:**
- Matches where authors already look (Connected plugins)
- Can bundle skills+MCP like other Cursor plugins

**Novelty:** Moves distribution onto Cursor's 2026 Customize/Marketplace surface instead of treating project mcp.json as the primary UX.

**Weakest link:** Marketplace/plugin packaging + review + dual maintenance; cold path now has two install surfaces (binary + plugin) that can drift.

**Risks:**
- Latency/approval of marketplace
- Doesn't remove need for local binary for stdio serve
- May leave git-based project mcp.json as secondary/confusing

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Opens team marketplace / one-click install for non-CLI authors later.

**Diversity role:** distribution/infra swap

### V3. CLI mechanical I/O so cold path does not need live MCP

Add first-class `pysar` CLI commands for the same persistence ops MCP exposes (intake bundle save, author defaults read, etc.) and teach ps-* skills to use CLI when MCP tools are absent. Project MCP becomes optional acceleration, not a hard gate for /ps.

**Strengths:**
- Works even when Cursor MCP UI is hostile
- Debuggable from terminal without Customize

**Novelty:** Removes MCP liveness as a hard dependency for the author journey — KIND change vs fixing MCP spawn.

**Weakest link:** Reopens/contradicts the host-agnostic MCP-only mechanical I/O contract (note-20260725-fad5f166 / related decisions); dual paths drift unless one core is shared.

**Risks:**
- Skill complexity (detect MCP vs CLI)
- Permission prompts move to shell
- Governance cost to supersede MCP-only I/O

**Diversity role:** workflow restructure / bypass

### V4. Install packaging puts pysar on GUI-visible PATH

Change the documented/default install so the binary lands somewhere Dock-launched Cursor already searches (e.g. /usr/local/bin via installer, or a small macOS PATH helper). Keep shipping bare command=pysar in mcp.json like Claude.

**Strengths:**
- Keeps mcp.json portable (bare pysar)
- Helps all GUI hosts, not only Cursor

**Novelty:** Fixes the environment Cursor inherits, not the mcp.json content — install-layer KIND, not scaffold KIND.

**Weakest link:** Still fails if Cursor keeps project MCP disconnected without enable; also harder on Windows/Linux and non-admin macOS installs.

**Risks:**
- Install privilege / Homebrew vs ~/.local politics
- Doesn't address Customize Connected UX gap

**Diversity role:** install/infra

### V5. Init emits Cursor deeplink + one-toggle enable copy (no archaeology)

After writing mcp.json (preferably with resolved path from V1), `pysar init --cursor` prints/opens a Cursor MCP install deeplink and a single explicit next action: 'In Customize → MCPs, turn on pysar' — productized one step, not a troubleshooting essay. Optionally a project rule that only states that one toggle.

**Strengths:**
- Honest about Cursor product constraints
- Cheap to ship beside V1
- Aligns with postponed post-install briefing problem without blocking on voice/style

**Novelty:** Treats Cursor's required enable toggle as a designed product step with a deeplink, not a hidden failure mode.

**Weakest link:** Still one human click in Cursor UI; if authors ignore the printed step, cold path still fails — cannot fully automate enablement from outside Cursor.

**Risks:**
- Deeplink format churn across Cursor versions
- Looks like 'docs instead of engineering' if shipped without V1 path fix

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Composable with V1 (resolved path) and later V2 (marketplace) without rewriting skills.

**Diversity role:** workflow/UX ceremony
