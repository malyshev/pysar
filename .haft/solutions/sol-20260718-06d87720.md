# Solutions for: Bare `pysar` invocation needs a meaningful product intro, not hello-world

Problem: prob-20260718-27800005

## Variants (4)

### V1. Hand-authored static usage block in main (no framework)

Replace the hello-world branch with a fixed multi-line stdout string: one-paragraph product identity (author-directed editorial engine / bring your take), console surfaces that exist today (init, --version), 1–2 copy-pastable examples, and a clear note that agentic /ps skills are a separate host surface when they exist. Pure fmt print in cmd/pysar; no new deps.

**Strengths:**
- Ships in minutes
- Zero dependency risk
- Matches tactical mode and current main.go shape

**Novelty:** Content/UX change only — keeps the current hand-rolled switch dispatcher and plain-toolchain invariant; dogfood shape as CL1 inspiration with Pysar-original copy and only-real-commands discipline.

**Weakest link:** Command list drifts as soon as new subcommands land — every new command requires manually editing the banner or users get a lie by omission.

**Risks:**
- Maintenance drift
- Temptation to over-copy haft wording

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Establishes the voice and acceptance bar for the intro immediately; later variants can move the same text behind a registry or cobra Long without re-debating what 'good' looks like.

### V2. Bare invoke = one-line tip; full intro lives under `pysar help`

Default `pysar` prints a single line pointing at `pysar help` (and maybe version). Implement `help` / `--help` as the home of the meaningful intro + command list. Separates 'I typed the binary by mistake' from 'I want documentation'.

**Strengths:**
- Keeps default output tiny
- Natural home for growing docs

**Novelty:** Changes the trigger/workflow of discovery (two-step) rather than the richness of the default path — opposite discoverability bet from V1/dogfood.

**Weakest link:** Cold-start users who only run `pysar` never see the product story unless they follow the tip — fails the acceptance criterion that bare invoke alone answers 'what is this and what next?'.

**Risks:**
- Misses operator's dogfood-shaped expectation for bare invoke
- Extra hop for the primary use case

### V3. Adopt a CLI framework (e.g. cobra) with Long/Examples as the intro

Introduce a structured CLI library so root command Long description + Examples + auto-generated Available Commands become the intro. init/--version become registered commands; bare `pysar` and `pysar --help` share one source.

**Strengths:**
- Scales when many subcommands exist
- Help/flags consistency

**Novelty:** Infrastructure swap: discovery UX is a property of the framework, not a custom string — different cost center than editing main.

**Weakest link:** Adds a dependency and refactor of the working hand-rolled init path for a one-screen UX problem; overkill while the command surface is still tiny (init + version).

**Risks:**
- Violates spirit of 'no wrapper/tooling sprawl' if done early
- Larger blast radius than tactical needs

### V4. internal/cli command registry that renders usage from registered cmds

Extract a tiny Pysar-owned registry (name, summary, run func). Bare invoke and help both call RenderUsage(). New commands register once; banner cannot omit them by forgetfulness. Still no third-party CLI framework.

**Strengths:**
- Prevents command-list drift
- Stays dependency-free
- Fits functional-core/shell later

**Novelty:** Architectural extraction — single source of truth for discoverability vs either static prose (V1) or external framework (V3).

**Weakest link:** If the registry grows into a mini-framework (flags, aliases, middleware) before real needs exist, you pay redesign cost once — not because a ~50–80 LOC name+summary+run table is expensive now, but because an *overbuilt* registry API can be wrong for later flag-heavy commands.

**Risks:**
- Overbuilding the registry beyond name/summary/run (+ usage render)
- Slightly more files to open than a single string in main (~tens of minutes, not a day)
- If cobra (V3) is adopted later, this thin registry may be deleted — sunk cost is small and bounded

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Opens a clean path to grow subcommands without re-litigating usage formatting; can absorb V1's copy as the header above the generated list.
