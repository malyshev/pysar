# Solutions for: Piece/export slugs collapse non-Latin titles to template-{hash}

Problem: prob-20260809-59175eae

## Variants (5)

### V1. Extend Slug with Unicode letters then ASCII-fold (NFKD + strip marks)

Keep one Slug entrypoint. For non-ASCII letters, NFKD-normalize and drop combining marks (é→e); for scripts without Latin folding (Cyrillic, CJK), apply a small built-in transliteration table (at least Ukrainian/Russian Cyrillic) then the existing [a-z0-9-] collapse. No new deps.

**Strengths:**
- Zero deps
- Deterministic
- Touches one function + tests

**Novelty:** Same function, Unicode-aware fold+table — continues the Degenerate i18n pattern without a new package surface.

**Weakest link:** CJK/Arabic still need tables or they stay 'template'; incomplete tables produce ugly or lossy slugs; NFKD alone does not fix Cyrillic.

**Risks:**
- Partial script coverage looks 'done' while Japanese still fails
- Table maintenance debt

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Establishes Slug as the single i18n naming gate; tables can grow per script without API change.

**Diversity role:** algorithmic in-place fix

### V2. stdlib-only go-runes + ICU-style via golang.org/x/text/transform

Use golang.org/x/text/unicode/norm and/or transform for Latin fold, and a maintained transliteration library if one fits (or x/text only for fold + hand Cyrillic). Accept one module dependency for broader correctness.

**Strengths:**
- Better Unicode edge cases
- Common Go ecosystem choice

**Novelty:** Outsources folding/normalization to x/text rather than hand-rolling NFKD.

**Weakest link:** Still need a Cyrillic/CJK policy; x/text alone does not transliterate Ukrainian to Latin.

**Risks:**
- Dep + version surface for little Cyrillic gain without tables anyway

**Diversity role:** dependency-backed fold

### V3. Separate Transliterate(lang) API; Slug calls it when script ≠ Latin

Introduce internal/slug or onboarding.Transliterate with explicit language/script hint (from piece metadata or detected script). Ukrainian uses a named standard (e.g. Ukrainian national transliteration). Slug stays ASCII collapse only after transliterate.

**Strengths:**
- Standards-aligned for UA
- Testable per locale

**Novelty:** KIND: language-aware transcription contract, not a silent global table.

**Weakest link:** Needs language/script detection or author metadata; wrong lang → wrong romanization; more API surface.

**Risks:**
- Overkill if detection is wrong
- Authors never set lang → fallback still needed

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Opens per-locale SEO slug standards later without rewriting piece naming.

**Diversity role:** architectural extraction

### V4. Hash-prefix only for non-Latin; keep readable English when present

If Slug's Latin extract is empty, use a short content-hash prefix (not the word template) plus optional first-letter script code — no transliteration attempt.

**Strengths:**
- Trivial
- No wrong romanization

**Novelty:** Honest non-transliteration fallback — uniqueness without fake Latin words.

**Weakest link:** Fails operator desire for readable Latin slug from Ukrainian title; directories stay opaque.

**Risks:**
- Does not meet acceptance as drafted

**Diversity role:** workflow downgrade / anti-transliteration

### V5. Agent-proposed Latin slug at intake (LLM) persisted as piece name

ps-intake asks the model to propose an ASCII slug from the idea; persist as name override. Slug() stays ASCII-only for safety.

**Strengths:**
- Handles any language the model knows

**Novelty:** Moves transcription to the agent, not Go core.

**Weakest link:** Non-deterministic, host-dependent, fails offline/MCP-only paths; contradicts 'authors never invent slug' if the agent asks them.

**Risks:**
- Flaky names
- Not a library contract

**Diversity role:** workflow/agent
