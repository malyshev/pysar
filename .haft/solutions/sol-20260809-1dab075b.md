# Solutions for: /ps --seo is prose-only; agents skip ps-seo before humanize even when the flag is set

Problem: prob-20260809-87cd047c

## Variants (5)

### V1. Strengthen /ps prose only for --seo

Tighten ps/SKILL.md MUST NOT skip wording, add resume checks, maybe louder progress lines. No piece mark, no MCP change to save_humanize_bundle.

**Strengths:**
- Zero Go change
- No touch to dec-20260804 humanize SEO-awareness invariant

**Novelty:** Doubles down on the already-shipped soft contract that dogfood shows agents violate.

**Weakest link:** Same failure mode as today — prose MUST does not stop save_humanize_bundle.

**Risks:**
- Will not fix observed skips
- Wastes another skill-edit cycle

### V2. MCP humanize gate without piece frontmatter

save_humanize_bundle gains an optional requires_seo argument (or session-only flag) that /ps passes when --seo was on this invocation. No durable brief field. Gate: if flag true and seo.md missing → reject.

**Strengths:**
- Smaller schema blast than V3
- Fail-closed for the orchestrated call path

**Novelty:** Machine gate scoped to the current tool call only — no piece schema.

**Weakest link:** Standalone /ps-humanize or a later resume without the arg bypasses the gate; flag is not durable across sessions.

**Risks:**
- Does not match bound research V5 pattern
- Easy to forget the MCP arg

### V3. Piece requires_seo + humanize owns hard gate

Mirror dec-20260809-3a372a15: /ps --seo persists requires_seo on the piece (brief frontmatter or equivalent). /ps still invokes ps-seo after sharpen before humanize. save_humanize_bundle refuses when requires_seo is true and seo.md is absent; success requires save_seo_bundle to have written seo.md. Unmarked pieces unchanged. Skills + docs updated; clarify that humanize gains precondition awareness only (not SEO content work) relative to dec-20260804.

**Strengths:**
- Matches operator ask and bound research DRR shape
- Survives standalone /ps-humanize on a marked piece
- Preserves default SEO-free /ps

**Novelty:** Same durable policy vs outcome split as requires_research vs research_mode — here requires_seo vs presence of seo.md.

**Weakest link:** If requires_seo is never persisted, gate never arms; also export may still ship sharpen.md if humanize is skipped entirely unless a secondary export check is added.

**Risks:**
- Touches humanize MCP — must not violate detector-evasion / content SEO rules
- Two frontmatter policy booleans to teach

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Second instance of opt-in stage preconditions — proves the pattern before extracting a shared substrate.

### V4. Always-on SEO in /ps (no flag)

Make ps-seo mandatory in every /ps run. Remove opt-in.

**Strengths:**
- No flag to forget

**Novelty:** Eliminates skip by eliminating the flag.

**Weakest link:** Breaks dec-20260804 invariant that default /ps is byte-identical / SEO-free when --seo unset.

**Risks:**
- Latency and citation-resolution cost on every piece
- Violates framed opt-in constraint

### V5. Shared stage-precondition substrate for research and SEO

Generalize now: one piece policy map / MCP helper (e.g. required_stages: [research, seo]) enforced at save_draft_bundle and save_humanize_bundle (and optionally export). /ps --research/--seo set entries; completion checked against research_mode full / seo.md. Implements both gates via one mechanism in this change set.

**Strengths:**
- One pattern to learn and test
- Avoids dual boolean drift

**Novelty:** Factory-of-factories move — one precondition system instead of two parallel booleans.

**Weakest link:** Larger design+impl blast while research V5 is still unassessed/unimplemented; risk of over-abstracting before second concrete gate ships.

**Risks:**
- Slower ship; couples SEO fix to research impl sequencing
- Abstraction may be wrong before two gates exist in code

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Opens product-capability and future stage gates without new per-flag fields each time.
