# Solutions for: Distribution/install mechanism so end users can install pysar locally without building from Go source

Problem: prob-20260805-060a1177

## Variants (6)

### V1. Manual GitHub Release + hand-written install.sh, no CI automation

Push to a new GitHub repo, cross-compile locally with GOOS/GOARCH for macOS/Linux/Windows (native Go cross-compilation, no CGO in this project so no per-OS build machines needed), run gh release create by hand per release, ship a small install.sh (OS/arch detect, fetch latest release via GitHub API, install to ~/.local/bin). The maintainer personally types and runs every step, every release.

**Strengths:**
- No CI secrets/credentials to manage
- Real, working cross-platform installs today

**Novelty:** Matches this project's actual current scale (solo maintainer, zero CI history) instead of importing a reference project's full automation on day one.

**Weakest link:** Every release is a manual multi-step ritual the maintainer must personally remember and execute correctly by hand each time -- no safety net catches a forgotten platform or a bad build before it ships.

**Risks:**
- Human error in the manual release ritual

### V2. GoReleaser + GitHub Actions, tag-triggered

Adopt a goreleaser config + a release workflow that builds, checksums, and publishes a GitHub Release automatically on every version tag push, plus the same install.sh as V1. Verified against the actual reference project's real files: stripped of that project's sidecar-runtime build steps (Elixir/OTP, Rust/cargo) which don't apply here since this project has zero CGO dependencies and no sidecar processes, the real equivalent is materially smaller than it first appeared -- checkout, setup-go, go test, cross-compile natively from one Linux runner (no macOS runner needed, unlike the reference project which needs one only for its Rust sidecar), package, checksum, gh release create using the default GITHUB_TOKEN (no extra secrets).

**Strengths:**
- Zero manual human steps per release once working
- Structural safety gate: the build job cannot run if the test job fails -- enforced by the CI dependency graph itself, not by anyone remembering to check
- Checksums and reproducible builds come from the tool itself

**Novelty:** The only variant offering repeatable, CI-verified releases with zero manual human steps per release once working, and -- now confirmed by reading the reference project's actual files rather than assuming -- genuinely simpler to port than its source project's own pipeline suggests, precisely because this project has none of the sidecar/CGO complexity driving most of that pipeline's real length.

**Weakest link:** Real one-time setup cost before the first release ships: writing/debugging the CI workflow and goreleaser config correctly with no existing CI history on this project to fall back on if something misconfigures.

**Risks:**
- CI/YAML debugging cost is real for a first pipeline, even a small one

### V3. `go install github.com/<org>/pysar/cmd/pysar@latest` -- Go toolchain as the entire distribution mechanism

No custom binaries, no install.sh, no release pipeline at all -- point users at the standard go install command.

**Strengths:**
- Already true today with zero additional work
- Legitimate secondary path for Go-literate users/contributors regardless of what else ships

**Novelty:** The cheapest possible option -- zero new infrastructure, reuses Go's own module system as the entire distribution story.

**Weakest link:** Fails the acceptance criterion outright: requires the end user to have a Go toolchain installed, exactly what was asked to avoid. Verified: even the reference project's own real install.sh falls back to this exact mechanism (go build from source) for every platform it doesn't prebuild for (Windows, Intel Mac) -- so this is not a hypothetical fallback, it's what actually happens today for a real, comparable project's non-covered platforms.

**Risks:**
- Silently narrows the real target audience to people who already have Go installed

### V4. Homebrew tap (macOS/Linux) + manual Windows zip guidance

Publish a Homebrew tap repo for brew install; Windows users get documented manual download-and-unzip.

**Strengths:**
- No curl|bash trust-ask for macOS/Linux users

**Novelty:** The only variant using an existing, widely-trusted package manager instead of a custom curl|bash script.

**Weakest link:** Windows users are back to a fully manual process regardless; needs a second repo plus a cross-repo credential beyond the default token if automated via CI.

**Risks:**
- A second small repo to create and keep in sync

### V5. Ship prebuilt binaries as plain GitHub Release assets, no script at all

Push to GitHub, attach cross-compiled binaries (including a real macOS build) to one manually-created Release, document manual download/chmod+x/PATH steps per platform. No install.sh, no CI.

**Strengths:**
- Fastest possible path to a real, downloadable macOS build existing at all

**Novelty:** Gets a genuine, working, cross-platform artifact into an end user's hands with the least possible new infrastructure.

**Weakest link:** Manual multi-step process for the end user too -- clunkier than a one-line install command, and doesn't reduce the maintainer's own recurring manual-release burden either.

**Risks:**
- End users hit OS unsigned-binary warnings with no guidance beyond a README

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Forces the cross-platform build matrix and the GitHub-repo/Release existence question to get resolved first, in isolation, before investing in scripting or automation on top.

### V6. Agentic on-request release: a documented recipe an AI coding agent executes when asked, no CI

No goreleaser, no GitHub Actions. A short, checked-in release recipe (a script and/or explicit instructions) defines the exact steps: verify clean git status and a passing test suite, cross-compile each target (trivial -- no CGO, no cross-toolchain needed), compute checksums, stage the GitHub Release. When the maintainer wants to cut a release, they ask their AI coding agent to run the recipe; the agent executes it and pauses for explicit human confirmation before the actual publish/push step -- consistent with this project's own established practice of never publishing externally without being asked first. Pairs with the same install.sh as V1, or V5's plain-download approach, for the end-user-facing half.

**Strengths:**
- Lowest initial_setup_cost among anything that removes recurring human toil -- write a recipe once, no CI infrastructure to learn or debug
- Same trivial native cross-compilation as V1/V2 (no CGO) applies here too
- Reuses the exact human-confirmation-before-publish pattern already established this session, rather than inventing a new trust model

**Novelty:** Gets V2's near-zero recurring HUMAN effort (the maintainer just asks, doesn't type the steps) without V2's CI/YAML/secrets setup cost -- substitutes an agent following a documented recipe for both the human's own hands (V1/V5) and for a CI pipeline (V2). Not previously in the portfolio -- proposed mid-comparison by the operator.

**Weakest link:** No structural enforcement: correctness depends entirely on the agent (and its instructions) actually following the recipe correctly every time -- unlike V2, where the CI job dependency graph makes it mechanically impossible to build-and-publish if tests fail first. A recipe followed by an agent (or a human) can still be skipped, run against a dirty working tree, or run with a stale local build cache in a way a clean CI runner never would.

**Risks:**
- No clean-room build environment guarantee the way a fresh CI runner has -- local machine state (uncommitted changes, wrong branch, stale cache) can leak into a release unless the recipe explicitly guards against each case
- Depends on the recipe itself staying correct and complete as the project evolves -- nothing forces it to be updated the way CI failing loudly would

## Pareto Front Trade-Offs

- Agentic on-request release: a documented recipe an AI coding agent executes when asked, no CI — Sole non-dominated point on the declared targets -- matches V2's low recurring effort without V2's setup cost, by substituting an AI agent following a documented recipe for a CI pipeline. This mechanical result should not be read as a clean win: on the two observation dimensions (deliberately excluded from domination), V6 scores worse than V2 on release_process_integrity (documented-recipe, correctness depends on the recipe being followed correctly vs. V2's structural, CI-job-dependency-enforced gate) and ties V1/V2 for worst end_user_trust_ask (high, curl|bash -- inherited from pairing with V1's install.sh; pairing with V5's plain-download instead would lower trust-ask at the cost of dropping platform_coverage to 0%, a sub-choice this comparison did not resolve). The per_release_maintainer_effort tie with V2 (both 'low') is also a closer judgment call than the other comparisons -- the scoring agent itself noted V6 sits at the high end of 'low', not deep in it.

**Selection policy:** Declared before scoring: eliminate any variant requiring Go on the end user's machine as the sole mechanism (V3 eliminated). Among survivors, minimize initial_setup_cost first, tie-break by maximizing platform_coverage, then by minimizing per_release_maintainer_effort. end_user_trust_ask and release_process_integrity are reported, never used to eliminate or rank -- Anti-Goodhart: neither was declared a hard requirement by the operator.

**Recommendation (advisory):** Agentic on-request release: a documented recipe an AI coding agent executes when asked, no CI

**Recommendation rationale:** Mechanical result: V6 dominates every other constraint-surviving variant on all three declared targets simultaneously -- an unusually clean outcome worth being suspicious of rather than just accepting. Two honest caveats, not hidden in the dominance computation because they're observation dimensions by design: (1) V6's safety property is weaker than V2's -- 'documented-recipe' vs 'structural' on release_process_integrity -- nothing mechanically stops a skipped step the way CI's job-dependency graph does for V2; (2) V6 inherits V1's high end_user_trust_ask because it's paired with the same curl|bash install.sh, not because the agentic-release idea itself demands that pairing. Additionally, the per_release_maintainer_effort tie between V6 and V2 (both scored 'low') is the least confident judgment call in this comparison -- if an operator scores 'ask an agent and review its output' as meaningfully more effort than 'git tag && git push', V6 no longer dominates V2 and the two become genuine non-dominated trade-offs instead. This is advisory only -- the operator chooses via /h-decide.
