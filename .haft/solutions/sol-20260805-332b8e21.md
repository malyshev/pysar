# Solutions for: Eliminate per-call permission prompts for ps-research/ps-factcheck/ps-intake's web grounding

Problem: prob-20260805-c8ab2784

## Variants (5)

### V1. Pre-approve native WebFetch/WebSearch in settings.json

Add WebFetch and WebSearch to permissions.allow alongside mcp__pysar__*. Zero new code -- a one-line settings.json change that ships to every future pysar init project.

**Strengths:**
- No engineering cost
- Fully solves the friction immediately, both fetch and search

**Novelty:** Cheapest possible fix -- the direct, minimal-effort response to the observed friction.

**Weakest link:** Grants the agent completely generic, unscoped internet access for the entire session, not just Pysar's research passes -- any skill or off-script agent behavior in a pysar-init'd project inherits blanket web access with zero server-side audit trail, domain control, or rate limit. Broadest blast radius of all variants.

**Risks:**
- Widens trust for the whole session/project, not just the research/factcheck flow that actually needed it

### V2. MCP-mediated fetch only (mcp__pysar__web_fetch), native WebSearch left as-is

Add a new Go MCP tool that does a server-side HTTP GET + basic content extraction, wildcard-covered by the already-trusted mcp__pysar__*. WebSearch stays a native Claude Code tool, still subject to prompting.

**Strengths:**
- No new external cost or API key
- Narrower blast radius than V1 -- only Pysar's own server code decides what a fetch call can do
- Fetch results become audit-loggable via the existing run-log mechanism

**Novelty:** Reuses the exact precedent this project already set for this class of problem: dec-20260719-fa0366dd mediated file-write permission friction through Pysar's own MCP server instead of pre-approving raw Write/Bash -- this applies the same pattern to fetch.

**Weakest link:** Only half-solves the observed friction -- WebSearch (the call actually shown interrupted in the transcript) still prompts every time. Also: a Go-side HTML-to-text reimplementation risks being a worse, less robust fetch than Claude Code's own native WebFetch, which likely already handles redirects, content types, and extraction more maturely.

**Risks:**
- Reimplementing fetch/extraction in Go is real, ongoing maintenance surface

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Establishes the MCP tool-registration and content-handling plumbing that a future mcp__pysar__web_search addition (V3) would reuse directly -- doing the cheaper half first de-risks the harder half.

### V3. MCP-mediated fetch AND search via a paid third-party search API

Build both mcp__pysar__web_fetch and mcp__pysar__web_search, the latter calling a real third-party search API (Brave Search API, Google Custom Search, Bing, or SerpAPI) the operator provisions a key for. Fully closes the loop -- neither native tool is needed for research grounding.

**Strengths:**
- Fully closes the prompting gap for the actual observed friction
- Search queries and results become audit-loggable and potentially rate-limitable/domain-filterable server-side

**Novelty:** The only variant that fully eliminates prompting for BOTH fetch and search while keeping the whole capability inside Pysar's own scoped, audited MCP boundary.

**Weakest link:** Real, ongoing cost and setup burden: requires the operator to sign up for and pay for a third-party search API before ps-research/ps-factcheck even work. Every future pysar init user inherits this requirement or grounding degrades/breaks. Highest build cost of all variants -- two new Go integrations plus credential management for an external paid dependency this project doesn't control.

**Risks:**
- Introduces an external paid-service dependency into what was previously a self-contained local binary
- Search API keys/credentials become a new class of thing pysar init or the operator must manage and keep valid

### V4. Split policy: pre-approve WebFetch natively, leave WebSearch prompted

Add only WebFetch to settings.json permissions.allow; WebSearch stays unapproved. Treats "fetch a specific already-chosen URL" as lower-risk than "search the open web with an arbitrary query."

**Strengths:**
- Zero engineering cost
- Solves most of the volume (fetch calls were the majority in the observed transcript) while leaving the more open-ended tool gated

**Novelty:** No new code, but a narrower trust grant than V1 -- a judgment-based split rather than all-or-nothing.

**Weakest link:** The risk distinction is soft, not a technical guarantee -- a pre-approved WebFetch can still be pointed at an attacker-controlled or sensitive URL surfaced by a prompt-injected page, so this reduces prompt volume without reducing worst-case blast radius much. Also still leaves WebSearch prompting -- the one call actually shown interrupted in the transcript -- so the operator's concrete complaint isn't solved by this alone.

**Risks:**
- Splitting policy by tool name is a coarse proxy for actual risk, not a real control

### V5. Status quo -- rely on the operator's own client-level "always allow"

No project change. The operator uses their own Claude Code client's per-tool "always allow" setting to stop being prompted, same as any other tool.

**Strengths:**
- Already available today with no Pysar change at all
- Each operator controls their own trust level individually

**Novelty:** The only variant requiring zero project changes at all -- solved per-operator, not per-project.

**Weakest link:** Doesn't travel with the project -- every new pysar init'd project, and every other operator on a shared project, starts back at square one with per-call prompts. Also doesn't actually answer the operator's question, which was specifically about Pysar's own shipped settings.json not covering this.

**Risks:**
- Operator remains confused about why mcp__pysar__* doesn't cover this, recurring the same question later
