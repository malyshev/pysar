# Solutions for: Reference-agnosticism gate: external writing POCs and haft are inspiration-only, never copy-paste or load-bearing justification

Problem: prob-20260718-7b559d43

## Variants (4)

### V1. Convention only -- state the rule in prose (spec + term-map), rely on self-policing

Add a term-map entry ('reference project': not a source of truth, not reusable code, not a locked decision) and a paragraph in an existing enabling-system section stating that external POCs/haft are inspiration-only. No structural check -- future sessions rely on the agent reading CLAUDE.md/specs and remembering to apply the rule.

**Strengths:**
- Zero new ceremony, one paragraph to write
- Immediately in effect, no dependency on other tooling

**Novelty:** Cheapest possible fix; matches how most projects handle 'don't copy the competitor' informally, via prose nobody mechanically checks.

**Weakest link:** Pure discipline with no structural backstop. Silently erodes across long sessions, context compaction, or a future agent/session that doesn't happen to re-read the relevant paragraph before citing a reference -- exactly the failure mode that produced dec-20260718-239680d4's 'mirrors haft's own distribution' title in the first place.

**Risks:**
- Already demonstrated to fail once (the current decision's title) -- prose alone didn't stop it

**Diversity role:** minimal-ceremony baseline

### V2. Typed-field discipline -- reuse haft's existing congruence_level / counterargument / why_not_others fields as the enforcement surface

Write the rule as: whenever a SolutionPortfolio variant or DecisionRecord names an external reference project, (a) any evidence_refs pointing at it must be recorded with congruence_level capped at CL1, (b) why_selected must not name the reference as sole justification, (c) the variant/decision must state what Pysar-original design diverges from the reference. No new spec section -- this is a stated discipline for how I already fill in fields the kernel already validates on every explore/decide call.

**Strengths:**
- No new spec section or ceremony to maintain
- Directly actionable starting with the next SolutionPortfolio/DecisionRecord
- Fixes dec-20260718-239680d4 today as a concrete first application

**Novelty:** Uses fields the kernel already validates (congruence_level, counterargument, why_not_others) rather than inventing new ceremony -- the cheapest variant that's actually somewhat harder to forget than pure prose, since it maps to fields I fill in every time regardless.

**Weakest link:** Still relies on the agent (me) correctly recognizing 'this counts as a reference citation' and applying the rule in the moment -- there is no kernel-level check that rejects a why_selected mentioning 'haft' without a capped CL and a stated divergence. A rushed or compacted session can still slip.

**Risks:**
- Still fully discretionary -- nothing stops a violation from being recorded if I misjudge what counts as a 'reference citation'

**Diversity role:** pragmatic-immediate, no new ceremony

### V3. Formal spec invariant -- a governed ES section that gates future /h-explore and /h-decide content

Add a new enabling-system spec section (e.g. ES.enabling.reference_policy) with an explicit invariant: 'no SolutionPortfolio variant or DecisionRecord may treat an external writing POC or haft as sufficient justification; any citation requires a stated Pysar-original divergence.' Unlike V2, this is a first-class governed artifact -- discoverable via haft_query(action='related'/'code_context'), tracked in spec coverage, subject to the same drift/baseline discipline as the other 10 onboarded sections, and requires explicit operator approval like they all did.

**Strengths:**
- Discoverable and auditable after the fact via haft's own query/coverage tools, not just 'hope the agent remembers'
- Consistent with how the rest of Pysar's enabling-system is already governed (11th section alongside the 10 already onboarded)
- Can carry its own evidence_required for periodic re-verification (e.g. a manual audit of recent decisions for compliance)

**Novelty:** The only variant that makes this rule a governed, coverage-tracked artifact rather than free-floating prose or an unwritten discipline -- future /h-status and spec-coverage checks would surface it as a real section, and haft_query(action='related') on any future decision would resurface the invariant automatically.

**Weakest link:** Heavier ceremony for what is fundamentally a discipline problem, not a structural one -- like V1 and V2, nothing mechanically stops a violation from being recorded; the section makes the rule more discoverable and auditable after the fact, not harder to violate in the moment.

**Risks:**
- Adds a section to maintain/re-baseline like any other spec section
- Still doesn't mechanically block a violation at write-time -- only surfaces it on query/audit

**Diversity role:** formalized, coverage-tracked governance

### V4. Mechanical check -- a future haft-check rule that flags reference-project mentions missing the CL-cap/divergence statement

Longer-term: a project-specific haft check (informational/non-blocking, mirroring the validated 'haft check in pre-commit, non-blocking' pattern from a related project) that scans new DecisionRecords/SolutionPortfolios for mentions of external writing POC names or 'haft' and flags ones missing a capped congruence_level or a stated Pysar-original divergence -- surfaced in /h-status rather than silently trusted.

**Strengths:**
- If buildable, the only variant that doesn't depend on the agent's moment-to-moment discipline at all
- Non-blocking/informational framing avoids the failure mode of an overzealous gate blocking legitimate work

**Novelty:** The only variant with a path to non-discretionary, mechanical enforcement rather than relying on the agent remembering -- directly modeled on a pattern already validated elsewhere (informational, non-blocking haft check in pre-commit).

**Weakest link:** Doesn't exist yet and its buildability is unverified -- Pysar has no code, no CI, and it's unconfirmed whether haft's check subsystem supports project-defined custom rules versus only its built-in governance-debt checks. Highest risk this simply isn't buildable soon.

**Risks:**
- Unbuildable or not worth building until Pysar has actual code and a CI-equivalent -- premature today
- False sense of security if built naively (keyword-matching 'prior writing POC'/'haft' is crude and could miss paraphrased references)

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Not viable today (no code/CI exists), but V2's typed-field discipline and V3's spec invariant both produce exactly the structured data (congruence_level, stated divergence) that a future mechanical check would need to scan for -- adopting V2/V3 now is what makes V4 buildable later without rework.

**Diversity role:** mechanical-enforcement, explicit stepping stone
