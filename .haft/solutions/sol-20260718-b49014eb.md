# Solutions for: Memory engine: cross-piece continuity so new pieces don't unknowingly repeat prior openings, examples, or wording

Problem: prob-20260718-4e1bda1b

## Variants (4)

### V1. Lexical index -- SQLite FTS5 full-text search over past pieces

Every finished (and in-progress) piece is indexed into a local SQLite FTS5 full-text index, with openings and flagged examples/anecdotes stored as separate rows. Before or after drafting, Pysar runs a keyword/phrase query (e.g. the new piece's opening line, named examples) against the index and surfaces close lexical matches with piece references.

**Strengths:**
- Simplest to implement in Go -- mature SQLite driver, no external service, no embedding pipeline
- Fully offline/local, fast
- Transparent -- matched text is directly readable, no black-box score

**Novelty:** Reuses a generically well-known SQLite capability (FTS5), independently built for Pysar's own piece-repetition problem -- not haft's schema or design, just the same widely-available database engine, per the reference-agnosticism gate.

**Weakest link:** Purely lexical -- catches exact/near-exact phrase reuse ('I woke up at 2 A.M.' twice) but misses paraphrased repetition (e.g. 'I woke up in the middle of the night' vs 'I woke up at 2 A.M.' -- same beat, different words), which is the actual case the operator's own example points at.

**Risks:**
- False negatives on paraphrased repetition -- the most common real-world case per the operator's own example
- Needs sensible chunking heuristics (what counts as 'the opening', what counts as 'an example') -- itself a design problem

**Diversity role:** lexical, zero-dependency, literal-match-only

### V2. Semantic index -- embedding-based similarity search

Each piece (and/or extracted chunks -- opening, examples, key scenes) is embedded into a vector representation. New pieces are checked via nearest-neighbor similarity search against stored vectors, catching paraphrased or semantically similar repetition that lexical matching misses.

**Strengths:**
- Catches the paraphrase case the operator explicitly described
- Embeddings are a well-understood, generically available technique, not tied to any reference project

**Novelty:** The only variant that catches meaning-level repetition, not just wording-level -- directly answers the operator's actual example (different wording, same beat), which lexical matching structurally cannot.

**Weakest link:** Requires an embedding model -- either an external LLM/embeddings API call (network dependency, per-piece cost, and a real question of whether this crosses the 'default input is your idea/draft, not web research' promise) or a local embedding model (a real Go-ecosystem gap, the same category of weakest_link already accepted in dec-20260718-239680d4).

**Risks:**
- Adds either a network dependency or a real local-inference ecosystem gap
- Similarity thresholds are fuzzy and need tuning to avoid false positives (flagging unrelated pieces as 'too similar')

**Diversity role:** semantic, catches paraphrase, adds a dependency

### V3. Structured continuity ledger -- extracted facts/scenes/examples as queryable records

As each piece is finished, extract structured records (opening-hook type, named examples/anecdotes used, recurring phrases, topics covered) into a queryable ledger, similar in spirit to a 'series bible' for serial fiction. New pieces are checked against the ledger's structured fields, not raw text similarity.

**Strengths:**
- Most legible to the author -- a real, inspectable ledger, not a black-box score
- Catches structural/pattern repetition neither V1 nor V2 can, since those only compare content

**Novelty:** The only variant that produces human-auditable, structured continuity data -- an actual readable 'what have I already used' ledger, not a similarity score -- and the only one that can catch structural repetition (e.g. 'third chapter in a row opening with a flashback'), not just content repetition.

**Weakest link:** Requires an extraction step (raw prose -> structured facts), which is itself an LLM-orchestration task -- this variant doesn't avoid the embedding/LLM-ecosystem question, it just moves it from query-time to extraction-time, and extraction quality directly gates the whole variant's usefulness.

**Risks:**
- Highest build cost -- needs both an extraction pass and a query layer
- Extraction quality is a moving target and needs the same LLM-orchestration capability already flagged as a weakest_link in the Go tech-stack decision

**Diversity role:** structured extraction, most legible, highest cost

### V4. No index -- brute-force context stuffing from prior pieces

Skip building a separate memory engine. When drafting a new piece, load the raw text of some or all prior pieces in the project directly into the LLM's context window and let the model notice repetition informally, the way a human editor re-reads past chapters before writing a new one.

**Strengths:**
- Trivial to build -- days, not weeks
- No false negatives from bad chunking/embedding choices at small corpus sizes
- Lets the author validate the whole feature concept cheaply before committing to V1/V2/V3

**Novelty:** The only variant that ships with zero new engineering -- no index, no schema, no extraction pipeline. Its value is as an honest baseline: it proves whether continuity-checking is actually valuable to the author before any indexing investment is made.

**Weakest link:** Doesn't scale -- token cost and latency grow with corpus size, and eventually exceeds context-window limits, at which point older pieces silently fall out of context with no signal to the author that coverage has degraded.

**Risks:**
- Silent degradation at scale -- looks like it's working, then stops, with no warning
- Costs real tokens/money on every drafting session regardless of whether anything is actually similar

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Validates whether continuity-checking is actually valuable to the author, and at what corpus size it starts mattering, before investing in V1/V2/V3's indexing infrastructure -- the cheapest way to de-risk the larger build.

**Diversity role:** zero-engineering baseline, explicit stepping stone

## Pareto Front Trade-Offs

- Lexical index -- SQLite FTS5 full-text search over past pieces — Cheapest real option, zero new dependency, best scalability -- but structurally cannot catch the paraphrase case that motivated this problem in the first place.
- Semantic index -- embedding-based similarity search — Best repetition_recall, the only variant that catches meaning-level repetition (the operator's actual stated case). Costs a real dependency and the weakest author_legibility.
- Structured continuity ledger -- extracted facts/scenes/examples as queryable records — Best author_legibility, ties for best scalability, only variant catching structural repetition. Highest build cost, same dependency risk as V2 moved to extraction time.
- No index -- brute-force context stuffing from prior pieces — Cheapest to ship with V1, zero new dependency. Worst scalability by far. Its main justification (cheap validation before investing, since there was nothing to index yet) is now weakened -- see evid-20260718-706181000: a real corpus already exists and the feature's value is not in question.

**Selection policy:** Pareto front, not a scalar winner -- all four variants remain genuinely non-dominated on the technique-level dimensions, which are unchanged by the correction. What changed is sequencing logic: V4 was recommended as a cheap way to validate value before a corpus existed; that justification is now weakened (evid-20260718-706181000), since a real corpus (prior writing POC's articles) already exists and the operator has confirmed the feature's value independently. The comparison stays a genuine trade-off among V1/V2/V3 for what to build first, with V4 available as a fallback tactic, not a required first step.

**Recommendation (advisory):** Semantic index -- embedding-based similarity search

**Recommendation rationale:** Revised from the prior V4-first lean. With a real corpus already available and the operator's stated pain point specifically being paraphrase-level repetition (same beat, different wording) -- exactly the case V1 structurally cannot catch and V2 was scored to catch (repetition_recall=4) -- V2 is the variant most directly justified by what's actually being asked for. V1 remains a legitimate cheap complement (catches literal repeats at near-zero cost) but does not by itself solve the motivating example. V3 is the most complete answer (structured, legible, catches structural repetition too) but at the highest build cost, better justified once it's clearer which patterns actually recur across a real corpus. Not proposing a combined variant unilaterally -- flagging that a V1+V2 bundle is a real option if the operator wants one decision covering both, rather than assuming it.
