# Solutions for: Codex prompts per pysar MCP tool; Claude pre-approves

Problem: prob-20260808-f9cd1683

## Variants (4)

### V1. Ship default_tools_approval_mode = auto

Add default_tools_approval_mode = "auto" to the shipped [mcp_servers.pysar] block in assets/codex/config.toml so init/--force writes Claude-parity pre-approval for all pysar MCP tools. Update init golden and docs with trusted-project caveat.

**Strengths:**
- Closest friction match to Claude mcp__pysar__*
- One-line packaging change
- Documented OpenAI Codex setting

**Novelty:** Uses Codex's native MCP approval dial rather than inventing a Claude settings.json twin.

**Weakest link:** Project .codex/config.toml only applies when the project is trusted — untrusted projects may still prompt despite auto.

**Risks:**
- Auto-approves write tools (save_*_bundle, export) without per-call prompts
- Codex version skew if key ignored

### V2. Ship default_tools_approval_mode = writes

Use writes mode so read-only tools auto-run but write/save/export tools still prompt. Document the split.

**Strengths:**
- Safer than blanket auto for save/export
- May remove the observed read_author_defaults prompt if read-only marking works

**Novelty:** Splits read vs write approval instead of all-or-nothing Claude mirror.

**Weakest link:** Depends on Codex correctly classifying pysar tools as read-only vs not — if tools lack read-only marks, behavior may still prompt for everything.

**Risks:**
- May not match Claude full allowlist experience
- Unknown whether pysar MCP tools advertise read-only to Codex

### V3. Docs-only: tell authors to paste auto

Leave scaffold unchanged; document the TOML snippet and trusted-project caveat for manual fix.

**Strengths:**
- No security-default controversy in init
- Reversible

**Novelty:** Zero product default change — operator education only.

**Weakest link:** Non-technical authors still hit prompts until they hand-edit config — fails Claude-parity friction goal.

**Risks:**
- Does not meet acceptance for init-time allowance

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Unblocks operators today without binding a security-sensitive default; can escalate to V1/V2 after more smoke.

### V4. Per-tool tools.*.approval_mode = auto for every pysar tool

Enumerate each MCP tool under [mcp_servers.pysar.tools.<name>] with approval_mode = auto. Same runtime effect as V1 with a longer TOML that must track tool inventory.

**Strengths:**
- Visible allowlist analogous to Claude named permissions
- Can carve exceptions later

**Novelty:** Explicit tool inventory in config rather than server-wide default.

**Weakest link:** Dual maintenance: every new MCP tool must update the TOML list or silently falls back to prompt.

**Risks:**
- Drift vs mcpserver tool registry
- Larger config, same security posture as V1 if all set auto
