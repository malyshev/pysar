# Solutions for: Pipeline/orchestration mechanism: shared execution model every future Pysar command plugs into

Problem: prob-20260718-831e79e5

## Variants (5)

### V1. Code-enforced finite state machine: typed Status enum + phase registry

A Go type for piece status (mirroring the shape of Medium's Status field, with Pysar-original values) plus a Phase struct (name, precondition status, postcondition status, work function that may call an LLM). A Pipeline type walks a piece through phases either one at a time (per author command) or end-to-end. Hard-ordering rules become status precondition checks in code -- a phase literally cannot run if the piece isn't in the right status, not just documented as a rule to remember.

**Strengths:**
- Ordering rules are structurally impossible to violate, not just documented
- Piece state is a real, queryable Go value

**Novelty:** Converts Medium's proven prose design directly into compiled, type-checked Go control flow -- but per operator correction, Medium is a POC to improve on, not a template: this variant's rigid linear-status model is the one place Medium's own shape (always-on OPTIMIZE) would need real rework, not just renaming, to support conditional applicability.

**Weakest link:** The full legal status/transition graph must be defined reasonably correctly up front; getting it wrong either blocks legitimate author workflows or requires a schema migration once real Status values exist on real pieces. Also weaker fit for conditional/optional passes (e.g. skipping SEO for non-digital output) than variants where applicability is a first-class per-pass check.

**Risks:**
- Status/transition graph errors are a real correction cost once discovered
- Conditional applicability (SEO-for-paper-letters case) needs bolting on, not native to the model

**Diversity role:** compiled state machine, strongest ordering guarantee, weakest native fit for conditional passes

### V2. Event-driven handler pipeline: passes subscribe to trigger conditions

Each pass is a handler registered against trigger conditions (e.g. 'piece has a draft AND author signals sharpen-intent') rather than a fixed linear phase list. A dispatcher evaluates which handlers are eligible given current piece state and author signal, and runs them.

**Strengths:**
- Adding a pass never requires editing a shared file
- Naturally accommodates target-surface-conditional passes via trigger predicates

**Novelty:** Lets new commands be added without any central orchestrator file being touched, and trigger conditions can naturally include target-surface checks -- decent native fit for conditional applicability, but at the cost of central auditability.

**Weakest link:** Ordering becomes implicit in the union of each handler's own trigger conditions rather than one explicit, auditable sequence -- harder to answer 'what is the canonical order' at a glance than any of the other variants.

**Risks:**
- Auditing 'what is the actual pipeline order' requires reading every handler's trigger conditions, not one table
- Higher risk of two handlers' trigger conditions silently overlapping

**Diversity role:** decoupled event/handler dispatch, weakest central auditability

### V3. Command-as-entrypoint with shared helpers, no central orchestrator

Each command is its own Go function calling shared library helpers (call an LLM, read/write artifacts, append a run-log entry) but there is no Pipeline/Phase abstraction imposing a specific execution model. Ordering discipline, if any, lives in each command's own logic and in operator documentation.

**Strengths:**
- Fastest to ship a first real command
- No orchestration abstraction to get wrong before real usage reveals what's needed

**Novelty:** Trivially 'supports' conditional applicability only because nothing is structured at all -- that is not the same as modeling target-surface relevance, it is the absence of any model whatsoever.

**Weakest link:** Ordering safety is the weakest of all variants -- nothing in code prevents a command from running out of the intended sequence; reproduces the operator's originally-named Medium gap almost exactly, just in Pysar's own codebase.

**Risks:**
- Reproduces the operator's originally-named Medium gap almost exactly
- Every future command re-implements its own sequencing/applicability logic, likely inconsistently

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Ships the first real command fastest, but Medium's already-run design work weakens (without eliminating) the case for rediscovering requirements from scratch here.

**Diversity role:** near-zero orchestration code, reproduces the exact named gap if chosen without mitigation

### V4. Declarative pipeline spec (data) interpreted by a generic runner

The phase graph -- names, order, preconditions, artifact names -- is defined as data (e.g. embedded YAML or a Go data literal), interpreted by one generic pipeline-runner function. Adding a phase means adding a data entry.

**Strengths:**
- Adding a phase or an applicability rule is a data change, not a code change, once the runner exists
- Strong native fit for target-surface-conditional passes

**Novelty:** Preconditions expressed as data can naturally include applicability predicates (e.g. 'applies_if: target_surface != paper'), a strong native fit for conditional passes, at the highest build cost of the five.

**Weakest link:** Requires building both the phase logic AND a generic spec-interpreter capable of enforcing arbitrary preconditions correctly -- meaningfully more upfront engineering than V1 or V5 for a comparable guarantee.

**Risks:**
- Highest upfront build cost
- A bug in the generic interpreter affects every phase at once

**Diversity role:** data-driven spec + generic interpreter, strong conditional-applicability fit, highest build cost

### V5. Precondition-guarded actions over a lightweight ref-holding cycle state (haft's own evolved v2 pattern)

A small Cycle-like struct tracks which artifact refs are bound so far (not a rich named-phase enum). Each pass has its own small guard function checking whatever preconditions actually matter for it -- both ordering (has the prior step happened) and applicability (does this piece's target surface even need this pass) -- against the shared state, returning a structured, self-correcting error if not satisfied. No central phase-transition table. Multi-step flows (the equivalent of Medium's /w-write full pipeline) are realized by an orchestrator that calls passes in sequence, each still passing through its own guard -- not one server-side function that owns the whole sequence.

**Strengths:**
- Cheapest of the four real-guarantee variants to extend -- new pass = new guard function, no central table to edit
- Native, unforced fit for conditional applicability (same mechanism handles ordering AND relevance)
- Reflects a lesson already learned by trial in a directly comparable system, not an untested hypothesis

**Novelty:** The only variant directly inherited from a real, already-evolved decision in a comparable Go/MCP-tool codebase: haft's own phase.go explicitly states 'Phase machine logic removed... FPF order enforced by tool guardrails, not phase transitions' -- this is not a hypothetical design, it is what a structurally similar system tried (a rigid FSM, i.e. this problem's own V1) and moved away from. It also natively separates 'is this pass applicable' from 'has this pass's precondition been met', which is exactly what the SEO-for-paper-letters case needs -- a guard can simply check target_surface and no separate skip-flag mechanism is required.

**Weakest link:** No single, one-glance-readable diagram of 'the pipeline' the way Medium's canonical-order ASCII art gives you -- understanding the full flow means reading each guard function's preconditions individually, unless a separate human-readable doc is maintained alongside (which then risks drifting from the code, same discipline problem the run-log decision exists to catch).

**Risks:**
- No centralized human-readable view of the full flow without separate, disciplined documentation
- A careless new pass could omit its own guard where a central FSM would have structurally forced the case to be handled

**Diversity role:** precondition guards over lightweight cycle state, best native fit for conditional applicability, real prior art from a second reference system

## Pareto Front Trade-Offs

- Code-enforced finite state machine: typed Status enum + phase registry — Best ordering_safety and queryable_pipeline_state, but weakest conditional_applicability_support of the three survivors -- a fixed status enum has no native way to say 'this pass doesn't apply here'; SEO-for-paper-letters needs bolting on, not modeling.
- Declarative pipeline spec (data) interpreted by a generic runner — Ties V5 on flexibility and conditional_applicability, matches V1 on queryable_state -- effectively the strongest guarantees across the board. Costs the highest build_cost of all five: a generic spec interpreter is real engineering before any phase benefits.
- Precondition-guarded actions over a lightweight ref-holding cycle state (haft's own evolved v2 pattern) — Cheapest of the three survivors by far, ties V4 on flexibility and conditional_applicability. Costs the lowest queryable_pipeline_state and ordering_safety of the three -- precondition guards are real but distributed, not one central table; a careless new pass could omit its own guard where V1's FSM would structurally force the case to be handled.

**Selection policy:** Pareto front, deep mode, full parity_plan declared before scoring per CMP-02. V2 and V3 are cleanly dominated by V5 once conditional_applicability_support is weighted in alongside the original four dimensions -- confirmed correct after fixing the dimension-polarity bug from the prior attempt. design_risk_transfer stays an observation, excluded from tie-breaking.

**Recommendation rationale:** The real choice is V1 vs V4 vs V5. V1's weakness (no native conditional-applicability) is a genuine gap now that the SEO-for-paper-letters requirement is explicit -- bolting applicability checks onto a fixed status enum is exactly the kind of awkward retrofit that argues against it. Between V4 and V5: V4 gives the same guarantees at meaningfully higher build cost (a generic interpreter is real, nontrivial engineering all future phases depend on). V5 gives nearly the same guarantees -- slightly weaker on queryable_state and ordering_safety, both real but bounded costs -- at the lowest cost of any variant offering real guarantees at all, and reflects a lesson a directly comparable system already learned by building the V1-equivalent first and moving away from it. My lean is V5, specifically because it is not a hypothetical design: haft tried the rigid-FSM shape this problem's V1 represents and replaced it with this exact pattern in its own production codebase -- stronger evidence than either Medium's prose (never code-tested for this specific ordering-enforcement question) or an untested Pysar-only design.
