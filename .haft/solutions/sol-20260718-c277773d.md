# Solutions for: Local dev/build loop for Pysar's greenfield Go skeleton: build, install, iterate

Problem: prob-20260718-faa6f3bf

## Variants (4)

### V1. Plain Go toolchain only -- `go build` / `go install`, no wrapper tool

No separate build tool at all. `go install ./cmd/pysar` compiles and installs directly to $GOBIN (already on PATH by Go convention). The entire dev loop is: edit code, run `go install ./cmd/pysar`, run `pysar`.

**Strengths:**
- Zero learning curve, zero extra dependency
- Fastest possible path to a working loop today
- Nothing to misconfigure -- it's just the Go toolchain doing what it's designed to do

**Novelty:** Zero extra tooling or config to learn -- pure Go, directly matches the 'Go's cross-compilation is simply mature' reasoning that already won the tech-stack decision.

**Weakest link:** No room for extra steps (version-stamping via -ldflags, running tests before install, cross-compiling for release) without the operator remembering and typing them manually every time -- scales poorly the moment building needs more than 'compile'.

**Risks:**
- No single discoverable entry point for 'how do I build this project' as it grows
- Manual, easy-to-forget steps the moment version-stamping or cross-compilation enters the picture

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Cheapest possible way to get a real, working build+install+run loop today. Whatever wrapper tool (Makefile, Taskfile, goreleaser) gets adopted later still sits on top of `go build`/`go install` as the underlying primitive -- nothing here is thrown away if the project graduates to V2 or V3.

**Diversity role:** zero-tooling baseline, fastest to start

### V2. Makefile-driven build (`make build`, `make install`, `make test`)

The most common Go-community convention: a Makefile with named targets wrapping `go build`/`go install`/`go test`, with room to add version-stamping, formatting, and lint hooks as the project grows.

**Strengths:**
- Near-universal Go-community convention, low learning curve for anyone who has touched a Go project before
- make ships preinstalled on macOS (Xcode CLT) and virtually every Linux distro -- no new dependency to install for most environments
- Room to grow into version-stamping, test, and lint targets without changing tools

**Novelty:** The single most recognized convention in the Go ecosystem specifically, independent of any project-specific tool choice -- the highest odds that a future contributor, or the operator's own future self returning after months away, already knows to check the Makefile first.

**Weakest link:** Make's own syntax (tab-sensitivity, .PHONY targets, real cross-platform quirks on native Windows) is a small but genuine separate learning surface, and Makefiles are well-known to accumulate undocumented tribal-knowledge targets if not kept disciplined.

**Risks:**
- Make's whitespace-sensitivity and limited native-Windows story are a real, if small, tax
- Targets can silently become tribal knowledge if not documented

**Diversity role:** Go-community convention, near-zero new dependency

### V3. Taskfile-driven build (`task build`, `task install`) -- same tool the dogfood project uses

A modern YAML task runner (go-task/task) -- explicitly the same tool haft's own Taskfile.yaml uses. Haft's actual Taskfile.yaml is consulted as a concrete, capped example of task naming/structure for a Go CLI with cross-compilation and install steps, not copied.

**Strengths:**
- Cleaner YAML syntax than Make, genuinely cross-platform
- A concrete, already-working precedent to learn task-naming/structure from for growing into cross-compilation/release tasks later
- Matches a workflow the operator has already said they like the shape of

**Novelty:** The only variant that directly reuses a concrete, already-validated task-naming/structure pattern -- explicitly capped as inspiration only, Pysar-original content required per dec-20260718-eafefad2 -- from a tool the operator already runs daily, lowering the cognitive switching cost between working on Pysar and working on haft itself.

**Weakest link:** Adds one more external dependency to the local dev environment -- the `task` binary itself must be installed before any of this works, a real (if minor) tension with the whole 'single self-contained binary, no separate runtime' philosophy, this time applied to dev tooling rather than the shipped product.

**Risks:**
- New external tool dependency purely for local dev
- Must be actively kept Pysar-original in content -- structure/naming as inspiration only, per the reference-agnosticism gate

**Diversity role:** modern task runner, direct (capped) precedent from haft

### V4. goreleaser snapshot builds from day one

Adopt goreleaser -- the actual cross-compilation/release tool implied by the tech-stack decision and used by haft's own .goreleaser.yaml -- immediately, using `goreleaser build --snapshot` for local iteration, unifying the dev loop and the eventual real release process into one tool from the first commit.

**Strengths:**
- Zero future migration cost when it's time to actually cross-compile and release for real
- Single tool to learn, total, across the whole project lifecycle

**Novelty:** The only variant that unifies 'how I build to test locally' and 'how I'll eventually cross-compile and release' into one tool from the very first commit, rather than adopting a lightweight dev-loop tool now and a release tool later.

**Weakest link:** The heaviest tool for the earliest, most exploratory phase of the project -- goreleaser is built around producing full multi-OS release artifacts, more ceremony than a fast 'change one line, rebuild, run it' loop needs; likely the slowest single-iteration feedback loop of the four.

**Risks:**
- Premature ceremony for a hello-world-stage project
- Slowest local iteration loop of the four, a real cost during the exploratory early phase where fast feedback matters most

**Diversity role:** release-tool-from-day-one, heaviest, most future-proof

## Pareto Front Trade-Offs

- Plain Go toolchain only -- `go build` / `go install`, no wrapper tool — Best iteration_speed and tooling_simplicity, tied for best extra_dependency_cost -- the fastest, simplest way to a working loop today. Costs the worst growth_headroom -- nothing captures 'the right way to build this' as the project needs more than compile.
- Makefile-driven build (`make build`, `make install`, `make test`) — Middle ground on iteration_speed and tooling_simplicity, ties V1 for lowest extra_dependency_cost (make ships with most systems already). Real growth headroom without adding a new dependency to install -- the balanced choice.
- Taskfile-driven build (`task build`, `task install`) -- same tool the dogfood project uses — Best growth_headroom, ties V2 on iteration_speed and tooling_simplicity. Costs the worst extra_dependency_cost of the non-dominated set -- a real new tool to install, in tension with the product's own single-binary philosophy applied to dev tooling.

**Selection policy:** Pareto front, not a scalar winner. All four dimensions are targets, none a hard constraint -- this is a real tooling trade-off (speed/simplicity now vs. headroom later vs. dependency cost), not a technical pass/fail. V4 is the one clean elimination: strictly dominated, not just weaker on balance.

**Recommendation rationale:** V1 is explicitly a stepping stone in this portfolio and the natural starting point regardless of where the project ends up -- it's the fastest way to get a real, working build+install+run loop today, and nothing about starting there forecloses V2 or V3 later, since both wrap the same underlying go build/go install primitive. Between V2 and V3 as the likely next step once the build needs more than one command: V2 (Makefile) costs nothing extra to install on the operator's own machine and is the more universally recognized Go convention; V3 (Taskfile) has better growth headroom and happens to match a tool the operator already runs daily for haft, at the cost of one more thing to install. Given the reference-agnosticism gate, I would not let 'haft already uses Taskfile' tip this on its own -- on the dimensions actually scored, V2 and V3 are close enough that either is defensible, and V1 first either way.
