# Solutions for: Revisit: internal/cli command registry that renders usage from registered cmds

Problem: prob-20260718-ac41adb5

## Variants (4)

### V1. Adopt Cobra now, fully migrate root + init to cobra.Command

Replace internal/cli/registry.go with a cobra.Command tree; root command's Long/Short mirrors the existing hand-authored intro copy; init becomes a real cobra subcommand with its flags bound via cobra's own flag API instead of stdlib flag.NewFlagSet.

**Strengths:**
- Full feature set for free as the command surface grows
- Cobra's Command struct genuinely preserves single-source-of-truth, it doesn't trade it away
- Matches the operator's explicit stated direction

**Novelty:** The only variant that gives every future subcommand cobra's full feature set (nested subcommands, shell completion, per-subcommand flag binding, auto-generated --help) without hand-rolling any of it, and matches the operator's literal instruction most directly. Cobra's own Command struct preserves the same 'one registration site drives both dispatch and usage' property the existing registry was specifically valued for.

**Weakest link:** Discards a small (~90 LOC), already-tested, already-measured-working implementation (dec-20260718-c4cd8f62, 36s wall-clock to build, verdict partial-passing) for a still-small two-to-three-command surface -- the exact premature-abstraction shape the prior decision already worked through once, though note-20260718-c1b9df53 already established that near-zero-cost structure should not be rejected purely on YAGNI grounds, and this migration is not near-zero cost.

**Risks:**
- Real rewrite cost today for a benefit that mostly pays off later
- Re-opens exactly the trade-off already reasoned through once in dec-20260718-c4cd8f62

**Diversity role:** full migration, matches operator's literal request

### V2. Keep the existing registry unchanged, re-affirm the standing decision

No code change. Close this reopened problem with the conclusion that nothing material has changed since dec-20260718-c4cd8f62 was decided -- still a two-to-three command surface, registry still passes its tests.

**Strengths:**
- Zero cost, zero risk
- Already shipped and measured

**Novelty:** The only variant that costs zero new code or dependency and is already proven working via real measurement, not hypothetical.

**Weakest link:** If the operator's real reason for invoking the refresh trigger is that they already have concrete near-term plans for more subcommands or flag complexity, flatly re-affirming with no change just delays an outcome that's already effectively decided by one more round trip, and leaves the exact same vague 'third+ subcommand' trigger that already required a manual nudge once to reconsider.

**Risks:**
- Doesn't engage with why the operator invoked the trigger right now
- Leaves the same vague trigger that already needed a manual nudge

**Diversity role:** flat re-affirmation, no change

### V3. Hybrid: adopt Cobra for the root/help/version only, leave init on stdlib flag

Use cobra.Command for the root command's rich intro rendering and top-level dispatch, replacing internal/cli/registry.go, but leave runInit's flag.NewFlagSet as-is rather than migrating it to cobra's flag binding immediately.

**Strengths:**
- Smallest code change that still gets cobra's root-level polish

**Novelty:** The only variant that gets cobra's polished root output without touching init's already-working, already-tested flag logic (dec-20260718-8278c494) at all -- but this is included for completeness, not because it is likely to be the right answer once its single-source-of-truth cost is made explicit.

**Weakest link:** Explicitly breaks the single-source-of-truth property the prior decision specifically valued in the registry (one registration site drives both dispatch and usage) -- cobra's root now knows about init only as an opaque subcommand name, while init's actual flags (--claude/--cursor/--codex, mutual exclusivity) live in a completely separate, cobra-unaware stdlib flag set that cobra's own generated --help for init cannot see or describe.

**Risks:**
- Two incompatible flag-handling conventions coexisting is more confusing to a future reader than either pure approach
- cobra's auto-generated --help for init would be wrong or empty since init's real flags are invisible to it

**Diversity role:** partial migration, breaks single-source-of-truth

### V4. Keep the registry now, but tighten the refresh trigger from vague to concrete

No code change today. Instead of re-affirming with the same vague 'third+ subcommand lands' trigger, update the decision's refresh trigger to fire on the very next new console subcommand (not the third), explicitly informed by the operator having just invoked this reconsideration -- so the next real trigger point requires no manual /h-reason nudge to be noticed.

**Strengths:**
- Zero cost today, same as V2, but the next decision point is concrete rather than vague
- Directly responds to why this reopening happened instead of ignoring it

**Novelty:** The only variant that treats the operator's act of invoking the refresh trigger as itself informative -- not enough to force a migration today, but enough to conclude the standing trigger was too loose and should tighten, rather than either blindly migrating or blindly re-affirming the exact same policy.

**Weakest link:** Still defers the actual cobra-vs-registry migration cost to a future session -- if the operator's underlying reason for asking now is more informed than 'let's just check', this doesn't actually answer that pressure, it just makes the next check-in point sharper.

**Risks:**
- Still a deferral, not a resolution, if the operator wanted a resolution today

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Costs nothing today and doesn't foreclose V1 or V3 later -- it specifically sets up a cleaner, faster future decision (next subcommand becomes the forcing function) informed by today's reopening, rather than leaving the same vague trigger that already required a manual nudge once.

**Diversity role:** policy adjustment, no migration, sharper future trigger
