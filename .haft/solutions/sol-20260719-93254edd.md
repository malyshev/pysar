# Solutions for: Template identity: persisted display name decoupled from a stable machine slug

Problem: prob-20260719-9f11bd6e

## Variants (5)

### V1. Add an optional Name field directly to the Profile schema

internal/onboarding.Profile gains an optional Name string field, rendered into frontmatter only when non-empty. save_voice_profile never sets it (stays empty for onboarding-produced profiles); save_voice_template sets it from the author's display name. Slug decoupling is handled by giving save_voice_template an optional `slug` parameter: omitted on first save (derives from name as today), passed explicitly on a later re-save to update the same file in place regardless of the new name.

**Strengths:**
- Simplest possible code change -- one new optional field
- Name travels in the same file, same YAML block as everything else -- no second parsing convention

**Novelty:** The most direct fix -- treats display name as just another structured attribute alongside tone/formality, reusing Render/Validate exactly as they already work for every other field.

**Weakest link:** Directly breaks this problem's own schema-parity constraint: Profile is supposed to be one identical shape shared by onboarding profiles and templates (prob-20260718-00bf7ca6's own decided constraint), and this variant makes that shape capability-different depending on which caller populates it -- a quiet divergence, not an examined one.

**Risks:**
- An onboarding profile could technically also carry a Name now with nothing stopping it, blurring a boundary this project already decided on purpose
- Schema drift risk grows the moment Style templates (pending task #11) also want this -- was this field voice-specific or profile-generic? Ambiguous by construction

### V2. Store name in the existing per-directory manifest, Profile untouched

Extend the already-existing skillManifest JSON (.pysar-manifest.json, dec-20260719-25712417) with a parallel Names map alongside its Files hash map: {"files": {...}, "names": {"generic.md": "Measured plain English..."}}. save_voice_template writes the Profile content exactly as today (byte-identical to save_voice_profile's output) and separately records the display name in this same manifest file pysar already reads/writes for staleness tracking. list_voice_templates merges manifest names with file content when responding. Slug decoupling via the same optional explicit `slug` parameter as V1.

**Strengths:**
- Profile.go and Render() stay completely untouched -- zero risk to the onboarding-profile path
- Structured JSON field, unambiguous to read back -- no prose-parsing fragility

**Novelty:** Reuses infrastructure that already exists for an unrelated purpose (hash tracking) rather than inventing new storage -- one system-owned file carries all of pysar's own bookkeeping about the template tree, author content files stay pure.

**Weakest link:** A template's display name only exists in the manifest, not in the template file itself -- copy, email, or git-vendor just the .md file elsewhere (exactly the portability this project's own design philosophy has praised in every prior decision this session) and the name is silently lost, leaving only the slug/filename.

**Risks:**
- Couples template identity to a file whose primary job is staleness bookkeeping, not content metadata -- a maintenance surprise for whoever next reads that manifest expecting only hashes
- If the manifest is ever deleted/corrupted (already a named risk in dec-20260719-25712417's own rollback triggers), names are lost even though the actual template content survives intact

### V3. Encode the name as the template's own Markdown heading

When a template is saved, its rendered body's H1 becomes "# <Name>" instead of the fixed "# Voice Profile" every onboarding-produced profile uses. list_voice_templates (and any future reader) extracts the name by reading the first H1 line after frontmatter. Slug decoupling via the same optional explicit `slug` parameter as V1/V2.

**Strengths:**
- Name and content live in exactly one self-contained, git-vendorable file -- nothing external to keep in sync
- Reads naturally to a human -- the file's title genuinely is the template's name, no separate concept to explain

**Novelty:** Treats the name as what it visually already is to a human reading the file -- the document's own title -- rather than inventing a second metadata channel alongside it.

**Weakest link:** Extracting structured meaning from a Markdown heading is convention, not a typed field -- an author hand-editing the file (a portability strength this project has repeatedly praised) could reformat or edit that heading without realizing it silently changes what future tooling reports as the template's name, or breaks extraction entirely if the line no longer matches the expected `# ` prefix pattern exactly.

**Risks:**
- Fragile to manual edits or reformatting of the heading line
- No validation path (unlike a typed field) to catch a malformed or missing name at save time

### V4. Dedicated template-metadata frontmatter wrapper

Prepend a second, small YAML frontmatter block ahead of the existing Profile-rendered content: `---\nname: <Name>\n---\n\n` followed by exactly what Render(profile) already produces today, unmodified. Profile.go and Render() stay completely untouched (like V2/V3); the name lives inside the same portable file (like V3); but it is read back as a structured YAML field via yaml.Unmarshal, not parsed from prose (like V2's robustness, without V2's external-file coupling). Slug decoupling via the same optional explicit `slug` parameter as the other variants.

**Strengths:**
- Profile.go, Validate, and Render for onboarding profiles are completely unaffected -- zero risk to that path
- Structured, typed field -- no prose-parsing fragility, unlike V3
- Name travels in the one portable file -- no external manifest dependency, unlike V2

**Novelty:** A template-only wrapper layer around the exact same Render() output every other variant already produces -- gets V2's structured-field robustness and V3's single-file portability simultaneously by not choosing between them.

**Weakest link:** Two stacked `---`-delimited YAML blocks in one file is a convention nothing else in this project uses yet -- genuinely new plumbing (a small wrap/unwrap parse function), not a reuse of any existing mechanism, and could look unusual to an author opening the file for the first time even though it remains fully valid and human-editable.

**Risks:**
- A genuinely new parsing convention to introduce and document, however small
- Two adjacent frontmatter blocks may read as unusual or malformed to a human unfamiliar with the convention on first encounter

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** The wrapper is not name-specific -- it is a general 'template-only metadata that Profile itself should never carry' layer. Future template-only fields (e.g. a created-by note, a based-on reference to another template) can be added to this same wrapper without ever touching Profile.go or reopening the schema-parity question, unlike V1 which would need to keep extending Profile itself for every new template-only need.

### V5. Status quo -- slug always derived from name, no independent identity

Keep exactly what ships today: save_voice_template always derives the filename slug from the display name via onboarding.Slug(name), with no way to rename a template's display name without also changing (or duplicating) its file. Included specifically as the floor this problem exists to fix, not a genuine contender.

**Strengths:**
- Zero implementation cost
- Already shipped and tested

**Novelty:** Deliberately included as the do-nothing baseline to make explicit what the operator's own signal already identified as broken -- not a real proposal.

**Weakest link:** Fails this problem's own acceptance criterion outright: renaming a template's display name either silently reassigns its addressable key (breaking anything that referenced the old slug) or creates an orphaned duplicate file under the old slug -- exactly the gap the operator's signal named.

**Risks:**
- Directly blocks the operator's stated future-automation goal of addressing a template by a fixed key
