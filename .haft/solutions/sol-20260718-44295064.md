# Solutions for: Pysar command-interface naming convention: CLI subcommand prefix and slash-command entry point

Problem: prob-20260718-12c1f841

## Variants (3)

### V1. `ps-*` subcommands, `/ps` auto mode (operator's proposal)

Short two-letter prefix drawn from Pysar's initials, with intentional wordplay: 'ps' as post scriptum, or the 'pssst... I have an idea' framing. Individual commands take the form `ps-<verb>`, auto mode is `/ps`.

**Strengths:**
- Shortest to type, best for a CLI used many times a day
- Memorable wordplay the operator already likes
- Distinct from haft's own `/h-*` convention -- not a copy, per the reference-agnosticism gate

**Novelty:** The only variant chosen for its wordplay/personality (post scriptum, 'pssst...') rather than purely for namespace safety or semantic clarity -- ties the brand identity to an evocative phrase, not just an abbreviation.

**Weakest link:** Exact collision with the near-universal Unix `ps` (process status) command. Any literal alias or muscle-memory habit of typing `ps` alone hits the OS tool, not Pysar; a shell alias literally named `ps` would shadow the system command, which is the kind of collision that breaks scripts and surprises users. The `ps-*` subcommand namespace itself doesn't collide (e.g. `ps-init` is fine), but `/ps` and bare `ps` usage carries real ambiguity.

**Risks:**
- Collision risk with `ps` in shell muscle memory and any alias/completion setup
- Two letters carry no self-evident meaning without the wordplay explanation

**Diversity role:** brand-initial, evocative wordplay

### V2. `pysar-*` subcommands, `/pysar` auto mode

Full product name as the prefix. Zero ambiguity about what the command belongs to, zero collision with any existing shell command.

**Strengths:**
- No collision risk whatsoever
- Self-explanatory without needing the wordplay explanation
- Safest choice if the CLI is ever scripted/aliased heavily by users

**Novelty:** The only variant with zero collision risk and zero ambiguity -- a new user (or a script) can never confuse it with an existing system command.

**Weakest link:** Longer to type on every invocation in a tool meant for frequent daily use -- the exact opposite trade-off of V1. Also forfeits the wordplay identity the operator explicitly likes.

**Risks:**
- Meaningfully more keystrokes for a tool used many times per session
- Loses the personality/wordplay hook

**Diversity role:** zero-collision, maximum clarity

### V3. `wr-*` subcommands, `/wr` auto mode (verb-based, not brand-based)

Prefix drawn from the product's actual author-facing promise ('write it') rather than from the brand name at all -- ties the command surface to what the author is doing, echoing TS.environment-change.001's insistence that authors speak in verbs, not phase/brand vocabulary.

**Strengths:**
- Directly echoes the already-recorded author-surface promise ('write it') rather than inventing new brand vocabulary
- No known collision with common Unix tools

**Novelty:** The only variant that names the prefix after the verb the target-system spec already promises authors, rather than after the brand -- a genuinely different naming logic (semantic/verb-based vs brand-initial-based), not just a different two-letter guess.

**Weakest link:** Loses brand identity entirely -- nothing about `wr-*` signals 'this is Pysar' without external documentation, and 'wr' carries no built-in evocative meaning of its own (weaker wordplay than V1's 'ps').

**Risks:**
- Weak brand recall -- doesn't read as 'Pysar' to a new user at all
- Verb-based prefix could feel arbitrary once more verbs (edit, ship, etc.) also need commands

**Diversity role:** verb-based, promise-echoing

**Recommendation (advisory):** `ps-*` subcommands, `/ps` auto mode (operator's proposal)

**Recommendation rationale:** The operator has already stated a clear preference for V1 (`ps-*`/`/ps`) with explicit reasoning (brevity, wordplay). That preference is consistent with what V1 actually wins on this front (typing_efficiency, personality_distinctiveness) -- it is not an uninformed pick. The one thing to make sure is genuinely accepted, not overlooked, is V1's collision_risk=4: `ps` bare and `/ps` both sit on top of the single most common process-inspection command on any Unix-like system. This doesn't make V1 wrong -- namespaced subcommands like `ps-init` don't collide -- but bare `ps`/`/ps` usage and any literal shell alias named `ps` genuinely do.
