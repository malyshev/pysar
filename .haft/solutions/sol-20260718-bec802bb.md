# Solutions for: Voice/style template structure: schema design + built-in neutral default for zero-config use

Problem: prob-20260718-00bf7ca6

## Variants (5)

### V1. Rule-based descriptive schema (structured attributes only, no full exemplar passages)

The schema is a set of discrete, queryable attributes -- tone, formality, sentence-length preference, register, banned phrases/words, punctuation habits -- with no full prose reference passages included. Closest in spirit to efeoncepro/voice.md's machine-readable-tokens approach (CL1 inspiration, format only).

**Strengths:**
- Every field is independently queryable and testable -- easiest schema to write a completeness validator against
- Compact, no large prose blocks to maintain or accidentally over-fit to a single source

**Novelty:** Treats voice/style purely as a set of measurable knobs, never as demonstrated prose -- optimizes for programmatic validation over generation quality.

**Weakest link:** Abstract attribute lists steer AI generation more weakly than concrete examples -- exactly the gap the operator's own research identified: 'almost nobody ships a good generic literary persona you can drop in unchanged.' A tone value like 'formal, precise' underdetermines actual sentence-level behavior far more than a real paragraph would.

**Risks:**
- Generated text may technically satisfy every field yet still read generic/flat, since no exemplar anchors actual phrasing
- Attribute vocabulary itself becomes a design burden (what does 'formal: 7/10' actually produce?)

**Diversity role:** pure structured-attribute schema

### V2. Exemplar-primary schema (goldens are the main content, light metadata)

The schema centers on a small set of reference passages (the goldens) plus a handful of lightweight descriptor fields (e.g. register, formality) as secondary metadata -- not a full attribute system. Closest to the 'temperature-0 classic baseline' approach the operator researched (GOV.UK/Economist-style clarity distilled into example prose, CL1 inspiration for the idea of exemplar-led guides, not their content).

**Strengths:**
- Strongest direct steering of generation -- an AI shown real passages reproduces register and rhythm more reliably than abstract rules
- Naturally supports the 'drop-in unchanged, works for tests' need the operator specifically called out

**Novelty:** Inverts the usual config-first instinct -- treats worked examples as the schema's primary content and structured fields as a thin wrapper around them, rather than the reverse.

**Weakest link:** With only light metadata, there is little to programmatically validate beyond 'are N examples present' -- the schema can't structurally check whether a profile is actually neutral/international-standard versus accidentally personal-voice-flavored; that judgment stays almost entirely human/LLM-inferred from the prose itself.

**Risks:**
- Harder to diff/review changes to a profile (prose edits are less scannable than field edits)
- Light metadata may prove too thin once a second questionnaire-driven use (style) needs more than a couple of shared descriptor fields

**Diversity role:** exemplar-primary, minimal structure

### V3. Hybrid: structured attributes plus required golden examples

The schema combines V1's queryable attribute fields (tone, formality, register, banned phrases, etc.) with a required set of 3-4 golden reference passages, matching the operator's literal request. Attributes give the completeness validator (per dec-20260718-5570376d) something concrete to check; goldens give the AI something concrete to imitate. Structurally similar in shape to aaronjmars/soul.md's STYLE.template.md and StyleRef/style.md (CL1 inspiration for the combined-shape idea, not content).

**Strengths:**
- Directly matches the operator's own stated request shape -- fields plus 3-4 goldens, not one or the other
- The generic default profile, once authored against this schema, exercises both halves of the schema at once -- the strongest test that the schema itself is sufficient
- Composes cleanly with the already-decided completeness validator: required fields AND a minimum golden count are both checkable

**Novelty:** Refuses to choose between rules and examples -- treats them as complementary evidence types the same way this project's own evidence model treats CL/congruence, rather than picking one steering mechanism.

**Weakest link:** Slightly larger schema than either single-mode variant (V1 or V2) -- more surface to author correctly for the first generic profile, and a real risk of the two halves (attributes vs. goldens) drifting out of sync with each other if not authored carefully (e.g. a golden passage that doesn't actually match its own declared 'formality' field).

**Risks:**
- Authoring the first generic profile well (both fields and goldens, consistent with each other) is real editorial work, not just schema design
- Largest field count of the non-out-of-scope variants -- more to maintain long-term

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Whatever mechanism the future template-inheritance ADR picks, it will need a resolved profile shape to inherit into and override -- this schema is exactly that resolved shape, so the inheritance ADR can design purely the composition mechanics without also re-deriving the profile's own field structure.

**Diversity role:** hybrid, matches operator's literal request

### V4. Layered schema with base/override built in now

Same content shape as V3 (attributes + goldens), but the schema itself also carries base-reference and override-delta fields so a template can declare 'inherits from generic, overrides these three fields' directly in its own data. This is the template-inheritance mechanism the operator explicitly deferred to a separate future ADR -- included here specifically to test whether folding it in now is actually premature, not to quietly assume it should be adopted.

**Strengths:**
- Would answer the inheritance question the operator flagged as coming later, if it turns out cheap to include now
- Avoids a hypothetical future schema migration if inheritance is added afterward

**Novelty:** Included as a deliberate boundary-test, not a genuine recommendation -- makes the cost of jumping ahead concrete and comparable rather than leaving 'why not just add inheritance now' as an unexamined assumption.

**Weakest link:** Directly violates the operator's own explicit scope boundary for this problem ('how to will be separate ADR') -- bakes in an unreviewed inheritance/override resolution design (what does a partially-overridden, unresolved template even mean for the completeness validator?) before that design has had its own framing and comparison.

**Risks:**
- Inheritance-resolution edge cases (unresolved override, circular base reference) get designed under time pressure inside an unrelated problem
- If the eventual inheritance ADR picks a different mechanism, this schema-level plumbing becomes dead weight to remove

**Diversity role:** in-scope violation, included to make the boundary explicit

### V5. Corpus/reference-only schema (goldens plus one free-text caption, no fields)

The schema is minimal to the point of being just a list of reference passages plus a single free-text description -- no discrete attribute fields at all. Closest to a raw few-shot prompt with a caption, no schema beyond that.

**Strengths:**
- Smallest possible schema -- fastest to author a first version of
- Zero risk of fields and examples drifting out of sync, since there are no separate fields to drift from

**Novelty:** Tests the minimal-structure floor -- how little schema can still count as a 'template' at all, as a deliberate contrast point against V1's maximal-structure ceiling.

**Weakest link:** Almost nothing is programmatically checkable beyond 'are there examples present' -- the schema cannot structurally distinguish a genuinely neutral, international-standard profile from an accidentally personal or off-register one; that check falls entirely on human/LLM judgment at authoring time, with no schema-level guardrail at all.

**Risks:**
- Weakest fit with dec-20260718-5570376d's own completeness-validator requirement -- there's barely anything for a validator to check
- Hardest of the five to extend later without a real schema migration, since there's no field structure to add to incrementally

**Diversity role:** minimal-structure baseline

## Dominated Variant Elimination

- Exemplar-primary schema (goldens are the main content, light metadata) — dominated by Hybrid: structured attributes plus required golden examples. V3 ties V2 on steering_strength (both 5, goldens present in both) and stays_in_scope, but wins self_validating (5 vs 2) and structured_validatability (4 vs 2) -- V2's light metadata gives up programmatic checkability that V3 gets for free by also including V1's fielded attributes.
- Layered schema with base/override built in now — dominated by Hybrid: structured attributes plus required golden examples. V3 wins or ties V4 on every dimension: steering_strength (5 vs 4), self_validating (5 vs 3), structured_validatability (4 vs 3), and decisively on stays_in_scope (1 vs 0) -- V4's inheritance plumbing buys nothing V3 doesn't already have while violating the operator's explicit scope boundary.
- Corpus/reference-only schema (goldens plus one free-text caption, no fields) — dominated by Hybrid: structured attributes plus required golden examples, Exemplar-primary schema (goldens are the main content, light metadata). V3 beats V5 on every dimension. V2 also beats V5 on every dimension (steering_strength 5 vs 3, self_validating 2 vs 1, structured_validatability 2 vs 1, tied scope) -- the pure-corpus floor buys smallest field count but nothing else.

## Pareto Front Trade-Offs

- Rule-based descriptive schema (structured attributes only, no full exemplar passages) — Best structured_validatability on the front (5) -- every field independently queryable -- traded against the front's worst steering_strength (2): abstract attributes alone underdetermine actual generated phrasing, exactly the gap the operator's own research flagged.
- Hybrid: structured attributes plus required golden examples — Ties the portfolio's best steering_strength (5) and wins self_validating outright (5) by exercising both fielded attributes and goldens at once, at the cost of slightly lower structured_validatability than V1's pure-fields design (4 vs 5) and the largest field count among in-scope variants (8).

**Selection policy:** Pareto front over target-role dimensions (steering_strength, self_validating, structured_validatability, stays_in_scope); field_count is observation-role, watched per the ProblemCard's own indicator, never optimized (Anti-Goodhart). Declared before scoring.

**Recommendation rationale:** V3 is the recommended pick despite V1 formally sharing the Pareto front. V1's edge is a marginal one point of structured_validatability (5 vs 4) bought by dropping goldens entirely -- which directly contradicts the operator's own explicit request ('template structure... with 3-4 goldens') and their own research finding that abstract rules alone don't produce a good generic literary persona. V3 also uniquely scores best on self_validating, meaning authoring the required generic default profile against this schema is the strongest test that the schema itself is sufficient -- V1 would need a separate, weaker exemplar-free validation story. V4 is included and cleanly dominated specifically to make explicit that folding inheritance in now was considered and rejected, not silently skipped.
