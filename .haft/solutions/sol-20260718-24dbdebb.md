# Solutions for: Exclude multi-author/author-registry model from Pysar's target-system scope

Problem: prob-20260718-97b5a2a3

## Variants (4)

### V1. Spec-only boundary addition

Add an explicit out-of-scope line to TS.target.boundary.001 and a term-map entry (e.g. clarify 'voice-lock' or add 'author-identity') stating: one initialized project/piece = one voice, no cross-project author registry. No new DecisionRecord.

**Strengths:**
- Cheapest -- one artifact edit, no DRR ceremony
- Lives exactly where an operator reviewing target-system scope would look first

**Novelty:** Treats this as pure spec hygiene rather than governance ceremony -- correct if the constraint is genuinely low-stakes.

**Weakest link:** Spec sections carry less search/citation weight than DecisionRecords in this graph -- a future exploration citing a prior writing POC at CL1 may not surface this constraint the way it would surface a DecisionRecord match.

**Risks:**
- Under-weighted for a boundary this central to the product's identity model
- No falsifiable prediction to verify later

**Diversity role:** minimal-ceremony spec edit

### V2. Dedicated DecisionRecord mirroring the reference-agnosticism-gate pattern, cascading into specs

Bind a full DRR (like dec-20260718-eafefad2) stating Pysar's author/voice model is single-owner-per-initialized-project, explicitly citing a prior writing POC's multi-author/multi-voice decisions (dec-20260606-multi-author-v1-..., dec-20260530-multi-voice-v1-...) at CL1 as the pattern NOT being adopted and why (prior writing POC serves many personas on one platform; Pysar serves one author per init). Cascades into TS.target.boundary.001 + term-map, same rebaseline discipline as the publish-checklist removal.

**Strengths:**
- Matches this session's own precedent for durable guardrails (reference-agnosticism gate, publish-checklist exclusion)
- Citable dec-ID a future exploration's kernel search will actually surface
- Falsifiable predictions possible (e.g. memory-engine delivery never introduces a cross-project author table)

**Novelty:** Explicitly cites that prior POC's bound multi-author DRRs as the thing being deliberately not inherited, rather than just asserting Pysar is different in the abstract.

**Weakest link:** Heaviest ceremony for a constraint that, today, contradicts nothing already built -- risk of over-processing a non-conflict.

**Risks:**
- Governance overhead for a currently-hypothetical feature
- Another artifact to keep in sync if the on-disk topology is ever revisited

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Gives the memory-engine delivery-model decision (still open) a citable constraint to check against before it accidentally designs a cross-project author table.

**Diversity role:** full DRR governance guardrail

### V3. Fold as an amendment onto the existing on-disk-structure decision

Attach evidence/an amendment note directly to dec-20260718-4b222794, since the two risk/strength lines being closed off ("voice/author registry deferred", "shared author voice across pieces") originated in that decision's own dominated variants. No new top-level artifact.

**Strengths:**
- Reuses an artifact that already has the relevant history attached
- Zero new artifact count -- matches the 'minimal governance overhead' target directly

**Novelty:** Treats this purely as closing a loose end in a prior decision rather than as its own boundary statement.

**Weakest link:** Conflates two different decisions -- on-disk topology (a code-shape question) and author/voice identity model (a product-scope question). The exclusion is broader than that one decision (it also touches memory-engine and term-map), so tucking it inside topology's amendment history under-scopes it.

**Risks:**
- Future search for 'author model' won't find it under a topology-titled decision
- Memory-engine exploration has no direct citation target

**Diversity role:** attach-to-existing-artifact economy

### V4. Note-only capture

Record via haft_note: rationale captured, no spec edit, no DecisionRecord. Matches this skill's own listed common moment ('after a user correction -- capture the right approach').

**Strengths:**
- Fastest possible durable record
- Correctly sized if this truly never becomes load-bearing

**Novelty:** The lightest-touch option, useful as a baseline to compare ceremony cost against.

**Weakest link:** Notes don't cascade into spec sections or get surfaced the way DecisionRecords do in /h-status's Pending/Drift tracking -- if a future decision does contradict this, there's no drift/refresh mechanism watching it.

**Risks:**
- Under-weighted exactly like V1, but more so -- no spec section even names the boundary
- Relies on FTS search recall alone, not structured governance surfacing

**Diversity role:** lightest-touch baseline
