# Solutions for: Pipeline/orchestration mechanism: shared execution model every future Pysar command plugs into

Problem: prob-20260718-831e79e5

## Variants (4)

### V1. Code-enforced finite state machine: typed Status enum + phase registry

A Go type for piece status (mirroring the shape of prior writing POC's Status field, with Pysar-original values) plus a Phase struct (name, precondition status, postcondition status, work function that may call an LLM). A Pipeline type walks a piece through phases either one at a time (per author command) or end-to-end. Hard-ordering rules become status precondition checks in code -- a phase literally cannot run if the piece isn't in the right status, not just documented as a rule to remember.

**Strengths:**
- Ordering rules are structurally impossible to violate, not just documented
- Piece state is a real, queryable Go value -- 'what can run next' is a function call, not a file read
- Directly reuses a design prior writing POC has already run real published articles through, adapted with Pysar-original names/content

**Novelty:** The only variant that converts prior writing POC's proven prose design (Status enum, canonical order, non-reorderable doctrine) directly into compiled, type-checked Go control flow -- 'HUMANIZE after OPTIMIZE' becomes a precondition check the compiler and runtime both enforce, not a sentence an LLM has to remember to obey every session.

**Weakest link:** The full legal status/transition graph must be defined reasonably correctly up front; getting it wrong either blocks legitimate author workflows (the same risk flagged for the run-log decision's rejected V3 state-machine) or requires a schema migration once real Status values exist on real pieces.

**Risks:**
- Status/transition graph errors are a real, if bounded, correction cost once discovered
- Less flexible than an event-driven model for passes that don't fit a strict linear sequence

**Diversity role:** compiled state machine, strongest ordering guarantee, direct translation of proven prior art

### V2. Event-driven handler pipeline: passes subscribe to trigger conditions

Each pass is a handler registered against trigger conditions (e.g. 'piece has a draft AND author signals sharpen-intent') rather than a fixed linear phase list. A dispatcher evaluates which handlers are eligible given current piece state and author signal, and runs them. New passes are added by registering a new handler, without touching a central phase list.

**Strengths:**
- Adding a pass never requires editing a shared file
- Naturally accommodates passes that don't fit a strict linear order

**Novelty:** The only variant that lets new commands be added without any central orchestrator file being touched at all -- maximum decoupling, at the direct cost of the one-glance-readable pipeline diagram that is arguably prior writing POC's single most valuable asset.

**Weakest link:** Ordering becomes implicit in the union of each handler's own trigger conditions rather than one explicit, auditable sequence -- the exact 'HUMANIZE after OPTIMIZE, do not reorder' doctrine prior writing POC enforces by writing it in one place becomes distributed across N handler definitions, each of which must independently get its own preconditions right for the whole system's ordering to stay correct.

**Risks:**
- Auditing 'what is the actual pipeline order' requires reading every handler's trigger conditions, not one table
- Higher risk of two handlers' trigger conditions silently overlapping or conflicting as the pass count grows

**Diversity role:** decoupled event/handler dispatch, weakest central auditability

### V3. Command-as-entrypoint with shared helpers, no central orchestrator

Each command (mirroring the CLI's own current cmd/pysar/main.go + cobra shape) is its own Go function calling shared library helpers (call an LLM, read/write a piece's artifacts, append a run-log entry) but there is no Pipeline/Phase abstraction imposing a specific execution model. Ordering discipline, if any, lives in each command's own logic and in operator documentation, the same way it currently does in prior writing POC's AGENTS.md.

**Strengths:**
- Fastest to ship a first real command
- No orchestration abstraction to get wrong before real usage reveals what's actually needed

**Novelty:** The only variant with essentially zero new orchestration code -- ships commands fastest, and mirrors the same 'stepping stone first' pattern that worked for the CLI-dispatch and memory-engine decisions earlier this session.

**Weakest link:** Ordering safety is the weakest of all four variants -- nothing in code prevents a command from running out of the intended sequence; this reproduces the exact gap the operator originally identified in a prior writing POC (nothing structurally prevents skipping a step or misordering), just moved from Cursor-read prose to Pysar-read prose.

**Risks:**
- Reproduces the operator's originally-named prior writing POC gap almost exactly, just in a new codebase
- Every future command re-implements its own version of sequencing/gating logic, likely inconsistently

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Ships the first real command fastest and defers the bigger architectural bet until real authoring reveals which ordering rules actually matter in practice -- but unlike the CLI-dispatch and memory-engine cases, prior writing POC's AGENTS.md already represents substantial, already-run design work on exactly this problem, which weakens (without eliminating) the case for rediscovering requirements from scratch here.

**Diversity role:** near-zero orchestration code, reproduces the exact named gap if chosen without mitigation

### V4. Declarative pipeline spec (data) interpreted by a generic runner

The phase graph -- names, order, preconditions, artifact names -- is defined as data (e.g. embedded YAML or a Go data literal, not control flow), interpreted by one generic pipeline-runner function. Adding a phase means adding a data entry; the runner enforces preconditions generically from the spec rather than via phase-specific code.

**Strengths:**
- Adding a phase is a data change, not a code change, once the runner exists
- The spec itself is a readable, single-source-of-truth artifact very close in shape to that prior POC's pipeline table

**Novelty:** The closest structural translation of that prior POC's table-shaped design (the 'Pipeline (canonical order)' ASCII diagram and Status-enum table are themselves already data, not prose logic) into a machine-readable spec a generic engine interprets -- literally turns prior writing POC's documentation table into Pysar's actual configuration.

**Weakest link:** Requires building both the phase logic AND a generic spec-interpreter capable of enforcing arbitrary preconditions correctly -- meaningfully more upfront engineering than V1's direct Go control flow for the same guarantee, since the interpreter itself is a small orchestration DSL that must be designed, built, and gotten right before any phase can run through it.

**Risks:**
- Highest upfront build cost of the four -- the generic interpreter is real, nontrivial engineering before any phase benefits from it
- A bug in the generic interpreter affects every phase at once, unlike V1 where each phase's logic is independently compiled and checked

**Diversity role:** data-driven spec + generic interpreter, most direct structural translation of prior writing POC's table format, highest build cost

## Pareto Front Trade-Offs

- Code-enforced finite state machine: typed Status enum + phase registry — Best ordering_safety, ties for best queryable_pipeline_state, second-cheapest build_cost. Costs middling flexibility_for_new_passes -- a fixed status/transition graph is less accommodating of passes that don't fit a strict linear order than an event-driven model.
- Event-driven handler pipeline: passes subscribe to trigger conditions — Best flexibility_for_new_passes tied with V4, cheaper to build than V1 in the ordering-safety-per-dollar sense is worse -- ordering becomes implicit across N handler definitions instead of one auditable sequence, and piece state is the hardest of the four to query centrally.
- Command-as-entrypoint with shared helpers, no central orchestrator — Cheapest to build by far. Costs the worst of every other dimension -- reproduces the operator's originally-named prior writing POC gap (nothing prevents misordering) almost exactly, just in Pysar's own codebase instead of prior writing POC's.
- Declarative pipeline spec (data) interpreted by a generic runner — Ties V1 on ordering-adjacent guarantees and V2 on flexibility -- effectively the best of both on paper. Costs the highest build_cost of the four: a generic spec interpreter is real, nontrivial engineering that must exist and be correct before any phase benefits from it.

**Selection policy:** Pareto front, not a scalar winner -- deep mode, full parity_plan declared before scoring per CMP-02. All four variants are genuinely non-dominated. design_risk_transfer is tracked as an observation only (Anti-Goodhart) and excluded from tie-breaking -- V1 and V4 both score highest on it, but that is reported as context, not used to justify picking either over V2 or V3.

**Recommendation rationale:** V3 (command-as-entrypoint, no orchestrator) is technically the cheapest and was marked a stepping stone in this portfolio, mirroring the pattern that worked well for the CLI-dispatch and memory-engine decisions earlier this session -- but I would not extend that pattern here without flagging why it differs. In those cases, the requirements were genuinely unknown and cheap-first let real usage discover them. Here, prior writing POC's AGENTS.md already represents substantial completed design work on exactly this problem, already run through real published articles -- choosing V3 doesn't defer discovering the ordering rules, it defers RE-DISCOVERING rules that already exist, at the cost of reproducing the operator's own named gap (nothing prevents misordering) in a second codebase. Between V1 and V4, which both give the strongest guarantees: V1 is meaningfully cheaper to build for the same ordering/query guarantees, and a compiled Go state machine is easier to reason about and debug than a generic spec-interpreter with the same bug surface multiplied across every phase that runs through it. V4's extra flexibility (data-driven phase addition) is a real advantage only once the phase list is genuinely volatile -- not yet established. My lean is V1, with V4 as the natural escalation if the phase list turns out to grow and change faster than V1's compiled structure comfortably accommodates.
