# Solutions for: SEO/publish-packaging phase for Pysar's editorial pipeline, and its relationship to HUMANIZE

Problem: prob-20260804-02180d8d

## Variants (5)

### V1. Mirror dogfood doctrine exactly (OPTIMIZE before HUMANIZE)

New ps-seo skill inserted between sharpen and humanize, doing exactly what the dogfood's seo-optimizer does: resolve [^shortname] citations, tune title/subtitle (CTR + read-completion), fill tags/meta description/slug, check scannability + outbound-link authority. --seo flag makes the /ps orchestrator insert this stage; default ps-humanize is completely untouched. Pre-SEO snapshot is just sharpen.md (already preserved by existing convention), SEO output goes to its own seo.md, humanize.md is written from seo.md when --seo is on.

**Strengths:**
- Lowest implementation risk -- port a working spec
- No conflict with any existing decision or ps-humanize policy
- Matches the one documented rationale we actually have evidence for

**Novelty:** Zero new humanize logic; the only new surface is one new skill file plus orchestrator wiring -- reuses a fully specified reference implementation instead of designing from scratch.

**Weakest link:** Does not address the operator's original ask at all -- SEO still finishes before humanize, so anyone who specifically wanted 'SEO polish as the last, final pass' gets told no. If the operator's real reason for wanting it last is legitimate (e.g. wants humanize's rhythm changes to be truly final and unreviewed-after), this variant doesn't serve that.

**Risks:**
- Operator may feel overridden rather than persuaded if this ships without the doctrine conversation actually happening

### V2. Post-humanize, metadata-only SEO pass (body untouched)

--seo runs strictly after humanize but is scoped to publish metadata only: tags, meta title/description, URL slug, and a read-only citation-resolution pass. It never edits article prose, headings, or structure -- so it structurally cannot re-sterilize what humanize roughened, because it never touches the body at all.

**Strengths:**
- Genuinely safe -- cannot regress humanize output by construction
- Simple to verify: a diff of article.md before/after must be empty

**Novelty:** Resolves the ordering conflict by shrinking scope rather than by fighting the doctrine -- sidesteps the fight instead of winning or losing it.

**Weakest link:** Loses the highest-value SEO levers -- title/subtitle CTR tuning and on-page scannability/structure work are exactly the parts of the dogfood's optimizer with the most demonstrated impact, and this variant can't touch them without breaking its own no-body-edits rule. Ships a materially weaker SEO pass than the reference implementation to preserve a placement preference.

**Risks:**
- Operator may be unsatisfied because 'SEO' colloquially includes title/headline work, which this variant explicitly excludes

### V3. Split dual-pass: technical SEO before humanize, invariant-only verification after

Real on-page SEO work (citations, title/subtitle, structure, tags, meta) runs before humanize, matching doctrine for the parts that need it. A second, lightweight post-humanize pass runs last and is read-only: it re-checks that SEO invariants survived (title/subtitle still present and undamaged, meta fields intact, zero citation markers, link anchors unchanged) and flags -- but never edits -- any regression for the operator to resolve. This gives 'SEO is checked last' without 'SEO rewrites last.'

**Strengths:**
- Directly answers 'I want SEO confirmed last' without reopening the re-sterilization risk
- Reuses humanize's own already-documented locked-fields list as the verification's source of truth instead of inventing a new one

**Novelty:** Separates 'do the SEO work' from 'confirm the SEO work survived' into two different pass types (mutating vs. verifying) instead of treating SEO as one monolithic stage that has to pick a single position.

**Weakest link:** Two new artifacts (a real pass and a verification pass) instead of one -- more moving parts to build and maintain than either single-pass variant, for a benefit (post-humanize confidence) that may be redundant if humanize's own post-flight checks (already documented: 'locked packaging fields' unchanged) already guarantee the same thing.

**Risks:**
- Verification pass could become a second place invariants are defined, drifting out of sync with humanize's own post-flight self-check list

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** The verification-pass pattern (read-only post-stage invariant checker, separate from the mutating stage) generalizes to COVER (verify caption matches locked voice) and to export (verify nothing downstream broke citation/link integrity) -- a reusable pattern beyond just SEO.

### V4. Full SEO rewrite after humanize, with an automated re-humanize guardrail pass

Deliberately overrides the doctrine: run the complete SEO pass (including body edits -- link density, structural tightening, keyword placement) strictly after humanize. Immediately chain an automated guardrail that reruns humanize's own mechanical post-flight checks (sentence-length variance, section-symmetry, hedge-stack scan, banned-phrase scan) against the SEO pass's output and auto-reverts or flags any regression before the file is considered final.

**Strengths:**
- Only variant that fully satisfies 'SEO happens last' as literally requested
- Guardrail logic (reusing humanize's own post-flight scans) is at least grounded in an existing, tested checklist rather than invented from nothing

**Novelty:** The only variant that actually grants the operator's original ordering request while trying to engineer around the reason the doctrine exists, rather than accepting or sidestepping it.

**Weakest link:** This is chasing the dogfood's documented failure mode with an automated patch instead of avoiding it -- the guardrail can only catch what it has mechanical checks for (rhythm variance, symmetry, banned phrases); it cannot catch subtler re-sterilization (SEO's smoother transitions, safer word choices) because those aren't things the current post-flight checklist measures. Real risk of shipping something that mechanically passes the guardrail but reads sterile again -- the exact problem the dogfood doctrine was written to prevent, with no evidence this project's mechanical checks are as complete as they'd need to be to actually prevent it.

**Risks:**
- Builds and maintains two overlapping rewrite passes (SEO + guardrail-revert) for a problem the dogfood already solved by simple ordering
- If the guardrail's checks are ever incomplete, failures are silent -- ships sterile prose that mechanically 'passed'

### V5. SEO-tuned humanize variant selectable via --seo

Investigate the operator's literal proposal: a distinct humanize flavor, selected by --seo, tuned for search-engine-relevant structural signals (shorter paragraphs for mobile scannability, subheading cadence, keyword-bearing sentence placement) instead of default humanize's voice-authenticity focus -- explicitly excluding detector-evasion techniques per the standing constraint.

**Strengths:**
- Directly investigates what the operator asked for instead of assuming it's a non-question
- If it does collapse into 'humanize with SEO-relevant formatting knobs,' that's a useful, honest, cheap finding either way

**Novelty:** The only variant that treats 'humanize' itself, not a separate stage, as the thing that should change under --seo -- tests whether the operator's instinct (that humanize and SEO interact directly) points at something real once detector-evasion is subtracted out.

**Weakest link:** Once AI-detector-evasion is off the table (per this problem's hard constraint), it's unclear what's actually left that's specific to 'SEO' rather than just 'humanize with different formatting parameters' -- paragraph length and subheading cadence are on-page structure concerns that belong to the SEO/optimize stage in every variant above, not to voice-authenticity work. Real risk this variant is a re-labeling of variant 3's or variant 1's structural work with no independent substance, or worse, a re-opened door for detector-evasion techniques to sneak back in under a new name later.

**Risks:**
- Highest risk of quietly reintroducing the declined technique set if scoped loosely ('SEO-tuned' as a label doesn't self-enforce the exclusion)
- Splits humanize into two divergent code paths (default vs SEO) that both have to be kept in sync with future voice/banned-phrase changes
