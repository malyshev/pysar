# Solutions for: Tag push publishes even when no product-worthy change warrants a release

Problem: prob-20260808-3b1c09bf

## Variants (5)

### V1. Conventional-commit gate before GoReleaser (feat|feature|fix since previous tag)

Keep tag-triggered workflow. Add a cheap job/step that scans git log previous_tag..HEAD for conventional types matching /^(feat|feature|fix)(\(|:|!)/ (release-it style). If none match, exit 0 and skip the release job; if any match, run tests + GoReleaser as today.

**Strengths:**
- Directly encodes 'chore should not ship'
- Tiny workflow-only change, no new secrets
- Preserves explicit tag push as the deliberate action

**Novelty:** Gates on commit-message KIND in the version range, not on whether CI was triggered — matches the operator's release-it intuition without adopting Node release-it.

**Weakest link:** Does not fix today's failure mode: force-pushing the same already-released tag still sees the original feat/fix history (or an empty/ambiguous range) and can still attempt upload → 422. Also fails closed/open depending on how non-conventional historical commit subjects are treated.

**Risks:**
- Existing commit subjects are not consistently conventional — may block intentional releases until messages are cleaned
- Retag/chore-on-existing-tag still publishes or fails
- Operators must remember to write feat:/fix: when they want a ship

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Establishes a commit-type vocabulary the project can later reuse for automated version bumps without switching the whole pipeline yet.

### V2. Idempotent skip when GitHub Release assets already exist for this tag

Before GoReleaser, query the GitHub Releases API for the pushed tag; if a release exists with the expected archive assets, exit green and skip publish. Tag push with no existing release proceeds as today.

**Strengths:**
- Fixes the observed 422 with high confidence
- No conventional-commit adoption required
- Green CI on history rewrites that move tags

**Novelty:** Gates on published-artifact state (SCM truth), not on commit messages — solves the exact 422 retag failure observed today.

**Weakest link:** Says nothing about whether a NEW tag that only contains chore commits should ship — a mistaken v0.1.1 chore tag still publishes a full release.

**Risks:**
- Partial releases (some assets uploaded) need a clear policy: skip vs repair
- API check needs careful auth via GITHUB_TOKEN permissions

### V3. GoReleaser replace_existing_artifacts on re-upload

Set release.replace_existing_artifacts: true in .goreleaser.yaml so a retag re-run deletes colliding assets and re-uploads. CI stays tag-triggered; failures become overwrites instead of 422.

**Strengths:**
- One-line config; recovers partial/failed uploads
- No workflow branching logic

**Novelty:** Treats retags as intentional republish rather than skip — opposite policy polarity from V2.

**Weakest link:** Makes chore retags succeed by republishing binaries (possibly rebuilt with same version, different commit SHA) — increases false-publish surface instead of reducing it.

**Risks:**
- Silent overwrite of release assets on accidental tag force-push
- Does not address chore-only NEW tags

### V4. Adopt release-it / semantic-release as the version+publish driver

Replace 'human creates tag, CI publishes' with a release-it/semantic-release tool that analyzes conventional commits, bumps version, creates tag, and publishes only when feat/fix warrant it. CI becomes the executor of that tool (or a manual npm/pnpm release script).

**Strengths:**
- Industry-standard chore/feat/fix semantics
- Can refuse to cut a release when history is chore-only

**Novelty:** Moves version authority from human tag choice into commit-history analysis — full release-it.js model, not a thin gate in front of GoReleaser.

**Weakest link:** Conflicts with dec-20260805-db745b4a invariant that publish requires explicit deliberate operator tag action; adds Node toolchain to a Go-only release path; highest setup/maintain cost for a single-maintainer repo.

**Risks:**
- Amends/supersedes core of the existing release decision
- Two ecosystems (Go build + Node release driver)
- Harder rollback if the tool's opinionated defaults fight GoReleaser

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** If the project later wants fully automated changelogs and version bumps from conventional commits, this is the end-state architecture.

### V5. Composite gate: conventional-commit check AND already-published skip

Workflow runs two cheap preflight checks before tests/GoReleaser: (1) skip green if Release assets for this tag already exist; (2) else require at least one feat|feature|fix since previous tag, else skip green. Intentional republish stays a separate explicit path (workflow_dispatch with force input, or replace_existing_artifacts only when force=true).

**Strengths:**
- Covers today's 422 and the chore-should-not-ship intent
- Preserves explicit tag push
- Keeps GoReleaser + GITHUB_TOKEN

**Novelty:** Separates two failure modes the operator conflated — retag idempotency vs product-worthy content — and assigns a gate to each, with forced republish as an opt-in third path.

**Weakest link:** More workflow branches to get wrong; conventional-commit adoption still required for NEW tags; force republish path can be forgotten when actually needed.

**Risks:**
- Slightly more YAML than V1 or V2 alone
- Need a written policy for force republish

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Can land V2 first (stop the bleeding), then add V1's commit gate, then optional force — without committing to full release-it.
