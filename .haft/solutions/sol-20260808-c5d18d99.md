# Solutions for: Footer subscribe on static getpysar.com

Problem: prob-20260808-c0712044

## Variants (4)

### V1. Newsletter host form POST (Buttondown / ConvertKit)

Keep the static footer. On submit, POST the email to a newsletter host’s public form/API endpoint (e.g. Buttondown form action or ConvertKit forms). No Cloudflare Function; list, double-opt-in, and send live in the host. Wire success/error from their HTTP response into FooterSubscribe.

**Strengths:**
- Fits output:export with no Pages Functions
- Built-in list + campaigns + unsubscribe
- Smallest code change in footer-subscribe

**Novelty:** Zero new runtime on getpysar.com — capture ownership moves entirely to a mail product.

**Weakest link:** Public form endpoint + spam/bots; CORS/form quirks; brand/ops locked to that host’s list UX.

**Risks:**
- Provider lock-in for the list
- Client-visible form key if required
- Spam if no CAPTCHA

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Validates demand for a list before investing in Workers/D1; can later front the same host with a Worker if bot/spam becomes real.

### V2. Cloudflare Pages Function + Resend/Audience or D1

Add functions/api/subscribe under the Pages project (or a Worker route). Footer fetch()'s that same-origin path; Function holds the secret, writes to Resend Audiences / Mailchannels / D1. Still ships Next as static out/; Functions sit beside the export.

**Strengths:**
- Secrets stay off the client
- Same-origin UX, no CORS
- Composable with Turnstile

**Novelty:** Keeps email secret server-side on Cloudflare while motherhome HTML stays static.

**Weakest link:** New deploy surface (functions/, secrets, bot protection) and you still need a sending/list product unless D1 is dump-only.

**Risks:**
- Ops beyond current Direct Upload mental model
- Must confirm Functions work with wrangler pages deploy of out/
- DIY unsubscribe/compliance if using raw D1

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Opens any future same-origin API (contact, waitlist) without leaving Pages.

### V3. Embed provider widget / hosted form page

Replace or supplement the Boxsi email cell with the provider’s embed (iframe/script) or link the Subscribe button to a hosted signup page (Buttondown / Substack / Beehiiv).

**Strengths:**
- Provider handles spam/consent UX
- Almost no custom JS

**Novelty:** Abandons custom form control in favor of the provider’s owned UI.

**Weakest link:** Breaks Boxsi footer visual lock (embed chrome) or adds a hop off-site for a primary CTA.

**Risks:**
- Visual mismatch with template footer
- Third-party script on motherhome

### V4. No email list — announce via GitHub Releases / RSS only

Remove or de-emphasize Subscribe; point visitors to GitHub Releases / watch repo / docs changelog. No PII collected on getpysar.com.

**Strengths:**
- Zero PII/compliance surface
- Matches open-source distribution already used for binaries

**Novelty:** Solves ‘subscription’ by refusing email capture — channel substitution, not another form backend.

**Weakest link:** Does not satisfy authors who expect an email list; footer Subscribe UI becomes dishonest if left in place.

**Risks:**
- Wastes the Boxsi subscribe affordance
- Misses non-GitHub audience
