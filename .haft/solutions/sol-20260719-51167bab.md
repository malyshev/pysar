# Solutions for: Global skill artifact refresh mechanism: automatic vs. manual (--force)

Problem: prob-20260719-8571ddd1

## Variants (5)

### V1. Manual --force flag (already implemented)

The already-shipped mechanism: global skills refresh only when the operator explicitly passes --force. Everything else about init is unaffected. Zero new state, but requires the operator to know the flag exists and remember to use it after every pysar upgrade.

**Strengths:**
- Already built, tested, and verified against the real binary -- zero additional engineering cost
- Maximally safe by construction -- can never silently rewrite anything, satisfying the 'never destroy a hypothetical customization' constraint trivially

**Novelty:** The floor of the option space -- explicit opt-in only, no automation at all.

**Weakest link:** Depends entirely on the operator remembering to run a flag they have no automatic prompt to reach for -- this is the exact failure mode that caused four real incidents before the flag existed, and nothing about the flag's existence fixes the discovery problem: an operator still has to already suspect their skill is stale to think to use it.

**Risks:**
- Recurrence of the same confusion whenever a future ps-* skill ships an update and an operator doesn't happen to pass --force

**Diversity role:** manual opt-in baseline

### V2. Version-marker auto-refresh: purge and recreate on binary version change

Store a small marker file (e.g. ~/.claude/skills/.pysar-version) recording which pysar binary version last wrote the global skills. On every pysar init, compare it to the running binary's own version; if they differ (or the marker is absent), purge the entire ps-* skill tree and recreate it fresh from the embedded assets, then update the marker. No flag needed -- correct behavior is now the only behavior. A comparable pattern (a TOML marker file gating a CWD-based project/tool model) is real, bound prior art in a different project (dec-20260601-...-a89e47b3, CL1, different context).

**Strengths:**
- Zero-flag, zero-friction by construction -- directly satisfies the operator's stated goal and the acceptance criterion that a fresh init after upgrade just works
- Simple mental model: one marker, one comparison, one purge-and-rebuild -- easy to reason about and to test

**Novelty:** Ties correctness to the one signal that's genuinely unambiguous for a single-binary tool -- the binary's own version -- rather than trying to infer intent from file content.

**Weakest link:** Coarse-grained: a version bump for a completely unrelated reason (e.g. fixing an unrelated CLI bug) still purges and rewrites every global skill file, even ones that didn't change at all -- wasted I/O and, if a real customization is ever added later, the version bump alone destroys it with no finer signal than 'the binary changed.'

**Risks:**
- Every version bump is a purge event regardless of whether skills actually changed in that release
- If a real per-file customization ever exists, this has no way to spare it -- coarser than the risk this problem's own constraint asks to name explicitly

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** The marker-file mechanism itself (detect 'installed version differs from running binary') is reusable infrastructure regardless of whether the granularity later moves to per-file (V3).

**Diversity role:** coarse-grained automatic refresh, version-scoped

### V3. Per-file content-hash auto-refresh

Instead of one global version marker, record a hash of each shipped file's content at install time (e.g. alongside each skill, or in one small manifest). On every pysar init, compare each embedded asset's current hash to the recorded one; refresh only the files that actually changed, leave untouched files alone entirely -- still zero flag required.

**Strengths:**
- Minimal, precise writes -- a release that only touches ps-style never rewrites ps-voice, unlike V2's blanket purge
- If a real customization is ever added, this is the only automatic variant with a real chance of detecting and sparing it (a hash that matches neither the old nor the new shipped content is a legitimate 'this was customized' signal V2 cannot express)

**Novelty:** The only variant that structurally distinguishes 'this file changed because pysar shipped an update' from 'this file changed for some other reason' -- directly serves the constraint about not blindly assuming away customization risk.

**Weakest link:** More moving parts than V2: a manifest or per-file hash record to design, store, and keep consistent, for a benefit (skipping untouched files) that is a nice-to-have, not a must-have, at Pysar's current single-skill scale.

**Risks:**
- Real engineering cost for a distinction (customization vs. staleness) that may not matter until there are many more ps-* skills
- A missing or corrupted hash manifest needs a defined fallback (treat as stale? as customized?) that must be decided, not left implicit

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** The exact mechanism that would let Pysar someday tell a real customization apart from staleness for other file classes (CLAUDE.md, settings.json) too, if that ever becomes worth solving.

**Diversity role:** fine-grained automatic refresh, customization-aware

### V4. Unconditional purge-and-rewrite on every init

Simplest possible automatic mechanism: every pysar init call purges the entire global ps-* skill tree and rewrites it from the embedded assets, no version check, no hash comparison, no marker file at all.

**Strengths:**
- Trivial to implement and reason about -- there is no staleness-detection logic to get wrong

**Novelty:** Included as the deliberately weak floor of 'always automatic' to make the real cost of skipping version/hash detection concrete and comparable, not as a genuine recommendation.

**Weakest link:** Directly violates this problem's own acceptance criterion 2 (zero unnecessary writes when nothing changed) -- every single init on every project on the machine rewrites every global skill file even when the binary hasn't changed since the last run, which is by far the common case.

**Risks:**
- Wasted I/O on every single init call, at global scale (every project, every run)
- Zero ability to ever spare a real customization, the most reckless point on this axis

**Diversity role:** unconditional automatic refresh, deliberately weak contrast

### V5. Keep manual --force, add automatic staleness detection and a nudge

Keep V1's --force flag exactly as built (the actual refresh stays opt-in), but add a lightweight check -- comparable to V2's version marker -- that detects staleness and prints an informative one-line nudge ("a newer version of your skills is available -- run pysar init --force to update") instead of staying silent. No file is ever auto-rewritten; only the operator's awareness improves.

**Strengths:**
- Zero risk to any hypothetical customization -- nothing is ever touched without the operator's own explicit action, the safest point on the automation axis after V1 itself
- Directly fixes V1's actual weakest_link (silent unawareness) without taking on any auto-write risk at all

**Novelty:** Separates the two things V1 conflates -- detecting staleness and acting on it -- and automates only the detection half, leaving the action half manual by deliberate choice.

**Weakest link:** Still requires the operator to read the nudge and act on it manually every time -- doesn't fully satisfy the acceptance criterion that the very next init after an upgrade 'just works' with no manual step; it upgrades V1's UX without removing the manual dependency.

**Risks:**
- Same underlying failure mode as V1 remains possible if the operator ignores or doesn't notice the nudge

**Diversity role:** manual action, automatic awareness

## Pareto Front Trade-Offs

- Per-file content-hash auto-refresh — Best possible auto_reliability (5) tied with zero unnecessary churn (1, only rewrites what actually changed), at a real but bounded customization_risk (2) -- the only variant that structurally distinguishes 'shipped update' from 'possible customization' via per-file hash comparison, though the fallback policy for an ambiguous hash still needs to be decided explicitly, not assumed.
- Keep manual --force, add automatic staleness detection and a nudge — The safest point on the front -- ties V1's zero churn and zero customization risk exactly, while fixing V1's actual weakest_link (silent unawareness) with a staleness nudge. Does not fully satisfy the acceptance criterion that the next init after an upgrade 'just works': the operator still has to read the nudge and act on it manually.

**Selection policy:** Pareto front over target-role dimensions (auto_reliability, unnecessary_churn, customization_risk); new_state_files is observation-role, watched per the ProblemCard's own indicator, never optimized (Anti-Goodhart). Declared before scoring.

**Recommendation rationale:** V3 is the recommended pick: it is the only variant that fully satisfies all three of the ProblemCard's own acceptance criteria at once -- automatic correctness after upgrade, zero unnecessary churn on the common no-change case, and an explicit (not ignored) answer to the customization-risk constraint via per-file hash comparison, unlike V2/V4's blind purge. V5 remains a legitimate, more conservative alternative if the operator weighs the (currently theoretical, self-acknowledged near-zero) customization risk higher than closing the automation gap -- it is the correct choice if 'never auto-write, ever' is a harder line than this problem's constraints currently draw it as.
