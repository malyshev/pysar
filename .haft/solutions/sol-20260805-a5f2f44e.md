# Solutions for: Distribution/install mechanism so end users can install pysar locally without building from Go source

Problem: prob-20260805-060a1177

## Variants (5)

### V1. Manual GitHub Release + hand-written install.sh, no CI automation

Push to a new GitHub repo, cross-compile locally with GOOS/GOARCH for macOS/Linux/Windows (native Go cross-compilation, no per-OS machines needed per dec-20260718-239680d4), run `gh release create` by hand per release, and ship a small install.sh (OS/arch detect, fetch latest release via GitHub API, install to ~/.local/bin) modeled on haft's shape but far shorter -- no sidecar runtimes to install since Pysar has none.

**Strengths:**
- No CI secrets/credentials to manage
- No GoReleaser config to learn/maintain
- Real, working cross-platform installs today

**Novelty:** Matches this project's actual current scale (solo maintainer, zero CI history, dec-20260718-817bfb74 already decided plain-toolchain-only for the dev loop) instead of importing haft's full automation on day one.

**Weakest link:** Every release is a manual multi-step ritual (cross-compile 3+ targets, checksum, gh release create, upload) the maintainer must remember and execute correctly by hand each time -- no CI safety net catches a forgotten platform or a bad build before it ships.

**Risks:**
- Human error in the manual release ritual (wrong version tag, missing platform, stale binary)

### V2. GoReleaser + GitHub Actions, tag-triggered (mirrors haft closely)

Adopt .goreleaser.yaml + a release.yml workflow that builds, checksums, and publishes a GitHub Release automatically on every version tag push, plus an install.sh that fetches the latest release -- the same shape haft actually uses, scaled down (no sidecar-runtime install steps, since Pysar has no embedding/runtime dependency to bundle).

**Strengths:**
- Zero manual steps per release once working
- Directly reuses a pattern this operator already trusts and has read closely (haft's own pipeline)
- Checksums and reproducible builds come for free from GoReleaser

**Novelty:** The only variant offering repeatable, CI-verified releases with zero manual cross-compile/upload steps -- a release is just `git tag vX.Y.Z && git push --tags`.

**Weakest link:** Real setup cost before the first release ships: learning/writing .goreleaser.yaml correctly, wiring GitHub Actions permissions/secrets for release publishing, and debugging CI failures with no existing CI history on this project to fall back on -- a nontrivial one-time investment for a solo maintainer's first release pipeline.

**Risks:**
- CI/YAML debugging cost is real and can stall the very first release
- A misconfigured workflow could publish a broken release automatically with no human check before it's public

### V3. `go install github.com/<org>/pysar/cmd/pysar@latest` -- Go toolchain as the entire distribution mechanism

No custom binaries, no install.sh, no release pipeline at all -- point users at the standard `go install` command against the pushed repo/module. This is close to how the binary has actually been built and reinstalled throughout this very session.

**Strengths:**
- Already true today with zero additional work
- Legitimate secondary path worth documenting for contributors/Go-literate users regardless of what else ships

**Novelty:** The cheapest possible option -- literally zero new infrastructure, reuses Go's own module system as the entire distribution story.

**Weakest link:** Fails the problem's own acceptance criterion outright: it requires the end user to have a Go toolchain installed and understand `go install`, which is exactly what "similar to haft" and "without building from Go source themselves" was asking to avoid. Only viable as a supplementary path for Go-literate users, never as the sole mechanism for a non-technical end user.

**Risks:**
- Silently narrows the actual target audience to people who already have Go installed -- contradicts the framed acceptance criterion if adopted alone

### V4. Homebrew tap (macOS/Linux) + manual Windows zip guidance

Publish a Homebrew tap repo so macOS/Linux users run `brew install <org>/tap/pysar` (a package manager they likely already trust and use); Windows users get a documented manual download-and-unzip from the Releases page. GoReleaser has built-in Homebrew-tap publishing, so this can layer on top of V2 rather than being fully separate infrastructure.

**Strengths:**
- No curl|bash trust-ask for macOS/Linux users
- Familiar, well-understood update path (`brew upgrade`) for users who already have Homebrew

**Novelty:** The only variant using an existing, widely-trusted package manager instead of a custom curl|bash script -- lower trust-ask for the end user (no piping a script from the internet into bash).

**Weakest link:** Homebrew-only really serves macOS/Linux; Windows users are back to a fully manual process either way, so this variant alone doesn't cover the three-platform acceptance criterion without still building something else (V1 or V2) underneath it for Windows and for the tap-publishing automation itself.

**Risks:**
- A second small repo (the tap) to create and keep in sync with each release
- Homebrew review/trust conventions for a brand-new, low-adoption tap are a real, if minor, adoption friction

### V5. Ship prebuilt binaries as plain GitHub Release assets, no script at all -- download, chmod +x, move to PATH

The absolute minimum real step: push to GitHub, attach cross-compiled binaries (including a real macOS build, unlike the current dist/ artifacts) to one manually-created Release, and document in a new README exactly how to download, make executable, and place on PATH per platform. No install.sh, no CI, no package manager.

**Strengths:**
- Fastest possible path to a real, downloadable macOS build existing at all
- Zero scripting or CI investment before validating anyone actually wants to install this way

**Novelty:** Gets a genuine, working, cross-platform artifact into an end user's hands today with the least possible new infrastructure -- smaller step than even V1.

**Weakest link:** Manual multi-step process for the end user too (find the right file, chmod it, move it, maybe fight macOS Gatekeeper unsigned-binary warnings) -- meaningfully clunkier than haft's one-line curl|bash, and doesn't really satisfy "similar to haft" as a final state, only as a first move.

**Risks:**
- End users hit unsigned-binary OS warnings (especially macOS Gatekeeper) with no guidance beyond a README

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Forces the cross-platform build matrix (including the currently-missing macOS target) and the GitHub-repo/Release existence question to get resolved first, in isolation -- everything V1/V2/V4 need anyway -- before investing in the scripting/automation layer on top.

## Pareto Front Trade-Offs

- Manual GitHub Release + hand-written install.sh, no CI automation — Medium one-time setup cost, but high recurring per-release effort forever (manual cross-compile + manual release creation every time) -- smaller upfront investment traded for permanent manual toil.
- GoReleaser + GitHub Actions, tag-triggered (mirrors haft closely) — Highest one-time setup cost (GoReleaser + CI wired and debugged from zero prior CI history) but lowest recurring effort (tag and push, CI does the rest) -- largest upfront investment traded for near-zero ongoing cost.
- Ship prebuilt binaries as plain GitHub Release assets, no script at all -- download, chmod +x, move to PATH — Lowest one-time cost of the front and the fastest path to a real macOS build existing at all -- but scored worst on platform_coverage (0%, since manual download/chmod/move never clears the 'one-command-or-near' bar on any platform, regardless of the binary itself being real) and ties V1 for worst recurring effort. Cheapest to start, does not reduce end-user friction or maintainer toil at all.

**Selection policy:** Declared before scoring: eliminate any variant requiring a Go toolchain as its sole mechanism (constraint fails prob-20260805-060a1177's explicit acceptance bar) -- V3 eliminated. Among survivors, minimize initial_setup_cost first (this project has zero release history and one maintainer -- getting a first genuine cross-platform artifact out matters more than long-run automation right now), tie-break by maximizing platform_coverage, then by minimizing per_release_maintainer_effort. end_user_trust_ask is reported, never used to eliminate or rank.

**Recommendation (advisory):** Ship prebuilt binaries as plain GitHub Release assets, no script at all -- download, chmod +x, move to PATH
