# Solutions for: Configurable export destination for finished pieces

Problem: prob-20260812-906a271d

## Variants (5)

### V1. Manifest export_dir + init flag; hand-edit later

Add optional export_dir (project-relative path) to .pysar/project. pysar init --export-dir PATH writes it (default omit/empty = project root). WriteToRoot reads the manifest and lands <dir>/<slug>.md, MkdirAll as needed. MCP export_piece_to_root keeps its name but uses the configured dir and returns the resolved dest path. Post-init change = edit .pysar/project JSON.

**Strengths:**
- Minimal surface: one flag + one field + one WriteToRoot change
- Meets all three operator asks with least new machinery
- Backward compatible when field absent

**Novelty:** Single durable field in the existing projectManifest — no new CLI surface beyond one init flag; destination is project config, not a skill prose convention.

**Weakest link:** Non-technical authors editing raw JSON for post-init changes is error-prone (typos, invalid paths, schema bumps).

**Risks:**
- Tool name export_piece_to_root becomes misleading
- Hand-edit JSON is the only post-init path

### V2. Manifest export_dir + pysar config CLI

Same storage as V1 (export_dir in .pysar/project, init --export-dir), plus a small pysar config get|set subcommand so operators change export_dir without touching JSON. MCP still reads the same field and returns dest path.

**Strengths:**
- Post-init change is operator-friendly
- Same single source of truth as V1
- MCP unchanged in contract shape

**Novelty:** Introduces a general project-config CLI channel, not just an export knobs — future settings can reuse it.

**Weakest link:** First real config CLI expands cmd/pysar surface and docs; risk of overbuilding for a single field if nothing else needs config soon.

**Risks:**
- Scope creep into a full config subsystem
- Two ways to set the same field (init flag vs config set) need clear docs

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Opens a reusable get/set path for later project settings without inventing ad-hoc flags per field.

### V3. Per-call MCP export_dir only (no project setting)

Do not extend .pysar/project. export_piece_to_root gains an optional export_dir argument; skills/agents pass it each time (or default root). Init has no flag. Changing destination means changing what the agent passes or skill prose.

**Strengths:**
- Zero schema change
- One-off overrides are trivial
- No init UX work

**Novelty:** Workflow restructure: destination is call-site authority, not project state — avoids schema_version / migration questions.

**Weakest link:** Fails durable init + later-config asks: every agent session can invent a different path; no project-level memory of where finished pieces live.

**Risks:**
- Agents drift; root litter returns
- Operator cannot set-and-forget

### V4. Project default export_dir + optional per-call override

V1/V2 storage for the project default, plus optional MCP argument export_dir that overrides for one call. Init flag sets default; config/hand-edit changes default; agent can still redirect a single export when needed. Resolved path always returned.

**Strengths:**
- Covers set-and-forget and one-off needs
- MCP can report both configured and actual dest
- Composes with citation-resolve work at write time

**Novelty:** Two authority layers (project default vs call override) with explicit precedence — not just one or the other.

**Weakest link:** Precedence and skill instructions must be unambiguous or agents will ignore the project default and keep passing root/overrides inconsistently.

**Risks:**
- Slightly larger API + test matrix
- Skills may over-use override and defeat the config

### V5. Fixed convention subdirectory (e.g. published/)

Always export to a fixed relative directory under the project (e.g. published/<slug>.md). No init option, no config field — only code+docs change. MCP returns that path.

**Strengths:**
- Simplest implementation
- Stops root pollution without schema

**Novelty:** Removes choice entirely in favor of a single convention — opposite of operator "specify where".

**Weakest link:** Does not satisfy operator requirements 1–2 (specify at init / change in config); only cleans root by fiat.

**Risks:**
- Wrong directory name for some authors
- Still no configurability

## Dominated Variant Elimination

- Manifest export_dir + pysar config CLI — dominated by Project default export_dir + optional per-call override. Same durable setting and MCP clarity as V4, but worse implementation_surface (config CLI) and no one-off override — V4 strictly covers V2's UX goals without the new CLI.
- Per-call MCP export_dir only (no project setting) — dominated by Manifest export_dir + init flag; hand-edit later, Project default export_dir + optional per-call override. No durable project setting — fails operator asks 1 and 2.
- Fixed convention subdirectory (e.g. published/) — dominated by Manifest export_dir + init flag; hand-edit later. Cannot specify or change destination; changes default for everyone.

## Pareto Front Trade-Offs

- Manifest export_dir + init flag; hand-edit later — Smallest durable fix: init flag + .pysar/project field + WriteToRoot/MCP. Post-init = edit JSON. No per-call override.
- Project default export_dir + optional per-call override — Durable default plus optional MCP override; slightly more API/test surface than V1.

**Selection policy:** Pareto among variants with operator_set_and_forget>=4, mcp_agent_landing_clarity>=4, backward_compat>=4; optimize implementation_surface; human binds via /h-decide

**Recommendation (advisory):** Manifest export_dir + init flag; hand-edit later

**Recommendation rationale:** Under the declared constraints, V1 (Manifest export_dir + init flag; hand-edit later) is the smallest surface that meets init + later config + MCP landing path. Prefer V4 (Project default + optional per-call override) only if you already know one-off redirects matter. V2 (config CLI) is dominated by V4 on these scores; revisit config CLI later if JSON editing proves painful.
