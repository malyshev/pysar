# Solutions for: Cursor IDE authors cannot run Pysar's agentic editorial pipeline

Problem: prob-20260808-e2baaf41

## Variants (5)

### V1. Mirror Claude scaffold into Cursor-native paths

Implement scaffoldCursor parallel to scaffoldClaude: embed assets/cursor/ with MCP config (.cursor/mcp.json or project mcp), install the same skill markdown bodies into Cursor's skill install location (~/.cursor/skills/ps-*), and add whatever Cursor needs for slash/skill discovery and project rules. Keep if-chain dispatch; replace the not-yet-supported stub. Closest port of today's Claude experience.

**Strengths:**
- Reuses known init/sync machinery (content-hash refresh, force flag)
- Operator mental model stays 'pysar init --<host>'

**Novelty:** Literal second-host clone of the proven Claude init shape rather than inventing a new packaging theory

**Weakest link:** Cursor's skill/permission/MCP surface is not isomorphic to Claude's — a faithful mirror will still leave gaps (e.g. settings.json allow-list has no exact Cursor twin), so 'parity' may be fake until each gap is hand-verified in a live Cursor session

**Risks:**
- Divergent host quirks force ongoing dual-maintenance of nearly-duplicate asset trees
- Temptation to fork skill prose per host when a quirk appears

### V2. Thin Cursor init: MCP + AGENTS.md pointer only

scaffoldCursor only wires pysar serve into Cursor MCP config and drops a short AGENTS.md / .cursor/rules pointer that tells the agent to follow the existing skill bodies (read from a shared install path or repo assets). No full Cursor skill-install matrix; pipeline orchestration is 'read this skill and do it' rather than native Skill() tool routing.

**Strengths:**
- Smallest blast radius; fastest path to 'pysar tools visible in Cursor'
- Forces skill bodies to stay host-agnostic (no Cursor fork)

**Novelty:** Deliberately refuses host feature parity — treats Cursor as an MCP client + instruction file, not a Claude clone

**Weakest link:** Without native skill registration, Cursor agents will skip steps, invent Write paths, or ignore output discipline unless the operator babysits — acceptance criterion (2)/(5) may fail in practice

**Risks:**
- Looks 'supported' in README while the /ps experience is much worse than Claude
- May train operators that Pysar-on-Cursor is second-class permanently

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Unblocks MCP wiring and validates Cursor+pysar serve in days; later variants can add real skill install without throwing away MCP config

### V3. Shared skill core + hostAdapter registry (V3 trigger)

Treat second-host implementation as the moment dec-20260718-8278c494 already named: introduce hostAdapter + registry, move skill markdown to a host-neutral assets/skills/ (or keep one source of truth), and make Claude/Cursor adapters only own install paths, MCP JSON shape, and permission/settings dialects. Flag surface unchanged.

**Strengths:**
- Aligns with recorded consequence of 8278c494
- Best reuse of skill bodies; third host (Codex) becomes additive

**Novelty:** Uses the project's own pre-recorded migration trigger instead of growing a second ad-hoc scaffold function forever

**Weakest link:** Registry refactor touches the working Claude path while delivering Cursor — regression risk on the only host that already works

**Risks:**
- Scope expands from 'add Cursor' into 'restructure init'
- Adapter interface may be wrong until Cursor quirks are known from a live port

### V4. Cursor Rules/Commands packaging without global skill sync

Ship pipeline stages as project-local .cursor/rules and/or .cursor/commands (or Cursor command files) generated from the same skill markdown, installed only into the project by pysar init --cursor — no writes under ~/.cursor/skills. MCP still project-local.

**Strengths:**
- Matches how many Cursor repos already carry agent instructions
- No global home-directory coupling for skills

**Novelty:** Project-scoped Cursor conventions instead of mirroring Claude's global ~/.claude/skills install model

**Weakest link:** Per-project copies drift from binary-embedded skill versions unless content-hash refresh is reimplemented for project-local Cursor files; multi-project authors get N copies to refresh

**Risks:**
- Breaks the Claude-proven 'one global skill sync' ops model
- Larger project scaffolds; noisier git diffs in writing projects

### V5. Dual-host init: Claude defaults remain, --cursor adds Cursor files alongside

Allow a project to carry both Claude and Cursor scaffolds (or make --cursor additive to a prior Claude init) so the same writing project works in either IDE. Shared .mcp.json / .pysar data; host-specific instruction trees coexist.

**Strengths:**
- Matches real authors who switch IDEs
- Doesn't force choosing one host forever per project

**Novelty:** Optimizes for polyglot-editor authors rather than single-host purity

**Weakest link:** Two host configs in one repo create merge/permission conflicts and unclear 'which agent am I talking to' for output-discipline rules — acceptance smoke becomes ambiguous

**Risks:**
- Violates simple mental model of init --host
- Higher support burden; easy to test only one host and claim both work
