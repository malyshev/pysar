# Solutions for: Install counter on static getpysar.com + Cloudflare

Problem: prob-20260810-5af07d47

## Variants (5)

### V1. GitHub Releases download_count sum (no new infra)

Sum stargazer-adjacent but install-relevant GitHub REST asset download_count across release .tar.gz/.zip for malyshev/pysar. Site or a small script reads the public API (same pattern as live star count). No Cloudflare write path; pure observation of what install.sh already downloads.

**Strengths:**
- Fits current static architecture literally
- No secrets, no Workers
- Same client-fetch pattern as GitHubLink stars

**Novelty:** Reuses the release channel install.sh already hits — zero CF Functions/KV — rather than inventing a second telemetry plane.

**Weakest link:** Counts asset fetches, not successful PATH installs; CI, retries, and mirrors inflate; go install / source builds are invisible.

**Risks:**
- Misleading if labeled 'installs' without caveat
- API rate limits if not cached

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Gives a number this week without touching Pages static contract; later beacons can refine 'success' separately.

### V2. Cloudflare log/analytics on GET /install.sh

Use Cloudflare Pages/Web Analytics or Logpush/Log Explorer (or a thin Worker route in front of the static install.sh) to count HTTP GETs of /install.sh. Operator dashboard in CF; optional public number via Worker API reading a rolled-up KV key from logs cron.

**Strengths:**
- No phone-home from user machines
- Native to Cloudflare hosting

**Novelty:** Measures the documented curl entrypoint at the edge without changing install.sh behavior.

**Weakest link:** GET of the script ≠ run to completion; bots and preview deploys add noise; public display needs an extra rollup path Pages analytics UI alone does not give.

**Risks:**
- Overcounts curl -o inspect-only
- Product analytics vs vanity counter still split

### V3. Success beacon from install.sh to CF Worker + KV/D1

After binary lands on PATH, install.sh fires a best-effort curl to e.g. https://getpysar.com/api/install-ping (Pages Function or Worker). Handler INCR in KV or D1. Site reads public count via same origin or cached JSON. Beacon failure never fails install (|| true).

**Strengths:**
- Honest success-ish metric
- Fits Cloudflare edge + KV/D1
- Display on site is trivial

**Novelty:** Defines install as successful script completion, not mere script download — the closest signal without instrumenting pysar binary.

**Weakest link:** Users who block outbound HTTP, offline installs, or inspect-and-edit scripts never ping; first CF Function breaks the 'no server' MVP purity for that route.

**Risks:**
- Need Functions deploy wiring alongside Pages Direct Upload
- Spam/forgeable pings without signing
- Privacy expectations if overly identifiable

### V4. Umami custom event / pixel from install.sh

Reuse existing Umami Cloud: install.sh curls Umami collect/API or a 1x1 tracking URL with an 'install' event after success. Dashboard in Umami; site can call Umami stats API if key available, or stay operator-only.

**Strengths:**
- No new storage product
- Umami already on layout

**Novelty:** Extends the already-shipped analytics vendor instead of adding CF state.

**Weakest link:** Umami collect from curl is awkward/undocumented vs browser pixel; may need shareable URL or API token in the script; homepage pixel still cannot see curl installs.

**Risks:**
- Token in install.sh if API auth required
- Vendor lock for the metric

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** If Umami already trusted for ops, avoids new KV; can graduate to Worker later.

### V5. Phone-home from pysar binary (first-run / init)

Instrument `pysar` itself (e.g. first successful `pysar init` or anonymous install-id in ~/.pysar) to POST a ping. Counts 'activated installs' across curl, go install, and Windows zip. Site/CF only stores aggregates.

**Strengths:**
- Best activation signal
- Covers non-script installs

**Novelty:** Moves the metric from website architecture into the product CLI — architecture-agnostic to Pages static.

**Weakest link:** Touches Go CLI trust surface; needs clear privacy/opt-out; slower to ship than edge-only options; not 'on Cloudflare architecture' alone.

**Risks:**
- Scope creep into core CLI
- User distrust of telemetry
- Still needs a CF or third-party sink
