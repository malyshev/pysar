# Solutions for: Japanese and Arabic titles still collapse to template-* piece/export slugs

Problem: prob-20260809-19bd7e90

## Variants (5)

### V1. Hand-register ja + ar schemes (kana Hepburn + Arabic letter table); kanji omitted honestly

Extend schemes map with ja (Hepburn for hiragana/katakana, maybe common digraphs) and ar (UNGEGN/ISO-style consonant+long-vowel letter map). detectTransliterationLang picks ja/ar by Unicode script. Kanji left unmapped → if title is kanji-only, still template; mixed kana titles and Arabic work. Documents that ja is kana-scope, not full Japanese.

**Strengths:**
- Zero deps
- Matches V3 official-per-locale pattern
- Arabic letter table is tractable

**Novelty:** Locale fill under existing V3 API without new deps or kanji dictionary — scope honesty is the product.

**Weakest link:** Real Japanese article titles are often kanji-heavy; kana-only scheme fails the operator's dogfood if titles lack kana.

**Risks:**
- Kanji titles still template
- Arabic short vowels often unmarked → lossy romanization

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Registers ja/ar tags and detection; later kanji dictionary can fill ja without changing Slug contract.

### V2. Add go-unidecode / similar any-script approx as fallback scheme und

Keep uk (and optionally thin ja/ar) as named schemes; for other non-Latin scripts call a unidecode-style library registered as und or as last-resort inside Slug when detect returns empty. Produces Latin for Japanese and Arabic without claiming national-standard officialness.

**Strengths:**
- Covers JA+AR+future scripts in one stroke
- Does not claim CMU-style officialness for und

**Novelty:** Separates official schemes from a labeled non-official any-script approximator — invents readability without inventing officialness.

**Weakest link:** Library quality and license; Japanese kanji output is approximate and can look wrong; dependency surface for a naming path.

**Risks:**
- Dep churn
- Slug quality becomes library-defined
- May conflict with V3 'never invent officialness' if und is mislabeled

### V3. Vendor Japanese dictionary romanizer (e.g. kakasi/kuroshiro-class) + Arabic table

Ship a real JA kanji→romaji path via a maintained Go wrapper or embedded dictionary, plus a hand Arabic scheme. Heavier binary/deps; closest to readable Japanese titles.

**Strengths:**
- Handles kanji titles
- Best dogfood for Japanese authors

**Novelty:** Treats Japanese as a dictionary problem, not a letter table — kind change from uk-style schemes.

**Weakest link:** Binary size, embed data freshness, and ambiguous kanji readings yield wrong but confident Latin slugs.

**Risks:**
- Ops/deps cost
- Wrong reading → stable wrong slug
- Arabic still needs separate scheme

### V4. Script-tiered: Arabic full table + Japanese kana now; kanji → short content hash suffix with kana/latin stem when any exists

Hybrid naming: ar scheme full; ja kana transliterated; if after ja pass the slug would be empty/template but Han remains, append a short deterministic hash of the original title (or of remaining Han) so names are unique and non-template while remaining honest that kanji wasn't romanized. Prefer stem from any Latin/kana present.

**Strengths:**
- Never template for JA/AR fixtures in acceptance
- Honest about unmapped Han

**Novelty:** Uses hash only as kanji residual, not as the primary non-Latin strategy rejected in the prior portfolio.

**Weakest link:** Hash stems are still opaque for kanji-only titles — readability goal only half-met; authors may dislike hex.

**Risks:**
- Prior V4 hash-prefix was rejected for primary path — residual hash must stay clearly scoped
- Two naming regimes confuse support

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Unblocks non-template names for kanji-only while leaving room for dictionary romanization later.

### V5. Require profile/project language tag; SlugLang(lang) only — no script detection for ja/ar

Do not auto-detect Japanese vs Arabic vs other. Persist author/project language (or piece lang) and call SlugLang with that tag; schemes for ja/ar still need implementing (likely V1 tables). Avoids wrong-lang romanization across CJK/Arabic.

**Strengths:**
- Correct scheme selection
- Fits official-per-locale

**Novelty:** Moves the lang signal to project config instead of Unicode heuristics — addresses V3 weakest_link for multi-script.

**Weakest link:** Authors must set language; missing tag leaves JA/AR as template — cold-path regression of the gap.

**Risks:**
- Extra onboarding field
- Does not by itself implement JA/AR tables
