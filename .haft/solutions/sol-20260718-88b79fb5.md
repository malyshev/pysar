# Solutions for: Close the distributed-guard gap: structurally force every pass to declare its own precondition check

Problem: prob-20260718-e0dc6dc8

## Variants (4)

### V1. Compile-time interface contract: a Pass interface requiring a Precondition method

Define a Go interface (e.g. Pass) that every pass type must implement, with Precondition(state PieceState) error as a required method alongside Run and Name. Only types implementing the full interface can be registered. Omitting the method is a compile error, not a silent gap.

**Strengths:**
- Zero new dependency or tooling
- Closes the specific 'pass shipped with literally no check' failure mode at compile time
- A natural, near-free byproduct of implementing the already-decided mechanism correctly

**Novelty:** The cheapest possible structural improvement over the status quo -- pure Go idiom, zero new tooling, and effectively something any correct implementation of the already-decided mechanism would need to do anyway to have a consistent pass shape at all.

**Weakest link:** Enforces that the method exists, not that it is meaningful -- a trivial 'return nil' implementation satisfies the compiler and the interface but provides zero real protection. Closes the totally-forgotten failure mode named in the weakest_link; does nothing about the wrong-or-empty-check failure mode.

**Risks:**
- Does not catch a trivial or wrong precondition check -- only that a method with the right signature exists

**Diversity role:** compile-time shape enforcement, cheapest, catches omission only

### V2. Registry-time fail-fast self-test: refuse to register a pass whose Precondition rejects nothing

When a pass registers itself with the shared registry (at process startup), the registry calls Precondition once against a guaranteed-empty PieceState. If it returns nil (i.e. the check would let an empty piece through), registration panics with a clear message naming the offending pass. This runs once, at binary startup, before any real piece is ever processed.

**Strengths:**
- Catches trivial/empty-return checks, which V1 alone cannot
- Fails immediately and loudly at startup -- impossible to silently run a broken build

**Novelty:** Catches a real, meaningful class of the failure mode -- not just 'no method exists' (V1) but 'method exists and is trivially wrong' -- loudly, at the earliest possible moment (process start), before the binary can serve any real request.

**Weakest link:** Only catches the specific case of a check that wrongly permits a totally empty piece -- a check that's subtly wrong in some other way (checks the wrong prior artifact, or is correct for empty state but wrong for a partially-progressed piece) is not caught by this single smoke test.

**Risks:**
- Single smoke-test case (empty state) doesn't cover every way a check could be subtly wrong

**Diversity role:** runtime startup fail-fast, catches trivial checks V1 misses

### V3. CI-enforced meta-test iterating the pass registry

A single Go test (part of the normal `go test ./...` cycle, already run in CI before merge) iterates every registered pass and asserts: (a) Precondition is present and callable, (b) calling it against an empty PieceState returns a non-nil error unless the pass is explicitly marked as legitimately applicable to an empty piece (e.g. the very first idea-scaffolding pass).

**Strengths:**
- Catches the gap at the earliest point a human or CI would naturally look (test failure on a PR)
- No new tooling beyond the standard `go test` already in use

**Novelty:** The only variant that catches the gap before merge, in the normal Go test cycle already part of standard development -- no new custom tool, no separate lint binary, just a test file.

**Weakest link:** Only as strong as CI discipline itself -- if someone merges without running or without CI enforcing tests, this catches nothing. Requires a small registry metadata addition (an 'applies-to-empty' exception marker) to avoid false failures on the legitimately-first pass.

**Risks:**
- Depends on CI/test discipline actually being enforced, which is itself a process, not a code guarantee

**Diversity role:** test/CI-time enforcement, earliest human-visible catch point

### V4. Abandon distributed guards, escalate to the declarative-spec alternative from the original comparison

Reopen dec-20260718-20a08f83 and switch to the previously-compared declarative pipeline spec (data-driven preconditions interpreted by one generic runner), which structurally cannot register a pass with no declared precondition at all -- the interpreter itself would refuse.

**Strengths:**
- Would fully close the gap, not just narrow it

**Novelty:** The only variant that eliminates the weakest_link entirely rather than mitigating it -- at the cost of contradicting the decision's own stated rollback discipline by acting before its named trigger has fired.

**Weakest link:** This is not a mitigation of the chosen mechanism, it is reversing the decision made minutes ago before any real pass has been built and before either of that decision's own named rollback triggers (a real pass shipping without a check; auditability becoming a practical problem) has actually occurred. The prior decision's own rollback plan explicitly treats this escalation as premature absent that evidence.

**Risks:**
- Reopens a just-bound decision without new evidence the rollback plan itself requires before that reopening is warranted
- Pays the full higher build cost of the declarative-spec variant, already weighed and rejected on cost grounds

**Diversity role:** full reversal of the just-bound decision, premature per its own rollback discipline

## Dominated Variant Elimination

- Registry-time fail-fast self-test: refuse to register a pass whose Precondition rejects nothing — dominated by CI-enforced meta-test iterating the pass registry. V3 matches V2 on failure_coverage, build_cost, and composability, and wins outright on catch_point_earliness -- a CI test checking the same empty-state case a registry self-test would check simply catches it earlier (before merge, not only at process start), for the same cost. No reason to prefer V2 once V3 is on the table.

## Pareto Front Trade-Offs

- Compile-time interface contract: a Pass interface requiring a Precondition method — Cheapest, earliest catch point (compile-time), fully composable. Costs the weakest failure_coverage of the three survivors -- only catches total omission, not a trivial or wrong check.
- CI-enforced meta-test iterating the pass registry — Ties V1 on composability, meaningfully better failure_coverage, still catches the gap before merge. Costs slightly more build effort and a slightly later (though still pre-merge) catch point than V1.
- Abandon distributed guards, escalate to the declarative-spec alternative from the original comparison — Best failure_coverage of all four -- eliminates the gap entirely rather than narrowing it. Costs the worst build_cost and composability by far -- this is a reversal of dec-20260718-20a08f83, not a mitigation of it, contradicting that decision's own rollback plan absent the evidence it requires.

**Selection policy:** Pareto front, not a scalar winner. V2 is cleanly dominated by V3. V1, V3, and V4 remain genuinely distinct trade-offs, though V1 and V3 are additive/composable rather than mutually exclusive -- the comparison's own pinned_conditions note this explicitly.

**Recommendation rationale:** V4 is technically on the front but should not be treated as a serious option right now -- it reverses a decision bound minutes ago, before either of that decision's own named rollback triggers has actually occurred, exactly the premature escalation its own rollback plan warns against. The real choice is between V1 and V3, and they are not mutually exclusive: V1 (compile-time interface contract) is close to free and would likely be part of any correct implementation of the chosen mechanism regardless -- there is little reason not to adopt it. V3 (CI-enforced meta-test) adds real, additional failure_coverage (catching a trivial or empty-permitting check, not just a missing one) at a small, one-time cost, and dominates V2 outright so there is no reason to consider the runtime-startup version once this is on the table. My recommendation is V1 and V3 together, not a single pick -- they close different, adjacent slices of the same named gap for a combined cost lower than V4 alone, without touching or reversing the decision they harden.
