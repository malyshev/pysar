# Solutions for: No site-ready user docs corpus in-repo

Problem: prob-20260808-39f48c3d

## Variants (5)

### V1. Journey-first docs/ tree with SSG-ready frontmatter

Human-authored docs/ tree ordered by operator journey (install → init/hosts → pipeline → MCP/skills → export → troubleshoot). Each page is task-oriented Markdown with YAML frontmatter (title, slug, nav_order, section). Index navigates the path; README shrinks to a pointer. Same corpus for GitHub now and future static ingest without IA rewrite.

**Strengths:**
- Maps directly onto draft acceptance
- Single corpus by construction
- Ingest is mapping not rewrite
- High reversibility — Markdown only

**Novelty:** Journey-ordered IA + SSG-ingest frontmatter as day-one constraint, not a flat feature dump or a second website-only source later.

**Weakest link:** Hand-maintained journey pages and nav_order drift from shipped install/init/host behavior, so cold-path 'docs alone' fails silently while the tree still looks complete.

**Risks:**
- Journey IA may mismatch lookup-by-command habits
- Frontmatter may need a thin adapter for the eventual SSG
- Aggressive README shrink can hide install facts if index is skipped
- MCP/multi-host pages can sprawl into host internals

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Stable slugs/sections/nav_order are the dogfood substrate a future docs site can ingest; later SSG/hosting attaches to this tree instead of forking content.

**Diversity role:** workflow / journey IA

### V2. Docs-as-code generation from shipped surfaces

Generator emits docs/**/generated/*.md from pysar --help / subcommand help and skill frontmatter under cmd/pysar/assets/skills; thin hand-written glue for install, host init, and troubleshooting. Make target + CI fail on drift so the corpus stays tied to shipped surfaces.

**Strengths:**
- Hard drift resistance for flags/skills
- Enforces document-shipped-behavior for generated slice
- Single corpus; site-ingestible deterministic paths
- Human judgment only where generation cannot work

**Novelty:** Docs freshness is mechanical (regenerate-or-fail) for CLI/skills inventory, not a hand-maintained prose mirror.

**Weakest link:** Help/frontmatter are reference-shaped; naive generation yields coverage-shaped pages that still fail first-time task completion unless hand-written glue carries almost all narrative weight.

**Risks:**
- Generated pages look complete but fail as tutorials
- Skill blobs dump poorly as user prose
- Generator+CI become a second product surface
- Temptation to over-generate full skill bodies

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Establishes generated/ + hand-glue IA and a drift gate later extractors (MCP schemas, host matrices) can plug into without a second docs source.

**Diversity role:** data-flow / generate from product surfaces

### V3. Diátaxis tree under docs/ (tutorials · how-to · explanation · reference)

Split docs/ by Diátaxis type: Start-here tutorial for install→init; how-tos for pipeline/export/troubleshoot; explanation for pipeline/MCP mental models; reference for CLI+MCP. Cross-links between related pages; YAML frontmatter (title, type, slug); README points to Start here.

**Strengths:**
- Clear Start-here entry + task pages
- Separates how/what/lookup to reduce README conflation
- Dual-use single corpus
- Can flatten later if too heavy

**Novelty:** IA typed by reader intent (learn / achieve / understand / look up) rather than one page per feature.

**Weakest link:** Without a thin lint/checklist, authors collapse types into undifferentiated how-tos and frontmatter becomes cargo-cult metadata that no longer predicts nav.

**Risks:**
- More files; cold GitHub readers bounce between quadrants
- Wrong type placement breaks cold-path
- Four trees raise drift cost when CLI changes
- Frontmatter rename if SSG differs

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Typed docs/{tutorials,how-to,explanation,reference}/ with stable slugs is a ready-made section map for any later SSG — website work becomes theming + ingest.

**Diversity role:** architectural / Diátaxis IA

### V4. Docs tree plus undeployed SSG scaffold

Ship GitHub-readable Markdown under docs/ covering all aspects, plus a committed-but-undeployed SSG config (Docusaurus/Mintlify/VitePress — nav/sidebar only, no hosting). Proves ingest without shipping a live site; content stays plain Markdown.

**Strengths:**
- Meets corpus + IA acceptance without live site
- Early cheap feedback on path/slug survival
- Reversible: delete scaffold, keep Markdown
- Defers hosting without deferring structure

**Novelty:** Separates corpus delivery from hosting — undeployed config forces real ingest rehearsal instead of hoping Markdown ports later.

**Weakest link:** Scaffold dialect hardens around one SSG before hosting is chosen; if rejected, prove-ingest work becomes rewrite tax, and undeployed config can bitrot unnoticed.

**Risks:**
- Premature SSG lock-in
- Config bitrot = false confidence
- Looks like site commitment; scope creep into deploy/theme
- Dual nav (README index vs sidebar) if not single-sourced
- Tension with 'SSG choice out of scope'

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Opens later search over hosting/CI, SSG swap with a known nav contract, plugins, and chrome around an already-proven content tree.

**Diversity role:** infrastructure / website rehearsal scaffold

### V5. Root hub — expand README or DOCUMENTATION.md, defer docs/

Keep all user guidance in one root Markdown file (structured README with deep-link anchors, or DOCUMENTATION.md). No docs/ until a website project forces a split. Future site ingests one page or splits on heading boundaries later.

**Strengths:**
- Zero path bikeshed; matches today's README reality
- True single corpus
- Fastest coverage of named aspects
- Highest short-term reversibility
- Avoids fake SSG frontmatter before a consumer exists

**Novelty:** Anti-folder — refuses docs/ IA until website ingest needs force file boundaries; one sectioned root file is the corpus.

**Weakest link:** Draft acceptance literally requires a dedicated docs tree, per-aspect pages, and short README pointer — a root hub fails those criteria as written unless acceptance is revised.

**Risks:**
- Fails draft AC unless acceptance edited
- Single-file length hurts scanability and cold-path
- Megapage awkward for site nav/SEO until rushed split
- Heading renames break anchors more than file redirects
- README stuffing trap (length ≠ documented)

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Stable H2/H3 section IDs become natural split points into docs/*.md when the website starts — content moves without rewriting narrative twice.

**Diversity role:** anti-pattern / defer tree
