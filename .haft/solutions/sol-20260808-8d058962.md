# Solutions for: Editorial pipeline packages shipped without DecisionRecords

Problem: prob-20260808-eb6fb84e

## Variants (5)

### V1. One umbrella DRR: shared pipeline substrate + stage file contract

Record a single DecisionRecord that reverse-governs what master already ships: Pass/Precondition registration in internal/editorial, one revision file per stage (draft.md → staff-edit.md → sharpen.md → seo.md → humanize.md), shared draft.Write*/Validate helpers, MCP resolveAnchoredPass, and validation package as the shared error surface. List all blind packages in affected_files. Link/close prob-20260725-f12a3c92 as covered by this substrate unless research needs a follow-on note.

**Strengths:**
- Minimal ceremony for reverse-governance
- Matches how the code is actually factored
- Clears module blindness in one decide

**Novelty:** Closes coverage with one binding artifact sized to the invariant that is actually shared — not eight restatements of the same Pass pattern.

**Weakest link:** A single DRR will underspecify pass-specific policy (e.g. research tier floors, seo-before-humanize already has its own DRR) and future pass-only changes will either reopen the umbrella constantly or drift undocumented again.

**Risks:**
- False sense of full per-pass rationale
- Umbrella becomes a junk drawer for unrelated stage rules

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Once the substrate is governed, pass-specific DRRs can be added only when a real design fork appears — without blocking current coverage.

### V2. Per-pass DecisionRecords reverse-extracted from each package

Write a separate DRR for intake, research, draft, staff-edit, sharpen, seo (or amend existing seo decision), humanize, export, and validation — each with invariants taken from current code and skill prose. Full graph coverage, module-by-module.

**Strengths:**
- Clear ownership per module for future /h-verify
- Natural place for research-specific backlog

**Novelty:** Treats each stage as its own decision surface — maximum fidelity to how operators already talk about /ps-* commands.

**Weakest link:** Highest ceremony cost for reverse-governance; nine similar DRRs will rot in parallel and encourage copy-paste invariants that diverge from the shared helpers.

**Risks:**
- Operator fatigue; incomplete set if energy runs out mid-batch
- Duplicates Pass substrate already decided elsewhere

### V3. Substrate DRR + Notes (or micro-decisions) per blind package

One DecisionRecord for the shared pipeline substrate (same core as V1). For each blind package, record a Note (or /h-note micro-decision) capturing package-local invariants and pointing at the substrate DRR — lighter than full DRRs, still searchable and linkable. Research note explicitly addresses/closes prob-20260725-f12a3c92.

**Strengths:**
- Proportional ceremony
- Keeps package-local facts from vanishing
- Fits single-maintainer scale

**Novelty:** Splits binding weight (DRR) from local memory (Notes) — coverage without nine full E.9 ceremonies.

**Weakest link:** Notes are weaker carriers than DRRs for require_decision workflows; future haft path policies may still treat modules as under-decided if Notes do not count as governance for code edits.

**Risks:**
- If Notes are invisible to coverage/check, blindness returns in tooling even when humans feel covered

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Any Note can later be promoted to a DRR when a real fork appears, without rewriting the substrate.

### V4. Extend existing DRRs affected_files/baselines only — no new pipeline decisions

Do not create new DecisionRecords for the pipeline packages. Instead amend affected_files (and baselines) on existing decisions (a2a24f32, ffbfb04b, 20a08f83, 35fa2d24, e3234e50, 6ba897d4, etc.) so coverage tooling attributes those modules to already-bound choices.

**Strengths:**
- Fastest path to green coverage metrics
- Zero new decide ceremonies

**Novelty:** Closes the gap as a bookkeeping fix on the current graph rather than new reasoning artifacts.

**Weakest link:** Attribution without new rationale: modules look governed while their real stage-specific invariants remain unstated — coverage green, memory still thin.

**Risks:**
- Goodhart on coverage score
- Does not satisfy acceptance if interpreted as needing invariants that match code behavior

### V5. Spec-section carriers for pipeline modules, DRRs only on forks

Author SpecSection (or equivalent .haft spec) prose that documents each package contract as observed in code. DecisionRecords stay reserved for future changes that alter those contracts. Coverage gap closed via spec health / module docs rather than DRR count.

**Strengths:**
- Honest about reverse-governance vs deciding
- Avoids decision inflation

**Novelty:** Moves reverse-governance into the spec layer — Object≠Carrier: describe the system without pretending every description is a decision.

**Weakest link:** If this project require_decision path keys on DecisionRecords for code edits, spec sections alone will not unblock agents editing those packages — gap returns as workflow friction.

**Risks:**
- Tooling may not treat specs as clearing coverage gaps today
- Spec drift without verify loop

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Specs become the baseline that future /h-frame→decide cycles amend when behavior actually changes.
