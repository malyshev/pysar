# Solutions for: Post-install agent briefing: what Pysar is + voice/style onboarding

Problem: prob-20260809-27992844

## Variants (5)

### V1. Extend install carrier script (homepage + llms.txt step 3)

Add a mandatory step 3 to #for-ai-agents / meta / HowTo /llms.txt: after init succeeds, tell the human in plain language what Pysar is (writer stays in charge; never posts), 2–3 benefits, how to start (/ps), and that without /ps-onboard the project uses generic defaults — offer to run /ps-onboard next. Keep human hero free of this wall of text.

**Strengths:**
- Zero new host packaging
- Hits the exact URL-drop moment
- Aligned with dec-20260808-homepage-ai-install-signals-9eb5a6a9

**Novelty:** Extends the already-bound V4 co-located carrier — no new discovery surface; briefing rides the same fetch as install.

**Weakest link:** Agents that truncate HTML or stop after shell success may never execute step 3; compliance is instruction-only.

**Risks:**
- Longer carrier increases truncation risk
- May feel salesy if copy is wrong

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Can later deepen into a skill-backed welcome without changing the published step order.

**Diversity role:** minimal carrier extension

### V2. Post-init skill: ps-welcome / expand init-installed skill

Ship a short host skill (or expand an existing one) installed by pysar init that the install carrier tells the agent to invoke after init. Skill content holds what/why + onboarding CTA and calls check_onboarding_status so complete projects stay silent.

**Strengths:**
- Lives with MCP project after URL is closed
- Can gate on onboarding status
- Host-neutral skill corpus

**Novelty:** Moves durable briefing into the skill corpus the agent already loads after init — survives past the homepage fetch.

**Weakest link:** Depends on agent invoking the skill; if install carrier is ignored, skill never runs. Extra skill surface to maintain across hosts.

**Risks:**
- Skill sprawl
- Claude/Cursor/Codex invocation dialects differ

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Skill can later grow into richer first-run UX without changing the motherhome carrier again.

**Diversity role:** installed durable instructions

### V3. MCP welcome brief tool (structured pitch + status)

Add an MCP tool (e.g. get_welcome_brief) returning structured what/why, next actions, and onboarding outstanding flags. Install carrier / skills must call it after init and speak from the tool result — single source of truth, updatable without re-fetching the homepage.

**Strengths:**
- One source of truth
- Natural gate on check_onboarding_status
- Testable contract

**Novelty:** Machine-owned briefing object via MCP, not prose embedded only in HTML/skills.

**Weakest link:** Requires Go/MCP change + tool approval on hosts; overkill if agents won't call tools until asked to write.

**Risks:**
- Permission prompts
- Scope creep before install smokes exist

**Diversity role:** structured substrate

### V4. Auto-start /ps-onboard after init (no separate pitch)

Install carrier says: after init, immediately run /ps-onboard (or Skill ps-onboard). Product pitch is folded into the opening of onboarding conversation rather than a separate briefing message.

**Strengths:**
- Highest chance voice/style actually gets set
- Less dual messaging

**Novelty:** Skips marketing monologue; jumps straight into the valuable voice/style capture the operator cares about most.

**Weakest link:** Aggressive — author who only wanted install may feel hijacked; conflicts with output discipline if onboarding opens a long questionnaire unprompted.

**Risks:**
- Consent/hijack feel
- Bad for re-init on already-onboarded projects unless gated

**Diversity role:** action-first

### V5. Status quo: rely on /ps Step 0 onboarding mention only

Do not add install-moment briefing. Keep mechanical install; authors discover product narrative via human site/docs and onboarding CTA only when they start /ps.

**Strengths:**
- No new surface
- No hero/carrier bloat

**Novelty:** Explicit non-build baseline — proves whether the gap is real vs solved by existing /ps behavior.

**Weakest link:** Authors who install and never run /ps never hear about voice/style; install moment stays opaque.

**Risks:**
- Misses the operator's stated install-moment goal

**Diversity role:** control / do nothing
