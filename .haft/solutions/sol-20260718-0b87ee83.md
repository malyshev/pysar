# Solutions for: Onboarding command architecture: orchestrator vs standalone vs precondition-driven

Problem: prob-20260718-9459924b

## Variants (5)

### V1. Orchestrator + independent sub-commands (operator's proposal)

/ps-onboard is a thin sequencing skill: it runs /ps-voice then /ps-style in order for first-time setup. Both /ps-voice and /ps-style also exist as fully standalone, independently-invokable skill commands an author can run alone at any later time to re-tune just one profile. A comparable pattern (an init/orchestrator pair, each command with exactly one job) is real, bound prior art in a different project (dec-20260601-...billing-interface, CL1, different context) -- cited as bounded inspiration only, not justification.

**Strengths:**
- Directly satisfies acceptance criteria 1 and 2 by construction -- both the bundled and standalone paths are first-class commands
- Simple mental model: three commands, three files, no hidden state machine to reason about
- Matches a real precedent's own stated tradeoff reasoning (simpler files, each command one job)

**Novelty:** Treats orchestration as a documentation/sequencing convenience layered on top of two commands that are already complete and useful alone -- not a new completeness-tracking mechanism.

**Weakest link:** The sequencing in /ps-onboard is hardcoded prose ("run voice, then style") -- nothing structurally enforces the order or tracks partial completion if an author quits mid-onboarding after voice but before style; re-running /ps-onboard has no principled way to know to skip voice and resume at style without extra hand-written state-checking logic in the orchestrator skill itself.

**Risks:**
- Orchestrator and sub-commands can drift out of sync if one is updated without the other
- No structural resume-after-partial-completion story unless hand-built

**Diversity role:** hardcoded orchestrator, independently invocable subs

### V2. Single monolithic /ps-onboard skill, no separate sub-commands

Only one command exists: /ps-onboard. The same skill prompt handles both first-time setup (walks through voice then style) and later re-invocation (detects existing profile fields and asks "update voice, style, or both?"). No /ps-voice or /ps-style entry points at all.

**Strengths:**
- Smallest possible command surface -- one file, one thing to document
- No orchestrator/sub-command drift risk since there's only one skill to maintain

**Novelty:** Collapses the whole feature into one skill's internal conversational branching rather than the command surface itself expressing the two independent capabilities.

**Weakest link:** Directly fails acceptance criterion 2 as independently-dedicated commands -- an author who wants to jump straight to "just tune my voice" must go through the same single entry point and navigate its internal branching every time, which is a worse experience than a direct /ps-voice command for a frequent re-tuning action.

**Risks:**
- Skill prompt complexity grows as it has to handle more branches (first-run vs voice-only vs style-only vs both)
- Author has to correctly answer an internal 'what do you want to update' question every time instead of just typing the specific command

**Diversity role:** single-command, internally-branching

### V3. Independent commands only, no orchestrator at all

/ps-voice and /ps-style exist as standalone skills. There is no /ps-onboard command. First-time onboarding guidance (run both, in this order) lives in documentation or a README/CLAUDE.md note, not in an invokable command.

**Strengths:**
- Fewest total commands (2, not 3) -- lowest command-surface maintenance
- Perfectly satisfies acceptance criterion 2 (independent re-invocation) since that's the only mode that exists

**Novelty:** Bets entirely on documentation/convention to cover the bundling need, testing whether an orchestrator command is actually necessary at all.

**Weakest link:** Fails acceptance criterion 1 outright -- there is no single command that completes first-time onboarding in one go; a new author must know to run two separate commands in the right order from documentation alone, exactly the kind of hidden convention the target-system's author-surface principle warns against.

**Risks:**
- New authors miss the second command or run them out of order with no guardrail
- No natural place to say 'you're fully onboarded now' as a single observable event

**Diversity role:** no orchestrator, doc-only bundling

### V4. Precondition-driven generic /ps-onboard, reusing the Pass mechanism

Voice and style are registered as Passes in the same registry the editorial engine already uses (dec-20260718-20a08f83, dec-20260718-ffbfb04b), each with its own Precondition (e.g. "has a voice profile" / "has a style profile"). /ps-onboard is generic: it runs every registered onboarding-type Pass whose Precondition says it's still needed, with no hardcoded knowledge of 'voice' or 'style' by name. /ps-voice and /ps-style remain separate, independently-invokable commands for direct re-tuning; they are the two Passes /ps-onboard happens to discover today.

**Strengths:**
- Directly satisfies acceptance criterion 3 -- reuses the already-decided Precondition mechanism instead of inventing a parallel completeness tracker
- A future third onboarding item (e.g. a target-platform preference questionnaire) is discovered automatically by /ps-onboard once registered as a Pass -- zero orchestrator changes needed
- Partial-completion resume (V1's named weakest_link) falls out for free: re-running /ps-onboard naturally skips any Pass whose Precondition is already satisfied

**Novelty:** Makes /ps-onboard a generic 'run what's outstanding' command over the same registry future editorial passes will use, rather than a bespoke two-step sequence that only knows about voice and style.

**Weakest link:** Depends on the Pass/Precondition mechanism actually existing and being re-implemented first (dec-20260718-20a08f83 and dec-20260718-ffbfb04b are currently AT RISK, R_eff 0.10, their code was wiped) -- this variant cannot be built today without that rebuild landing first.

**Risks:**
- Coupling onboarding to the editorial Pass registry means a bug or design change there affects onboarding too
- Slightly more upfront design cost to express voice/style as Passes correctly (e.g. deciding what 'precondition satisfied' means for a schema-only questionnaire, not an editorial transform)

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Once the Pass/Precondition seam is rebuilt for real editorial passes, onboarding rides the same mechanism for free -- future onboarding-like additions never need new orchestrator code.

**Diversity role:** generic precondition-driven orchestrator, reuses existing mechanism

### V5. Orchestrator-only, sub-skills hidden from the command surface

/ps-onboard exists as the only user-facing command; /ps-voice and /ps-style exist internally as skill prompts /ps-onboard delegates to, but are not registered as their own ps-* slash commands. Re-tuning later means re-running /ps-onboard, which detects the existing profile and asks whether to update it.

**Strengths:**
- Cleanest single documented entry point for first-time users
- Internal reuse of the voice/style prompt logic without exposing it as separate commands to maintain in the public command list

**Novelty:** Tests whether hiding the sub-skills from the command surface (vs. V1's fully exposed subs) is worth the smaller public command count -- explores the exposure axis independently of the orchestration-logic axis V1/V2/V4 vary on.

**Weakest link:** Fails acceptance criterion 2 as directly as V2 does -- an author wanting only style re-tuned still has to invoke the bundling command and navigate its internal question, with no direct /ps-style shortcut, defeating the operator's explicitly stated reason for wanting two commands in the first place.

**Risks:**
- Directly contradicts the operator's stated motivation for this problem
- Internal-only skills are harder to test/invoke directly during development

**Diversity role:** orchestrator-only, hidden subs

## Dominated Variant Elimination

- Single monolithic /ps-onboard skill, no separate sub-commands — dominated by Orchestrator + independent sub-commands (operator's proposal). V1 ties V2 on bundled_onboarding_support, mechanism_reuse, and buildable_now, but wins outright on independent_reinvocation (5 vs 2) -- V2's internal-branching re-tune is strictly worse than V1's direct standalone command, with no compensating advantage.
- Orchestrator-only, sub-skills hidden from the command surface — dominated by Orchestrator + independent sub-commands (operator's proposal). Identical score vector to V2 on every target dimension -- V1 wins independent_reinvocation (5 vs 2) and ties the rest. Hiding the sub-skills from the command surface buys nothing once file count is honestly counted (the internal prompts still exist as files, V5 doesn't actually save the observation-role cost either).

## Pareto Front Trade-Offs

- Orchestrator + independent sub-commands (operator's proposal) — Best-possible independent_reinvocation (5) and full bundled support (2), buildable today (1), at the cost of the front's worst mechanism_reuse (1) -- the orchestrator's sequencing and any resume-after-partial-completion logic is entirely hand-built, duplicating what the Precondition mechanism could express.
- Independent commands only, no orchestrator at all — Ties V4 on independent_reinvocation and mechanism_reuse (nothing to reuse or duplicate since there is no orchestration at all), buildable today, but the only front member that fails bundled_onboarding_support outright (0) -- no single command completes first-time onboarding.
- Precondition-driven generic /ps-onboard, reusing the Pass mechanism — Only front member combining full bundled support (2), best independent_reinvocation (5), AND best mechanism_reuse (5) -- but it is the front's only variant that cannot be built today (buildable_now 0): it requires the AT-RISK Pass/Precondition rebuild (dec-20260718-20a08f83, dec-20260718-ffbfb04b) to land first.

**Selection policy:** Pareto front over target-role dimensions (bundled_onboarding_support, independent_reinvocation, mechanism_reuse, buildable_now); command_file_count is observation-role, watched per the ProblemCard's own indicator, never optimized (Anti-Goodhart). Declared before scoring.

**Recommendation rationale:** V4 is the strongest design on every dimension that matters except sequencing -- it is the only front member satisfying all three named acceptance criteria at once. But it cannot be built today: the Pass/Precondition mechanism it depends on is currently AT RISK with R_eff 0.10, its own affected files wiped, and rebuilding it is separately queued work not yet started. V1 (the operator's original proposal) is the pragmatic front member: buildable immediately, satisfies acceptance criteria 1 and 2 cleanly, and explicitly carries a named stepping-stone path -- its weakest_link (hand-built sequencing, no resume tracking) is exactly what V4 would fix once the Pass mechanism exists. Recommend V1 now, with V4 as the natural follow-up once dec-20260718-20a08f83/ffbfb04b are rebuilt, rather than blocking onboarding on that rebuild landing first.
