# Solutions for: Exclude platform publish checklist from current scope -- how, and what cascades

Problem: prob-20260718-1c88e620

## Variants (4)

### V1. Full removal from target-system scope now -- amend both TS sections

Amend TS.environment-change.001 and TS.target.boundary.001 to drop the publish-checklist promise entirely. 'I'm ready to post' no longer triggers checklist generation. Pysar's promise narrows to a ship-ready body only; platform-specific packaging becomes explicit future/out-of-scope work, not a deferred-but-still-promised item.

**Strengths:**
- No confusing partial-promise state
- Fully removes the maintenance burden the operator named

**Novelty:** The cleanest, most unambiguous option -- no partially-promised, partially-real state. The scope boundary is exactly what the specs say, nothing more.

**Weakest link:** Walks back language from the very first product pitch ('Outcome: body you trust + publish checklist for your target platform') and already-approved spec text -- any author-facing promise material elsewhere would also need updating to stay honest, not just internal specs.

**Risks:**
- Real edit to two already-approved TS sections
- Reintroducing the capability later requires a fresh TS amendment cycle, not just enabling-system work

**Diversity role:** full removal, cleanest boundary, highest spec-amendment cost

### V2. Defer with an explicit annotation -- TS sections stay, marked not-yet-scheduled

Leave TS.environment-change.001 and TS.target.boundary.001's core text as-is, but add an explicit annotation/invariant marking publish-checklist as deferred with no near-term build commitment, distinguishing 'promised eventually' from 'in active scope now'.

**Strengths:**
- Minimal disruption to already-approved spec text
- Cheapest to reverse if the operator wants it back soon

**Novelty:** Smallest possible edit to already-approved artifacts -- an annotation, not a rewrite.

**Weakest link:** The target-system spec still promises it conceptually -- a future reader (or the author-facing promise, if drawn from these specs) could still reasonably read this as current scope. Removes build burden, not the promise itself, which is the actual thing named as unnecessary responsibility.

**Risks:**
- Doesn't actually remove the promise, only the build timeline -- may not satisfy the operator's stated goal of shedding responsibility, only deferring labor

**Diversity role:** minimal edit, promise stays, only labor deferred

### V3. Minimal stub: a generic platform-agnostic ready-to-ship note instead of a real checklist

Narrow the responsibility (platform-specific publishing knowledge) while still closing the 'I'm ready to post' loop with something -- a generic, non-platform-specific note rather than committing to per-platform requirements (prior writing POC's rules, Confluence's, print's, etc.).

**Strengths:**
- Something still happens when the author signals readiness, rather than a dead end

**Novelty:** The only variant that keeps some closing gesture at the author's 'ready to post' signal without committing to per-platform expertise.

**Weakest link:** A compromise that risks satisfying no one -- still requires designing and maintaining a generic version, arguably not meaningfully less responsibility than a simple real checklist, while diluting the original promise's actual specificity.

**Risks:**
- Still real design and maintenance cost for the generic version
- Neither fully honest removal nor a real checklist -- a fuzzy middle state

**Diversity role:** generic middle-ground stub, satisfies neither removal nor commitment cleanly

### V4. Staged: excluded from current core, explicit separate future extension point (reuses the memory-engine's own validated staging pattern)

Publish-checklist is excluded from the core editorial engine's current responsibility entirely -- TS.target.boundary.001 is amended to explicitly name it as a separate, deferred capability with a real trigger for revisiting, the same staged shape already validated in dec-20260718-404573a2 (free/default memory engine now, explicit premium SaaS tier later with a named backfill design point). 'I'm ready to post' under current scope simply marks the piece ship-ready; the checklist capability is a clearly separate future addition, not a vague promise sitting inside the current core spec.

**Strengths:**
- Fully removes current responsibility, matching the operator's literal 'unnecessary responsibility ATM' framing
- Cheapest future reintroduction cost of the four -- the extension point is designed for exactly this
- Reuses an already-validated internal pattern rather than inventing a new one

**Novelty:** Doesn't invent a new deferral shape -- reuses a pattern already decided and evidence-gathered once this session (dec-20260718-404573a2's staged free/premium rollout), applying proven internal precedent rather than a fresh design.

**Weakest link:** Requires the TS boundary section to explicitly carve out this future extension point now -- a small design cost paid today. If that extension point's boundary is drawn wrong, it still needs revisiting later, similar residual risk to V2's deferral but with more upfront structure.

**Risks:**
- Moderate spec-amendment cost now to draw the extension-point boundary correctly

**Diversity role:** staged removal + explicit extension point, reuses validated internal precedent

## Pareto Front Trade-Offs

- Full removal from target-system scope now -- amend both TS sections — Best promise_honesty and ties best responsibility_reduction -- the cleanest possible boundary. Costs the highest spec_amendment_cost and worst future_reintroduction_cost of the survivors -- bringing it back later means a fresh TS amendment cycle from a clean removal, not from a pre-drawn extension point.
- Defer with an explicit annotation -- TS sections stay, marked not-yet-scheduled — Cheapest possible edit to already-approved specs, cheapest to reverse. Costs the worst promise_honesty and responsibility_reduction of the three -- the spec still conceptually promises the capability, which does not match the operator's stated goal of shedding responsibility, only deferring labor.
- Staged: excluded from current core, explicit separate future extension point (reuses the memory-engine's own validated staging pattern) — Ties V1 on responsibility_reduction, best future_reintroduction_cost of all four. Costs a real, if moderate, spec-amendment effort now to draw the extension-point boundary -- and its promise_honesty, while good, is not as unambiguous as V1's full removal.

**Selection policy:** Pareto front, not a scalar winner. V3 is cleanly dominated by V4. V1, V2, and V4 remain genuine trade-offs -- honesty and clean-break simplicity (V1) versus cheapest edit now (V2) versus fully removed current responsibility with the cheapest path back later (V4).

**Recommendation rationale:** V2 does not actually satisfy what the operator asked for -- it keeps the promise in the spec and only defers the labor, whereas the operator explicitly named the responsibility itself, not just the build timeline, as unnecessary right now. Between V1 and V4: V1 is marginally more honest (a completely clean spec with no forward-looking carve-out at all) but costs more to reverse if the operator wants this capability back in a few months, requiring a fresh TS amendment cycle from scratch. V4 achieves the same immediate responsibility reduction (tied at the top of that dimension) while being cheapest to reintroduce later, by reusing a staging pattern already validated once this session for a structurally similar situation (the memory engine's free-now/premium-later split). My lean is V4: it matches V1 on what the operator actually asked to shed right now, and is honest about being a staged exclusion rather than a permanent one -- appropriate given the operator's own framing ('unnecessary responsibility to the tool ATM' names a current-state judgment, not a permanent one).
