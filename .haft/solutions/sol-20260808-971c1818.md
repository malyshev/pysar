# Solutions for: Codex (ChatGPT) authors cannot run Pysar's agentic editorial pipeline

Problem: prob-20260808-7ba11dda

## Variants (5)

### V1. Haft-CL1 Codex adapter on existing hostAdapter

Add codexHost to hostRegistry. Scaffold writes project .codex/config.toml that launches pysar serve (TOML mcp_servers shape from haft CL1), installs the shared skill corpus to ~/.agents/skills via syncManagedTree, and reuses writeBuiltinTemplates. No second skill corpus. Claude/Cursor adapters untouched. Docs update init/troubleshooting from stub to supported.

**Strengths:**
- Matches dec-20260808-f3001106 extend-adapter consequence
- CL1 precedent in haft init for paths and TOML
- Maximum reuse of shared skill corpus and syncManagedFile

**Novelty:** Reuses the already-bound Cursor V3 shape with a verified Codex dialect (TOML + ~/.agents/skills) instead of inventing Pysar-specific Codex paths.

**Weakest link:** Codex skill discovery and invocation UX (slash vs $name, openai.yaml policies, prompts vs skills) may still require extras beyond copying Cursor's JSON MCP pattern — CL1 from haft shows openai.yaml and prompt migration as real Codex surface area.

**Risks:**
- Haft's openai.yaml / $h- rewrite may not map 1:1 to ps-* without a small Codex-specific packaging step
- Live Codex smoke may reveal permission or MCP field differences not visible from haft alone

### V2. MCP TOML only; skills documented not installed

pysar init --codex only writes .codex/config.toml for pysar serve and points authors at docs for manually placing skills. No ~/.agents/skills sync, no openai.yaml. Minimal code change.

**Strengths:**
- Smallest blast radius
- Forces dialect learning on one surface (MCP) before skill packaging

**Novelty:** Deliberately thinner product: host wiring for MCP persistence without owning Codex skill install.

**Weakest link:** Fails acceptance (2) for non-technical authors — without installed skills there is no agentic entry equivalent to /ps unless they hand-copy files.

**Risks:**
- Looks like 'support' in CLI while authors still cannot run the pipeline
- Docs-driven install drifts from shipped corpus hashes

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Unblocks MCP-mediated piece I/O on Codex first; skill install can land in a follow-up without redoing TOML dialect.

### V3. Project-local Codex skills (.agents/skills in repo)

Same MCP TOML as V1, but install skills under the project's .agents/skills (or .codex local equivalent) instead of ~/.agents/skills, so each repo carries its own skill tree and syncManagedTree manifest is project-scoped.

**Strengths:**
- Skills version with the repo
- No cross-project global skill overwrite fights

**Novelty:** Changes locality of skill install (per-project vs operator-global) rather than only the MCP config dialect.

**Weakest link:** Diverges from Claude/Cursor global skill install already shipped for Pysar and from haft's default Codex global ~/.agents/skills — two locality models in one product.

**Risks:**
- Breaks 'one corpus refresh across all projects' story used by Claude/Cursor
- Codex may still prefer global ~/.agents/skills — needs verification

### V4. Full Codex dialect including openai.yaml / invocation policy

V1 plus Codex-specific packaging haft already ships: write agents/openai.yaml (or per-skill agents/openai.yaml) so only the orchestrator skill allows implicit invocation; apply any $ps- naming rewrite Codex needs; optionally manage ~/.codex/prompts migration if still required by the Codex version under test.

**Strengths:**
- Closest to haft's proven --codex experience
- Best chance of acceptance (2) without surprise implicit-skill spam

**Novelty:** Treats Codex invocation policy as first-class product surface, not an afterthought to MCP+skills copy.

**Weakest link:** Highest coupling to Codex CLI version churn — openai.yaml and prompt vs skill behavior have already moved in haft's own changelog.

**Risks:**
- Overbuilds if current Codex discovers SKILL.md without policy files
- More assets to keep in sync when Codex changes

### V5. Fork Codex-only skill bodies from shared corpus

Copy or rewrite ps-* SKILL.md into Codex-specific prose/naming under assets/codex/skills, installed only for --codex. Shared corpus remains for Claude/Cursor.

**Strengths:**
- Can tailor Codex UX copy without host-agnostic constraints

**Novelty:** Splits editorial instruction ownership by host instead of packaging-only differences.

**Weakest link:** Violates the host-neutral skill corpus invariant from dec-20260808-f3001106 — dual maintenance of editorial rules across hosts.

**Risks:**
- Editorial drift between hosts
- Constraint violation — likely inadmissible without superseding f3001106
