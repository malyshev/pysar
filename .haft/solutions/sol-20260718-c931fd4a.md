# Solutions for: Structural backstop for Pysar's editorial-engine orchestration: making pass-routing verifiable, not just prose-followed

Problem: prob-20260718-7a847974

## Variants (4)

### V1. Structured per-piece run-log -- append-only record of every pass that touched a piece

Every pass that runs against a piece (idea scaffolding, draft edit, voice-lock, research opt-in, ship-ready packaging) appends an immutable, timestamped, structured entry to a per-piece log -- pass name, trigger, relevant config snapshot (e.g. active voice), and artifact references -- stored in the Artifact/state layer alongside the draft/checklist artifacts already specified.

**Strengths:**
- Directly answers 'what actually happened to this piece', queryable after the fact, no chat-transcript archaeology needed
- Minimal change to the routing/skills layer itself -- additive, not invasive
- Naturally composable with the memory engine's own artifact-layer storage

**Novelty:** The only variant that gives a complete, ordered history per piece with zero change to how routing itself works -- pure observability layered on top of the architecture already decided, the cheapest real backstop that isn't just trusting the AI's self-report.

**Weakest link:** Purely observational -- it records what happened but does not prevent anything. If a pass is silently skipped or misordered, the log simply stays silent or incomplete for that piece; someone or something still has to actively query and interpret the log to notice a problem. Detects drift after the fact, does not stop it.

**Risks:**
- Does not prevent a known-bad sequence (e.g. voice-lock before packaging) from happening, only makes it detectable if someone looks
- Log completeness itself depends on every pass remembering to write an entry -- a missed log write is itself an undetected failure unless something else checks for gaps

**Diversity role:** pure observability, cheapest real backstop, detection not prevention

### V2. Invariant-checked routing layer -- the skills/routing layer mechanically asserts known rules

Build real code-level checks into the routing/skills layer (the functional core) that assert specific known invariants at the moment a pass would run -- e.g. voice-lock refuses to execute unless a 'packaged' state already exists for the piece -- raising an error rather than silently proceeding.

**Strengths:**
- Prevention, not just detection, for the specific rules encoded
- Directly enforces existing recorded constraints (e.g. TS.target.boundary.001's 'voice-lock after packaging, never before') as executable code, not just as a sentence in a spec file

**Novelty:** The only variant that actually prevents a known-bad sequence rather than merely recording that it happened -- the closest literal match to what the operator means by 'structural backstop': the routing layer itself refuses to misbehave in the specific ways anyone thought to guard against.

**Weakest link:** Only guards invariants someone thought to enumerate and hand-code in advance. A routing mistake that was not anticipated as a named invariant goes completely unchecked -- this variant's guarantee is exactly as strong as the list of rules someone remembered to write, no stronger.

**Risks:**
- Coverage is only as good as the enumerated invariant list -- unanticipated misrouting is invisible to this mechanism entirely
- Requires the routing/skills layer to be real, testable code rather than prose the LLM interprets -- a genuine engineering commitment, not a config change

**Diversity role:** prevention of known cases, requires enumerated invariants

### V3. Formal piece state machine -- illegal states are unrepresentable

Model a piece's lifecycle as an explicit, typed state machine (idea -> stake -> drafted -> edited -> voice-locked -> ship-ready -> published) stored as structured state in the Artifact layer. Illegal transitions -- e.g. reaching 'ship-ready' with no 'drafted' state ever recorded -- are structurally impossible to represent, not just checked and rejected at runtime.

**Strengths:**
- Strongest guarantee of the four -- illegal combinations are structurally impossible, not merely detected or individually guarded
- The state itself IS the queryable record -- no separate logging mechanism needed

**Novelty:** The only variant offering the strongest possible guarantee -- not 'checked and rejected', but 'cannot be represented at all' -- by modeling the whole lifecycle as a closed, typed system rather than an open-ended log (V1) or a patchwork of ad-hoc checks (V2).

**Weakest link:** Requires fully enumerating a piece's legal lifecycle up front, which risks being too rigid for genuinely non-linear real authoring -- an author revising the stake after voice-lock because they changed their mind is a normal creative act that a closed state machine may need special-cased escape hatches for, or else it fights the author instead of backstopping the tool.

**Risks:**
- Highest design cost -- the full legal-transition space must be right from the start, and getting it wrong either blocks legitimate non-linear authoring or requires frequent schema changes
- Real risk of over-constraining creative work, which conflicts with the product's own promise that Pysar defers to the author's take rather than imposing process

**Diversity role:** strongest guarantee, highest rigidity and design cost

### V4. LLM self-attestation with periodic sampling audit

Keep the routing/skills layer prose-driven, as currently specified, but add a cheap validation loop: the LLM self-reports which passes it applied to a piece (a simple structured summary at the end of a session), and a periodic sample of pieces is spot-checked -- automatically or by the operator -- against what the skill files should have produced.

**Strengths:**
- Trivial to build -- no new architectural layer, just a structured end-of-session summary plus occasional spot-checks
- Lets the operator learn what kinds of drift actually happen in practice before committing to a heavier mechanism

**Novelty:** The only variant that ships with essentially zero new engineering, staying maximally close to what's already decided -- tests whether real routing drift is actually a problem in practice before investing in V1/V2/V3, the same stepping-stone logic already used successfully for the memory engine's own delivery decision.

**Weakest link:** Weakest guarantee of the four -- still fundamentally trusts the LLM's own self-report as the primary signal, and periodic sampling only catches problems that happen to land in the sampled pieces. Systematic, individually-invisible drift (e.g. voice-lock quietly running early on every single piece) could persist a long time before a spot-check happens to notice it.

**Risks:**
- Provides essentially no guarantee between audits -- this is much closer to prior writing POC's current shape than a real backstop
- Self-attestation from the same LLM that might be the one making the routing mistake is a weak signal -- it can misreport in good faith exactly when it's already gone wrong

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Tests whether routing drift is a real, observed problem in practice -- and what kind -- before committing to V1's logging infrastructure, V2's enumerated invariants, or V3's full state machine, all of which are real engineering investments this stepping stone can help target correctly rather than guessing upfront.

**Diversity role:** near-zero engineering, weakest guarantee, tests whether the problem is real in practice

## Pareto Front Trade-Offs

- Structured per-piece run-log -- append-only record of every pass that touched a piece — Ties for best creative_flexibility and queryability -- a complete, ordered history per piece with zero change to how routing works. Costs real drift_prevention_strength -- it only detects problems if someone queries the log, never prevents them.
- Invariant-checked routing layer -- the skills/routing layer mechanically asserts known rules — Middle-of-the-road on every dimension -- genuinely prevents the specific bad sequences someone thought to enumerate. Costs the worst queryability of the non-observational variants -- a passing check doesn't automatically leave a readable trail unless logging is added on top.
- Formal piece state machine -- illegal states are unrepresentable — Best drift_prevention_strength, ties for best queryability -- illegal states are structurally unrepresentable, not just checked. Costs the worst creative_flexibility and the highest build_cost -- real risk of fighting genuinely non-linear authoring.
- LLM self-attestation with periodic sampling audit — Cheapest to ship, ties for best creative_flexibility. Costs the worst drift_prevention_strength and queryability of all four -- closest to prior writing POC's current shape, provides almost no guarantee between audits.

**Selection policy:** Pareto front, not a scalar winner -- all four variants are genuinely non-dominated, each trading prevention strength against build cost, creative flexibility, and queryability differently. No dimension is a hard constraint; this is a real design-philosophy choice (observe vs. partially prevent vs. fully prevent vs. defer) rather than a technical pass/fail.

**Recommendation rationale:** V4 is the honest zero-risk starting point in isolation, but its cost is close to zero specifically because it provides almost no guarantee -- it's the least different from the exact gap just identified in a prior writing POC, so leaning on it alone would under-deliver on what was actually asked for ('a structural backstop'). V1 is the strongest standalone recommendation: it directly answers the acceptance criterion ('an observable, queryable record... checkable after the fact without re-reading a chat transcript') at moderate cost, is fully composable with the memory engine's own artifact-layer storage, and does not risk fighting non-linear authoring the way V3 could. It does not by itself prevent the one named bad sequence (voice-lock before packaging) -- for that specific, already-named invariant, V2's targeted enforcement is a natural, low-risk complement layered on top of V1's log, without committing to V3's full rigidity. V3 is the strongest guarantee available but is a bigger, riskier bet before it's known whether real authoring behavior tolerates a closed state machine -- better justified after V1+V2 reveal what actually goes wrong in practice, mirroring the same stepping-stone logic already used for the memory engine.
