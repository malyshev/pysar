# Solutions for: Persistence delivery for ps-* skill outputs: avoid raw file-write permission prompts for non-technical authors

Problem: prob-20260719-5bcc0be4

## Variants (5)

### V1. Ship a committed .claude/settings.json pre-approving Write(.pysar/**)

pysar init scaffolds a committed .claude/settings.json alongside CLAUDE.md, with permissions.allow containing Write(.pysar/**) (and Read(.pysar/**)). This is the exact mechanism haft itself relies on for its own prompt-free MCP tool calls -- confirmed via this repo's own settings.local.json, which allowlists mcp__haft__haft_note etc. by name -- applied here to a Write path pattern instead of an MCP tool name. No new process, no new binary.

**Strengths:**
- Zero new components -- pure scaffold-content addition, same writeIfAbsent pattern already used for CLAUDE.md
- Uses a mechanism already verified in Claude Code's own docs and already proven working in this very repo, not a novel untested approach
- Narrow, auditable scope -- Write(.pysar/**) is visible in one committed file, easy for a technical reviewer to check

**Novelty:** Solves the stated problem (permission friction) using the exact mechanism already validated in this project's own settings, rather than reaching for a heavier tool because haft happens to use MCP.

**Weakest link:** Does not fix the deeper issue the operator also raised: the skill's own completeness check (Step 5 of ps-voice) is just an LLM re-reading prose rules, not a real programmatic Validate() call -- this variant solves the permission-prompt friction but leaves that gap untouched.

**Risks:**
- Pre-approving a Write pattern is still a real trust grant, even if narrowly scoped -- worth being deliberate about, not automatic
- Doesn't cover any other tool (e.g. a future Bash call) if a later skill needs one

**Diversity role:** config-only fix, no new component

### V2. Pysar MCP server (pysar serve) with real schema-aware persistence tools

Add a pysar serve subcommand (same binary, per the single-static-binary constraint) exposing MCP tools like save_voice_profile and load_voice_profile. Skills call these instead of raw Write/Read. The server-side implementation calls the real internal/onboarding.Validate() -- so completeness checking becomes an actual Go function call, not an LLM's best-effort prose self-check. This is real, additional value beyond permission UX: it closes the gap V1 leaves open.

**Strengths:**
- Closes both problems at once: no permission prompt (once the MCP tools are allowlisted, same mechanism as haft's own) AND real programmatic validation instead of LLM self-checking
- The author never needs to know a file is even involved -- the mechanism is fully invisible, not just prompt-suppressed
- Precedent exists in a comparable system (dec-20260601-...prevent-billing-tool-architecture, CL1, different context) that chose exactly this shape: MCP server + structured configs + Claude Code

**Novelty:** Treats persistence and validation as a service the skill calls, not a file the skill touches directly -- the same shape this project's own governance layer (haft) already uses for itself.

**Weakest link:** Real, ongoing engineering investment: a new subcommand, an MCP tool surface to design and maintain, and the server itself still needs its own permission allowlist entry to avoid prompting -- it does not eliminate the permission question, it just moves it from a Write pattern to an MCP tool name, at much higher build cost.

**Risks:**
- Significant scope growth for what started as a single skill's save step
- A local MCP server is a new failure mode (must be running/reachable) that a plain file write never has

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** If Pysar's editorial passes eventually need more real Go-side logic invoked from skills (not just onboarding), this is the same server surface they'd use too -- built once, reused beyond voice/style.

**Diversity role:** full server component, real added value beyond UX

### V3. Conversational expectation-setting only, no config or code change

Keep the skill exactly as it is (direct Write call), but add a short line before writing: tell the author in plain language that saving requires a one-time permission confirmation, so the prompt doesn't arrive as a surprise. Purely a change to skill prose.

**Strengths:**
- Zero cost, zero new risk surface -- a one-sentence addition to existing skill content
- Directly addresses the operator's second concern (the author not understanding *why* a prompt appeared) even if the prompt itself still happens

**Novelty:** Tests the cheapest possible intervention -- addresses the comprehension gap without touching the mechanism at all, a genuine floor to compare the others against.

**Weakest link:** Does not reduce the actual friction at all -- the non-technical author still has to read and act on a permission dialog naming a file path and a tool name; this only makes the surprise smaller, not the interruption shorter.

**Risks:**
- Doesn't scale -- every future ps-* skill needs its own reminder line, and the underlying prompt-per-write friction compounds as more skills exist

**Diversity role:** prose-only mitigation, zero mechanism change

### V4. V1 + V3 combined: allowlist plus expectation-setting as a fallback

Ship the same .claude/settings.json allowlist as V1, and keep a short expectation-setting line in the skill for the edge cases the allowlist might not cover cleanly (e.g. the very first .pysar/ directory creation, or a host environment where the committed settings.json for some reason isn't picked up).

**Strengths:**
- Belt-and-suspenders at near-zero extra cost over V1 alone -- the prose addition is one sentence
- Degrades gracefully: if the allowlist fails silently for any reason, the author still isn't confused by an unexplained prompt

**Novelty:** Explicitly tests whether combining the two cheapest variants beats either alone, rather than assuming a single mechanism is sufficient.

**Weakest link:** Marginal benefit over V1 alone is small and unverified -- there is no confirmed case where the allowlist doesn't work that the prose line would actually catch; this is defensive, not proven necessary.

**Risks:**
- Slight risk of the prose line reading as an apology for a problem that (if V1 works as verified) doesn't actually occur, which could itself read oddly to the author

**Diversity role:** combined low-cost variants

### V5. Minimal MCP proxy server -- no domain logic, just a permission-bypass wrapper

A stripped-down pysar serve exposing only generic write_pysar_file / read_pysar_file MCP tools, with no schema-aware validation logic server-side -- purely a way to route file I/O through an allowlisted MCP tool name instead of the Write tool.

**Strengths:**
- Achieves the same permission-prompt suppression as V2 without designing a rich domain-specific tool surface

**Novelty:** Included to test whether 'just enough MCP to dodge the prompt' is a real middle ground or a false economy -- it's the latter.

**Weakest link:** Captures none of V2's real added value (server-side Validate()) while still paying nearly all of V2's cost (a new subcommand, a new process, its own allowlist entry) -- it is essentially V1's outcome achieved via V2's mechanism, for no compensating benefit over V1's much cheaper config-only path.

**Risks:**
- Builds real infrastructure (a server, a process lifecycle) purely to relocate a permission prompt, the weakest possible justification for that cost

**Diversity role:** minimal-server floor, deliberately weak contrast

**Recommendation rationale:** Recommend V4 now, with V2 named explicitly as a future upgrade path rather than dismissed.
