# Solutions for: Reusable questionnaire engine for onboarding (voice + writing-style capture), not hardcoded scripts

Problem: prob-20260718-277e8377

## Variants (5)

### V1. Declarative data-driven engine, console-prompt runner

Each questionnaire (voice, style, future ones) is declared as data -- a Go struct literal or embedded YAML describing questions, field types, and validation -- interpreted by one generic runner that prints prompts to the terminal and reads stdin. Adding a questionnaire means adding a new data file/struct, never touching the runner.

**Strengths:**
- Classic, well-understood pattern (config over code)
- Runner is fully unit-testable without any LLM or terminal in the loop -- feed it canned answers
- Directly satisfies acceptance criterion 1: new questionnaire = new data, zero runner changes

**Novelty:** Puts the completeness/extensibility guarantee entirely in the data model rather than in code structure -- a new questionnaire is reviewable as data, not as a diff to control flow.

**Weakest link:** Delivered entirely inside the console binary as a linear Q&A prompt sequence -- reads exactly like the 'rigid form' the author-surface constraint warns against, and conversational follow-ups ('what do you mean by punchy?') have no natural home in a fixed question list.

**Risks:**
- Author-surface tone risk: prompts read as a wizard, not a conversation
- Validation logic for open-ended answers (voice, style) is inherently fuzzier than the typical form-engine use case (structured fields like address/phone)

**Diversity role:** classic declarative form engine, console-native

### V2. Go builder/DSL, compiled questionnaire values

A small fluent Go API (questionnaire.New("voice").Ask(...).Ask(...)) builds a typed in-memory question graph at compile time; one engine walks whatever graph a questionnaire builder produces. Still console-terminal I/O, but questionnaire authors write Go, not external data files, keeping everything in the single static binary with compile-time type safety.

**Strengths:**
- No new file format or embedded-data parsing -- consistent with the plain-Go-toolchain preference
- Compile-time checked: a malformed questionnaire fails to build, not fails at runtime
- Still satisfies acceptance criterion 1 in spirit -- new questionnaire is a new builder call chain, not a change to the walking engine

**Novelty:** Trades the flexibility of external data files for compiler-enforced correctness of the question graph -- a different point on the code/data spectrum than V1, not just a implementation detail of it.

**Weakest link:** The line between 'declarative content' and 'new engine code' blurs: a Go builder chain IS code, so a careless questionnaire author can smuggle imperative logic into what should be pure content, defeating the separation this problem is trying to establish.

**Risks:**
- Requires a Go recompile + reinstall to add or edit a questionnaire -- no runtime content changes
- Same author-surface rigidity risk as V1 -- still a console-terminal Q&A loop

**Diversity role:** typed in-binary DSL, compiled content

### V3. Schema-only engine, LLM-conversational elicitation on the agentic surface

The Go engine defines ONLY the target data schema per questionnaire (e.g. a VoiceProfile struct: tone, formality, sentence-length preference, banned phrases) plus validation rules for completeness -- it never conducts the Q&A itself. The actual conversation happens on the ps-*/  /ps agentic surface: the host AI agent asks natural questions, the author answers conversationally, and a final structured-extraction step fills the schema and validates it before persisting to .pysar/project.

**Strengths:**
- Directly matches the author-surface constraint -- genuinely conversational, not a form, because a real conversational agent is doing the asking
- The console pysar binary stays small and dumb (schema + validator only), consistent with plain-Go/no-wrapper-tool preference
- New questionnaire = new schema struct + a skill prompt describing what to elicit -- no runner code touched at all

**Novelty:** Moves 'asking the questions' out of the engine's responsibility entirely and treats it as the host agent's job -- the Go engine's only contract is a schema plus a completeness check, not a question-flow interpreter.

**Weakest link:** The console pysar binary alone cannot run onboarding at all -- without a host AI agent session, there is no way to conduct the questionnaire, only to validate an already-filled schema. A user running bare `pysar` with no agent has no onboarding path.

**Risks:**
- Onboarding quality depends on the skill prompt's own conversational quality, not testable the way a deterministic runner is
- Two onboarding paths (agentic vs bare console) diverge in capability unless V3 is paired with a fallback

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** The schema-and-validator contract is reusable regardless of how the conversation is eventually conducted -- a future console-prompt fallback (V1-style) could be added later without changing the schema layer.

**Diversity role:** schema-first, conversation delegated to agentic surface

### V4. Hybrid: shared schema, two elicitation engines (console runner + agentic conversation)

Same schema-and-validation-completeness core as V3, but paired with BOTH a deterministic console-prompt runner (V1-style, for bare `pysar` with no host agent) and agentic conversational elicitation (for ps-*/  /ps sessions). Both paths fill and validate the same schema; the completeness check (a natural fit for the already-decided Pass/Precondition mechanism, dec-20260718-20a08f83) gates whether onboarding counts as done, regardless of which path was used.

**Strengths:**
- No onboarding capability gap between bare-console and agentic use -- both paths work
- Reuses the already-decided precondition-guard pattern for 'is this questionnaire complete' instead of inventing a second completeness mechanism
- New questionnaire = new schema + validation rule, same acceptance-criterion-1 guarantee as V1/V3

**Novelty:** Explicitly separates 'what must be true when done' (the schema, checked via the existing Precondition mechanism) from 'how it gets asked' (two composable strategies), rather than picking one delivery mode as canonical.

**Weakest link:** Real cost of building and maintaining two elicitation paths (console runner AND conversational skill prompt) that must both target the same schema and stay in sync -- more moving parts than either V1 or V3 alone.

**Risks:**
- Schema drift between the two elicitation implementations if not carefully shared
- Higher upfront build cost than either V1 or V3 alone -- may be premature before it's known whether bare-console onboarding is actually a real use case

**Diversity role:** dual-delivery, shared schema and completeness gate

### V5. Import an existing Go survey/form library

Adopt a third-party Go terminal-prompt/survey library (e.g. an interactive-CLI-prompt package) to drive questionnaires, writing thin per-questionnaire glue code against its API rather than building a bespoke engine.

**Strengths:**
- Fastest to a working first questionnaire -- no engine design or build cost
- Terminal UX (arrow-key selects, validation, etc.) is already polished by the library

**Novelty:** Zero-build-cost baseline included deliberately as a contrast point -- shows what 'just ship it' costs against the other variants' engineering investment.

**Weakest link:** Adds an external dependency for a domain-specific need (capturing voice/style, not generic form input) that the existing minimal-tooling preference (dec-20260718-817bfb74) was adopted specifically to avoid taking on without a real forcing gap -- and it still only solves the console-terminal delivery mode, not the author-surface conversational constraint.

**Risks:**
- New dependency to vet and maintain against a project whose own stated preference is minimal new tooling
- Library's own question model may not map cleanly onto structured VoiceProfile/StyleProfile output, forcing awkward post-processing

**Diversity role:** external-dependency baseline, deliberately weak by design

## Dominated Variant Elimination

- Go builder/DSL, compiled questionnaire values — dominated by Declarative data-driven engine, console-prompt runner, Hybrid: shared schema, two elicitation engines (console runner + agentic conversation). V1 beats V2 on extensibility (5 vs 3, pure data beats a code-blurred builder DSL) while tying conversational_fit and standalone capability. V4 beats V2 on extensibility (4 vs 3) and conversational_fit (5 vs 2) while tying standalone capability. V2 has no dimension where it beats either.
- Import an existing Go survey/form library — dominated by Declarative data-driven engine, console-prompt runner, Hybrid: shared schema, two elicitation engines (console runner + agentic conversation). V1 beats V5 on extensibility (5 vs 3) and conversational_fit (2 vs 1) while tying standalone capability. V4 beats V5 on extensibility (4 vs 3) and conversational_fit (5 vs 1) while tying standalone capability. Importing a library saves LOC (observation-only) but buys nothing on the target dimensions that V1 doesn't already deliver more of.

## Pareto Front Trade-Offs

- Declarative data-driven engine, console-prompt runner — Best-possible extensibility (5, pure declarative data) and full standalone console capability (5), traded against the weakest conversational fit on the front (2) -- a genuine terminal Q&A wizard, not a conversation.
- Schema-only engine, LLM-conversational elicitation on the agentic surface — Ties V1 on extensibility (5) and matches V4 on conversational_fit (5), at the cost of standalone console capability (1) -- bare `pysar` with no host agent has no onboarding path at all. Also cheapest on both observation dims (leanest LOC, though 2 files per new questionnaire vs V1's 1).
- Hybrid: shared schema, two elicitation engines (console runner + agentic conversation) — The only front member with strong conversational_fit (5) AND full standalone capability (5), at the cost of the front's lowest extensibility (4, still good) and by far the highest cost on both observation dims (most LOC, most files per new questionnaire -- two delivery paths to build and keep in sync).

**Selection policy:** Pareto front over target-role dimensions (extensibility, conversational_fit, standalone_console_capability); loc_estimate and new_files_per_questionnaire are observation-role, watched per the ProblemCard's own indicators, never optimized (Anti-Goodhart). Declared before scoring.

**Recommendation rationale:** A genuine three-way trade-off, not a clean winner. Given this project's own product identity -- an AI-agent-directed editorial engine where the primary experience is expected to run through a host agent session, not a bare terminal wizard -- and given the console binary's own stated role is deliberately thin (dec-20260718-817bfb74's minimal-tooling preference, dec-20260718-fe926229's already-minimal init), V3 is the recommended starting point: schema-only, conversation delegated to the agentic surface, cheapest to build, and its own stepping_stone_basis means V1's console-fallback runner can be added later without changing the schema layer if bare-console onboarding turns out to be a real gap. V4 is the more complete answer but risks over-building two delivery paths before it's known whether the console-only gap V3 leaves is one any real user actually hits.
