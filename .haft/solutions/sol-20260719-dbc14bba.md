# Solutions for: Voice profile templates: built-in generic default + author-saved reusable presets

Problem: prob-20260719-e0307745

## Variants (4)

### V1. Pysar-owned global directory, one file per template, MCP-mediated writes

A new host-agnostic home, ~/.pysar/templates/<kind>/<name>.md, holding each template as a plain file in the exact Markdown+YAML format Render() already produces for voice.md. Listing/reading a template is a direct Read (it's reference data, not authored project content, so no permission-avoidance rationale applies to it). Saving a new template (author's own profile -> named template) goes through a new save_voice_template MCP tool, mirroring save_voice_profile's already-proven rationale for cross-boundary writes. The built-in 'generic' default ships embedded in the binary and is seeded/kept current in this directory using the exact per-file content-hash mechanism just built for global skills (dec-20260719-25712417) -- zero new refresh logic, only a new target directory.

**Strengths:**
- Reuses the just-shipped hash-refresh mechanism verbatim for the built-in default -- no new staleness logic
- Individual template files are human-readable/editable/git-vendorable by an operator who wants to
- Works identically once Cursor/Codex hosts ship (dec-20260718-8278c494 already committed to those flags) since the directory has no dependency on any single host's config convention

**Novelty:** Treats the home directory itself as the novel piece: a dedicated, host-agnostic pysar directory (analogous to ~/.npm, ~/.cargo) distinct from ~/.claude/skills, rather than reusing a host-specific config path for host-agnostic data.

**Weakest link:** Requires operators to trust yet another dotfile-style directory under their home -- one more place pysar writes to, which needs its own documentation/discoverability the moment an author asks 'where did this template come from.'

**Risks:**
- A new top-level dotfile convention to introduce and document
- Direct-Read access to template files by a skill means the skill process must know the path convention, a small coupling not present if everything went through tools

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** A dedicated ~/.pysar/ home directory is a natural landing spot for other future host-agnostic global state already named as open problems in this project (the memory engine's delivery model, prob-20260718-0973a207; cross-piece continuity, prob-20260718-4e1bda1b) -- this variant resolves that shared foundation once instead of each future feature re-deciding where global pysar state lives.

### V2. Single registry file, fully tool-mediated

One file, ~/.pysar/templates.json (or .yaml), holding all templates for all kinds keyed by name -- no per-template files. list_voice_templates, save_voice_template, and apply_voice_template are all MCP tools; no component ever reads or writes the registry file directly except pysar serve itself.

**Strengths:**
- Enumeration (list_voice_templates) is a single read, not a directory walk
- Storage shape can change freely later since nothing outside pysar serve ever depends on its concrete format

**Novelty:** Collapses storage to a single source of truth and makes the MCP tool boundary absolute -- the registry's on-disk shape is a fully private implementation detail, never a contract any skill or operator reads directly.

**Weakest link:** A single shared file for every template of every kind is a concurrency and diff-ability regression versus one-file-per-template: any two saves in quick succession (or two pysar serve processes) risk a lost update, and an operator curious what's in a specific template can no longer just open one small file -- they get the whole registry.

**Risks:**
- Concurrent-write corruption risk grows with every future template kind added to the same file
- Fully hides templates from an operator who wants to inspect/hand-edit one without going through a conversation

### V3. Piggyback on ~/.claude/skills, built-in default only

Ship the one 'generic' built-in default as a plain file inside the existing ~/.claude/skills/ tree (e.g. alongside ps-voice), reusing dec-20260719-25712417's manifest/hash-refresh code with zero new plumbing. Author-saved reusable templates across projects are explicitly deferred again, exactly as prob-20260718-00bf7ca6 deferred them the first time -- this variant only ships the built-in half of the operator's chosen 'Both' scope.

**Strengths:**
- Cheapest possible implementation -- reuses tested code exactly as-is
- Zero new home directory or new MCP tools to design

**Novelty:** Minimum possible new code: reuses an existing, already-decided, already-tested mechanism verbatim instead of building a second one.

**Weakest link:** Directly under-delivers the scope the operator already chose ('Both') -- author-saved reusable templates stay unbuilt, deferred a second time. It also conflates host-specific config space (~/.claude/skills exists because Claude Code specifically reads it) with host-agnostic template data, which becomes a real, foreseeable migration the moment --cursor or --codex (already-stubbed flags) actually ship, since neither host reads ~/.claude/skills/ at all.

**Risks:**
- Guaranteed rework when a second host ships, since the storage location is architecturally host-specific
- Leaves the operator's explicitly chosen scope (author-saved reusable templates) unmet

### V4. Project-local-first, global is an explicit export action

Templates normally live inside each project's own .pysar/templates/<kind>/<name>.md -- git-trackable, project-scoped, no new global directory needed for the common case. The one built-in generic default is still embedded/global (it must be available with zero prior project). Making a project-local template available to OTHER projects is a separate, explicit 'promote to global' action that copies it into a cross-project store.

**Strengths:**
- No new global directory needed for the common single-project case
- Templates a project doesn't want shared never leave that project by default -- a real privacy/scope win for a multi-client freelance author

**Novelty:** Inverts the default scope: per-project is the default, cross-project reuse is the deliberate exception requiring its own action, rather than V1/V2's cross-project-by-default model.

**Weakest link:** The operator's stated goal was reuse across projects without extra ceremony -- this variant adds a second explicit step (promote) exactly where the operator wants zero-friction reuse, so it under-delivers the stated acceptance criterion of a template being 'usable in a later project' by default.

**Risks:**
- Adds friction exactly where the operator asked for reuse to be easy
- Two storage locations (project-local and global) to keep straight instead of one

## Dominated Variant Elimination

Fails the cross_project_availability constraint outright -- it ships only the built-in default and defers author-saved reusable templates a second time, directly under-delivering the 'Both' scope the operator already chose. Also worst on both targets: host_independence (1, tied to a Claude-Code-specific directory) and migration_cost_to_new_host (5, guaranteed rework the moment Cursor/Codex ship).
- Project-local-first, global is an explicit export action — dominated by Pysar-owned global directory, one file per template, MCP-mediated writes, Single registry file, fully tool-mediated. Fails the cross_project_availability constraint as strictly defined ('no extra manual step beyond the normal save action') -- V4 requires a separate explicit promote-to-global action, so a template saved in project A does not appear in project B without that extra step. Ties V1/V2 on both targets otherwise, so the constraint failure alone is decisive.

## Pareto Front Trade-Offs

- Pysar-owned global directory, one file per template, MCP-mediated writes — Ties V2 on both targets (host_independence 5, migration_cost_to_new_host 1) and both constraints, while needing only 1 new MCP tool (save_voice_template) against V2's 3 -- listing and applying stay direct Reads of individually inspectable, git-vendorable files. Trade-off is qualitative, not on a scored dimension: one more top-level dotfile-style directory for an operator to eventually learn about.
- Single registry file, fully tool-mediated — Ties V1 on both targets and both constraints, but centralizes everything behind MCP tools (3 new) and a single registry file -- storage shape is fully hidable and can change later without touching any consumer, at the cost of a real concurrency/diff-ability regression as more template kinds share the one file, and losing the ability for a curious operator to just open one small file.

**Selection policy:** Pareto front over target-role dimensions (host_independence, migration_cost_to_new_host), gated by both constraints (cross_project_availability, confirm_before_apply_preserved) which must hold true; new_mcp_surface is observation-role, watched but never optimized (Anti-Goodhart). Declared before scoring.

**Recommendation (advisory):** Pysar-owned global directory, one file per template, MCP-mediated writes

**Recommendation rationale:** V1 and V2 are formally tied on every target and constraint, so the tie-break is judgment, not the scored dimensions. V1 wins that judgment call for three reasons: (1) it reuses dec-20260719-25712417's per-file hash-refresh mechanism verbatim for the built-in default, a real, already-tested piece of code, where V2 would need new staleness logic for its single registry file; (2) it fits this project's own established preference for filesystem-native, human-readable artifacts over opaque blobs -- the same reasoning that already moved voice.md from JSON to Markdown+YAML this session; (3) V2's single shared file is a genuine (if not fatal) concurrency and diff-ability risk that only grows as more template kinds (style, per pending task #11) are added to the same file, where V1's one-file-per-template shape has no such coupling between kinds or entries.
