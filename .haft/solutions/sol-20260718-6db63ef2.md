# Solutions for: Delivery model for the semantic memory engine (V2): local-standalone vs. cloud-dependent vs. hosted SaaS feature

Problem: prob-20260718-0973a207

## Variants (4)

### V1. Bundled local embedding model (CGo/onnxruntime-style), fully offline

Ship a small local embedding model file alongside the Go binary, run inference on-device via a C/C++ inference runtime bound into Go (e.g. onnxruntime or similar). Zero network calls, zero account, zero API key -- everything works the moment the single installer finishes.

**Strengths:**
- Zero setup friction for a non-technical user -- install once, everything works
- No ongoing cost to the operator (Pysar) -- all compute happens on the user's own machine
- No network dependency at all -- works offline, no privacy concern about sending prose to a third party

**Novelty:** The only variant that is genuinely zero-config for the end user AND fully offline -- no account, no key, no internet required at all, which best matches a non-technical 'homewife writing kitchen stories' persona who should never need to think about infrastructure.

**Weakest link:** Requires a CGo dependency on a C/C++ inference runtime to actually run the model in Go -- this directly tensions with dec-20260718-239680d4's own reasoning for picking Go (simple, mature, native cross-compilation with zero per-OS build runners). A CGo dependency typically breaks or significantly complicates that clean cross-compile story, and adds real binary size (tens to hundreds of MB for the model file itself).

**Risks:**
- Meaningfully undermines the clean single-static-binary/native-cross-compile story that was the actual stated reason for choosing Go over TypeScript
- Larger download/install size than users of a 'simple CLI tool' might expect
- Model quality/size trade-off -- a small enough model to bundle reasonably may have materially worse embedding quality than a large hosted model

**Diversity role:** fully local, zero-config, breaks binary simplicity

### V2. User-supplied cloud embeddings API key, thin client

Binary stays small and pure Go. The memory-check feature calls a third-party embeddings API (e.g. an LLM provider's embeddings endpoint) using an API key the user obtains and enters themselves, similar to how many developer tools ask for a personal API key.

**Strengths:**
- Keeps the binary small and simple, fully consistent with the existing Go decision
- No ongoing hosting cost to Pysar -- the user pays their own API usage directly
- Technically simplest to build of the three real options

**Novelty:** The cheapest variant to build and the most consistent with dec-20260718-239680d4's binary-simplicity story -- no CGo, no bundled model, tiny binary -- but achieves that by pushing all the setup friction onto exactly the user this problem says must not experience friction.

**Weakest link:** Requires the end user to sign up for a third-party service and obtain/paste an API key -- exactly the kind of setup friction a non-technical user (the operator's own 'homewife' proxy) is least equipped to do without help, and support burden for 'my key doesn't work' scenarios falls on Pysar regardless.

**Risks:**
- Directly fails the non-technical-user acceptance criterion as stated -- API key setup is real friction for the target persona
- Support burden for key/billing confusion shifts to Pysar even though Pysar isn't the one charging

**Diversity role:** thin client, cheapest to build, worst fit for the stated persona

### V3. Pysar-operated hosted backend, premium/subscription feature

The core Pysar binary stays fully local and simple for every other feature. 'Memory/continuity checking' is a distinct, clearly-scoped feature that calls a backend Pysar itself operates and pays for -- the user just gets a working feature (possibly gated behind a paid tier), with no key management and no local model.

**Strengths:**
- No local model, no CGo, no user-managed API key -- second-best installability after full local bundling, without V1's binary-simplicity cost
- Pysar controls model quality/cost centrally and can improve it without shipping new binaries
- Directly monetizable if that's a goal -- turns a cost center into a potential revenue line

**Novelty:** The only variant that directly answers the operator's own explicit alternative framing ('should we provide memory as premium SaaS feature'), and the only one where the operator (not the user) absorbs the technical complexity -- user experience is simplest short of full local bundling, at the cost of making Pysar a service operator, not just a tool vendor.

**Weakest link:** Pysar (the operator) now owns real, ongoing infrastructure: hosting cost that scales with usage, uptime responsibility, and -- if gated behind payment -- subscription/billing engineering. This is a business commitment, not just a technical one, and is the first feature in the whole product that would require Pysar to operate a paid service rather than ship a tool.

**Risks:**
- Real, ongoing operating cost and support burden fall on the operator, not deferred to the user or a third party
- Requires building and maintaining actual backend infrastructure -- the biggest scope expansion of any variant here, arguably a separate product surface
- A network dependency for a 'default input is your own idea/draft, not the internet' product -- worth checking against the product's own promise language

**Diversity role:** hosted/SaaS, business-model shift, best non-technical fit without local bundling

### V4. Classical local statistical similarity (TF-IDF / n-gram overlap), no ML model at all

Skip true neural embeddings entirely. Use a classical, pure-Go, zero-dependency technique (e.g. TF-IDF cosine similarity or shared-n-gram/MinHash overlap) computed locally to approximate 'semantic-ish' similarity -- catches shared distinctive vocabulary and phrasing patterns across pieces without any model, network call, or CGo dependency.

**Strengths:**
- Zero setup friction, zero ongoing cost, zero new dependency of any kind -- fully preserves dec-20260718-239680d4's single-static-binary invariant
- Pure Go, no CGo, negligible binary size increase, works fully offline
- Meaningfully better than pure literal-phrase matching at catching near-paraphrase that shares distinctive vocabulary

**Novelty:** The only variant that is simultaneously zero-config, zero-network, zero-CGo, and fully consistent with the existing Go decision's binary-simplicity invariant -- trades some recall for a materially simpler and more honest fit to everything already decided about this product.

**Weakest link:** Weaker at true paraphrase detection than real embeddings -- 'I woke up at 2 A.M.' vs. a fully reworded opener with no shared distinctive words would likely be missed, since this technique still fundamentally depends on some vocabulary/n-gram overlap, unlike neural embeddings which capture meaning independent of exact wording.

**Risks:**
- Misses genuine full-reword paraphrase with no shared vocabulary -- the hardest and most literal version of the operator's own example
- Underdelivers on the original 'catches meaning-level repetition' promise that made semantic search attractive over lexical search in the first comparison

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Ships today with zero new dependency and zero conflict with any existing decision, and directly tests whether cheap vocabulary-overlap similarity is actually good enough in practice on the operator's real corpus (Medium's articles) before committing to V1's binary-simplicity trade-off or V3's business-model shift -- de-risks the harder, costlier variants rather than assuming true embeddings are necessary.

**Diversity role:** classical local statistics, best fit to existing constraints, weaker recall ceiling

## Pareto Front Trade-Offs

- Bundled local embedding model (CGo/onnxruntime-style), fully offline — Best non-technical installability tied with V4 (zero config, fully offline) and matches V2/V3 on repetition_recall (true embeddings). Costs the worst binary_simplicity -- a real CGo dependency that tensions with the Go decision's own stated reasoning.
- User-supplied cloud embeddings API key, thin client — Ties V3/V1 on repetition_recall and matches V4's best-in-class binary_simplicity and resource_footprint. Costs the worst non_technical_installability of all four -- fails the problem's own central acceptance criterion outright, its one real edge (matching V1/V3 on recall while staying a thin client) doesn't offset that for the stated non-technical persona.
- Pysar-operated hosted backend, premium/subscription feature — Second-best installability without breaking binary simplicity, matches V1/V2 on recall. Costs by far the worst operating_cost_to_pysar -- the only variant that makes Pysar an infrastructure operator, and the only one that directly matches the operator's own SaaS framing.
- Classical local statistical similarity (TF-IDF / n-gram overlap), no ML model at all — Ties for best installability, binary_simplicity, resource_footprint, and operating_cost -- the cheapest and most constraint-consistent option across the board. Costs the worst repetition_recall of the set -- genuinely weaker at true full-reword paraphrase than the ML-based variants.

**Selection policy:** Pareto front, not a scalar winner -- confirmed all four variants are genuinely non-dominated (my own manual read suspected V2 might be dominated by V4; the kernel's computation disagreed, consistent with past sessions where manual dominance intuition has been wrong -- trusting the kernel's computation as authoritative). All dimensions are targets, none a hard constraint, since this is a genuine multi-way trade-off rather than a technical pass/fail.

**Recommendation rationale:** V2 (user-supplied API key) technically survives the Pareto computation but fails the problem's own stated central acceptance criterion (non-technical installability) outright, with no dimension where it's uniquely better than the alternatives -- I'd steer away from it despite its formal non-dominated status. Among the other three: V4 is the honest, zero-risk starting point (matches every existing decision, costs nothing extra, ships immediately) but caps out below true embeddings on the hardest paraphrase cases. V1 gets the best of both worlds for the end user (offline, zero-config, full recall) but genuinely conflicts with why Go was chosen in the first place -- that tension needs the operator's explicit judgment, not a technical tiebreak. V3 answers the operator's own SaaS framing directly and is the cleanest technically, but commits Pysar to running and paying for real infrastructure -- a business decision this comparison can surface but should not make. Given V4 is marked a stepping stone in this portfolio, a defensible sequencing is: ship V4 now (zero conflict, immediate value, tests real recall against the Medium corpus), and treat the V1-vs-V3 choice as the actual hard decision once it's clear whether V4's recall ceiling is a real problem in practice.
