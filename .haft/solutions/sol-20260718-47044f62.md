# Solutions for: On-disk piece/project structure, storage location, and schema evolution across pysar versions

Problem: prob-20260718-f6ac8127

## Variants (5)

### V1. One directory = one piece; machine state in .pysar/; prose at root

init creates a piece root: author-owned idea/stake + draft/body as markdown; tool-owned .pysar/schema_version + state/run-log. Host agent files (CLAUDE.md) optional/host-specific. Inspired by prior writing POC's one-folder-per-article, but drops publish/cover/Status FSM and prior writing POC platform fields; produced-artifact refs live under .pysar for Pass preconditions.

**Strengths:**
- Matches pysar init [dir] mental model
- Clear overwrite boundary
- Fits multi-project coexistence on one machine

**Novelty:** Splits author prose vs tool machine state explicitly — prior writing POC mixes Status into publish.md with operator checklist.

**Weakest link:** Without a project-level parent, multi-piece memory/index and shared voice config have no natural home.

**Risks:**
- Orphan pieces
- Voice/author registry deferred

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Can later nest pieces under a project root without changing per-piece contract.

**Diversity role:** piece-as-root topology

### V2. Project root + pieces/<slug>/ (prior writing POC monorepo shape, Pysar names)

init scaffolds a writing project: root holds voice/config + schema_version; each piece is pieces/<slug>/ with prototype-like artifact set renamed to Pysar terms (stake/outline/angles/body, not brief/article/publish). Run-log and cycle state per piece under pieces/<slug>/.pysar/.

**Strengths:**
- Natural home for TF-IDF memory corpus
- Shared author voice across pieces

**Novelty:** Keeps prior writing POC's project+slug topology (where memory engine naturally attaches) while replacing Status/publish/cover with Pysar Pass state.

**Weakest link:** Heavier init; easier to over-copy prior writing POC file names and drag prior writing POC jargon onto author surface.

**Risks:**
- Scope creep at init
- Slug management UX

**Diversity role:** project-monorepo topology

### V3. Manifest-only machine layer; zero prose templates at init

init writes only .pysar/project (schema_version, host) and empty dirs or nothing else. Author creates prose files; first pass that needs an artifact creates it. Evolution: pysar migrate rewrites only .pysar/** by schema_version; never touches user markdown.

**Strengths:**
- Safest upgrade story
- Hard to clobber prose

**Novelty:** Maximally refuses the failed freelanced-template mistake — structure emerges from passes, not from init fiction.

**Weakest link:** Cold start UX is empty; author and agent lack a shared map until docs/skills explain conventions.

**Risks:**
- Looks like 'nothing happened' after init
- Convention drift without templates

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Defines the non-negotiable migration boundary first; templates can be added later as optional overlays.

**Diversity role:** minimal machine marker

### V4. Embedded schema + migrate command (tool-owned evolution)

Regardless of V1/V2 topology: every project/piece carries schema_version. New pysar release ships migrations that transform .pysar state and may add missing optional template files if absent; never overwrite non-empty author files. pysar doctor / pysar migrate --dry-run are the operator surfaces.

**Strengths:**
- Answers 'how does it rewrite on new versions' explicitly
- Testable migrations

**Novelty:** Makes version evolution a first-class product feature — prior writing POC has no equivalent (AGENTS.md edits only).

**Weakest link:** Migration code is ongoing tax; bad migration can brick state even if prose is safe.

**Risks:**
- Build cost before first real pass
- Over-engineering early

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Composable with V1 or V2; can decide topology separately from migration machinery.

**Diversity role:** evolution mechanism

### V5. Host-skill overlay versioned separately from piece schema

Piece/project schema (artifacts + .pysar) versioned in the Go binary; host agent files (CLAUDE.md, skills) versioned as an installable overlay (pysar init --claude refreshes host files with backup). Author prose never in the overlay refresh set.

**Strengths:**
- Matches dual-surface console vs agentic
- Lets host files update aggressively

**Novelty:** Separates 'piece data model evolution' from 'agent prompt/skill evolution' — prior writing POC couples both in one AGENTS.md monorepo.

**Weakest link:** Two version clocks confuse operators if not named clearly.

**Risks:**
- Split-brain versions
- More CLI surface

**Diversity role:** dual-version tracks
