# Solutions for: pysar init host-selection mechanism: --claude default, extensible to --cursor/--codex later

Problem: prob-20260718-35d97dc6

## Variants (4)

### V1. Boolean flags per host (--claude, --cursor, --codex) with if-chain dispatch

Three separate boolean flags, one per host. An if-chain resolves which is set (defaults to --claude=true when none given) and calls the matching scaffold function. --cursor/--codex parse successfully today but their scaffold functions print 'not yet supported' and exit non-zero.

**Strengths:**
- Directly matches the operator's stated syntax (--claude specifically)
- Simplest possible Go flag parsing, no new types
- Fastest to write and read today

**Novelty:** Zero abstraction beyond exactly what three named boolean flags require -- the most literal translation of the operator's own stated flag names.

**Weakest link:** Nothing in the flag shape itself stops `pysar init --claude --cursor` -- an ambiguous combined request needs an explicit mutual-exclusivity check written by hand, or it silently does whichever the if-chain checks first.

**Risks:**
- Ambiguous multi-flag input needs its own validation code
- A growing list of exclusive boolean flags is a slightly clunky CLI shape as more hosts are added

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Cheapest way to ship the literal --claude flag today. If a registry (V3) is adopted later, these three flags just become the values mapped into it -- nothing here is thrown away.

**Diversity role:** literal flag match, zero abstraction, weakest misuse-safety

### V2. Single enum flag (--host=claude, default claude)

One flag, --host, restricted to a small validated set (claude, cursor, codex). Mutual exclusivity is structural -- a single flag cannot hold two values. Same 'not yet supported' behavior for cursor/codex today.

**Strengths:**
- Cannot be invoked with two conflicting hosts at once
- Scales cleanly to more hosts without adding more flags

**Novelty:** The only variant where 'exactly one host, unambiguously' is enforced by the flag's own shape rather than by extra validation logic -- structurally impossible to misuse into a combined state.

**Weakest link:** Does not literally provide the --claude flag name the operator asked for -- would need --claude accepted as sugar for --host=claude if that exact syntax matters, adding back a small amount of glue code.

**Risks:**
- Diverges from the operator's literally requested --claude syntax unless sugar is added
- Slightly less discoverable via --help than named per-host flags

**Diversity role:** structurally safe, diverges from literal request

### V3. Minimal host-adapter interface + explicit registry map

A small hostAdapter interface (Scaffold(dir string) error, Name() string) with a plain Go map literal as the single registration point (map[string]hostAdapter{"claude": claudeAdapter{}, "cursor": notYetAdapter{"cursor"}, ...}) -- no dynamic plugin loading or init()-based magic, just one readable map a contributor edits directly to add a host. Flag surface (bool flags or --host=X) sits on top and resolves to a map key.

**Strengths:**
- Cheapest future extension_cost of the four -- adding a real host touches only one new adapter type and one map line
- No dynamic/reflective magic to debug later -- the whole registry is one visible map literal

**Novelty:** The only variant that gives future host support a genuinely clean seam -- implement the interface, add one map entry -- without any dynamic registration machinery, earning its structure specifically because the operator explicitly asked for an extension point rather than because more hosts are merely guessed to be likely.

**Weakest link:** More upfront structure (an interface, a map, two small types) than V1/V2 for exactly the same near-term behavior -- real cost paid today for a benefit that only pays off once Cursor/Codex support is actually implemented for real.

**Risks:**
- Most code written today for exactly one real host
- A small abstraction the operator or a future reader has to learn even though only one branch is real right now

**Diversity role:** cleanest extension seam, most upfront structure

### V4. Config/template-driven host definitions (declarative, no per-host Go code)

Host scaffolding described as data -- embedded per-host file-template sets -- read by one generic scaffold function. Adding a host means adding a data file, not Go code.

**Strengths:**
- Adding a host is a data file, not code, if the premise holds
- Templates are easy for a non-Go-fluent contributor to read and edit

**Novelty:** The only variant that could add a host with zero new Go code, if scaffolding really does stay pure file-templating.

**Weakest link:** Real host integration plausibly needs more than pure file-templating -- e.g. merging into an existing .mcp.json rather than overwriting it, per ES.enabling.agent_policy.001's Claude Code integration -- which breaks the 'pure data, no code' premise almost as soon as it's tested against a real host.

**Risks:**
- Premise likely breaks on the very first real host implementation, once merge-not-overwrite logic is needed
- Still needs an escape hatch for non-templatable logic, undermining the 'declarative' pitch

**Diversity role:** declarative/data-driven, fragile premise

## Pareto Front Trade-Offs

- Boolean flags per host (--claude, --cursor, --codex) with if-chain dispatch — Best literal_match and upfront_simplicity -- exactly the --claude syntax requested, zero new abstraction. Costs the worst misuse_safety of the four -- nothing stops --claude --cursor together without hand-written validation.
- Single enum flag (--host=claude, default claude) — Best misuse_safety -- structurally cannot request two hosts at once. Costs the worst literal_match -- doesn't provide the --claude flag name as-is without added sugar.
- Minimal host-adapter interface + explicit registry map — Best extension_cost by far -- adding a real host later touches one adapter type and one map line. Costs the worst upfront_simplicity -- most new structure written today for exactly one real host.
- Config/template-driven host definitions (declarative, no per-host Go code) — Balanced across all four dimensions, no clear win or loss. Its real risk is qualitative, not captured in these scores: the declarative premise is likely to break on the first real host needing merge-not-overwrite logic.

**Selection policy:** Pareto front, not a scalar winner -- all four variants are genuinely non-dominated. No dimension is a hard constraint; this is a real CLI-design trade-off (literal match vs. safety vs. extension cost vs. today's simplicity), consistent with CLAUDE.md's own stated discipline against premature abstraction, which argues against over-weighting extension_cost alone.

**Recommendation rationale:** V1 is explicitly a stepping stone and matches the operator's literal request most directly (--claude specifically, as stated) with the least code for exactly one real host today. Its one real gap -- misuse_safety -- is cheap to close without changing the flag shape: add a short validation check that rejects more than one host flag being set, rather than adopting V2's different flag syntax or V3's registry structure preemptively. V3's registry is the strongest long-term answer and worth adopting the moment a second real host (Cursor or Codex) actually gets implemented -- building it now, for one real host, is exactly the premature-abstraction CLAUDE.md warns against, even though the operator did ask for an extension point. The acceptance criteria's own definition of 'extensible' (item 4: adding a host later touches only host-specific logic) is already satisfied by V1 as long as scaffold logic is kept in its own function per host from the start -- the registry can be layered on top later without that host-specific code being rewritten.
