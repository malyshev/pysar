# Solutions for: /ps-intake: scaffold brief/outline/angles from an operator idea or draft

Problem: prob-20260725-53b2d8ea

## Variants (5)

### V1. Conversational restate-and-confirm intake; single MCP save tool; provisional local storage

One conversational pass. Skill restates the operator's stake/thesis in one sentence and asks for confirmation only if ambiguous (mirrors POC step 2), infers a topic-appropriate expert register internally without a separate confirmation round, then scaffolds brief/outline/angles together. A single new MCP tool (save_intake_brief) validates completeness and persists all three artifacts as one bundle to a provisional per-piece directory convention, explicitly flagged in code/docs as superseded once prob-20260718-f6ac8127 resolves. Registers its own Precondition check (piece has no existing intake artifacts yet) and appends to the run-log on success.

**Strengths:**
- Low friction for the common case (clear idea, no back-and-forth)
- One MCP tool, minimal new surface, mirrors already-shipped save_voice_template pattern
- Provisional storage is explicit and named, not silently permanent

**Novelty:** Balances speed and correctness-checkpointing by making confirmation conditional (only when ambiguous) rather than either always-on (V2) or never (V5) -- the restate step is the single grounding mechanism for 'force correct understanding', not a full Q&A gate.

**Weakest link:** The ambiguity judgment call ('confirm only if ambiguous') is itself made by the same agent doing the scaffolding, with no external check -- a confidently-wrong reading of a genuinely ambiguous idea can slip through without ever triggering the confirmation branch.

**Risks:**
- Provisional storage convention may need real migration work once prob-20260718-f6ac8127 lands
- Silent misread risk on genuinely ambiguous ideas (see weakest_link)

### V2. Elicitation-gated intake with explicit persona declaration; no file writes yet (conversation-only stepping stone)

Before scaffolding, intake asks a small fixed set of clarifying questions one at a time (never batched, per dec-20260719-7d675b61's output-discipline gate), and explicitly states which expert mode/persona it is adopting for operator confirmation before proceeding -- grounding 'correct expert mode' as a stated, checkable claim rather than a silent internal choice. Produces brief/outline/angles content in the conversation and shows it to the operator, but does NOT persist to disk at all this iteration -- deliberately defers the write step until prob-20260718-f6ac8127 resolves. Precondition check and run-log entry still fire (piece gains an 'intake-drafted' artifact ref even without a file on disk, if the state model supports in-memory/ephemeral artifact kinds -- flagged as an open question for this variant).

**Strengths:**
- Zero coupling to an undecided architecture question
- Forces explicit, checkable persona declaration -- directly grounds the flagged umbrella word 'correct'
- Cheapest to build and to throw away if the content contract itself needs rework

**Novelty:** The only variant that fully decouples validating the content contract from committing to storage topology -- proves what intake produces is right before deciding where it lives.

**Weakest link:** Delivers no persisted artifact to the operator this iteration -- if the storage-topology decision (prob-20260718-f6ac8127) stalls, this variant's output evaporates at the end of every session, which may not satisfy the operator's actual goal of having something durable to hand to /w-draft-equivalent next.

**Risks:**
- Operator may reject a 'nothing saved yet' first version as not actually useful
- Whether the Precondition/run-log model even supports an ephemeral (non-file-backed) ArtifactKind is untested

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Validates the content contract (brief/outline/angles shape, expert-mode declaration) independently of storage topology, so whichever variant wins prob-20260718-f6ac8127 later can adopt an already-proven content contract instead of designing both at once.

### V3. Draft-first differential intake -- two distinct sub-flows converging on one output contract

Treats idea-only entry and --from-draft entry as genuinely different processes rather than one flow with a conditional branch. Idea-only entry runs active expert-mode elicitation and restatement (like V1/V2). Draft entry runs extraction-only: thesis/outline/angles pulled strictly from the author's own words, explicitly refusing to add or 'improve' content from outside knowledge (mirrors POC's draft-intake rule and the project's no-web-search constraint). Both converge only at the final brief/outline/angles write step, via multiple MCP tools mirroring the existing save+list template pattern. Storage: same provisional convention as V1.

**Strengths:**
- Draft-extraction correctly avoids the temptation to 'research-synthesize' over an author's own words, closest fidelity to what the operator already validated in the POC
- Clear separation of concerns between elicitation and extraction

**Novelty:** The only variant that treats 'idea' and 'draft' entry as different problems with different failure modes (misunderstanding vs. over-improving) instead of one input-normalization step -- most faithful port of the POC's own explicit draft-intake special-casing.

**Weakest link:** Two maintained sub-flows instead of one means twice the surface to keep in sync when the shared output contract (brief/outline/angles shape) changes -- a change to brief.md's required sections must be applied and tested in both paths.

**Risks:**
- Duplication/drift risk between the two sub-flows over time
- More build cost than a single unified flow

### V4. editorial.Run integration-first; minimal placeholder content contract

Prioritizes correctly wiring intake as the first real pass through dec-20260718-20a08f83's Precondition mechanism and dec-20260718-6ba897d4's run-log -- since that decision's own 2026-07-19 measurement already names 'CLI/skill entrypoints not yet routing through editorial.Run' as the one open gap. Content contract is deliberately minimal this iteration (a single free-text thesis/angle field, not the POC's full multi-section brief) so the integration work isn't blocked on content-shape debate.

**Strengths:**
- Closes dec-20260718-20a08f83's own named open gap directly, with a real tested example other future passes (research, edit, packaging) can copy
- Smallest, most reviewable first PR

**Novelty:** The only variant that treats 'be the reference implementation for editorial.Run' as the primary deliverable, with rich brief content explicitly deferred -- inverts every other variant's priority order.

**Weakest link:** Does not actually deliver what the operator asked for (a real brief/outline/angles scaffold) in its first shippable form -- risks operator frustration if 'plumbing works' is mistaken for progress on the stated goal.

**Risks:**
- Operator has to wait for a second iteration before getting the actual brief-scaffolding value
- Placeholder content contract may get treated as 'done' and never revisited

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Establishes a real, tested editorial.Run integration pattern every subsequent pass (research, edit, voice-lock, packaging) can copy verbatim, opening that search space cheaply before content-contract complexity is layered on top.

### V5. Full POC-parity content contract, minus authors/length, single-shot no-clarification

Closest structural mirror to the Medium POC: replicate its brief.md's ~11 sections, outline.md, angles.md (misconceptions/contrarian/trade-offs/edge-cases), and a sources.md stub -- with every Author/Author-name field and the --length=N flag removed outright, not just left empty. No clarifying questions, no restatement step, no persona declaration -- the agent silently does its best single-shot read of the idea/draft and scaffolds directly.

**Strengths:**
- Fastest to ship, most content-complete on day one
- Lowest design risk -- content shape is already battle-tested by the POC, only trimmed

**Novelty:** The only variant with zero interactive checkpoint between operator input and written artifact -- maximum content fidelity to the proven POC shape, minimum process novelty.

**Weakest link:** Has no mechanism at all for catching a misread idea before it's scaffolded into a full brief -- directly the weakest on the operator's own stated goal ('force agent to correctly understand the idea'), since nothing forces anything; it's a best-effort single guess.

**Risks:**
- Silently scaffolds a full brief on a misunderstood idea with no checkpoint to catch it -- highest rework cost if wrong
- Directly contradicts the operator's own framing language ('force ... correctly understand') by having no forcing mechanism

## Pareto Front Trade-Offs

- Conversational restate-and-confirm intake; single MCP save tool; provisional local storage — Balanced default: durable, content-complete, moderate build cost -- but only conditional (not structural) misread-catching.
- Elicitation-gated intake with explicit persona declaration; no file writes yet (conversation-only stepping stone) — Best misread-catch and zero premature storage coupling, cheapest to build -- but ships nothing durable this iteration; a pure content-contract validator.
- Draft-first differential intake -- two distinct sub-flows converging on one output contract — Best combination of durable + complete + real misread-catch tailored per input type + highest fidelity to the POC's own validated draft-vs-idea distinction -- at the highest build cost of the non-stepping-stone variants.
- editorial.Run integration-first; minimal placeholder content contract — Best editorial.Run integration, closes the named architectural gap directly -- but weakest on delivering the operator's actual stated ask (real brief content) this iteration.
- Full POC-parity content contract, minus authors/length, single-shot no-clarification — Richest day-one content, closest POC parity -- but has no forcing mechanism at all, directly the weakest on the operator's own framing language ('force correctly understand').

**Selection policy:** Full Pareto front, no scalar winner -- all 5 variants are mutually non-dominated across the 6 target dimensions (misread_catch_capability, output_durability, content_completeness_day_one, storage_topology_coupling [inverted], editorial_run_integration_completeness, build_cost [inverted]); each variant is strictly better than at least one other on at least one dimension no other variant matches. poc_structural_fidelity is observation-role: read for context, never used to break ties (per dec-20260718-eafefad2's reference-agnosticism gate). Advisory recommendation below weights misread_catch_capability and output_durability highest, since they most directly answer the operator's own stated goal ('force agent to correctly understand the idea' + something usable at the end), with editorial_run_integration_completeness and build_cost as secondary tie-breakers.

**Recommendation (advisory):** Draft-first differential intake -- two distinct sub-flows converging on one output contract

**Recommendation rationale:** V3 is the only variant that scores well on both halves of the operator's stated goal at once: a real (if not maximal) misread-catch mechanism tailored to how the risk actually differs by input type (active elicitation for idea-only entry, strict extraction discipline for --from-draft, mirroring the POC's own validated special-case), AND a durable, content-complete, editorial.Run-wired output on day one. V1 is the cheaper sibling if the operator wants to defer the two-sub-flow investment -- it only loses to V3 on misread_catch_capability (1 vs 2) and poc_structural_fidelity, at meaningfully lower build cost. V2 deserves real consideration on its own terms if the operator reads 'force correct understanding' as the primary goal this iteration and is fine deferring persistence entirely until prob-20260718-f6ac8127 resolves anyway -- it is not a lesser variant, it optimizes a different half of the same problem.
