# Solutions for: Message-noise gate: prevent verbosity/noise recurrence across CLI and agentic (ps-*) output

Problem: prob-20260719-b97f5099

## Variants (5)

### V1. Prose-only addition to CLAUDE.md

Add a new 'Pysar output discipline' section to CLAUDE.md naming the noise patterns already caught, as guidance for future work. No test, no shared block referenced by the skill files -- purely a paragraph to read and remember.

**Strengths:**
- Zero implementation cost
- Captures the specific known incidents for future reference

**Novelty:** The minimal-effort floor -- documents the problem without building any mechanism to catch it before a live user does.

**Weakest link:** This is the same TYPE of mechanism (aspirational prose) that already exists in CLAUDE.md's Communication style section for an adjacent surface, and has already been shown insufficient: 3 recurrences happened this session despite that section's guidance already saying to be direct and skip noise. More prose without a check changes nothing structural.

**Risks:**
- Directly fails the acceptance criterion's own requirement for a testable component, not prose alone
- No reason to expect a 4th recurrence is actually prevented

### V2. Automated CLI-output pattern test only

Add a Go test scanning cmd/pysar/main.go's literal output strings for a small set of generic noise-phrase categories (redundant confirmations, explaining an absence, restating the obvious). Covers the CLI surface mechanically.

**Strengths:**
- Genuine machine enforcement, not just a reminder
- Directly prevents exact regression of the CLI incidents already fixed

**Novelty:** The only variant that adds real, machine-checked enforcement -- but only for the one surface where enforcement is technically possible before runtime.

**Weakest link:** Cannot cover the agentic/skill-prompt surface at all -- ps-voice and ps-style's actual output is LLM-generated live in conversation, not static text a pre-runtime test can scan. Two of the three real incidents this session (Step 2 checklist, Step 6 silence) were on exactly this uncovered surface.

**Risks:**
- Leaves the surface with more incidents this session (skill prompts) completely unaddressed
- Skills still re-derive their own noise-prevention wording ad hoc, with no shared source

### V3. Shared principle + explicit pre-ship self-check + targeted regression tests

Write one 'message discipline' principle once (a new CLAUDE.md section), naming the concrete noise patterns already caught as negative examples. Both ps-voice and ps-style SKILL.md files reference it by name instead of re-deriving their own wording. Add a concrete, explicit pre-ship self-check step -- three questions applied before considering any CLI-message or skill-prompt-text change complete: does this tell the reader something actionable? would removing it change what they do next? am I explaining an absence instead of staying silent? Add lightweight Go regression tests locking in the 3 specific CLI incidents already fixed (extending the existing init_test.go pattern, not a new broad linting layer).

**Strengths:**
- Single source both skills already reference rather than re-deriving, directly closing the inconsistency the signal named
- Real regression tests for the CLI incidents specifically, not just documentation
- The 3-question self-check is concrete enough to actually apply, unlike generic 'be concise' guidance

**Novelty:** Combines a single source of truth (not re-derived per skill), a concrete process gate applied by the agent doing the work (not just prose to remember), and real but narrowly-scoped automated regression coverage for the surface where automation is actually possible.

**Weakest link:** For the agentic/skill-prompt surface specifically, the 'testable component' is a self-check the agent applies to itself, not a machine-enforced gate -- it is concrete and repeatable, but nothing stops a future session from skipping it the way the existing Communication style prose was already skipped 3 times this session. This is a real, unresolved gap the operator should weigh, not a solved problem.

**Risks:**
- The agentic-surface component still depends on the agent choosing to apply it each time -- not provably prevented, only made easier to catch

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** The shared principle block and the 3-question self-check generalize to any future ps-* skill or CLI surface (Style already reuses it by construction); a future decision could later add machine enforcement (e.g. an agent-facing pre-commit reminder) on top of this same foundation without redoing the underlying principle.

### V4. Everything in the shared-principle variant, plus a dedicated .haft spec file and broader CLI noise-pattern linting

All of the shared principle, self-check, and targeted regression tests, plus: (a) a new .haft/specs/message-discipline.md formalizing this as project-wide governance, cross-referenced by any future skill or CLI work; (b) a broader, generic CLI noise-pattern test (not just the 3 known incidents) scanning for categories of bad phrasing, not just literal known strings.

**Strengths:**
- Full governance-graph presence, consistent with how this project tracks everything else
- Broadest CLI test coverage in principle

**Novelty:** The most complete version -- adds formal governance-graph presence and generalizes the CLI test beyond only the incidents already seen.

**Weakest link:** A generic noise-pattern-matching test has poor recall against genuinely new phrasing by construction -- every incident this session used different specific wording than the last, so a pattern test built after incident N would not have caught incident N+1 either; its main value is exact-regression prevention, which the targeted version already provides at far lower cost. The new spec file adds real ongoing maintenance (cross-referencing, keeping current) for marginal additional coverage over the lighter variant.

**Risks:**
- Meaningfully heavier to build and maintain for a problem that has, so far, been narrow in actual damage (each incident caught and fixed within one turn via live testing)
- Risk of the spec file becoming stale documentation nobody actually consults, the same failure mode as the plain-prose variant it's meant to improve on

### V5. Status quo -- continue catching incidents reactively via live testing

No new mechanism. Keep relying on the operator's own live testing to surface each noise incident, fixed one at a time as it happens, same as this session's actual history. Included specifically to make the cost of doing nothing explicit and comparable.

**Strengths:**
- Zero cost
- Has, in fact, worked every time so far -- every incident was caught and fixed

**Novelty:** The floor this problem exists to move past -- not a genuine proposal.

**Weakest link:** Directly fails the operator's own stated goal: they explicitly asked for something structural, not another one-off reactive fix, after the third recurrence.

**Risks:**
- Depends entirely on the operator continuing to catch every future instance themselves, which is the exact burden they are now asking to be relieved of
