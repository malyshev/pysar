# Solutions for: Tech stack for Pysar as an installable, globally-accessible multi-project CLI

Problem: prob-20260718-7d913b89

## Variants (4)

### V1. Go single static binary (mirrors haft's own distribution)

Implement Pysar as a Go CLI, cross-compiled to a single static binary per OS via goreleaser (the exact toolchain haft itself uses), distributed via install.sh + Homebrew tap. Each project directory gets a marker file (e.g. .pysar/project.toml) analogous to haft's .haft/project.yaml. `pysar init <dir>` and `pysar onboard <dir>` scaffold and configure a project; the binary itself stays topic/voice-agnostic, reading topic/voice/surface config from the project-local marker.

**Strengths:**
- True zero-runtime-dependency single binary, trivial native cross-compilation
- Directly reuses a distribution pipeline (goreleaser/install.sh) the operator has already validated with haft
- Strong concurrency primitives if the editorial engine ever parallelizes multi-pass edits

**Novelty:** Deliberately mirrors the dogfooded haft binary's own toolchain (goreleaser, install.sh, Go) rather than picking a language in isolation — opens a path to shared distribution tooling and a consistent mental model across the two tools the operator already runs daily.

**Weakest link:** Go's LLM-orchestration ecosystem (prompt templating, streaming, structured output parsing) is thinner than Python/TS — more boilerplate to hand-roll for the actual editorial-engine core, and zero reuse of the content-processing utilities (gray-matter, fast-glob, mdx handling) already proven in the Medium project.

**Risks:**
- Steepest reimplementation cost — none of Medium's existing TS content-processing code carries over
- Smaller pool of LLM-SDK conveniences than the TS/Python ecosystems

**Diversity role:** runtime-independent, ecosystem-mirrors-dogfood-tool

### V2. Bun-compiled TypeScript binary (reuses Medium's proven content stack)

Implement Pysar in TypeScript, compiled to a single-file executable via `bun build --compile`. Directly reuses patterns and libraries already validated in the operator's own Medium project (gray-matter for frontmatter, fast-glob for content discovery, zod for config validation). Project marker + init command follow the same CWD-based model validated in billing-calculator-cc, just implemented in TS.

**Strengths:**
- Fastest realistic path to a working editorial-engine core — TS/Node has the richest LLM SDK + prompt-orchestration ecosystem
- Direct reuse of gray-matter/fast-glob/zod patterns already proven in Medium
- Single language across Pysar and Medium if the two projects ever need to share code

**Novelty:** The only variant that reuses actual code/patterns the operator has already written and validated (Medium's content-processing utilities), rather than starting the editorial-engine core from zero.

**Weakest link:** Bun's single-file-binary compilation is younger and less battle-tested than Go's native cross-compilation; producing binaries for OSes other than the build machine typically needs per-OS build runners (CI) rather than one-command native cross-compile.

**Risks:**
- Bun-specific compile toolchain is a smaller, faster-moving target than Go's — more exposure to breaking changes between Bun versions
- Larger binary size than Go/Rust equivalents typically

**Diversity role:** fastest-to-working-core, maximum-code-reuse

### V3. Rust single static binary

Implement Pysar in Rust, producing a fully static, zero-runtime binary via standard `cargo build --release` cross-compilation. Same CWD-based project-marker + init-command model, implemented with Rust's strong CLI ecosystem (clap, serde).

**Strengths:**
- Smallest, fastest binaries of all four variants
- Strongest compile-time correctness guarantees
- Excellent native cross-compilation story, comparable to Go

**Novelty:** The only variant chosen purely for maximal runtime guarantees (memory safety + zero-cost abstractions + smallest/fastest binaries) rather than for ecosystem or dogfood-consistency reasons — the ceiling pick if performance or binary size ever becomes a hard constraint.

**Weakest link:** Development velocity — the borrow checker and Rust's stricter type discipline impose real iteration-speed cost on rapidly-changing, LLM-prompt-orchestration logic that will be rewritten often in the early product phase; steepest learning/authoring cost of all four variants for a solo maintainer.

**Risks:**
- Highest authoring friction for a solo maintainer during a phase where the product's core logic is still being discovered, not yet stable
- No reuse of existing Medium/haft-adjacent code or patterns

**Diversity role:** maximal-rigor-and-performance-ceiling

### V4. Python + uv-based packaging, positioned as a deliberate stepping stone

Implement Pysar in Python, using uv for dependency/venv management and a packaged single-command entry point (uv tool install / PyInstaller for a semi-standalone binary). Fastest possible prototyping velocity for the actual editorial-engine logic (LLM orchestration, prompt chains) using Python's richest-in-class LLM/text-processing ecosystem, explicitly traded against a weaker 'single clean binary' distribution story.

**Strengths:**
- Richest LLM-orchestration and text-processing ecosystem of any variant (fastest to prototype the actual hard problem)
- uv makes dependency management and reproducible environments fast and modern
- Large pool of existing libraries for editorial/NLP-adjacent tasks

**Novelty:** The only variant that explicitly optimizes for fastest iteration on the actually-novel, actually-hard part of the product (the editorial-engine core's prompt/LLM orchestration) at the deliberate cost of the distribution story, rather than optimizing distribution first.

**Weakest link:** The 'single installable binary, globally accessible' requirement is the weakest fit of all four variants — Python packaging (PyInstaller/uv tool) is the most fragile, heaviest, and slowest-startup path to a distributable binary; genuinely satisfying acceptance criterion (1) is the hardest here.

**Risks:**
- Weakest binary/distribution story of all four — real risk of not meeting acceptance criterion (1) cleanly
- Requires bundling a Python runtime one way or another, working against the 'no separate runtime install' constraint

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Lets the operator validate and iterate on the editorial-engine core's actual hard problem (LLM orchestration quality) fast, with a planned migration of the validated core logic to Go or TS once the product's real behavior stabilizes — the distribution-story weakness is deliberately deferred, not ignored.

**Diversity role:** fastest-iteration-on-hard-problem, explicit-stepping-stone
