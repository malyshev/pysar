# Solutions for: Style profile content fit: does Style's structural/mechanical content have a genuine home in the shared Profile schema?

Problem: prob-20260719-aa6d932e

## Variants (5)

### V1. Status quo -- force Style content into the existing voice-named fields

Build /ps-style entirely on the current Profile struct unchanged. The skill asks style questions but stashes answers into Tone/Formality/SentenceLength/Register/Notes as best it can -- e.g. "cut what doesn't earn its place" and "active voice" end up crammed into Notes since no field fits them.

**Strengths:**
- Zero new code -- reuses everything exactly as shipped

**Novelty:** Not a real proposal -- the floor this problem exists to test, included to make the mismatch concrete rather than assumed.

**Weakest link:** A style.md's frontmatter would literally read "tone: ..." for content that isn't about tone at all -- actively misleading to a human reading the file, and the schema's own structured-attribute value (why Hybrid was chosen over pure-exemplar in dec-20260718-ab150a73) is wasted since most of the operator's actual style content has nowhere structured to go.

**Risks:**
- Resulting style.md files actively mislead a reader about what each field means
- Most of the operator's own listed style content (main-point-first, active voice, cutting) has no structured home at all -- gets dropped or flattened into prose

### V2. Rename fields to genuinely Kind-neutral labels, same shape

Keep exactly four structured fields plus banned_phrases/notes/goldens, but rename them to labels that plausibly serve both kinds (e.g. Tone -> a more neutral term). Since Voice and Style share one Go struct (dec-20260718-ab150a73), this rename applies retroactively to every already-shipped Voice profile and template, including the operator's own dogfooded .pysar/voice.md and the built-in generic.md template.

**Strengths:**
- No new fields, no schema growth

**Novelty:** Treats the mismatch as a labeling problem rather than a capacity problem -- relabel instead of restructure.

**Weakest link:** Renaming a field on a struct already used to persist real, already-dogfooded data (the operator's own voice.md, the shipped generic.md template) is a breaking migration, not a free rename -- every existing file's frontmatter key changes. It also doesn't add any real capacity: main-point-first, active voice, and cutting still have no field to live in, just a differently-named absence.

**Risks:**
- Breaking change to already-shipped, already-dogfooded voice.md content and the built-in generic template
- Solves the naming complaint but not the actual content-capacity gap

### V3. Add one new shared field: a structured Rules list, usable by both kinds

Add a single new optional field to the shared Profile struct -- Rules []string -- holding short, imperative, individually checkable statements (e.g. "Put the main point first", "Prefer active voice", "Use everyday words", "Cut what doesn't earn its place"). Both Voice and Style can use it (Voice profiles typically leave it thin or empty; Style profiles make it their primary content-bearing field), so the schema stays one shared, interchangeable type -- no Kind gets a field the other cannot also use.

**Strengths:**
- Directly matches the operator's own literal example content -- each of their listed style rules maps to one list item
- Preserves "one shared type, no divergent format" in spirit -- both kinds can use the new field, neither is schema-exclusive
- Style profiles read honestly: real content in a field actually named for what it is

**Novelty:** Extends the schema's existing structured-vs-exemplar duality with a third, list-shaped kind of structure -- discrete prescriptive rules -- rather than trying to force list-shaped content into scalar fields designed for something else.

**Weakest link:** Render/Validate (and the MCP tool schemas built on Profile) need a small, real code change to handle this new field -- a genuine, if bounded, extension of already-shipped, already-tested code, not a pure relabeling.

**Risks:**
- A genuinely new field to add to the completeness validator's rules (how many Rules are required, if any)
- Two ways to express prescriptive content now exist (Rules vs. Goldens) -- needs a clear editorial line for when to use which

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** A generic, kind-agnostic Rules list is exactly the shape any future third profile kind (this project's onboarding schema is explicitly designed for more than just voice+style) would also want for its own discrete, checkable prescriptions -- this doesn't just solve Style, it generalizes the schema's own structured-content capacity for whatever comes after Style.

### V4. No schema change -- Style's content lives entirely in Notes and Goldens

Leave the four structured fields thin or unused for Style; put every actual style rule as prose inside Notes, and demonstrate the rest purely through golden before/after passages. No new field, no rename -- the purist reading of "no divergent format" taken to its limit.

**Strengths:**
- Truly zero schema changes -- cheapest possible option that doesn't rename anything

**Novelty:** Tests whether the schema's existing free-text/exemplar half alone is sufficient for Style, without adding any new structured capacity.

**Weakest link:** Notes is one undifferentiated blob and goldens can only demonstrate, not state, a rule -- neither is separately queryable or individually validatable the way a discrete field is, which directly contradicts why Hybrid (structured fields + goldens) was chosen over a pure-exemplar schema for Voice in the first place (dec-20260718-ab150a73's own steering_strength/structured_validatability reasoning).

**Risks:**
- Under-uses exactly the structured-attribute value this project already decided the schema needed
- A future completeness validator has nothing specific to check for Style beyond "are there goldens and some notes"

### V5. Supersede dec-20260718-ab150a73 -- give Style its own distinct schema type

Reopen the "one shared type" invariant entirely. StyleProfile becomes its own Go type with purpose-built fields (e.g. StructureRules, SentenceRules, WordChoiceRules, FormattingRules, Goldens), fully decoupled from VoiceProfile's shape. Included to test whether purpose-built fields are worth reopening already-shipped ground, not because superseding is assumed correct.

**Strengths:**
- Purpose-built fields would fit Style's actual content perfectly, no compromise
- No ambiguity about which field to use for what, unlike Rules vs. Goldens in the shared-field variant

**Novelty:** The only variant that actually resolves the semantic mismatch at its root by not sharing a type at all -- included as the genuine alternative to "extend the shared type," not a strawman.

**Weakest link:** Requires an explicit /h-refresh supersede of an already-decided, already-shipped, already-dogfooded invariant, and internal/onboarding's generic machinery (Render, Validate, TemplatesDir, Slug, WrapTemplate/UnwrapTemplate -- all built and tested this session on the assumption of one shared Profile type) would need either per-Kind duplication or a new interface layer -- real, nontrivial rework of working, tested code, not a bounded addition.

**Risks:**
- Reopens a decision this project has already built five features on top of
- Duplicates or generalizes a meaningful amount of already-shipped, already-tested code for a problem a smaller extension may already solve
