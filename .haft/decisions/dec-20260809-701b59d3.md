# Shared stage-precondition substrate for research and SEO

## 1. Problem Frame

**Signal:** Shipped /ps --seo inserts ps-seo between sharpen and humanize by skill prose only (dec-20260804-e3234e50). There is no durable piece mark and no MCP gate: save_humanize_bundle succeeds from sharpen.md whether or not seo.md exists. Latest operator dogfood/tests show agents skip ps-seo even when --seo was given — same failure class as research being skipped under soft MUST. Sibling decision dec-20260809-3a372a15 already bound piece requires_research + draft-owned hard gate for --research; --seo needs the same shape of hard gate so opt-in SEO cannot be skipped into humanize/export.

**Constraints:**
- Default /ps without --seo must stay SEO-free (dec-20260804-e3234e50 invariant)
- SEO before humanize ordering must hold — never after humanize
- Reuse existing /ps-seo + save_seo_bundle; no second SEO implementation
- Hard gate must be machine-enforced (MCP), not prose-only — admissibility from research DRR pattern
- Do not reintroduce AI-detector-evasion into humanize
- Transformer Mandate: explore then manual /h-decide; do not silently amend dec-20260804 without explicit binding

**Acceptance:** With /ps --seo, a durable requires_seo (or equivalent) is set on the piece; save_humanize_bundle fails closed until seo.md exists from a successful save_seo_bundle; without --seo, humanize/export behavior stays as today (sharpen→humanize, no seo.md required). /ps still orders SEO before humanize (dec-20260804-e3234e50). Documented in ps/SKILL.md, ps-humanize/SKILL.md, docs/pipeline.md. Verifiable by Go test (marked piece, no seo.md → humanize save error; after seo.md → success) plus skill chain wording.

## 2. Decision

**Selected:** Shared stage-precondition substrate for research and SEO

**Selection policy:** Eliminate if opt_in_surface_ok is false. Among survivors, maximize must_durability, then maximize future_gate_extensibility. impl_coupling_risk is observation only. Tie-break toward shared/learnable precondition substrate over one-off skill wording (BLP).

**Why selected:** Operator bound V5 after long-term compare. One piece-level stage-precondition substrate (not parallel requires_research / requires_seo booleans) enforces opt-in MUST for --research (draft save) and --seo (humanize save), with room for later gates. Preserves default research-free and SEO-free /ps. Replaces deprecated dec-20260809-3a372a15 mechanism while keeping that decision's behavioral acceptance (research after intake before draft when flagged).


**Invariants:**
- Default /ps without --research never invokes /ps-research
- Default /ps without --seo never requires or invokes /ps-seo
- When --research is set, /ps runs /ps-research after intake before draft (skip re-run only if research completion already satisfied)
- When --seo is set, /ps runs /ps-seo after sharpen before humanize (dec-20260804-e3234e50); never after humanize
- Research precondition means save_draft_bundle refuses until research_mode is full
- SEO precondition means save_humanize_bundle refuses until seo.md exists from save_seo_bundle
- Policy (required stages) is distinct from outcomes (research_mode, presence of seo.md)
- Reuse existing /ps-research and /ps-seo via Skill tool — no forked implementations
- Humanize gains precondition awareness only — no SEO content rewriting or detector-evasion techniques
- Do not break --seo-before-humanize ordering

**Pre-conditions:**
- [ ] sol-20260809-1dab075b compare recorded with V5 advisory recommendation
- [ ] save_research_bundle sets research_mode full; save_seo_bundle writes seo.md
- [ ] dec-20260804-e3234e50 SEO-before-humanize remains binding for order

**Post-conditions:**
- [ ] docs/pipeline.md documents --research and --seo hard-gate behavior
- [ ] ps and plugin mirrors agree on flags + chain
- [ ] Draft and humanize MCP enforce the shared substrate
- [ ] Unmarked pieces behave as today for both paths

**Admissibility:**
- NOT: Prose-only MUST for --research or --seo without MCP fail-closed
- NOT: Always-on research or SEO as default /ps
- NOT: Parallel unrelated booleans as the long-term end state when a shared substrate was bound
- NOT: Treating research_mode targeted as satisfying a research precondition
- NOT: Running or requiring SEO after humanize
- NOT: Agent judgment that a flagged stage can be skipped

## 3. Rationale

**Counterargument:** Ship two thin isomorphic gates (research boolean + SEO boolean / V3) first — research DRR already bound that shape — and extract a shared substrate only after both exist in code. Binding the substrate now couples the SEO fix to research-gate implementation and risks designing the wrong abstraction before the second concrete gate is real.

**Selected variant weakest link:** Over-abstraction or incomplete shared helper leaves both flags soft again; if /ps fails to persist precondition entries when flags are set, gates never arm; export may still ship an earlier revision if the gated stage is skipped entirely unless export also consults the substrate.

**Rejected alternatives:**
| Variant | Verdict | Reason |
|---------|---------|--------|
| Shared stage-precondition substrate for research and SEO | **Selected** | Operator bound V5 after long-term compare. One piece-leve... |
| Strengthen /ps prose only for --seo | Rejected | Prose MUST already exists and dogfood shows agents skip --seo anyway. |
| MCP humanize gate without piece frontmatter | Rejected | Session-only arg loses on resume and standalone /ps-humanize; dominated on must_durability. |
| Piece requires_seo + humanize owns hard gate | Rejected | Equal MUST but lower extensibility — second parallel boolean beside requires_research; operator chose the shared substrate as the long-term end state. |
| Always-on SEO in /ps (no flag) | Rejected | Fails opt_in_surface_ok; breaks dec-20260804 default SEO-free contract. |

**Evidence requirements:**
- Unit tests for draft and humanize reject/accept around preconditions
- Shared policy reader used by both save paths
- Skill text review for /ps chain and gated skills
- Dogfood: /ps --research and /ps --seo each show stage then gated next save

| One substrate API is used for both gates (not two unrelated boolean parsers) | Shared helper or piece field consulted by draft and humanize save paths | Single policy reader; both stages register completion checks against it |

## 4. Consequences

**Rollback plan:**
Triggers:
- Shared substrate blocks unmarked pieces or false-blocks targeted-research / no-seo defaults
- Abstraction churn delays both --research and --seo hard gates past useful dogfood window
- Humanize/export gates contradict dec-20260804 SEO-before-humanize or inject SEO content rules into humanize
Steps:
1. Revert substrate + skill flag wiring for --research and --seo
2. Restore prior soft-prose /ps behavior for both flags
3. If needed, fall back to two concrete piece booleans without shared helper
4. Revert docs/pipeline.md flag rows that claim hard gates
Blast radius: Piece policy schema; intake/orchestrator persistence; draft + humanize (+ optionally export) MCP validation; ps/ps-draft/ps-humanize skills and plugin mirrors; docs/pipeline.md; replaces mechanism of deprecated dec-20260809-3a372a15

**Refresh triggers:**
- Third opt-in stage wants a hard gate
- False blocks on unmarked or targeted-research pieces
- Export bypass of SEO/research preconditions in dogfood
- Change to brief/piece schema or research_mode / seo.md contracts

**Affected files:** cmd/pysar/assets/skills/ps/SKILL.md, plugins/pysar/skills/ps/SKILL.md, cmd/pysar/assets/skills/ps-draft/SKILL.md, plugins/pysar/skills/ps-draft/SKILL.md, cmd/pysar/assets/skills/ps-humanize/SKILL.md, plugins/pysar/skills/ps-humanize/SKILL.md, cmd/pysar/assets/skills/ps-intake/SKILL.md, plugins/pysar/skills/ps-intake/SKILL.md, docs/pipeline.md, internal/intake, internal/draft, internal/humanize, internal/mcpserver/tools_draft.go, internal/mcpserver/tools_humanize.go, internal/mcpserver/tools_intake.go
