# GoReleaser + GitHub Actions, tag-triggered

## 1. Problem Frame

**Signal:** Verified on disk: Pysar has no git remote at all (git remote -v returns empty -- purely local repo, never pushed anywhere), no README.md, no GitHub Actions workflows, no GoReleaser config, and no install script. The only distribution artifact is .pysar-repo-root/dist/ containing 3 manually-built binaries (linux-amd64, windows-amd64, windows-arm64, last built 2026-07-18/19) that are gitignored and NOT git-tracked -- purely local build leftovers, no macOS build despite the operator's own machine being macOS, no checksums, no version tagging. Operator wants an install experience for end users similar to /Users/malyshev/Projects/Me/haft's: verified haft ships install.sh (curl -fsSL <url>/install.sh | bash, OS/arch detection, downloads from GitHub Releases API, installs to ~/.local/bin or /usr/local/bin), backed by .goreleaser.yaml (cross-platform build + archive + checksum config) and .github/workflows/release.yml + install-test.yml (CI that builds and publishes releases on tag push, and tests the install script itself). None of this scaffolding exists for Pysar today -- this is a build-from-scratch synthesis problem, not a tweak.

**Constraints:**
- Must not push this local-only repo to any remote, or make any repo public, without a separate, explicit operator confirmation at that specific step -- creating a public release pipeline is a one-way-ish door (once released, hard to fully unpublish) distinct from and downstream of choosing HOW to distribute
- Must produce genuine working builds for the operator's own platform (macOS) at minimum -- current dist/ artifacts don't even cover it
- Must not require the end user to have Go toolchain installed -- a `go install` instruction alone does not satisfy "similar to haft", which explicitly targets people without a Go dev environment
- Whatever CI/release mechanism is chosen must be maintainable by this project's actual scale (single maintainer, no existing CI history) -- do not port haft's full pipeline complexity (goreleaser + multi-workflow CI + sidecar-runtime installs) uncritically when Pysar has no equivalent sidecar/runtime dependency to install

**Acceptance:** An end user on macOS, Linux, and Windows can install a working pysar binary onto their machine via one documented command, without having Go installed or building from source themselves, and pysar init works immediately after -- verified by actually running the chosen install method on a clean machine/container per platform (or at minimum macOS + Linux, given no Windows test environment is readily available this session) and confirming `pysar --version` and `pysar init` both work post-install.

## 2. Decision

**Selected:** GoReleaser + GitHub Actions, tag-triggered

**Selection policy:** Pre-declared policy (minimize initial_setup_cost first, tie-break platform_coverage, then per_release_maintainer_effort) mechanically selected V6, not V2. Operator's choice is an explicit, informed override of that mechanical outcome, made on the strength of release_process_integrity (structural CI test-gate vs. V6's documented-recipe-only gate) -- a dimension intentionally kept out of the ranking (Anti-Goodhart) specifically so it could be weighed by a human rather than silently optimized away or silently ignored.

**Why selected:** Operator explicitly chose V2 over the mechanically-dominant V6 (agentic on-request release), after being shown that V6 wins on every declared target dimension (setup cost, platform coverage, recurring effort) but scores worse on release_process_integrity -- an observation dimension by design, deliberately excluded from the automatic ranking so a human could weigh it consciously. V2 is also the variant verified to mirror haft's own real release mechanism most closely (confirmed by reading haft's actual .goreleaser.yaml and release.yml), stripped of haft-specific sidecar-runtime complexity (Elixir/OTP, Rust) that doesn't apply to Pysar's zero-CGO codebase.


**Invariants:**
- install.sh and the release pipeline never publish without an explicit, deliberate operator action (a version tag push) -- no automatic or scheduled releases
- The build job's CI dependency on the test job (needs: [test], or equivalent) is never removed or bypassed -- this is the exact property V2 was chosen over V6 for
- No sidecar runtime (Elixir/OTP, Rust) build steps are copied from haft -- Pysar has none and must not inherit that complexity
- Default GITHUB_TOKEN is sufficient -- no additional secrets/PATs are introduced unless a future decision explicitly requires one (e.g. a Homebrew tap)

## 3. Rationale

**Counterargument:** V6 (agentic on-request release) achieves the same low recurring effort V2 offers, without CI/YAML/secrets setup cost, and matches V2 on every other measured target dimension. The entire case for V2 over V6 rests on one unmeasured-by-domination-design dimension (structural vs. documented-recipe safety), which the operator is trusting matters more than V6's real, measured cost savings. If the structural gate rarely or never actually catches a real problem in practice, V2 will have cost more for a safety margin that goes largely unexercised -- this can't be known in advance, only verified after real usage.

**Selected variant weakest link:** Real one-time setup cost before the first release ships: writing and debugging .goreleaser.yaml and the release workflow correctly, with zero existing CI history on this project to fall back on if something misconfigures. Verified to be smaller than a naive haft-mirror would suggest (no CGO, no sidecar runtimes, single Linux runner suffices, default GITHUB_TOKEN is enough) -- but "smaller than expected" is not "zero," and the first green CI run is still unproven.

## 4. Consequences

**Rollback plan:**
Triggers:
- The first CI pipeline setup proves substantially harder or slower than expected, stalling the first real release for an extended period
- After several releases, the structural test-gate is observed to never actually catch a real problem, undermining the rationale for paying V2's higher setup cost over V6
- Release cadence or project circumstances change such that CI debugging/maintenance overhead becomes the bigger cost relative to V6's simplicity
Steps:
1. If CI setup stalls: fall back to V1 (manual release, same install.sh) to ship a first real release while continuing to debug CI in parallel -- reuse sol-20260805-75944e9e's already-compared V1 rather than re-exploring from scratch
2. If the structural gate proves not load-bearing in practice: revisit via a fresh /h-decide referencing V6 in the same portfolio -- do not silently switch mechanisms without recording why
Blast radius: New, purely additive distribution infrastructure: .goreleaser.yaml, .github/workflows/release.yml, install.sh, README.md. No existing code or shipped behavior changes -- nothing currently in use depends on this.

**Refresh triggers:**
- haft's own release pipeline changes materially (e.g. adds Windows support, changes runner strategy) -- worth re-checking whether Pysar's stripped-down copy should follow
- Pysar adds a CGO dependency (e.g. a future SQLite-backed memory feature) -- would break the 'single Linux runner cross-compiles everything' assumption this decision relies on
