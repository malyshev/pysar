# Schema-only engine, LLM-conversational elicitation on the agentic surface

## 1. Problem Frame

**Signal:** After pysar init, an author needs onboarding to establish at least two things: voice (how they want to sound) and writing style. Operator wants this built as a general-purpose questionnaire engine/mechanism -- an enabling-system architecture decision -- rather than a heap of hardcoded per-questionnaire scripts, so future questionnaires beyond these first two can be added without engine-level rework. This is developer-facing framing ("as a developer I want...") -- the question is HOW the engine is built, not WHETHER onboarding needs a questionnaire (operator has already decided that).

**Constraints:**
- Must fit the already-decided 5-layer architecture and the Go/Cobra stack -- no new language/runtime (dec-20260718-239680d4, dec-20260718-fd782668, dec-20260718-817bfb74)
- Must not force pipeline/phase vocabulary or a rigid-form feel onto the author surface -- answers should read as conversational (TS.environment-change.001 author-surface principle)
- Must compose with the already-decided on-disk manifest (dec-20260718-4b222794) for persistence -- no separate ad hoc storage format
- Medium/haft citations CL1 max, never sole justification, must name Pysar-original divergence (dec-20260718-eafefad2)
- One voice/style profile per project, no cross-project persona registry (dec-20260718-e84221af)

**Acceptance:** A mechanism is selected such that: (1) adding a new questionnaire (a third one, hypothetically) requires adding declarative content/data or a schema, not new engine code; (2) captured answers persist into the already-decided on-disk manifest structure (dec-20260718-4b222794), structured and queryable, not just prose notes; (3) the interaction can read as natural conversation on the author surface, not a rigid form, even though the underlying data model is structured.

## 2. Decision

**Selected:** Schema-only engine, LLM-conversational elicitation on the agentic surface

**Selection policy:** Pareto front over target-role dimensions (extensibility, conversational_fit, standalone_console_capability), declared before scoring; loc_estimate and new_files_per_questionnaire are observation-role, watched per the ProblemCard's own indicators, never optimized (Anti-Goodhart). Policy fixed at comparison time (sol-20260718-6066d57d), unchanged for this decision.

**Why selected:** V3 ties the front's best extensibility (5/5 -- new questionnaire = new schema struct + skill file, zero engine code touched) and matches the front's best conversational fit (5/5), at the lowest build cost of the three non-dominated options. This is also the variant structurally aligned with the product's own established identity: the agentic surface (ps-*/  /ps, run through a host AI agent) is Pysar's real interaction layer, not the thin console binary, which every prior decision this session has kept deliberately minimal (dec-20260718-817bfb74's no-wrapper-tool preference, dec-20260718-fe926229's manifest-only init). Building a scripted console Q&A runner now would invest real effort into the surface the product has consistently treated as secondary.


**Invariants:**
- The Go engine layer only defines schema and validation/completeness checks -- it never conducts the questionnaire conversation itself
- Captured voice/style profiles persist into the .pysar/project manifest structure, structured and queryable, never as prose-only notes
- Adding a new questionnaire requires a new schema struct plus a skill file -- never a change to shared engine code

## 3. Rationale

**Counterargument:** If a real fraction of users run pysar from a bare terminal without any host AI agent session, V3 leaves them completely blocked from onboarding -- not a degraded experience but a hard wall. This is a real, not hypothetical, cost being accepted here. V4 (the hybrid with a console-runner fallback) would have avoided this entirely at a bounded, known extra build cost; V3 defers that cost on the bet that bare-console onboarding is not a real near-term use case for this product.

**Selected variant weakest link:** Bare `pysar` invocation with no host agent session has no onboarding path at all -- the console binary can validate an already-filled schema but cannot conduct the questionnaire itself. This is V3's own stated weakest_link, not a new observation.

## 4. Consequences

**Rollback plan:**
Triggers:
- A real user attempts bare `pysar` onboarding with no host agent session and is blocked with no path forward
- Operator decides bare-console onboarding is a required use case before it is organically observed as a real gap
- Schema/skill drift causes captured profiles to fail validation in practice, suggesting the schema-only contract is insufficient
Steps:
1. Add V1's console-prompt runner as an additive fallback against the same schema -- this is this decision's own named stepping-stone basis, not a rewrite
2. If the schema itself proves wrong, revise the VoiceProfile/StyleProfile structs and their validators, not the skill-delegation architecture
3. If skill-prompt conversational quality proves the real bottleneck, iterate the skill content, not the Go schema layer
Blast radius: A new internal package (schema + completeness validator), the .pysar/project manifest schema (new fields for captured profiles), and new skill files that conduct the voice/style conversations on the agentic surface

**Affected files:** internal/onboarding/**, .pysar/project
