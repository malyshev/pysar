# Add list_&lt;kind&gt;_templates as a second MCP tool per template kind; amend dec-20260719-3e36577e prediction 3

## 1. Problem Frame

**Signal:** Decision dec-20260719-3e36577e needs re-evaluation: Prediction "listing stays a direct filesystem Glob+Read, no new list_voice_templates/apply_voice_template tool required" was falsified: list_voice_templates/list_style_templates were added (internal/mcpserver/tools_voice.go, tools_style.go) because Glob can't expand ~ and triggered an unwanted permission prompt -- a real constraint not foreseen at decide time. The rest of the decision (Pysar-owned ~/.pysar/templates/<kind>/, one file per template, MCP-mediated writes) still holds and is unaffected; only the listing-mechanism sub-claim needs re-deciding now that the actual constraint is known.

## 2. Decision

**Selected:** Add list_&lt;kind&gt;_templates as a second MCP tool per template kind; amend dec-20260719-3e36577e prediction 3

**Selection policy:** Not a scored multi-variant comparison -- the fix path was pre-declared by dec-20260719-3e36577e's own rollback plan step 3 ('if a list/apply tool proves necessary, add it without invalidating V1'). Selection criterion applied: implement the minimal fix that satisfies the missing constraint (server-side path resolution, since Glob cannot expand '~') without reopening the original V1-vs-V2 comparison, because the discovered constraint is orthogonal to the constraints that decided V1 over V2 at the time (cross_project_availability, confirm_before_apply_preserved).

**Why selected:** Glob(~/.pysar/templates/&lt;kind&gt;/*) cannot expand '~' inside the MCP tool sandbox and fell back to a raw Bash `ls`, triggering the exact unwanted permission prompt this project has fought to eliminate (real Claude Code session, SKILL.md Step 1a). This is exactly the scenario dec-20260719-3e36577e's own rollback plan (step 3) pre-authorized: 'If a list/apply tool turns out necessary after all: add it -- this doesn't invalidate V1, it just narrows the gap with V2 on new_mcp_surface, an observation dimension that was never meant to be optimized directly.' list_voice_templates was implemented and tested (internal/mcpserver/tools_voice.go, TestListVoiceTemplates* suite), sidesteps path expansion server-side (the server already knows homeDir) and returns full content inline so the skill never needs a second per-template Read either, then was mirrored for Style (list_style_templates) when the same Glob-tilde constraint applied there too. This decision formally ratifies that already-shipped fix and corrects prediction 3's threshold from 'exactly one new tool' to 'two new tools per template kind (save_X_template, list_X_templates)', so the parent decision's prediction record matches reality instead of sitting permanently falsified.


**Invariants:**
- Listing available templates never bypasses /ps-voice's or /ps-style's confirm-before-save step -- list_<kind>_templates only returns candidates for the author to review, applying one still requires explicit confirmation before .pysar/<kind>.md is written
- Every template kind gets exactly two MCP tools: save_<kind>_template and list_<kind>_templates -- no kind grows a third (e.g. a separate apply_<kind>_template) without its own decision

## 3. Rationale

**Counterargument:** The strongest argument against ratifying this via a narrow amendment rather than reopening the full V1-vs-V2 comparison: the new_mcp_surface dimension that helped select V1 over V2 has now degraded from V1's predicted 1 to 4 (across two kinds), while V2 needed 3. Had this constraint been known at original decide time, V2's tool-count disadvantage would have looked much smaller, possibly comparable. Re-litigating the comparison now, after V1 is already implemented, risks motivated reasoning to protect the earlier choice rather than honestly re-scoring it -- this decision does not re-run that comparison, it only documents the gap for the future trigger (a third template kind) already named in the rollback plan.

**Selected variant weakest link:** new_mcp_surface (the observation dimension from the original V1-vs-V2 comparison) has grown from V1's predicted 1 to 4 total across two kinds (save_voice_template, list_voice_templates, save_style_template, list_style_templates) -- narrowing V1's stated tool-count advantage over rejected V2 (which needed 3). V1 still wins that dimension, but a third template kind would erode the gap further and is worth revisiting V2 at that point.

**Rejected alternatives:**
| Variant | Verdict | Reason |
|---------|---------|--------|
| Add list_&lt;kind&gt;_templates as a second MCP tool per template kind; amend dec-20260719-3e36577e prediction 3 | **Selected** | Glob(~/.pysar/templates/&lt;kind&gt;/*) cannot expand '~'... |
| Have the skill call Glob with a manually-resolved absolute path (e.g. via a separate tool that returns homeDir), then Read each matched template file individually | Rejected | Still requires adding new MCP surface (a homeDir-resolving tool) so it does not preserve V1's original 1-tool advantage either; also costs N+1 round trips per listing (one Glob-equivalent call plus one Read per template) versus list_voice_templates' single call returning all content inline -- strictly worse on both the dimension this was meant to protect and on latency. |

**Predictions:**
| Claim | Observable | Threshold |
|-------|------------|-----------|
| No template kind beyond Voice and Style needs a tool count higher than 2 (save + list) without a new decision authorizing it | Count MCP tools registered per template kind in internal/mcpserver after any future template-kind addition | Each kind has exactly 2 template-related tools (save_X_template, list_X_template) unless a dedicated decision records why a third was needed |

## 4. Consequences

**Rollback plan:**
Triggers:
- A third template kind requires yet another new tool beyond save/list, suggesting the per-kind MCP-tool pattern doesn't scale
- Two tools per kind times N kinds becomes enough total MCP surface that operators or hosts start hitting tool-list-length friction
Steps:
1. If a third kind needs more than save/list: reopen and reconsider V2's single-registry-file shape from the original comparison, which centralizes tool surface instead of multiplying it per kind
2. If total tool count becomes a real problem: consolidate the list_<kind>_templates variants into one generic list_templates(kind) tool
Blast radius: internal/mcpserver/tools_voice.go, internal/mcpserver/tools_style.go, any future tools_<kind>.go

**Affected files:** internal/mcpserver/tools_voice.go, internal/mcpserver/tools_style.go, cmd/pysar/assets/claude/skills/ps-voice/SKILL.md, cmd/pysar/assets/claude/skills/ps-style/SKILL.md
