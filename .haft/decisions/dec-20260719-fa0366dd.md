# Pysar MCP server (pysar serve) with real schema-aware persistence tools

## 1. Problem Frame

**Signal:** Decision dec-20260719-57b52733 needs re-evaluation: Named rollback trigger fired: three independent real permission-prompt failures observed after implementing this decision (Write/Edit rule-name mismatch, uncovered Bash gate, file-creation-vs-edit gate), each discovered only via live testing, not predictable in advance. This is a pattern across multiple independent Claude Code permission surfaces, not a single fixable bug -- matches the rollback plan's own escalation trigger toward V2 (Pysar MCP server). Per this decision's own rollback plan, the next step is reusing sol-20260719-a6e09400 (already contains the fully-specified V2 variant) via a new /h-decide, not re-exploring from scratch.

## 2. Decision

**Selected:** Pysar MCP server (pysar serve) with real schema-aware persistence tools

**Selection policy:** Pareto front over target-role dimensions (prompt_friction, maintenance_cost, verified_confidence, validation_rigor) from sol-20260719-a6e09400, declared before scoring; new_components observation-role, never optimized. Reused per this decision's own prior rollback plan rather than re-scored: the original scoring assumed no observed failures for V4 (verified_confidence 5) and no build for V2 (verified_confidence 2) -- real evidence has since inverted the practical confidence ordering (V4 now has three confirmed live failures; V2's core mechanism, MCP tool calls, is independently proven reliable in this same repo), which is why this reopened decision revisits the front's own recommendation rather than treating it as re-litigating settled math.

**Why selected:** V2's own named rollback trigger fired three times with real evidence (evid-20260719-500316000, verdict refutes): Write/Edit rule-name mismatch, an uncovered Bash permission gate, and a file-creation-vs-edit gate -- each a genuinely independent Claude Code permission surface, none predictable from documentation, each only discoverable through live testing. This is not one bug to patch; it is a structural property of the client-side Write/Edit-tool path that every future ps-* skill would independently inherit. V2 collapses all of these into a single surface -- "may Claude call this MCP tool" -- which this exact session's own haft MCP tool usage has already proven reliable (zero prompts, zero edge cases, across the entire session). V2 also closes the validation-rigor gap V4 never addressed: a real Go Validate() call server-side, not an LLM self-check.


**Invariants:**
- pysar serve ships inside the same pysar binary as a subcommand -- never a separate install (dec-20260718-239680d4 single-binary constraint)
- MCP tools call the real Go Validate() function -- completeness checking is never re-implemented as a second, divergent LLM-only check
- Once pysar serve ships, ps-* skills call its MCP tools for persistence -- never raw Write/Edit for .pysar/** content

## 3. Rationale

**Counterargument:** Nothing about pysar serve has been built or live-tested yet. The pattern that justified reopening this decision -- Claude Code's permission model having more independent, undocumented layers than assumed -- is itself a reason for caution here, not just for V4: assuming the MCP tool-call surface is fully safe based on haft's own behavior in this repo, without directly live-testing pysar serve's own tool calls once built, would repeat the exact mistake that cost three rounds of rework on V4 (trusting reasoning over live verification). This decision's own predictions are written to force that live verification before declaring success, not to assume it.

**Selected variant weakest link:** Real, ongoing engineering investment: a new subcommand, an MCP tool surface to design and maintain, and the server itself still needs its own permission allowlist entry (mcp__pysar__*) to avoid prompting -- this decision does not eliminate the permission question in the abstract, it moves it to a surface already proven reliable in this repo. This is V2's own stated weakest_link in the portfolio, not a new observation.

## 4. Consequences

**Rollback plan:**
Triggers:
- The MCP server itself is found to have its own undiscovered permission-prompt or reliability quirks once actually implemented and live-tested (the same live-testing-required lesson V4 just taught, applied to V2)
- Build/maintenance cost of pysar serve proves substantially higher than anticipated relative to the problem it solves
- A future Claude Code version changes MCP tool permission semantics in a way that reintroduces friction on the mcp__pysar__* surface
Steps:
1. If pysar serve has its own live-discovered permission quirks: fix iteratively -- the underlying pattern (mcp__pysar__* tool-name allowlisting) is independently proven sound via haft's own usage in this repo even if a specific tool's exposure needs adjustment
2. If cost proves prohibitive: reopen this decision, but note V4's three confirmed failures make a plain revert to client-side Write/Edit a worse fallback than persisting with and fixing V2
3. If Claude Code changes MCP permission semantics: re-verify via a fresh /h-verify pass, same discipline as any other decision
Blast radius: A new pysar serve subcommand and its MCP tool surface (new internal package), ps-voice (and future ps-*) skill content rewritten to call MCP tools instead of raw Write/Edit, .mcp.json scaffolding so a pysar-init'd project auto-connects to the local server, and the permission allowlist shifting from Edit(.pysar/**) to mcp__pysar__* tool names

**Affected files:** cmd/pysar/**, internal/mcpserver/**, cmd/pysar/assets/claude/**
