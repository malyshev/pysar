# Precondition-driven generic /ps-onboard, reusing the Pass mechanism

## 1. Problem Frame

**Signal:** Operator proposes /ps-onboard as an orchestrator command invoking /ps-voice and /ps-style separately, motivated by wanting voice/style independently re-tunable later, not just once at init. This is the first concrete command-surface design for the schema-only onboarding engine (dec-20260718-5570376d) and must use the ps-* naming convention (dec-20260718-a2a24f32, which explicitly left the actual command list open -- "No command list is being decided here"). Must also consider whether a bespoke orchestrator duplicates the Pass/Precondition pipeline mechanism currently being rebuilt (dec-20260718-20a08f83, dec-20260718-ffbfb04b) for tracking "what's done, what's needed" rather than reusing it.

**Constraints:**
- Must use ps-* subcommand / /ps auto-mode naming convention (dec-20260718-a2a24f32); this stays on the agentic surface, no console pysar binary involvement, per dec-20260718-5570376d
- Go engine layer stays schema+validation only -- these are skill/prompt-level commands, not new Go engine code, per dec-20260718-5570376d's own invariant
- Should not duplicate the Pass/Precondition mechanism (dec-20260718-20a08f83, dec-20260718-ffbfb04b) with a parallel bespoke 'is onboarding done' tracker if that mechanism can express it directly
- One voice/style profile per project, no cross-project registry (dec-20260718-e84221af)

**Acceptance:** A command architecture is selected such that: (1) an author can run one command to complete first-time onboarding (voice + style) in one go; (2) an author can also independently re-invoke voice tuning or style tuning alone at any later time, without re-running the other; (3) the mechanism for knowing "what's already set up" does not duplicate the Pass/Precondition tracking mechanism if that mechanism can express it directly.

## 2. Decision

**Selected:** Precondition-driven generic /ps-onboard, reusing the Pass mechanism

**Selection policy:** Pareto front over target-role dimensions (bundled_onboarding_support, independent_reinvocation, mechanism_reuse, buildable_now), declared before scoring; command_file_count is observation-role, watched per the ProblemCard's own indicator, never optimized (Anti-Goodhart). Policy fixed at comparison time (sol-20260718-0b87ee83), unchanged for this decision.

**Why selected:** V4 is the only Pareto-front member satisfying all three acceptance criteria at once: full bundled first-time onboarding (2/2), best independent re-invocation (5/5), and best mechanism reuse (5/5, no hand-built completeness tracker duplicating the Precondition mechanism). Operator explicitly rejected the alternative sequencing (ship V1's hardcoded orchestrator now, migrate to V4 later) on the grounds that Medium already represents the hardcoded-POC phase Pysar is meant to evolve past -- shipping V1 as a stopgap would mean building a second hardcoded tool that itself needs future evolution, repeating that pattern one layer down rather than moving past it (note-20260718-c6b7cd72). Build order: rebuild internal/editorial's Pass/Precondition mechanism first (already decided via dec-20260718-20a08f83 and dec-20260718-ffbfb04b, currently AT RISK only because its code was wiped, not because the design is wrong), then build onboarding directly against it -- no throwaway intermediate implementation.


**Invariants:**
- Voice and style are registered as Passes in the same registry as editorial passes -- never a bespoke onboarding-only orchestration mechanism
- /ps-onboard contains no hardcoded knowledge of specific questionnaire names -- it discovers outstanding Passes generically via their Precondition
- /ps-voice and /ps-style remain independently invocable commands, not hidden behind /ps-onboard
- No onboarding implementation work begins before the internal/editorial Pass/Precondition rebuild lands -- this decision's whole premise is not building a throwaway intermediate

## 3. Rationale

**Counterargument:** This decision delays shipping any onboarding capability until the internal/editorial rebuild lands -- a real time cost with zero interim capability, unlike V1 which could ship today. There is also a real risk the Pass/Precondition abstraction, designed for editorial content transforms, does not cleanly fit a schema-only questionnaire-completeness check once actually implemented -- if so, onboarding would be blocked on a dependency not designed with its needs in mind, and the "no throwaway work" premise of this decision could be undermined by an awkward forced fit instead.

**Selected variant weakest link:** buildable_now scored 0 -- this variant cannot be built today. It requires the AT-RISK Pass/Precondition rebuild (dec-20260718-20a08f83, dec-20260718-ffbfb04b) to land first. This is V4's own stated weakest_link, accepted explicitly rather than worked around with a stopgap.

## 4. Consequences

**Rollback plan:**
Triggers:
- The internal/editorial rebuild stalls or is deprioritized for an extended period, leaving onboarding with no path to ship at all
- Once rebuilt, the Pass/Precondition abstraction proves a poor fit for schema-only questionnaire completeness (e.g. its semantics assume content transforms, not profile-field completeness), requiring an awkward forced fit
- Operator decides shipping some onboarding capability sooner is worth accepting V1's hand-built sequencing as a real, permanent implementation rather than a stopgap
Steps:
1. If the rebuild stalls: reopen this decision via haft_refresh(action="reopen") and reconsider V1 as the real implementation, explicitly recorded as superseding this decision, not silently reverted to
2. If Precondition semantics don't fit onboarding cleanly: adapt or extend the Pass interface itself (e.g. a lighter-weight completeness-check variant) rather than forcing an awkward fit, reusing sol-20260718-0b87ee83 via a new /h-decide if the mismatch is significant
3. If faster shipping becomes the priority: explicitly choose to build V1 for real via a new /h-decide superseding this one, rather than silently building a stopgap under this decision's name
Blast radius: New ps-onboard/ps-voice/ps-style skill files, the rebuilt internal/editorial Pass registry, and the internal/onboarding schema package (dec-20260718-5570376d)
