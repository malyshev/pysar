# Write intake artifacts now, to a clearly-marked provisional location (not deferred pending prob-20260718-f6ac8127)

## 1. Problem Frame

**Signal:** Reframe of prob-20260725-53b2d8ea (deprecated) after discussion resolved how intake should handle sparse or broad input. The prior frame treated 'how does the agent force correct understanding of the idea' as an open multi-variant design question, including an explicit confirmation-gate as one candidate. That was wrong on two counts, established through concrete test cases with the operator: (1) audience/register/depth are not intake's judgment call at all -- Pysar already has this answer on file the moment an author has run /ps-voice or /ps-style: the same input 'write something about AI' means a plain-language explainer for a general audience if the profile says so, a peer-technical piece if the profile says the author is a cybersecurity practitioner, and a child-appropriate piece if the profile says the author writes for kids. Guessing generic-broad-default when a profile already answers the question is itself a misread. (2) A blocking clarification question is not the right response to merely broad or vague input ('I want water' does not require 'still, sparkling, cold, or with lemon' -- bring water; correction after the fact is cheap, interrogating up front is not). It IS the right response to genuinely degenerate input the operator explicitly called 'absolutely stupid' -- input with no extractable semantic content at all (gibberish, a stray word, explicitly self-contradictory instructions) where even a profile-informed guess has nothing to anchor to.

**Constraints:**
- Audience/register/depth defaults are read from the author's existing voice/style profile (.pysar/voice.md, .pysar/style.md) when one exists -- intake never asks 'who is this for' and never silently substitutes a generic-public default when a profile already answers it. This is an invariant, not a comparison axis.
- A blocking clarification question fires ONLY for input with no extractable semantic content even combined with the profile (empty/gibberish/single stray word) or input containing explicitly self-contradictory instructions (the operator's own words demand two incompatible things). Broad, vague, or topic-only input is NOT grounds for a question -- it gets the most likely default, stated declaratively, non-blocking. This replaces the prior frame's 'confirm if ambiguous' axis entirely.
- When no voice/style profile exists yet (author hasn't onboarded), intake still must not block-and-interrogate -- falls back to the broadest generalist default (general-audience explainer register), stated declaratively, same as any other resolvable default.
- Topic-scope-within-domain (e.g. 'more secure' naming a domain but not a specific angle within it) is resolved by picking the single most likely angle -- informed by the profile's stated expertise/topic-family if present, and by prior pieces via the memory engine (dec-20260718-404573a2) if queryable at intake time to avoid re-pitching an already-covered angle -- stated as an assumption, never asked.
- Must plug into dec-20260718-20a08f83's precondition-guarded pass mechanism as its own pass (produced-artifact state as ArtifactKind refs, own Precondition check) and append to dec-20260718-6ba897d4's run-log on a successful run -- real wiring, not a stub.
- No author registry, --author flag, or per-author resolution -- prob-20260718-97b5a2a3 already excludes the multi-author model from scope.
- No fixed/operator-supplied word-count cap on the brief -- length follows from the idea's actual complexity, not a --length=N ceiling.
- Storage location/topology for the produced artifacts is governed by prob-20260718-f6ac8127, still ACTIVE and UNDECIDED -- this remains a genuinely open dependency for exploration to take an explicit position on, not something to silently assume.
- a prior writing POC ([prior-writing-POC]/.cursor/commands/w-intake.md + .cursor/skills/article-intake/SKILL.md) is CL1-capped inspiration per dec-20260718-eafefad2's reference-agnosticism gate -- its content-contract shape (brief/outline/angles/sources-stub) and its single restate-the-stake step are legitimate to port; its author-registry coupling and fixed --length flag are the two named, deliberate divergences.
- No web search / synthesized research at intake time, mirroring the POC's own INTAKE-phase rule -- matches Pysar's already-stated author-practitioner-voice priority.

**Acceptance:** A ProblemCard + SolutionPortfolio exist such that the operator can /h-compare and /h-decide among variants that differ ONLY on the axes that are genuinely still open: (A) storage-topology stance given prob-20260718-f6ac8127 is undecided (write to a provisional, clearly-marked location now vs. defer writing until that problem resolves), and (B) how much of the profile-derived assumption (audience, register, chosen topic-scope) gets surfaced back to the operator in the restatement -- fully stated for transparency vs. minimal/implicit since the author already knows their own profile. Audience-resolution-from-profile and ask-only-when-degenerate are INVARIANTS in every variant, not points of comparison. Each variant states its weakest_link.

## 2. Decision

**Selected:** Write intake artifacts now, to a clearly-marked provisional location (not deferred pending prob-20260718-f6ac8127)

**Selection policy:** Single binary fork (write-now-provisional vs. defer-until-storage-decided), already fully characterized in conversation with both trade-offs stated before the operator chose -- not a multi-variant Pareto comparison, since only two live values existed on this one axis and everything else in the design had already collapsed to invariants during framing. Operator chose directly per the Quick Decision Framework's inline path; formal portfolio ceremony was explicitly offered and declined as unnecessary for an already-characterized binary choice.

**Why selected:** Operator chose directly given the fully-characterized binary trade-off: durable output on day one beats shipping a command that persists nothing until an unrelated architecture decision (prob-20260718-f6ac8127, on-disk piece/project structure) lands. The cost of being wrong is bounded -- intake's content contract is already de-risked by years of real POC operation, and the storage location is explicitly marked provisional in code/docs, so the exposure is a migration pass, not a redesign. This decision also binds the full /ps-intake v1 shape that emerged through framing discussion (prob-20260725-747fcd29's constraints): audience/register/depth read from the author's existing voice/style profile rather than asked or generically defaulted; a blocking clarification question reserved for genuinely degenerate input (no extractable semantic content, or explicit self-contradiction) rather than merely broad/vague input; content contract adapted from a prior writing POC (brief/outline/angles/sources-stub) with Author fields and the --length=N cap removed; real wiring into dec-20260718-20a08f83's Precondition mechanism and dec-20260718-6ba897d4's run-log as intake's own pass.


**Invariants:**
- Audience/register/depth are read from the author's existing voice/style profile when one exists -- intake never asks 'who is this for' and never substitutes a generic-public default when a profile already answers it
- When no profile exists yet, falls back to the broadest generalist default (general-audience register), stated declaratively, never by asking
- A blocking clarification question fires only for input with no extractable semantic content (gibberish, empty, a single stray word) or explicitly self-contradictory instructions -- broad or vague-but-resolvable input always gets a stated best-guess default instead, non-blocking
- Every restatement is one concise line covering audience, register, and chosen topic-scope -- always shown, never expanded into a confirmation question, never omitted
- Content contract mirrors a prior writing POC brief/outline/angles/sources-stub shape with Author/Author-name fields removed and --length=N removed entirely -- no fixed word-count cap
- Intake is implemented as its own pass with its own Precondition check under dec-20260718-20a08f83's mechanism, and appends a structured entry to the run-log per dec-20260718-6ba897d4 on every successful run
- The provisional storage location is explicitly marked as provisional in code and docs, not presented as final, so a future migration under prob-20260718-f6ac8127 is expected, not a surprise
- No author registry, --author flag, or per-author resolution of any kind

## 3. Rationale

**Counterargument:** The strongest case against this: writing now commits real bytes to a location that prob-20260718-f6ac8127 might resolve completely differently -- not just a different path, but potentially a different topology entirely (e.g. monorepo pieces/ vs. one-dir-per-piece). Every piece scaffolded via intake before that problem resolves needs a migration pass, and if intake sees real usage in the meantime, that migration touches real author data, not just code. The rejected alternative (defer writing) would have avoided this risk entirely, at the cost of delivering no durable artifact in the meantime -- which is exactly what the operator judged not worth the wait.

**Selected variant weakest link:** The provisional location is a real, unreviewed guess at file layout made without prob-20260718-f6ac8127's own comparison discipline behind it. If that problem's eventual decision picks a fundamentally different topology rather than just a different path, every piece scaffolded via intake in the meantime needs a real migration, not a mechanical rename.
