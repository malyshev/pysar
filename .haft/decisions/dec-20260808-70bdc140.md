# Composite gate: conventional-commit check AND already-published skip

## 1. Problem Frame

**Signal:** Observed 2026-08-08: force-pushing rewritten tag v0.1.0 (author email chore only — no product code change) re-triggered .github/workflows/release.yml; GoReleaser failed with GitHub 422 already_exists on every release asset (release-id 366204459). Current pipeline treats every tags:v* push as a full publish. Existing decision dec-20260805-db745b4a requires an explicit tag push as the deliberate publish action, but has no second gate for whether that push represents a product-worthy change (feat/fix) vs history/metadata chore, and no idempotency when the GitHub Release for that tag already has assets.

**Constraints:**
- Preserve dec-20260805-db745b4a invariant: no scheduled/automatic releases without an explicit deliberate operator action (tag push or equally explicit equivalent)
- Must not remove the CI test job gate before build/publish (needs: [test])
- Default GITHUB_TOKEN remains sufficient — no new PATs/secrets unless a later decision requires them
- Single-maintainer scale: no heavy release-it/semantic-release Node toolchain unless it clearly earns its keep vs a small workflow gate

**Acceptance:** A tag push that does not introduce any conventional-commit feat|feature|fix since the previous version tag exits the release workflow green without creating or mutating GitHub Release assets; a tag push that does include at least one such commit still publishes a complete cross-platform release as today; re-push of an already-published tag does not fail CI with 422 already_exists.

## 2. Decision

**Selected:** Composite gate: conventional-commit check AND already-published skip

**Selection policy:** Cover both observed failure modes (retag 422 and chore-should-not-ship) while preserving dec-20260805-db745b4a explicit tag-push publish action and Go-only/GITHUB_TOKEN release path; prefer the smallest workflow change that satisfies both gates over adopting a Node release driver or overwrite-on-retag.

**Why selected:** Operator explicitly bound V5. It pairs an already-published asset skip (fixes today's force-push 422) with a conventional-commit feat|feature|fix gate since the previous version tag (release-it semantics without release-it), and keeps forced republish as an explicit opt-in path rather than silent overwrite.


**Invariants:**
- Tag push remains the deliberate publish action — no scheduled or push-to-master auto-releases
- If a GitHub Release for the pushed tag already has the expected archive assets, the workflow exits green without mutating those assets (unless an explicit force-republish path is invoked)
- If the tag is new (no existing assets) and git log previous_tag..HEAD contains no conventional feat|feature|fix commit, the workflow exits green without creating a GitHub Release
- CI test job remains a hard dependency of publish (needs: [test] or equivalent) whenever publish runs
- Default GITHUB_TOKEN remains sufficient — no new PATs/secrets
- Forced republish is only via an explicit opt-in path (e.g. workflow_dispatch force input), never the default on tag push

**Pre-conditions:**
- [ ] ProblemCard prob-20260808-3b1c09bf and portfolio sol-20260808-8edc9e01 exist
- [ ] dec-20260805-db745b4a remains the base distribution mechanism (GoReleaser + GHA); this decision refines its trigger gates, does not replace GoReleaser

**Post-conditions:**
- [ ] .github/workflows/release.yml implements both preflight gates before GoReleaser publish
- [ ] Force-republish path is documented in the workflow (input or equivalent) and is not the default
- [ ] A green skip path produces no new/changed Release assets

**Admissibility:**
- NOT: Silent overwrite of existing release assets on ordinary tag push
- NOT: Node release-it/semantic-release as a required publish driver
- NOT: Removing the test gate before publish
- NOT: Failing CI red on chore-only or already-published skips — skip must be green success

## 3. Rationale

**Counterargument:** V2 alone would stop the bleeding on retags with less policy surface, and today's incident was a retag not a chore-only new tag — paying for a conventional-commit gate now may block the next intentional release before the commit-message practice exists.

**Selected variant weakest link:** Existing commit subjects are not consistently conventional; until feat:/fix: discipline is adopted for shippable work, intentional new tags may be skipped green incorrectly — or the gate regex may be loosened until the vocabulary is real, weakening the chore filter.

**Rejected alternatives:**
| Variant | Verdict | Reason |
|---------|---------|--------|
| Composite gate: conventional-commit check AND already-published skip | **Selected** | Operator explicitly bound V5. It pairs an already-publish... |
| Conventional-commit gate before GoReleaser (feat\|feature\|fix since previous tag) | Rejected | Does not fix the observed 422 on force-push of an already-published tag; incomplete against the acceptance criteria. |
| Idempotent skip when GitHub Release assets already exist for this tag | Rejected | Fixes retag/422 but leaves chore-only NEW tags able to publish a full release — misses the operator's release-it intent. |
| GoReleaser replace_existing_artifacts on re-upload | Rejected | Turns accidental chore retags into successful overwrites; increases false-publish instead of reducing it. |
| Adopt release-it / semantic-release as the version+publish driver | Rejected | Conflicts with the explicit tag-push invariant of dec-20260805-db745b4a and adds a Node toolchain to a Go-only release path for single-maintainer scale. |

**Evidence requirements:**
- CI run log showing green skip on already-published tag
- CI run log showing green skip on chore-only new tag
- CI run log showing successful GoReleaser publish on feat/fix new tag

**Predictions:**
| Claim | Observable | Threshold |
|-------|------------|-----------|
| Force-pushing an already-published tag with existing assets exits the release workflow green without 422 and without changing Release assets | Re-push v0.1.0 (or equivalent already-published tag) after the gate lands and inspect the Actions run + Release asset list/timestamps | Workflow conclusion success; asset set unchanged unless force republish was explicitly requested |
| Pushing a new tag whose previous_tag..HEAD range has only chore/docs/style (no feat\|feature\|fix) skips publish green and creates no GitHub Release | Push a disposable test tag on a chore-only tip (or simulated range) and inspect Actions + Releases API | Workflow success; no new Release for that tag |
| Pushing a new tag with at least one feat\|fix conventional commit still publishes a full cross-platform release as today | Next intentional product tag using feat: or fix: subject; inspect Release assets | Archives for declared GOOS/GOARCH plus checksums.txt present on the GitHub Release |

## 4. Consequences

**Rollback plan:**
Triggers:
- Gate incorrectly skips an intentional product release more than once
- Already-published check false-positives and blocks a needed first publish for a tag
- Workflow complexity causes repeated CI misconfiguration
Steps:
1. Revert .github/workflows/release.yml gate jobs/steps to pre-decision tag→test→goreleaser flow
2. If replace_existing_artifacts was added only for force path, remove it
3. Keep dec-20260805-db745b4a base mechanism intact
Blast radius: Release CI workflow only; no product code; install.sh consumers unaffected if skips are silent-success

**Refresh triggers:**
- First intentional release blocked incorrectly by the conventional-commit regex
- Need to force-republish becomes common enough that the opt-in path is painful
- Project adopts full conventional-commit automation (changelog/version bump) and outgrows the thin gate

**Affected files:** .github/workflows/release.yml, .goreleaser.yaml
