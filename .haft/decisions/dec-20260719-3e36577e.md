# Pysar-owned global directory, one file per template, MCP-mediated writes

## 1. Problem Frame

**Signal:** No template mechanism exists in Pysar today (confirmed by code search: only unrelated "template" hits like claudeMDTemplate and haft's own artifacts). Operator ran /ps-voice in a real test project, reviewed the resulting profile, wants to name it "Measured plain English -- speakable, understated, general audience" and ship it as Pysar's built-in "generic" voice default -- using the same underlying mechanism that will later let any author save their own completed profile as a named, reusable template across projects (operator explicitly chose this scope over a built-in-only or author-only variant).

**Constraints:**
- Single static binary distribution (dec-20260718-239680d4): the built-in template ships embedded in the binary, no network fetch or separate install step
- Author-saved templates must survive across projects, so they cannot live in a single project's .pysar/ -- needs a cross-project location, same class of problem already solved once for skills (dec-20260718-a2a24f32 / global ~/.claude/skills), not necessarily the same location
- Applying a template is a starting point for the /ps-voice conversation, never a silent bypass of its existing confirm-before-save step (SKILL.md Step 4) -- an author must still see and confirm the profile before it's written to .pysar/voice.md
- Must not silently overwrite an existing .pysar/voice.md the way /ps-voice already refuses to (SKILL.md Step 1 re-tune flow)
- This is the first of what the operator has already signaled will repeat for Style (pending task #11) -- the mechanism shouldn't be so voice-specific that reusing it for a second profile kind requires a rewrite, but must not be built as a speculative generic system before a second real use case exists (YAGNI vs premature reuse tension worth naming, not resolving by default)

**Acceptance:** A named voice template -- starting with the shipped "generic" one -- can be offered by /ps-voice as an explicit starting point instead of a blank conversation, the author can accept-as-is or edit before saving, and the same storage/retrieval mechanism lets an author save any completed .pysar/voice.md as a new named template usable in a later project; verified with unit tests plus a real-binary smoke test per this project's standing discipline.

## 2. Decision

**Selected:** Pysar-owned global directory, one file per template, MCP-mediated writes

**Selection policy:** Pareto front over target-role dimensions (host_independence, migration_cost_to_new_host), gated by both constraints (cross_project_availability, confirm_before_apply_preserved) which must hold true; new_mcp_surface is observation-role, watched but never optimized (Anti-Goodhart). Declared before scoring (sol-20260719-dbc14bba).

**Why selected:** V1 and V2 tied on every scored dimension (host_independence 5/5, migration_cost_to_new_host 1/1, both constraints satisfied), so the choice comes down to judgment: V1 reuses dec-20260719-25712417's already-shipped, already-tested per-file content-hash refresh mechanism verbatim for the built-in default -- zero new staleness-tracking design. It also fits this project's established preference for filesystem-native, human-readable artifacts over opaque blobs (the same reasoning that already moved voice.md from JSON to Markdown+YAML earlier this session), and avoids V2's growing concurrency/diff-ability risk as more template kinds (Style, pending task #11) would share one registry file.


**Invariants:**
- Applying a template never bypasses /ps-voice's existing confirm-before-save step -- it only seeds the conversation with a starting draft; the author must still explicitly confirm before .pysar/voice.md is written
- The global template directory (~/.pysar/templates/) and its access pattern have no dependency on any single host's own config convention -- must work unchanged once Cursor/Codex (dec-20260718-8278c494) ship
- The built-in generic template's content is embedded in the pysar binary itself (go:embed), never fetched over the network at runtime

## 3. Rationale

**Counterargument:** V1 and V2 are a formal tie on every scored dimension -- this decision rests entirely on judgment, not measurement, and could plausibly have gone the other way on a different day. More fundamentally: committing to a dedicated ~/.pysar/ host-agnostic home directory is architecture being built for future use cases (Style templates, a possible future memory engine per prob-20260718-0973a207/prob-20260718-4e1bda1b) that do not exist yet -- exactly the YAGNI-vs-premature-reuse tension the ProblemCard's own constraints named without resolving. If Style templates never materialize and no memory engine ships, this directory was scaffolding for a future that didn't arrive.

**Selected variant weakest link:** Requires operators to trust yet another dotfile-style directory under their home (~/.pysar/templates/) -- one more place pysar writes to, which needs its own documentation/discoverability the moment an author asks "where did this template come from." This was V1's own stated weakest_link at exploration time.

## 4. Consequences

**Rollback plan:**
Triggers:
- The ~/.pysar/templates/ directory convention causes real operator confusion (support burden, confused bug reports about 'where did this file come from') disproportionate to the feature's value
- Style templates (pending task #11) or any second template kind never materialize, leaving this as speculative architecture that never earns its cost
- The single save_voice_template MCP tool proves insufficient in practice and a list/apply tool ends up needed anyway, undermining the '1 new tool' rationale that helped select V1 over V2
- Cross-project template sharing turns out to need conflict resolution (same name saved differently in two projects) that a flat one-file-per-template directory can't express cleanly
Steps:
1. If the directory convention itself is the problem: reconsider the location (e.g. move under an existing better-known convention) without changing the one-file-per-template shape
2. If a second template kind never ships: leave the mechanism as-is for the one built-in default; no need to unwind anything since it costs nothing sitting idle
3. If a list/apply tool turns out necessary after all: add it -- this doesn't invalidate V1, it just narrows the gap with V2 on new_mcp_surface, an observation dimension that was never meant to be optimized directly
4. If cross-project naming conflicts become real: revisit this decision and reconsider V2's single-registry-file shape, which can express conflict resolution more centrally
Blast radius: cmd/pysar/main.go (new global template directory + seeding logic reusing the skill hash-refresh mechanism), internal/onboarding/profile.go (template read/apply helpers), internal/mcpserver/tools_voice.go (new save_voice_template tool), cmd/pysar/assets/claude/skills/ps-voice/SKILL.md (conversation flow offering templates)
