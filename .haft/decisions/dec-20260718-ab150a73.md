# Hybrid: structured attributes plus required golden examples

## 1. Problem Frame

**Signal:** dec-20260718-5570376d (schema-only onboarding engine) established that a VoiceProfile/StyleProfile schema will exist, but not its actual shape. Operator wants: (1) a built-in generic/neutral default voice+style profile so an unonboarded user still gets sensible, non-personal-voice output (zero-config principle); (2) the template's field structure, including 3-4 "golden" reference examples the AI can be steered by, using the SAME schema shape onboarding itself produces -- not a divergent format. Operator explicitly scoped OUT how optional reusable templates are stored/composed/inherited beyond this generic default -- that mechanism is deferred to a separate future ADR by the operator's own instruction. Operator did real research citing external style-guide baselines (GOV.UK, Microsoft, Google dev docs, Economist/Orwell rules, Guardian/AP) and open-source voice/style schema formats (soul.md, voice.md, style.md, SKILL-TEMPLATE.md, ghostwriter, agent-writing, humanizer) as reference points -- that prior POC's voice pack is explicitly a strong PERSONAL voice, not a generic one, which is exactly the gap this problem fills.

**Constraints:**
- Must reuse the exact schema shape as what onboarding produces (dec-20260718-5570376d) -- the generic default and an onboarded profile must be structurally interchangeable
- Template composition/inheritance mechanism is explicitly out of scope here -- deferred to a separate future ADR per operator's own instruction
- External style-guide citations and open-source schema-format references are CL1 inspiration only, never sole justification, never adopted wholesale -- the generic profile must be an original synthesis, mirroring the spirit of dec-20260718-eafefad2 even though that gate names external POCs/haft specifically
- No multi-author/persona registry (dec-20260718-e84221af) -- the generic default is one neutral profile, not a set of personas to pick from
- Must fit the schema-only architecture (dec-20260718-5570376d) -- this is a data schema plus example content, not new orchestration/engine code

**Acceptance:** A voice/style template schema is defined such that: (1) a single schema shape is shared by onboarding-produced profiles and any future reusable template, including the generic default; (2) a built-in generic/neutral profile exists, populated using this schema, suitable as a zero-config fallback when no onboarding has occurred; (3) the schema includes 3-4 concrete "golden" reference examples, not abstract descriptive rules alone, that an AI can be steered by; (4) template inheritance/composition mechanics are explicitly not decided in this pass.

## 2. Decision

**Selected:** Hybrid: structured attributes plus required golden examples

**Selection policy:** Pareto front over target-role dimensions (steering_strength, self_validating, structured_validatability, stays_in_scope), declared before scoring; field_count is observation-role, watched per the ProblemCard's own indicator, never optimized (Anti-Goodhart). Policy fixed at comparison time (sol-20260718-bec802bb), unchanged for this decision.

**Why selected:** V3 ties the portfolio's best steering_strength (5/5, goldens present) and wins self_validating outright (5/5) -- authoring the required generic default profile against this schema exercises both the fielded attributes and the golden examples at once, the strongest available test that the schema itself is sufficient. It directly matches the operator's literal request ("template structure... with 3-4 goldens") and their own research finding that abstract rules alone underdetermine actual phrasing ("almost nobody ships a good generic literary persona you can drop in unchanged"). The formal Pareto co-leader, V1 (pure structured fields), scores one point higher on structured_validatability (5 vs 4) only by dropping goldens entirely -- a real but marginal edge purchased by contradicting the operator's stated requirement.


**Invariants:**
- VoiceProfile/StyleProfile schema always carries both structured attribute fields and a golden-examples array with a minimum count of 3 -- neither half is optional
- The generic default profile and any onboarding-produced profile share exactly the same schema type -- no divergent format
- Template inheritance/composition fields are not present in this schema -- deferred to a separate future ADR, not yet created

## 3. Rationale

**Counterargument:** V1 (pure structured fields, no goldens) scores higher on structured_validatability (5 vs 4) and is strictly simpler and cheaper to author correctly -- it can never suffer the fields/goldens internal-consistency failure mode this decision accepts as a real risk. The strongest case against V3 is that its added complexity is genuine editorial work that could go wrong, where V1 would have no equivalent failure mode at all.

**Selected variant weakest link:** Largest field count among in-scope variants (8), and a real risk that the two halves -- structured attributes and golden passages -- drift out of sync with each other if not authored carefully (e.g. a golden passage that doesn't actually match its own declared formality field). This is V3's own stated weakest_link, not a new observation.

## 4. Consequences

**Rollback plan:**
Triggers:
- The generic default profile's goldens and fields are found inconsistent with each other in practice (e.g. a golden passage doesn't match its own declared formality field)
- Authoring the first generic profile proves too costly or error-prone relative to V1's simpler pure-fields approach
- The completeness validator (dec-20260718-5570376d) turns out to need V1's fuller structured_validatability and cannot adequately check golden-example presence/quality at all
Steps:
1. Add an explicit consistency check (e.g. a lint step flagging goldens whose apparent register/length looks inconsistent with their declared fields) rather than dropping goldens
2. If authoring cost proves prohibitive: fall back to V1's pure-fields shape for the generic default specifically while keeping V3's shape for onboarding-produced profiles, via a new /h-decide
3. If the validator genuinely cannot check golden quality: accept that as inherent (human/LLM judgment, not fully automatable) rather than treating it as cause to abandon goldens
Blast radius: internal/onboarding schema package (VoiceProfile/StyleProfile struct shape), the built-in generic default profile shipped with the binary, future skill files that read this schema to steer generation
