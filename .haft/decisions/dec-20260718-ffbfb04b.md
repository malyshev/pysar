# Compile-time interface contract: a Pass interface requiring a Precondition method

## 1. Problem Frame

**Signal:** dec-20260718-20a08f83 bound the distributed precondition-guard mechanism for Pysar's editorial pipeline, with an explicitly named weakest_link: nothing structurally forces a future pass to declare its own precondition check -- a careless pass could omit one and nothing catches it before shipping. That decision's own rollback plan named a review-discipline mitigation as a 'cheap stopgap, not a fix.' Operator wants a real structural fix adopted now, while no real passes exist yet and the cost of fixing this is lowest, rather than waiting for the rollback plan's named trigger (a real pass shipping without a check, or auditability becoming a practical problem).

**Constraints:**
- Must not reintroduce a central phase-transition table (re-adopting the rejected FSM variant from dec-20260718-20a08f83's own comparison) unless explicitly chosen as the answer, with that reopening named plainly
- Should compose with, not duplicate, dec-20260718-6ba897d4's run-log
- Pure Go / stdlib-preferred, consistent with the project's established minimal-new-tooling preference (dec-20260718-817bfb74) unless a real gap forces otherwise

**Acceptance:** A concrete mechanism (or composed set of mechanisms) is selected such that: (1) a pass registered without a precondition check either fails to compile, or fails loudly at a well-defined point before it can ever run against a real piece -- never silently; (2) the mechanism does not require abandoning dec-20260718-20a08f83's chosen approach (distributed guards) unless the comparison concludes that is genuinely warranted, in which case that must be named explicitly as reopening the prior decision, not smuggled in as a cleanup.

## 2. Decision

**Selected:** Compile-time interface contract: a Pass interface requiring a Precondition method

**Selection policy:** Pareto front -- V2 dominated by V3 (same coverage and cost, earlier catch point); V1, V3, and V4 non-dominated. Operator chose to adopt V1 and V3 together rather than pick one, consistent with the advisory recommendation that they compose naturally, and explicitly declined V4 as premature relative to dec-20260718-20a08f83's own rollback discipline.

**Why selected:** Combined adoption of V1 (compile-time interface contract) and V3 (CI-enforced meta-test), which the comparison's own pinned_conditions noted are additive rather than mutually exclusive. Together they close both halves of dec-20260718-20a08f83's named weakest_link: V1 catches a totally-omitted precondition check at compile time; V3 catches a trivially-wrong or empty-permitting check before merge, via the same `go test` cycle already in use. Combined cost is lower than V4 (full escalation), and neither piece touches or reverses the chosen pipeline mechanism.


**Invariants:**
- Every registered pass type implements the Pass interface's Precondition method -- enforced by the Go compiler, not by convention
- A CI-run test iterates all registered passes and verifies each Precondition rejects an empty piece state, except passes explicitly marked as legitimately applicable to an empty piece
- These checks are additive to dec-20260718-20a08f83's chosen mechanism -- they harden it, they do not replace or reverse it
- The registry-time runtime self-test (V2) is not adopted -- V3 provides equivalent coverage earlier, at the same cost

## 3. Rationale

**Counterargument:** V4 (full escalation to the declarative-spec mechanism) would eliminate the failure mode entirely rather than narrowing it. The strongest case against this combined choice is that it still leaves a residual, narrower gap that V4 structurally cannot have -- a subtly-wrong pass could still theoretically ship despite both new checks passing.

**Selected variant weakest link:** Even combined, failure_coverage remains below V4's: a precondition check that satisfies V1's compile-time shape requirement and passes V3's single empty-state test, but is still substantively wrong in some other way (checks the wrong prior artifact, or is correct for an empty piece but wrong for a partially-progressed one), is not caught by either mechanism. This residual gap is real and named, not eliminated.

**Rejected alternatives:**
| Variant | Verdict | Reason |
|---------|---------|--------|
| Compile-time interface contract: a Pass interface requiring a Precondition method | **Selected** | Combined adoption of V1 (compile-time interface contract)... |
| Registry-time fail-fast self-test: refuse to register a pass whose Precondition rejects nothing | Rejected | Dominated by V3 -- identical coverage and cost, but V3 catches the same class of error earlier (before merge, not only at process start). No reason to prefer it once V3 is adopted. |
| Abandon distributed guards, escalate to the declarative-spec alternative from the original comparison | Rejected | Rejected as premature -- this would reverse dec-20260718-20a08f83 before either of that decision's own named rollback triggers has fired. The residual gap left by V1+V3 is accepted as a monitored risk, not treated as sufficient cause to reverse a decision made minutes earlier. |

**Predictions:**
| Claim | Observable | Threshold |
|-------|------------|-----------|
| A pass type that does not implement the Precondition method fails to compile once the Pass interface and registry exist | Attempt to register a stub pass type missing the Precondition method | Compilation fails with a clear interface-satisfaction error naming the missing method |
| The CI meta-test correctly fails when a registered pass's Precondition trivially returns nil against an empty piece state, and correctly passes for a legitimately-first pass marked as an exception | Implement the meta-test and run it against a deliberately-broken stub pass (trivial nil-returning Precondition) and against a correct one | Test fails for the broken stub, passes for the correct pass and for the marked exception |

## 4. Consequences

**Rollback plan:**
Triggers:
- The residual gap is actually observed in practice -- a precondition check passes both V1's shape check and V3's empty-state test but is still substantively wrong, and a real pass runs when it should not (or declines when it should not)
- dec-20260718-20a08f83's own named rollback triggers fire despite this hardening (a pass ships without any check at all, or auditability becomes a real practical problem)
Steps:
1. If the residual gap is observed: strengthen V3's test to cover the specific failure pattern found (e.g. add a partially-progressed-state case alongside the empty-state one) before escalating further
2. If dec-20260718-20a08f83's own triggers fire despite this hardening: escalate per that decision's own rollback plan, reusing the relevant SolutionPortfolios via a new /h-decide rather than re-exploring
Blast radius: Pre-implementation -- no passes exist yet. Adding these checks later, once passes exist, remains additive and low-cost, not a rewrite.
