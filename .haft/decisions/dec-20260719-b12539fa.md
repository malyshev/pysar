# Dedicated template-metadata frontmatter wrapper

## 1. Problem Frame

**Signal:** Live testing of dec-20260719-3e36577e surfaced a real gap: save_voice_template currently derives the on-disk filename slug directly from the author's display name (onboarding.Slug(name)), so a rename would silently change the template's addressable key too -- name and slug are one conflated thing, not two. The built-in generic template makes this concrete: its only name-bearing data is the bare filename stem "generic" -- the meaningful display name the operator actually chose for it ("Measured plain English -- speakable, understated, general audience") was only ever used as descriptive prose during design, never persisted as data, so list_voice_templates has nothing but "generic" to show. Operator wants both a persisted, meaningful display name AND a separate stable slug/key that survives renames, explicitly for future automation (addressing a specific template by a fixed key regardless of what it's currently called).

**Constraints:**
- Must not silently break the existing schema-parity constraint from prob-20260718-00bf7ca6 (templates and onboarding profiles share one Profile schema) -- if Profile itself gains a name-like field, that must be an explicit, examined divergence, not an accident
- Slug stability must survive a rename: re-saving a template under a new display name but the same slug updates the existing file in place, never creates an orphaned duplicate
- The author must never be asked to type or think about a slug during the /ps-voice conversation -- slugs are machine-facing, names are human-facing
- Must stay inside the already-decided global template store location and never touch project-local files (dec-20260719-3e36577e invariant)
- Must reuse the existing hash-refresh/manifest mechanism (dec-20260719-25712417 via dec-20260719-3e36577e) rather than a second parallel implementation

**Acceptance:** A template carries a persisted display name distinct from its stable slug. Renaming a template's display name (re-saving under a new name) never changes its slug or creates an orphaned duplicate file. list_voice_templates surfaces both the stable slug and the current display name. The built-in generic template's slug is "generic" and its display name ("Measured plain English -- speakable, understated, general audience") is actually persisted as data, not only prose. Verified with unit tests plus a real-binary smoke test per this project's standing discipline.

## 2. Decision

**Selected:** Dedicated template-metadata frontmatter wrapper

**Selection policy:** Pareto front over target-role dimensions (self_contained_portability, name_extraction_robustness), gated by both constraints (schema_parity_preserved, rename_preserves_slug) which must hold true; new_plumbing_cost is observation-role, watched but never optimized (Anti-Goodhart). Declared before scoring (sol-20260719-93254edd).

**Why selected:** V4 strictly dominates both surviving contenders after constraint-gating eliminated V1 (breaks Profile schema parity) and V5 (status quo, fails rename safety outright). Against V2 (manifest-stored names) it wins on self_contained_portability (5 vs 2) at equal name_extraction_robustness (5=5): a template's name travels inside the one portable file instead of being lost the moment just the .md file is copied elsewhere. Against V3 (name as Markdown H1) it wins on name_extraction_robustness (5 vs 3) at equal self_contained_portability (5=5): a typed YAML field instead of a heading an author could reformat without realizing it carries meaning. V4 gets both wins simultaneously by not choosing between them.


**Invariants:**
- internal/onboarding.Profile's Go struct/schema shape never gains a template-only field; template-only metadata lives exclusively in the wrapper layer added in tools_voice.go
- The wrapper is absent-safe: a template file's content past the wrapper's closing `---` is byte-identical to what Render(profile) already produces for a plain onboarding profile -- stripping the wrapper always yields a valid standalone profile
- Renaming a template via an explicit slug parameter never creates a second file at a different slug for the same logical template -- it updates the existing file in place

## 3. Rationale

**Counterargument:** This decision spends genuinely new plumbing (a convention nothing else in the project or its ecosystem uses) on a narrow current pain point -- one built-in default's display name plus a hypothetical future rename -- when V2 would have solved it with zero new file conventions, purely by extending already-existing, already-tested manifest infrastructure. There is also a concrete risk I did not weigh during comparison: most Markdown tooling (Jekyll, Hugo, GitHub's own renderer) only recognizes a single leading `---`-delimited block at the very top of a file as real frontmatter -- a second stacked block would render as a literal visible YAML blob in the body if this file were ever opened in a Markdown previewer, not hidden the way true frontmatter is. This doesn't change the selection: every consumer of these files in this project is either an LLM agent reading raw text or a human in a plain text editor, never a Markdown renderer, so the risk is real but currently inert. It should be treated as a live constraint if a Markdown-rendered view of templates is ever built.

**Selected variant weakest link:** Two stacked `---`-delimited YAML blocks in one file is a convention nothing else in this project uses yet -- genuinely new plumbing (a small wrap/unwrap parse function), not a reuse of any existing mechanism, and could look unusual to an author opening the file for the first time even though it remains fully valid and human-editable. This was V4's own stated weakest_link at exploration time.

## 4. Consequences

**Rollback plan:**
Triggers:
- The two-stacked-frontmatter convention genuinely confuses an operator or future contributor reading a template file for the first time, disproportionate to the naming problem it solves
- A future need to render template files through an actual Markdown renderer (not just LLM/text-editor consumption) surfaces the counterargument's inert risk as a real, visible bug -- the second frontmatter block displaying as raw YAML in the rendered body
- The wrap/unwrap parsing logic proves fragile in practice (e.g. an author manually edits a template file and breaks the two-block structure)
- Style templates (pending task #11) reveal template-only metadata needs beyond just name, and the wrapper's shape doesn't extend cleanly
Steps:
1. If the convention confuses people: consider migrating to V2 (manifest-stored names) instead -- Profile.go is already untouched under both, so this migration only touches the wrap/unwrap and list_voice_templates code, not the schema
2. If Markdown rendering becomes a real need: reconsider at that point rather than pre-solving now -- possibly migrate to V3's single-block-with-named-H1 approach if a rendered view specifically wants the name as a visible document title
3. If manual edits break the wrapper: add a clear validation error in save_voice_template / list_voice_templates naming exactly what's malformed, rather than migrating storage shape
4. If Style's metadata needs don't fit: extend the same wrapper with additional fields first (it was designed as a stepping stone for exactly this) before reconsidering the whole mechanism
Blast radius: internal/mcpserver/tools_voice.go (save_voice_template, list_voice_templates -- wrap/unwrap logic), cmd/pysar/assets/templates/voice/generic.md (re-authored with the wrapper), cmd/pysar/assets/claude/skills/ps-voice/SKILL.md (Step 1a/6 display and save flow), internal/onboarding/profile.go untouched by design (an invariant of this decision, not just incidental)
