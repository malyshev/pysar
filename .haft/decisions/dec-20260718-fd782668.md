# Adopt Cobra now, fully migrate root + init to cobra.Command

## 1. Problem Frame

**Signal:** Decision dec-20260718-c4cd8f62 needs re-evaluation: Operator invoked /h-reason 'adopt Cobra', which is exactly this decision's own named refresh trigger ('Operator adopts a CLI framework'). Reopening to properly reconsider the previously-rejected cobra alternative in context, rather than reasoning about it in a disconnected new ProblemCard.

## 2. Decision

**Selected:** Adopt Cobra now, fully migrate root + init to cobra.Command

**Selection policy:** Pareto front -- V1/V3/V4 non-dominated, V2 strictly dominated by V4. Operator chose V1 over my advisory lean toward V4 (defer, tighten trigger), based on information about near-term command/flag growth only the operator has. Per the Transformer Mandate, that override is exactly the operator's call to make.

**Why selected:** Operator overrode the deferral lean with explicit intent to pay the migration cost now. V1 gives full feature headroom for the growing command surface, and importantly cobra's own Command struct preserves the single-source-of-truth property the prior decision (dec-20260718-c4cd8f62) specifically valued -- this is not a regression on that front, just a paid-for upgrade in capability.


**Invariants:**
- internal/cli/registry.go and its tests are removed once the cobra migration is verified complete -- no dual-maintained CLI dispatch mechanism coexists
- Cobra's root command Long/Short text remains Pysar-original copy; haft's own root-command text stays CL1 inspiration only, per dec-20260718-eafefad2
- Console binary remains pysar; ps-*/`/ps` agentic-tool naming (dec-20260718-a2a24f32) is not conflated with cobra's subcommand tree
- All behavior already verified for dec-20260718-8278c494 (init's flag semantics) must be re-verified, not assumed, against the cobra implementation before this migration is considered complete

## 3. Rationale

**Counterargument:** V4 (keep the registry, tighten the refresh trigger) would have delivered the same practical outcome today at zero cost and zero risk, since the actual command surface has not grown since dec-20260718-c4cd8f62 was measured. The strongest case against V1 is that this cost is being paid speculatively, ahead of the concrete need that would normally justify it -- if the anticipated near-term growth does not materialize, this becomes exactly the premature-reinvention cost the original decision was designed to avoid.

**Selected variant weakest link:** migration_cost scored worst of the surviving variants (4/4): this requires a full rewrite of internal/cli/registry.go (deleting already-tested, already-measured-working code) plus migrating runInit's stdlib flag.NewFlagSet to cobra's flag binding -- real, immediate cost paid today, ahead of the command-surface growth (still just init/--version/help at decide time) that would otherwise force it.

- The anticipated near-term subcommand/flag growth that justified this migration does not materialize within a reasonable window
Steps:
1. Re-verify all of dec-20260718-8278c494's predictions (default/--claude parity, --cursor/--codex fail loudly, mutual-exclusivity rejection) against the cobra-based implementation before considering this migration complete
2. If regressions are structural (cobra cannot express the required behavior): revert to the internal/cli registry via git history and supersede this decision; if not structural, fix within the cobra implementation rather than reverting
Blast radius: cmd/pysar and internal/cli -- the existing registry.go and its tests are deleted/replaced; init's flag handling changes from stdlib flag.NewFlagSet to cobra's flag binding.
