# Dedicated DecisionRecord mirroring the reference-agnosticism-gate pattern, cascading into specs

## 1. Problem Frame

**Signal:** Medium's POC implements a multi-author model (an authors/ registry, per-article author assignment). No current Pysar spec section or bound decision claims multi-author support -- specs consistently say "the author" (singular) -- but the risk of it being reintroduced by a future Medium-inspired exploration (CL1 citation) is real: the now-dominated variants of the on-disk-structure comparison (sol-20260718-47044f62) explicitly floated it -- V2's strength was "shared author voice across pieces," V1's risk was "voice/author registry deferred" -- both assumed a future multi-author path. Operator's reasoning: since pysar init scaffolds a distinct project per invocation, each with its own voice, a cross-project author/voice registry is redundant scope, not a missing feature.

**Constraints:**
- Medium/haft citations CL1 max, never sole justification (dec-20260718-eafefad2)
- Must not contradict the already-bound on-disk-structure decision (dec-20260718-4b222794), which already has no project-level author concept
- Voice-lock (the editorial pass that removes AI-sounding prose) is unaffected -- this constraint is about identity/ownership model, not the voice-lock pass

**Acceptance:** A durable, citable artifact exists such that future explorations (memory engine delivery, run-log, any project-root topology revisit) can check against it instead of re-deriving or accidentally reintroducing a multi-author/author-registry model from Medium.

## 2. Decision

**Selected:** Dedicated DecisionRecord mirroring the reference-agnosticism-gate pattern, cascading into specs

**Selection policy:** Pareto front over target-role dimensions (future_discoverability, governance_overhead), declared before scoring; new_artifacts_count is observation-role, watched per the ProblemCard's own indicator, never optimized (Anti-Goodhart). Policy fixed at comparison time (sol-20260718-24dbdebb), unchanged for this decision.

**Why selected:** V2 wins discoverability outright (5/5) among the Pareto front: a citable dec-ID that future kernel search will actually surface, unlike V1's spec-only edit (3/5) or V4's note (2/5, tied with the dominated V3). This matches the session's own established precedent for target-system boundary guardrails -- the reference-agnosticism gate (dec-20260718-eafefad2) and the publish-checklist exclusion (dec-20260718-e9f5b5e6) were both bound as full DecisionRecords, not notes or spec-only edits, because they shape what future explorations are allowed to propose. This decision explicitly names the Medium pattern being deliberately not inherited -- Medium's own bound dec-20260606-...multi-author-v1-author-files-manifest-defaults and dec-20260530-...multi-voice-v1-persona-files (CL1, cross-project search) -- rather than asserting Pysar is different in the abstract.


**Invariants:**
- Pysar never persists a cross-project author/persona identity table or registry
- Voice-lock (the editorial pass) remains scoped to a single piece/project's own POV, never a shared persona library
- Each pysar init instance is the sole unit of authorial voice -- a distinct voice means a distinct initialized project, not a role assignment within one

## 3. Rationale

**Counterargument:** The strongest argument against binding a full DRR here is that this guardrail currently corrects zero active promise or code, unlike the publish-checklist removal (which walked back a live spec commitment). V1 (spec-only edit) would have covered the actual near-term review-time need -- an operator or agent reading target-system scope -- at a fraction of the overhead. Preventative DRRs for hypothetical features risk becoming stale ceremony nobody re-verifies, since their own predictions can only be checked against things that haven't been built yet.

**Selected variant weakest link:** Heaviest ceremony of the three front options for a constraint that, today, contradicts nothing already built -- this is a preemptive guardrail, not a fix for an active conflict. This is V2's own stated weakest_link in the portfolio, not a new observation.
