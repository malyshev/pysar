# Plain Go toolchain only -- `go build` / `go install`, no wrapper tool

## 1. Problem Frame

**Signal:** The tech stack (Go, dec-20260718-239680d4) and 5-layer architecture (ES.enabling.architecture.001) are decided, but no code or build tooling exists yet, and there is no established local development loop -- build, install a runnable pysar binary, verify, repeat -- comparable to what the dogfood haft project has (Taskfile.yaml, install.sh, goreleaser). Operator wants a genuine greenfield hello-world Go project rooted at this directory that builds, installs locally (on PATH or via an alias) so each implementation step can be verified end-to-end as it's built, and eventually produces the cross-compiled installable artifacts already decided. Haft may be consulted for code-standard/design inspiration, capped per the reference-agnosticism gate (dec-20260718-eafefad2) -- never copied, never sole justification.

**Constraints:**
- Must not depend on haft's own build scripts, config, or code at runtime or build time -- may consult them for structure/naming inspiration only (CL1 max, explicit Pysar-original divergence stated), per dec-20260718-eafefad2
- Must respect dec-20260718-239680d4's invariants: single self-contained executable, no separate runtime for the END USER, native cross-compilation without per-OS build machines
- Must be realistically maintainable by a solo maintainer with no CI yet, echoing the original tech-stack acceptance criterion

**Acceptance:** A local dev/build loop is chosen such that: (1) one command from the project root builds a pysar binary; (2) one command installs/updates that binary on the operator's PATH (or an explicit alias) so invoking pysar picks up the latest local build; (3) the first working version proves the whole loop end-to-end via real observable output (e.g. pysar --version or pysar hello actually runs after build+install); (4) the project layout matches what dec-20260718-239680d4 already named as affected_files (cmd/pysar/**, internal/**).

## 2. Decision

**Selected:** Plain Go toolchain only -- `go build` / `go install`, no wrapper tool

**Selection policy:** Pareto front -- V1/V2/V3 non-dominated, V4 eliminated by strict dominance (V3 beats it outright). Operator chose V1 specifically per its stepping-stone framing: get a real loop working immediately, defer the V2-vs-V3 choice until the build actually needs more than one step.

**Why selected:** Fastest, simplest path to a real, working build+install+run loop today, with zero new dependency. Explicitly a stepping stone: whatever wrapper tool (Makefile or Taskfile) gets adopted later still sits on top of `go build`/`go install` as the underlying primitive, so starting here forecloses nothing.


**Invariants:**
- The build entry point is `go install ./cmd/pysar` (or equivalent `go build`) -- no wrapper tool exists yet; this is intentional, not an oversight
- Project layout follows dec-20260718-239680d4's already-named affected_files: cmd/pysar/** for the binary entrypoint, internal/** for implementation packages
- This decision does not preclude adopting V2 (Makefile) or V3 (Taskfile) later -- both remain valid, already-compared options in sol-20260718-c277773d, not requiring re-exploration
- No code or structure is copied from haft's own build tooling -- haft is consulted for inspiration only, per dec-20260718-eafefad2

**Spec sections:**
- ES.enabling.architecture.001

## 3. Rationale

**Counterargument:** Adopting a wrapper (Makefile or Taskfile) from day one, even at hello-world stage, costs almost nothing extra right now and would avoid a near-certain future migration. Starting with zero tooling optimizes for a stage of the project (single-file hello-world) that will last only a few sessions, at the cost of having to formalize a Makefile or Taskfile later anyway.

**Selected variant weakest link:** growth_headroom scored worst of the three non-dominated variants (1/4): no single discoverable 'how do I build this' entry point once version-stamping, cross-compiled release builds, or test/lint hooks are needed -- those steps would have to be typed manually and remembered each time.

**Rejected alternatives:**
| Variant | Verdict | Reason |
|---------|---------|--------|
| Plain Go toolchain only -- `go build` / `go install`, no wrapper tool | **Selected** | Fastest, simplest path to a real, working build+install+r... |
| Makefile-driven build (`make build`, `make install`, `make test`) | Rejected | Not adopted now -- real growth headroom, but adds structure before there is more than one build step to structure. Deferred as the likely next layer once the build needs more than `go install`, reusing this same portfolio. |
| Taskfile-driven build (`task build`, `task install`) -- same tool the dogfood project uses | Rejected | Not adopted now for the same reason as the Makefile, plus it adds an external dependency (the task binary) that V1 avoids entirely. Deferred as an alternative next layer, not ruled out. |
| goreleaser snapshot builds from day one | Rejected | Already eliminated by strict dominance in the comparison -- V3 beats it outright on iteration_speed and tooling_simplicity with no offsetting gain. Not reconsidered here. |

## 4. Consequences

**Rollback plan:**
Triggers:
- The build needs more than a single compile step (version-stamping, running tests before install, cross-compiling for a real release) and manually remembering multiple commands becomes error-prone or annoying
- A future contributor, or the operator returning after time away, can't quickly discover 'how do I build this project'
Steps:
1. Adopt V2 (Makefile) or V3 (Taskfile) per the already-recorded comparison in sol-20260718-c277773d, via a new /h-decide rather than re-exploring
2. Wrap the existing `go build`/`go install` invocations as named targets/tasks -- no changes needed to the underlying Go commands themselves
Blast radius: Pre-implementation, single hello-world file today -- migrating to a wrapper tool later costs writing one Makefile/Taskfile, not touching any Go source.
