# V1 + V3 combined: allowlist plus expectation-setting as a fallback

## 1. Problem Frame

**Signal:** /ps-voice persists via the skill's own Write tool call directly to .pysar/voice.md, which triggers Claude Code's per-write permission prompt -- confirmed by operator's real test ("claude code asked me for permissions write JSON"). Operator contrasts this with haft's own MCP-tool-based persistence (haft_note, haft_decision, etc.), which never prompts in this repo. Investigation of .claude/settings.local.json shows that's because this repo explicitly allowlists those specific MCP tool names in permissions.allow -- not because MCP calls are inherently prompt-free. A parallel mechanism exists for direct file writes: Claude Code's own docs confirm a committed .claude/settings.json can pre-approve Write(pattern) for specific paths, applying to any user who opens the project, the same allow-rule mechanism haft already relies on. Target audience is explicitly a "wide non-tech target group" (dec-20260718-ab150a73's own framing) -- a raw permission prompt naming a file path and requiring the author to understand "write" access is real friction for that audience.

**Constraints:**
- Must not violate dec-20260718-5570376d's schema-only invariant -- the Go engine layer defines schema+validation only, never conducts the questionnaire; a persistence mechanism is a different concern but must not smuggle in orchestration logic
- If a server component is introduced, it must ship inside the same pysar binary (e.g. a subcommand), not a separate install -- single static binary constraint (dec-20260718-239680d4)
- Pre-approving Write access is a trust decision, not just a UX one -- scope must be demonstrably narrow (only Pysar-managed paths under .pysar/**), never broad or arbitrary
- Must work for the same non-technical target audience dec-20260718-ab150a73 was framed around

**Acceptance:** A persistence mechanism is selected such that: (1) a first-time author using /ps-voice in a fresh pysar init'd project experiences zero, or clearly pre-explained, permission prompts for saving their own voice profile; (2) the mechanism's security scope is demonstrably narrow (limited to Pysar-managed paths, never arbitrary filesystem access); (3) the author never needs to understand implementation terms (JSON, MCP, permission scopes) to complete the flow.

## 2. Decision

**Selected:** V1 + V3 combined: allowlist plus expectation-setting as a fallback

**Selection policy:** Pareto front over target-role dimensions (prompt_friction, maintenance_cost, verified_confidence, validation_rigor), declared before scoring; new_components is observation-role, watched per the ProblemCard's own indicator, never optimized (Anti-Goodhart). Policy fixed at comparison time (sol-20260719-a6e09400), unchanged for this decision.

**Why selected:** V4 solves the concrete problem the operator actually hit -- an unexplained Write permission prompt -- at effectively zero cost (maintenance_cost 1, zero new components), using a mechanism already proven working in this exact repo (this repo's own settings.local.json allowlists haft's MCP tools the same way). It ties V1 on cost but wins verified_confidence (5 vs 4) via the fallback prose line, at negligible extra cost. Unlike V2, choosing V4 now creates no throwaway work if V2 (a real MCP server) is built later -- the settings.json and prose stay valid regardless; V2 would be additive, not a replacement.


**Invariants:**
- Write access is only ever pre-approved for paths under .pysar/** -- never broader
- pysar init ships this permission allowlist automatically for every scaffolded project, not as an opt-in step
- The completeness check remains an LLM self-check until/unless V2 is separately decided -- this decision does not claim programmatic validation rigor

## 3. Rationale

**Counterargument:** V2 closes a real, separate problem (validation rigor) that this decision leaves untouched -- if the LLM self-check ever lets an incomplete or inconsistent profile through, V4 will look like it deferred a known, named gap rather than an unknown risk. Additionally, V4's own fallback prose line is unverified insurance: there is no confirmed case where the settings.json allowlist actually fails that the prose line would catch -- it is defensive, not proven necessary, and could itself read oddly to an author if the allowlist works exactly as expected and the prompt never appears.

**Selected variant weakest link:** validation_rigor scored 1/5 -- the completeness check the skill performs before saving remains an LLM re-reading prose rules, not a real programmatic Validate() call. This decision does not close that gap. This is V4's own stated weakest_link, inherited from V1's.

## 4. Consequences

**Rollback plan:**
Triggers:
- A real author still hits an unexplained permission prompt despite the shipped settings.json allowlist (the mechanism doesn't work as expected in some environment)
- The LLM self-check completeness gap causes an actual observed failure -- an incomplete or internally inconsistent profile gets persisted despite the skill's own stated checks
- Enough ps-* skills exist that repeating this same permission-scaffolding pattern per skill becomes real, measurable toil
Steps:
1. If the allowlist fails in practice: investigate root cause (Claude Code version, settings precedence, path pattern syntax) before adding more scaffolding -- the fallback prose should already prevent author confusion in the interim, so this is not an emergency
2. If a self-check failure is observed: that specific, real failure is the trigger to build V2's real Validate() call, reusing sol-20260719-a6e09400 via a new /h-decide rather than re-exploring from scratch
3. If per-skill scaffolding toil becomes real as more ps-* skills ship: same trigger, escalate to V2
Blast radius: pysar init scaffold output (new .claude/settings.json), ps-voice skill content (fallback sentence), and every future ps-* skill, which inherits the same shipped settings.json automatically

**Affected files:** cmd/pysar/main.go, cmd/pysar/assets/claude/**, cmd/pysar/init_test.go
