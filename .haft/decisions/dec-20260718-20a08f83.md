# Precondition-guarded actions over a lightweight ref-holding cycle state (haft's own evolved v2 pattern)

## 1. Problem Frame

**Signal:** Pysar's editorial engine needs a shared execution model that every future author-facing command (idea scaffolding, draft intake, editing passes, voice-lock, research, packaging) plugs into as an entry point to a single, orchestrated flow -- analogous to how haft's own note/decide commands share one underlying kernel. Nothing defines this today: ES.enabling.architecture.001 names the layers and ES.enabling.work_methods.001 names the artifact-per-pass table, and dec-20260718-6ba897d4 established a per-piece run-log, but nothing defines HOW a pass is actually invoked, sequenced, gated by preconditions, or composed into a full end-to-end flow. that prior POC's AGENTS.md (operator's prior prototype) already has a complete, battle-tested prose design for exactly this: a canonical phase order (INTAKE -> RESEARCH? -> WRITE -> STAFF-EDIT -> SHARPEN -> OPTIMIZE -> HUMANIZE -> COVER), a Status enum persisted per-piece gating what can run next, an artifact-per-phase convention, hard non-reorderable doctrine (HUMANIZE must follow OPTIMIZE), a skill-picker table mapping author intent to command, and pre/post-flight discipline every skill follows -- all of it prose an LLM reads and follows each session, none of it code-enforced.

**Constraints:**
- Scoped to the MECHANISM (how passes are invoked/sequenced/gated), not the actual phase list/names -- Pysar's own pass vocabulary is separate future work, consistent with TS.environment-change.001 keeping harness-internal phase names off the author surface
- prior writing POC's AGENTS.md is real, battle-tested prior art from the operator's own prototype -- citing its structural pattern (status enum, phase order, skill picker, pre/post-flight discipline) is legitimate CL1-capped inspiration per dec-20260718-eafefad2, never sole justification, and Pysar's own pass content/names must be original
- Must fit inside the already-decided 5-layer architecture (ES.enabling.architecture.001) and compose with, not duplicate, the already-decided run-log (dec-20260718-6ba897d4) and memory engine (dec-20260718-404573a2)
- Must respect the Go/Cobra stack already decided (dec-20260718-239680d4, dec-20260718-fd782668) -- no new language/runtime

**Acceptance:** A pipeline/orchestration mechanism is selected such that: (1) it defines a concrete, nameable way to add a new author-facing command as 'an entry point to a single pipe' -- not a vague aspiration; (2) it states plainly whether hard-ordering rules (the equivalent of prior writing POC's 'HUMANIZE must follow OPTIMIZE') are enforced in code or remain documentation-only, and if documentation-only, that is named as a real weakest_link, not glossed over; (3) it states whether 'what state is this piece in, what can run next' is answerable by a structured query/type, or only by reading files by hand.

## 2. Decision

**Selected:** Precondition-guarded actions over a lightweight ref-holding cycle state (haft's own evolved v2 pattern)

**Selection policy:** Pareto front, deep mode, full parity_plan declared before scoring per CMP-02. V1/V4/V5 were the non-dominated set after correcting a dimension-polarity bug found mid-comparison; V2/V3 were cleanly dominated by V5. Operator selected V5, consistent with the advisory recommendation, citing trust in the pattern's real-world evolution in a comparable system as a supporting factor alongside the comparison's own dimension scores (cheapest real-guarantee option, tied-best on flexibility and conditional applicability).

**Why selected:** The mechanism, described in Pysar's own terms rather than by reference to any external file: each piece carries a lightweight state object recording only which artifacts/results have been produced for it so far (e.g. 'has a stake', 'has a draft', 'voice-lock has run') -- not a single named phase value assuming one fixed universal sequence. Every pass (idea scaffolding, draft editing, voice-lock, research, packaging, and any future pass) owns its own small, independent precondition check that runs before the pass does. That check inspects both the piece's produced-artifact state (has what this pass needs already been produced -- ordering) and the piece's own declared context, including its target surface (is this pass even relevant to this piece's output type -- applicability). A pass whose relevance depends on target surface, such as a discoverability-oriented pass that is meaningless for a paper-letter output, declines to run via this same check -- no separate bolted-on skip-flag system is needed alongside it. When a precondition is not met, the check returns a structured, actionable message naming exactly what is missing, so whatever is driving the piece through its passes (an orchestrator, or an interactive agent session) can self-correct rather than silently proceeding or failing opaquely. No single central table or object owns 'the one correct sequence' -- the guarantee that passes run in a sane order emerges from each pass correctly declaring its own precondition, not from one authority walking a fixed transition graph. This composes directly with the already-decided run-log (dec-20260718-6ba897d4): every pass that actually runs appends its entry there, so the emergent order is also the audited order after the fact. Selected as the cheapest of the three real-guarantee variants in the comparison while matching the strongest of them on flexibility and conditional-applicability support; the pattern reflects a lesson already learned by a comparable system's own real evolution (it tried a rigid, centrally-sequenced version of this idea first and moved away from it toward independent per-action preconditions) -- the operator's stated trust in that evolved shape is one supporting factor, not the sole justification, per the reference-agnosticism gate.


**Invariants:**
- Piece state is tracked as a lightweight set of references to what has been produced so far, never a single named phase/status value that assumes one fixed universal sequence
- Every pass owns its own independent precondition check before it runs; no central table or object owns 'the one correct sequence' for all passes
- A pass's precondition check may consider both prior-artifact state (ordering) and piece context such as target surface (applicability) -- the same mechanism handles both, no separate skip-flag system is built alongside it
- When a precondition is not met, the pass returns a structured, actionable message naming what is missing and what to do instead -- it never silently proceeds and never fails without explanation
- This mechanism composes with, and writes into, the already-decided run-log (dec-20260718-6ba897d4) -- every pass that actually runs appends its own entry there
- No external file path or another project's source code is required to understand or maintain this mechanism -- its design is documented here in Pysar-original terms

## 3. Rationale

**Counterargument:** The declarative-spec alternative in this comparison would give the same practical guarantees (ordering safety expressed as data-driven preconditions, full conditional-applicability support, tied-best flexibility) through a single generic interpreter enforcing them uniformly -- meaning a pass registered with no declared precondition could be made a structurally detectable data-completeness problem, rather than a silent omission only human review would catch. The strongest case against this decision is that its guarantee is only as strong as every future pass author remembering to write their own check, where the alternative could make that omission impossible to miss.

**Selected variant weakest link:** The mechanism's guarantee is fully distributed: there is no single central table or type that structurally forces a new pass to declare its own precondition check. A careless future pass could simply omit one, and nothing in the mechanism itself would catch that omission before it ships -- unlike a compiled state-machine approach, where a new phase must be slotted into one central transition definition or the code will not route to it at all.

**Rejected alternatives:**
| Variant | Verdict | Reason |
|---------|---------|--------|
| Precondition-guarded actions over a lightweight ref-holding cycle state (haft's own evolved v2 pattern) | **Selected** | The mechanism, described in Pysar's own terms rather than... |
| Code-enforced finite state machine: typed Status enum + phase registry | Rejected | Strongest ordering and query guarantees of all five variants, but no native way for a pass to declare itself inapplicable to a given piece's target surface -- the SEO-for-paper-letters requirement needs retrofitting onto a fixed status enum rather than being modeled directly. |
| Event-driven handler pipeline: passes subscribe to trigger conditions | Rejected | Dominated by the selected variant on every scored dimension -- no compensating advantage. |
| Command-as-entrypoint with shared helpers, no central orchestrator | Rejected | Dominated by the selected variant on every scored dimension -- reproduces the operator's originally-named prior writing POC gap (nothing prevents misordering) almost exactly, just in Pysar's own codebase. |
| Declarative pipeline spec (data) interpreted by a generic runner | Rejected | Matches the selected variant's guarantees on flexibility and conditional applicability, and would make a missing precondition structurally detectable rather than a silent omission -- but at meaningfully higher build cost: a generic spec interpreter is real, nontrivial engineering every future pass would depend on being correct before benefiting from it. |

**Predictions:**
| Claim | Observable | Threshold |
|-------|------------|-----------|
| A piece's produced-artifact state is queryable as a structured value, not a file read, and a pass's own precondition check correctly blocks it from running when its required inputs are not yet ready | Implement the first two real passes (e.g. idea scaffolding and one edit pass) with their own precondition checks; attempt to run the second pass before the first has produced anything | The second pass's check refuses to run and returns a structured, actionable message naming what is missing, rather than running incorrectly or failing without explanation |
| A pass whose relevance depends on a piece's target surface can decline to run via its own precondition check alone, with no separate skip-flag mechanism required | Implement one target-surface-conditional pass (even a stub) and verify it correctly declines for an inapplicable target surface using only its own check, with no additional flag or branching system built alongside it | The pass's own check, considering target surface, correctly declines when inapplicable and correctly proceeds when applicable, using no mechanism beyond the check itself |

## 4. Consequences

**Rollback plan:**
Triggers:
- A real pass ships without its own precondition check -- the exact failure mode this mechanism does not structurally prevent -- and a piece is observed moving through passes out of intended order as a result
- The number or complexity of passes grows to the point where auditing 'what is the actual intended order' by reading each pass's own check individually becomes genuinely hard, making the ordering/query guarantee gap versus the rejected FSM or declarative-spec alternatives a real practical cost rather than a theoretical one
Steps:
1. If a specific pass shipped without a check: add the missing check, and adopt a lightweight review discipline requiring every new pass to declare one -- a cheap mitigation for the named weakest_link short of a full architecture change
2. If auditability becomes a real practical problem: escalate to the declarative-spec variant (data-driven preconditions, structurally checkable) or the compiled state-machine variant, reusing SolutionPortfolio sol-20260718-18a9ce18 via a new /h-decide rather than re-exploring from scratch
Blast radius: Pre-implementation -- no editorial-engine passes exist yet, so this establishes the first shape rather than migrating real pieces off an existing mechanism.
