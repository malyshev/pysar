# Manifest-only machine layer; zero prose templates at init

## 1. Problem Frame

**Signal:** Operator asked three open questions after a failed freelanced init scaffold was wiped: (1) what belongs in the base on-disk structure of a writing project/piece, (2) where that structure lives, (3) how it evolves and is rewritten/migrated when the pysar tool version changes. No DecisionRecord binds piece layout, storage root, or schema_version/migration. prior writing POC at [prior-writing-POC] has a battle-tested articles/<slug>/ layout (brief, outline, angles, article, publish, sources, changelogs, Status in publish.md) inside a monorepo with AGENTS.md + authors/ — CL1 inspiration only per dec-20260718-eafefad2; Pysar must improve, not copy (decided pipeline is precondition-guards not prior writing POC Status FSM; publish checklist out of scope per dec-20260718-e9f5b5e6). Failed session scaffold (idea.md/draft.md/CLAUDE.md) ignored that POC.

**Constraints:**
- external POCs/haft citations CL1 max; never sole justification; name Pysar-original divergence (dec-20260718-eafefad2)
- Must compose with Pass/State + run-log decisions (dec-20a08f83, dec-ffbfb04b, dec-6ba897d4) — layout must make produced-artifact refs and run-log attachable
- No platform publish checklist/cover as required base files (dec-20260718-e9f5b5e6)
- Author prose must not be silently clobbered on tool upgrade
- Console binary remains pysar; agentic ps-* separate (dec-a2a24f32)

**Acceptance:** A recorded ProblemCard + SolutionPortfolio such that the operator can choose (via later /h-compare + /h-decide) answers to: (A) minimal vs full base file set for a new piece/project, (B) storage topology (one dir = one piece vs project root with pieces/ vs multi-project), (C) explicit schema_version + migration/rewrite policy when pysar upgrades — including what is never overwritten (author prose) vs what tool may rewrite (markers, empty templates, machine state).

## 2. Decision

**Selected:** Manifest-only machine layer; zero prose templates at init

**Selection policy:** Pareto front computed over target-role dimensions only (ownership_boundary_clarity, multi_piece_shared_state_support, migration_policy_completeness), declared before scoring; init_file_count and medium_resemblance are observation-role — watched per the ProblemCard's own indicators, never optimized (Anti-Goodhart). Policy fixed at comparison time (sol-20260718-47044f62), unchanged for this decision.

**Why selected:** V3 is the clean Pareto-front winner on the two target dimensions that matter most for a first real dogfood session: ownership_boundary_clarity (5/5 — nothing but a manifest exists to confuse the author/tool boundary) and migration_policy_completeness (2/2 — the variant states its own concrete mechanism: `pysar migrate` rewrites only `.pysar/**` by schema_version, never touches user markdown). It also scores best on both observation dimensions (leanest init footprint, least reference-resemblance), and it directly refuses the failure mode that opened this ProblemCard: a freelanced session previously scaffolded idea.md/draft.md/CLAUDE.md as template fiction and had to be wiped. V3 makes that class of mistake structurally impossible — there is nothing for `init` to invent since it writes only the machine manifest.


**Invariants:**
- pysar init never writes author-facing prose template files, only .pysar/** machine state
- pysar migrate never modifies a non-empty author-created file, only files under .pysar/**
- .pysar/project's schema_version is the single source of truth for how .pysar/** is laid out at any given tool version

## 3. Rationale

**Counterargument:** The agent's own recommendation at comparison time was V1, not V3 — precisely because V3 wins the formal Pareto front only by scoring 0 on multi_piece_shared_state_support, same as V1, while V1 at least carries an explicit stepping-stone basis ("can later nest pieces under a project root without changing the per-piece contract") that V3 does not state. Choosing V3 means the eventual multi-piece home (needed for the already-decided TF-IDF memory engine, dec-20260718-404573a2, and for shared voice config) is deferred with no committed growth path — it will have to be designed fresh later rather than grown from something V3 already implies. That is a real, not hypothetical, cost being accepted here.

**Selected variant weakest link:** Cold-start UX is empty: `pysar init` produces only `.pysar/project`, so an author or agent with no prior context has no shared map of conventions until docs/skills explain them out-of-band. This is V3's own stated weakest_link in the portfolio, not a new observation.

## 4. Consequences

**Rollback plan:**
Triggers:
- First real dogfood session produces explicit author or agent confusion after `pysar init` (e.g. "nothing happened", no idea where to start) that isn't resolved by pointing at docs/skill guidance
- Memory-engine implementation work (dec-20260718-404573a2) gets structurally blocked by having no natural multi-piece root to attach a shared corpus/index to
- A later decision adds a project-level root anyway, making V3's flat single-manifest layout inconsistent with the rest of the system
Steps:
1. First response: add non-binding template/convention guidance in docs or a skill, without changing what `pysar init` writes to disk — cheapest fix, tries to resolve the weakest_link without touching the schema
2. If memory-engine work is blocked: reopen this ProblemCard and layer V2's project-root concept on top as an additive change (V3's per-piece manifest contract does not have to be broken to add a parent root)
3. If cold-start confusion proves unresolvable by docs alone: supersede this decision with V1, restoring minimal prose scaffolding at init
Blast radius: cmd/pysar init command and its output; any future internal piece/project package; pysar migrate command surface; onboarding docs/skills that explain post-init conventions

**Affected files:** cmd/pysar/main.go, cmd/pysar/init_test.go, .pysar/**, internal/piece/**
