# `ps-*` subcommands, `/ps` auto mode (operator's proposal)

## 1. Problem Frame

**Signal:** Pysar needs a consistent naming convention for its command surface before any commands are defined: a CLI subcommand prefix (analogous to haft's own commands) and a slash-command entry point for auto/agent mode. Operator proposes `ps-*` for individual commands and `/ps` for auto mode, motivated by brevity and wordplay (ps = Pysar initials, and 'post scriptum' / 'pssst... I have an idea'). No command list is being decided here -- only the naming/prefix convention.

**Constraints:**
- Must not enumerate or lock the actual command list -- operator explicitly deferred that
- Per dec-20260718-eafefad2 (reference-agnosticism gate): if compared against haft's own '/h-*' convention, that comparison is inspiration-grounding only (CL1 at most), never justification on its own, and must state what's Pysar-original

**Acceptance:** A prefix convention is recorded such that: (1) it is short enough for comfortable typing in a global CLI context; (2) it does not silently collide with a near-universal existing shell command in a way that risks user confusion or aliasing conflicts; (3) it carries an intentional, stated meaning (not arbitrary letters); (4) it is documented as a convention future command names must follow, without yet enumerating the command list itself.

## 2. Decision

**Selected:** `ps-*` subcommands, `/ps` auto mode (operator's proposal)

**Selection policy:** Pareto front, not a scalar winner -- all three variants (ps-*, pysar-*, wr-*) are genuinely non-dominated, each winning on different dimensions (brevity+personality vs. brand-clarity+safety vs. brevity+safety-without-brand). This is a values call, not a technical constraint problem, so the operator's stated preference for brevity/personality is the deciding factor, made with the collision risk explicitly surfaced first.

**Why selected:** Operator's explicit, informed preference: brevity and intentional wordplay (ps = Pysar initials, post scriptum, 'pssst... I have an idea') for a CLI meant to be typed many times per session. This is consistent with what V1 actually wins on in the comparison (typing_efficiency, personality_distinctiveness).

**Scope clarification (2026-07-18, corrects ambiguity in the original framing):** `ps-*`/`/ps` names the AI-agentic-tool command surface only (Claude Code-style slash commands). The console/CLI binary is named `pysar` (full name) -- a separate surface, not renamed by this decision. Slash commands are parsed by the host application's own command registry, a structurally separate namespace from shell binaries; the real Unix `ps` remains fully callable (e.g. via the same tool's Bash facility) with zero interference. See evid-20260718-444164000.

**Invariants:**
- `ps-*`/`/ps` is reserved exclusively for Pysar's agentic-tool command surface; the console/CLI binary is `pysar` and is out of scope for this decision
- This convention governs prefix/entry-point naming only -- it does not enumerate or lock the actual command list, which stays open per the frame's constraint
- Any future comparison of this convention against haft's own `/h-*` pattern stays inspiration-grounding only (CL1 max) per dec-20260718-eafefad2 -- never cited as sole justification for a Pysar naming choice

## 3. Rationale

**Counterargument (revised 2026-07-18):** Originally recorded as a real namespace collision risk; corrected after scope clarification -- `/ps` (agentic-tool slash command) and shell `ps` occupy structurally separate namespaces (host-app command registry vs. OS shell), so there is no actual technical collision, and the console binary being `pysar` removes that surface's risk too. What remains is a much smaller human-factors concern: a reader encountering `/ps` in documentation or a shared transcript, out of context, could momentarily misread it as shell `ps` output/invocation. This is a legibility nuance, not a functional collision.

**Selected variant weakest link (revised 2026-07-18):** Originally scored collision_risk=4/4 assuming `ps-*`/`/ps` might span the console surface; that assumption was wrong (console binary is `pysar`). The actual residual risk is low: only documentation/transcript legibility when `/ps` is shown out of the agentic-tool context, not a real invocation conflict. See evid-20260718-444164000 for the correction; sol-20260718-44295064's collision_risk score for V1 is now understood to overstate the risk relative to the actual product scope.

## 4. Consequences

**Rollback plan:**
Triggers (narrowed 2026-07-18 after scope clarification -- console binary is `pysar`, not `ps`, and agentic slash commands don't share a namespace with the shell, so the original 'real collision' framing no longer applies):
- Documentation/transcript legibility confusion is actually reported -- e.g. someone reading a shared `/ps` transcript out of context mistakes it for shell `ps` output or invocation
- Once real `ps-*` agentic commands ship, users report they find the abbreviation unclear or unmemorable without the wordplay explanation (a brand-recall issue, not a collision issue)
Steps:
1. Rename the prefix to `pysar-*`/`/pysar` (V2) via a new /h-decide superseding this one, reusing SolutionPortfolio sol-20260718-44295064 rather than re-exploring from scratch
2. Since no commands exist yet at decision time, renaming pre-launch costs nothing beyond updating this convention; if commands have shipped by the time this triggers, provide a deprecation-alias period rather than a hard cutover
Blast radius: Pre-code, pre-launch -- zero users depend on this prefix today, so rollback cost is currently limited to updating the convention. Cost rises materially once real commands and users exist, per this decision's medium-reversibility framing.
