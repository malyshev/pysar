# Boolean flags per host (--claude, --cursor, --codex) with if-chain dispatch

## 1. Problem Frame

**Signal:** dec-20260718-239680d4 already committed to init/onboard subcommands scaffolding a new project in an arbitrary directory; ES.enabling.agent_policy.001 already named Claude Code as the currently-supported host, Cursor/Codex experimental/deferred. Not yet decided: how pysar init selects and applies host-specific scaffolding -- operator wants --claude as the explicit flag (default when omitted), with a genuine extension point for --cursor/--codex to be added later without restructuring the command.

**Constraints:**
- Must not build a general-purpose plugin/registry system for 3 hosts, 2 of which don't exist yet -- match CLAUDE.md's own stated discipline against designing for hypothetical requirements, while still satisfying the operator's explicit 'window for extension' ask
- Must be consistent with dec-20260718-a2a24f32: init is a pysar console subcommand, not part of the ps-*/`/ps` agentic-tool surface
- Must build on the greenfield Go foundation already established (dec-20260718-817bfb74) -- plain go build/go install, no wrapper tool yet

**Acceptance:** pysar init [--claude|--cursor|--codex] [dir] is implemented such that: (1) omitting the flag defaults to Claude Code scaffolding; (2) --claude explicitly requests the same; (3) --cursor/--codex are recognized as valid flag values at the CLI-parsing level today, even though their scaffolding logic isn't implemented yet -- invoking them yields a clear 'not yet supported' message, not a parse error or silent no-op; (4) adding real Cursor/Codex support later touches only host-specific scaffold logic, not the flag-parsing/dispatch shape.

## 2. Decision

**Selected:** Boolean flags per host (--claude, --cursor, --codex) with if-chain dispatch

**Selection policy:** Pareto front, all four variants non-dominated. Operator chose V1 for its literal match to the requested flag names and lowest upfront cost for exactly one real host, consistent with CLAUDE.md's own discipline against building structure (V3's registry) for hosts that don't exist yet.

**Why selected:** Matches the operator's literally requested syntax (--claude specifically) with the least new code for the one host that's actually real today. Marked a stepping stone: if a second host is ever implemented for real, migrating to V3's adapter+registry pattern doesn't discard anything, since each host's scaffold logic already lives in its own function.


**Invariants:**
- Omitting the host flag is equivalent to --claude -- both scaffold identically
- --cursor and --codex are valid, parseable flags today even though their scaffold logic is not yet implemented -- invoking them fails loudly with a clear message, never silently
- Passing more than one host flag together is rejected with an explicit error, not silently resolved
- Each host's scaffold logic lives in its own named function from the start, so migrating to a registry pattern later (V3) requires no rewrite of that logic, only wrapping it
- This command is a pysar console subcommand per dec-20260718-a2a24f32 -- not part of the ps-*/`/ps` agentic-tool surface

## 3. Rationale

**Counterargument:** V2 (single --host=claude enum flag) makes an ambiguous multi-host request structurally impossible rather than requiring a hand-written check -- the strongest case against V1 is that it trades a real, if small, correctness guarantee for literal syntax match alone. If the mutual-exclusivity check is ever forgotten or has a bug, `--claude --cursor` could silently do the wrong thing instead of being rejected outright by construction.

**Selected variant weakest link:** misuse_safety scored worst of the four (1/4): nothing in the flag shape itself stops `pysar init --claude --cursor` from being passed together. Requires an explicit, hand-written mutual-exclusivity check at parse time, not structurally prevented like V2's single enum flag would be.

## 4. Consequences

**Rollback plan:**
Triggers:
- A second host (Cursor or Codex) is actually implemented for real, not just stubbed -- the trigger to migrate to V3's adapter+registry pattern
- The hand-written mutual-exclusivity check is found to have a gap (e.g. --claude --cursor silently does something unintended) -- trigger to reconsider V2's structurally-safe enum flag instead
Steps:
1. If a second real host arrives: introduce V3's hostAdapter interface and registry map, migrating each existing per-host scaffold function into an adapter implementation -- no scaffold logic needs to be rewritten, only wrapped
2. If the mutual-exclusivity check proves insufficient: switch the flag surface to V2's single --host=claude enum flag, reusing SolutionPortfolio sol-20260718-9dc51a75 via a new /h-decide rather than re-exploring
Blast radius: Pre-implementation -- no init command exists yet, so this is establishing the first shape, not migrating real users off an existing one.

**Affected files:** cmd/pysar/**, internal/init/**
