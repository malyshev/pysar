# Classical local statistical similarity (TF-IDF / n-gram overlap), no ML model at all

## 1. Problem Frame

**Signal:** V2 (embedding-based semantic similarity) was the leading technique for catching paraphrased repetition, but 'embeddings' implies either a local ML model or a network call somewhere -- neither is free, and the target user for this question is explicitly non-technical (operator's proxy: 'even a homewife writing kitchen stories'), not someone comfortable managing API keys or config files. Operator is asking whether V2 can be fully standalone and easy to install for such a user, what concrete resources it needs, and whether 'memory' should instead be delivered as a premium hosted (SaaS) feature rather than bundled into the local binary.

**Constraints:**
- Must not silently violate dec-20260718-239680d4's invariant that the distributed Pysar binary remains a single self-contained executable requiring no separate runtime install -- a variant may accept that trade-off, but must say so explicitly
- Per ES.enabling.effect_boundaries.001, only the platform-adapter/imperative-shell layer may touch network -- any network-dependent variant must fit that existing boundary, not invent a new one
- If a SaaS/hosted option is considered, that is a business-model decision (ongoing hosting cost, pricing, support), not purely a technical one -- must be flagged as such, not decided as if it were only an engineering choice

**Acceptance:** A delivery-model variant is selected such that, per variant: (1) it's stated plainly whether end-user setup requires anything beyond running the single Pysar installer/binary -- no manual API key entry, no account signup, no separate dependency install -- a concrete yes/no, not a vague 'easy'; (2) real resource costs are named (approximate binary size delta, disk, RAM, network requirement); (3) it's explicit whether the variant preserves or breaks the 'single self-contained executable, no separate runtime' invariant already recorded in dec-20260718-239680d4, and if it breaks it, that conflict is surfaced, not hidden.

## 2. Decision

**Selected:** Classical local statistical similarity (TF-IDF / n-gram overlap), no ML model at all

**Selection policy:** Pareto front, not a scalar winner -- all four variants (V1 bundled local model, V2 user-supplied API key, V3 Pysar SaaS, V4 classical local stats) were non-dominated. V2 was ruled out despite formal non-domination: it fails the problem's own central acceptance criterion (non-technical installability) outright with no compensating advantage. Between the remaining three, operator chose to start with V4 as the zero-risk, zero-conflict stepping stone, explicitly deferring the harder V1-vs-V3 choice (CGo binary-simplicity cost vs. SaaS infrastructure commitment) until real usage shows whether V4's recall ceiling is actually a problem.

**Why selected:** Zero new dependency, zero conflict with the existing Go binary decision (dec-20260718-239680d4), best-tied installability for a non-technical persona, and the cheapest possible way to ship real value today. Works equally well in single-user local mode and in an operator-hosted multi-tenant server/web-chat deployment (per-project isolation and low per-tenant cost, confirmed against dec-20260718-239680d4's own acceptance criterion for multi-project coexistence on one machine). Adopted as the permanent free/default tier, not a throwaway prototype -- staged rollout plan already recorded in note-20260718-cfa48124: V3 (Pysar-operated SaaS) remains available as a future premium upgrade with an explicit backfill step, not an assumed free toggle.


**Invariants:**
- V4 (classical local statistical similarity) is the default, free-tier memory engine for every Pysar project unless/until a premium tier is built
- A memory on/off toggle must be available per project/session, gating whether the drafting pass calls the memory-check step at all -- engine-agnostic, must keep working unchanged if the backend is later upgraded to V3
- Per-project isolation is mandatory: one project's memory index must never be queryable by or leak into another project's results, whether single-user local or multi-tenant server-hosted
- This decision does not preclude a future premium tier (V3, Pysar-operated SaaS) being added later per the staged rollout plan (note-20260718-cfa48124); any such addition requires an explicit backfill/re-index step for upgrading users, not an assumed free config toggle
- V1 (bundled local CGo model) remains available as a documented fallback if V4's recall proves insufficient and the operator prefers to stay fully local rather than go the SaaS route

## 3. Rationale

**Counterargument:** V1 (bundled local embedding model) would deliver full semantic recall while staying just as offline/zero-config as V4 -- the strongest case against choosing V4 is that it may simply underdeliver on the actual promise that motivated this whole feature (catching meaning-level repetition), and real usage may show the operator needs V1 or V3 anyway, making V4's build partially throwaway if the upgrade path isn't designed cleanly from the start.

**Selected variant weakest link:** repetition_recall scored worst of the four (2/4): TF-IDF/n-gram overlap still depends on some shared vocabulary between two passages, so it will miss a genuine full-reword paraphrase with no shared distinctive words -- the hardest and most literal version of the operator's own motivating example ('I woke up at 2 A.M.' vs. a completely different-wording opener with the same beat). This is the one case V4 is not expected to catch.

**Predictions:**
| Claim | Observable | Threshold |
|-------|------------|-----------|
| V4's classical local similarity (TF-IDF/n-gram overlap) catches a meaningful majority of real repetition cases in the operator's own writing, even though it structurally cannot catch a full-reword paraphrase with zero shared vocabulary | Running V4's technique against the existing Medium corpus (~64 articles) and checking how many known/suspected repeats (openings, examples) it actually flags vs. misses | V4 reliably catches literal-and-near-literal repeats (comparable to or better than plain lexical FTS matching), and the operator judges the false-negative rate on true paraphrase acceptable for a free-tier default |
| V4 works correctly and without excessive cost in a server-hosted, multi-tenant deployment (per-project isolation, concurrent access) once/if the operator builds the server/web-chat surface | Per-project index isolation holds (no cross-tenant leakage) and storage/query cost scales roughly linearly, not superlinearly, with number of tenants/projects | No observed cross-tenant data leakage; aggregate cost for N tenants stays within a small constant factor of N times single-tenant cost |

## 4. Consequences

**Rollback plan:**
Triggers:
- Real usage (against the operator's own Medium corpus or new Pysar-authored pieces) shows V4's recall ceiling is a material problem -- genuine paraphrased repeats with no shared vocabulary go unnoticed at a rate the operator judges unacceptable for a free-tier default
- Sufficient user demand emerges to justify building V3 (Pysar-operated SaaS) as a premium upgrade tier, per the staged rollout plan in note-20260718-cfa48124
Steps:
1. If recall is the trigger: build V1 (bundled local model, stays offline) or escalate directly to V3 (SaaS), reopening SolutionPortfolio sol-20260718-6db63ef2 and binding via a new /h-decide rather than re-exploring from scratch
2. If premium demand is the trigger: build V3 with an explicit, designed backfill/re-index step for upgrading users' existing V4 indexes to hosted-semantic quality -- not an assumed free config toggle, per note-20260718-cfa48124
3. V4 remains the free-tier default in either case -- this decision does not need to be reversed even if V3 is added later, only supplemented
Blast radius: Pre-implementation -- no memory engine exists in any form yet, so switching or adding techniques later costs re-engineering the indexing/query layer, not migrating live user data. Once real users have V4-built indexes, upgrading them to V3 requires the backfill step already flagged as real work, not free.
