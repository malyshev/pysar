# Mirror Claude scaffold into Cursor-native paths

## 1. Problem Frame

**Signal:** Operator wants Pysar usable inside Cursor IDE as the next AI-editor host after Claude Code. Today: pysar init --cursor is intentionally stubbed (dec-20260718-8278c494) with 'not yet supported'; all ps-* skill bodies, permission pre-approvals, and MCP launch config ship only under assets/claude/ into ~/.claude/skills + project .claude/settings.json + .mcp.json. A Cursor author who installs the pysar binary still has no host-native way to invoke the pipeline (equivalent of /ps, /ps-intake, …) or to get pysar serve wired with the same mechanical-I/O contract. Prior problem prob-20260718-35d97dc6 only covered flag/dispatch shape, not real Cursor scaffold content. 'Support Cursor' is the proposed solution label — the broken condition is missing Cursor-host scaffolding for the already-shipped agentic surface.

**Constraints:**
- Preserve dec-20260718-8278c494 flag surface (--cursor stays a boolean; mutual exclusivity with --claude/--codex)
- Do not weaken host-agnostic skill content invariants (skills must not become Claude-only prose; Cursor packaging may differ, editorial rules must not)
- Piece I/O remains via pysar MCP (dec-20260719-fa0366dd class of decision) — no regression to agent Write/Bash for .pysar/**
- Implementing a second real host is the recorded trigger to migrate to V3 hostAdapter+registry from sol-20260718-9dc51a75 / dec-20260718-8278c494 consequences — do not invent a third dispatch shape without revisiting that decision
- Codex remains out of scope for this problem unless it falls out of a shared adapter with zero extra product commitment
- No Medium/haft copy-paste of host conventions beyond CL1 inspiration

**Acceptance:** From a clean scratch directory, `pysar init --cursor` exits 0 and writes a Cursor-host project such that: (1) Cursor can launch `pysar serve` as an MCP server for that project without hand-editing config; (2) the operator can invoke an agentic entry equivalent to the Claude /ps orchestrator (and at least the stage skills /ps-intake through /ps-humanize + onboarding) with instructions that match the host-agnostic skill bodies already shipped; (3) piece persistence still goes through pysar MCP tools (not raw Write/Bash for .pysar/**); (4) `pysar init --claude` behavior is unchanged; (5) a short smoke: open the project in Cursor, run the entry command with a one-sentence idea, and observe a provisional piece directory under .pysar/pieces/ with brief.md written via MCP.

## 2. Decision

**Selected:** Mirror Claude scaffold into Cursor-native paths

**Selection policy:** Maximize cursor_pipeline_fidelity subject to claude_regression_risk staying on the computed Pareto front (prefer <=3). Operator overrode advisory V3 by requiring full Cursor pipeline parity this cycle (note-20260808-46fa5198). false_support_risk is observation-only — do not optimize by shipping thin MCP and calling it support.

**Why selected:** Operator explicitly required full Cursor pipeline parity this cycle. V1 is the only front member that aims at Claude-equivalent orchestrator + stage skills + MCP wiring without refactoring the working Claude init path. It keeps --cursor as a real host scaffold under the existing boolean flag surface (dec-20260718-8278c494) and isolates Claude risk to 'add scaffoldCursor', not 'reshape registry'.


**Invariants:**
- pysar init --cursor exits 0 and writes a real Cursor host scaffold (no longer the not-yet-supported stub)
- pysar init --claude behavior and asset paths remain unchanged by this decision's Cursor work
- Flag surface stays --claude/--cursor/--codex booleans with mutual exclusivity (dec-20260718-8278c494)
- Piece persistence goes through pysar MCP tools, not agent Write/Bash for .pysar/**
- Skill editorial bodies stay host-agnostic in content; only install paths and host permission/MCP dialects differ
- Codex remains stubbed unless it falls out with zero extra product commitment
- This decision fulfills --cursor as a second real host under 8278c494 without requiring the registry migration in the same change set; registry remains an allowed later supersession, not blocked

**Pre-conditions:**
- [ ] pysar binary builds; existing Claude init tests pass before Cursor work lands

**Post-conditions:**
- [ ] Acceptance criteria of prob-20260808-e2baaf41 met or explicitly deferred items listed in measure
- [ ] dec-20260718-8278c494 prediction that --cursor prints not-yet-supported is superseded for Cursor by this decision's new predictions

## 3. Rationale

**Counterargument:** dec-20260718-8278c494 already named 'second real host' as the trigger to migrate to the hostAdapter+registry pattern (portfolio V3). Choosing a second ad-hoc scaffold clone deliberately pays init_structure_debt and middling skill_body_reuse that V3 was designed to avoid — we may rebuild this seam within months when Codex or skill-source sharing forces the registry anyway.

**Selected variant weakest link:** Cursor's skill/permission/MCP surface is not isomorphic to Claude's — a faithful mirror can still leave gaps (no exact twin of .claude/settings.json allow-lists), so claimed parity may be fake until verified in a live Cursor session with a real piece write via MCP.

**Rejected alternatives:**
| Variant | Verdict | Reason |
|---------|---------|--------|
| Mirror Claude scaffold into Cursor-native paths | **Selected** | Operator explicitly required full Cursor pipeline parity ... |
| Thin Cursor init: MCP + AGENTS.md pointer only | Rejected | Fails the operator's parity requirement — no native stage/orchestrator skill surface; high false-support risk if README claims Cursor support. |
| Shared skill core + hostAdapter registry (V3 trigger) | Rejected | Highest Claude regression risk this cycle; operator chose parity without restructuring the working Claude path. Registry remains the recorded follow-on when structure debt hurts, not a blocker to shipping Cursor now. |
| Cursor Rules/Commands packaging without global skill sync | Rejected | Weaker pipeline fidelity than a Claude-shaped skill install; project-local copies drift from binary-embedded skill versions and diverge from the Claude global-sync ops model. |
| Dual-host init: Claude defaults remain, --cursor adds Cursor files alongside | Rejected | Dominated by V1 on the comparison — same fidelity target with worse structure debt, time, and false-support risk. |
