# Full removal from target-system scope now -- amend both TS sections

## 1. Problem Frame

**Signal:** Operator wants the platform-scoped publish checklist (+ cover) capability excluded from Pysar's current responsibility -- judged unnecessary burden at this stage. This capability is written directly into already-approved target-system spec sections: TS.environment-change.001 names it as part of the environment-change statement and one of the four core use cases ('Go from idea to ship-ready body plus platform publish checklist'); TS.target.boundary.001 lists it explicitly in-scope ('Pysar produces the checklist, not the post'); ES.enabling.work_methods.001's actor/trigger table assigns it to the platform-adapter layer, triggered by 'I'm ready to post'. The original product pitch also promised it as an outcome. Excluding it is not a small implementation tweak -- it walks back language in specs a human already approved.

**Constraints:**
- Must not silently leave TS.environment-change.001 or TS.target.boundary.001 inaccurate -- whatever is decided, the spec sections' actual text must be brought into agreement with it, not left contradicting the new scope
- Must not contradict dec-20260718-20a08f83's pipeline mechanism, which already assumed a 'packaging' pass exists in some form -- this decision narrows what packaging promises, it doesn't reopen how passes are dispatched
- Should reuse the already-validated staged-rollout pattern from dec-20260718-404573a2 (free/default now, explicitly deferred premium tier later) if a comparable shape fits here, rather than inventing a new deferral mechanism

**Acceptance:** A scope-reduction approach is selected such that: (1) it states plainly whether already-approved TS spec sections get amended now, deferred with an explicit annotation, or left untouched with the gap absorbed elsewhere; (2) 'unnecessary responsibility' is grounded concretely -- specifically the ongoing burden of maintaining accurate, up-to-date platform-specific publishing requirements across many possible target platforms, distinct from and additional to core editorial-engine work; (3) it names what happens, concretely, when an author says 'I'm ready to post' under the new scope -- not left as an unanswered gap.

## 2. Decision

**Selected:** Full removal from target-system scope now -- amend both TS sections

**Selection policy:** Pareto front -- V3 dominated by V4; V1, V2, and V4 non-dominated. Operator chose V1 over the advisory recommendation (V4), preferring V1's unambiguous, fully-clean boundary over V4's cheaper-to-reverse staged approach.

**Why selected:** Operator chose the cleanest, most unambiguous option -- no partially-promised, partially-real state. Full removal matches 'unnecessary responsibility' literally and completely: nothing in the target-system spec continues to promise platform publish checklist generation, current or forward-looking.


**Invariants:**
- TS.environment-change.001 and TS.target.boundary.001 no longer name platform publish checklist (or cover generation) as part of Pysar's current environment-change promise or in-scope boundary
- 'I'm ready to post' under current scope means the piece is marked ship-ready; it does not trigger checklist or cover generation
- ES.enabling.work_methods.001's actor/trigger table is brought into consistency with this removal, not left referencing a capability no longer in scope
- Reintroducing this capability later requires a fresh problem-framing cycle, not a flag flip -- no extension point is pre-drawn by this decision

**Spec sections:**
- TS.environment-change.001
- TS.target.boundary.001
- ES.enabling.work_methods.001

## 3. Rationale

**Counterargument:** V4 (staged exclusion with an explicit extension point) would have achieved the exact same immediate responsibility reduction while being materially cheaper to reverse later, by reusing the already-validated memory-engine staging pattern. The strongest case against V1 is that it pays a real, avoidable future cost (re-amending TS sections from scratch if this capability is wanted back) for a marginal honesty gain over V4, which scored nearly as well on promise_honesty.

**Selected variant weakest link:** Highest spec_amendment_cost and worst future_reintroduction_cost of the three real contenders: bringing this capability back later requires a fresh problem-framing and TS-amendment cycle from a clean removal, not a pre-drawn extension point. Also walks back language from the original product pitch ('Outcome: body you trust + publish checklist for your target platform'), which may need reflecting in any author-facing promise material outside these two spec sections.
