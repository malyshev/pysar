# Add one new shared field: a structured Rules list, usable by both kinds

## 1. Problem Frame

**Signal:** dec-20260718-ab150a73 already decided VoiceProfile and StyleProfile share exactly one Go struct type (Tone, Formality, SentenceLength, Register, BannedPhrases, Notes, Goldens) with "no divergent format" as an explicit invariant. That schema's field names and the MCP tool descriptions built on it (save_voice_profile's "tone": "How the author wants to come across, e.g. warm, direct, a little dry") were authored with voice/personality content specifically in mind. Operator now wants a /ps-style command and has explicitly distinguished the two: "Style is not personality... the shared rules for structure, sentences, word choice, and formatting... put the main point first, keep sentences short, use active voice, prefer everyday words, be specific, cut what doesn't earn its place." Several of the operator's own example style rules (main-point-first ordering, active voice, cut-what-doesn't-earn-its-place) have no clean home in the current four structured fields -- Tone in particular reads as purely voice-specific. Need to decide how Style's actual content populates (or extends) the shared schema before building /ps-style, rather than forcing a mismatch or silently diverging from the already-decided invariant.

**Constraints:**
- Any change must not silently contradict dec-20260718-ab150a73's "no divergent format" invariant without an explicit supersede -- if the answer requires diverging, that must be examined and decided, not assumed
- Whatever schema shape wins must still satisfy dec-20260718-5570376d's completeness-validator requirement (structured fields + goldens both checkable)
- Must not require internal/onboarding's already-shipped generic machinery (Render, Validate, TemplatesDir, Slug, WrapTemplate/UnwrapTemplate) to be duplicated per-Kind unless the chosen variant explicitly justifies that cost
- The /ps-style skill's questions to the author must read naturally as style questions, not voice questions wearing a style disguise
- Must not disturb the already-shipped, already-dogfooded VoiceProfile behavior or its saved .pysar/voice.md format

**Acceptance:** A schema shape is chosen such that Style's actual content (main-point-first structure, short sentences, active voice, everyday words, specificity, editorial cutting) has a genuinely fitting structured home -- not force-fit into voice-flavored field names or dumped entirely into free text -- while /ps-style and /ps-voice both remain built on dec-20260718-5570376d's schema-only, completeness-validated architecture. Verified by actually authoring a real style profile against the chosen shape and confirming it reads as genuine style guidance, not repurposed voice fields.

## 2. Decision

**Selected:** Add one new shared field: a structured Rules list, usable by both kinds

**Selection policy:** Pareto front over target-role dimensions (structural_content_fit, voice_field_semantic_honesty), gated by the constraint (invariant_preserved_without_supersede) which must hold true; shared_machinery_reuse is observation-role, watched but never optimized (Anti-Goodhart). Declared before scoring (sol-20260719-e6edeb02).

**Why selected:** V3 strictly dominates every variant that preserves the existing "one shared type" invariant (V1, V2, V4) on both target dimensions simultaneously (structural_content_fit, voice_field_semantic_honesty), and matches V5's content fit and semantic honesty without V5's cost of reopening an already-shipped, already-dogfooded decision (dec-20260718-ab150a73) or reworking already-tested generic machinery (Render, Validate, TemplatesDir, WrapTemplate). A single new Rules []string field gives the operator's own listed style content (main-point-first ordering, active voice, everyday words, editorial cutting) a genuine, individually-queryable home, while Voice profiles remain free to leave it thin or unused -- both kinds still share one interchangeable type.


**Invariants:**
- Profile stays one shared Go struct type across all Kinds (voice, style, and any future kind) -- Rules is available to any Kind, never Kind-exclusive, preserving dec-20260718-ab150a73's 'no divergent format' invariant
- Already-shipped Voice content (.pysar/voice.md, the built-in generic voice template, saved voice templates) remains valid and unaffected -- Rules is additive/optional, never a breaking change to existing serialized content
- Rules entries are short, individually actionable imperative statements -- not a dumping ground for content that belongs in Notes or is better demonstrated via Goldens

## 3. Rationale

**Counterargument:** Adding a new field, even a small bounded one, to an already-shipped, already-dogfooded shared struct is still schema growth that every future profile kind inherits whether it needs Rules or not. More importantly, this decision creates a real, unresolved editorial-line question it does not itself answer: when should an author state something as a Rule versus demonstrate it as a Golden? If /ps-style's conversation design doesn't draw that line clearly, Rules could become a dumping ground with no more discipline than V4 (the "everything in Notes" variant) this decision was chosen specifically to beat.

**Selected variant weakest link:** Render/Validate (and the MCP tool schemas built on Profile) need a small, real code change to handle this new field -- a genuine, if bounded, extension of already-shipped, already-tested code, not a pure relabeling. This was V3's own stated weakest_link at exploration time.

## 4. Consequences

**Rollback plan:**
Triggers:
- Rules and Goldens prove impossible to keep editorially distinct in practice -- authors (or the /ps-style skill) consistently misuse one for the other
- The completeness validator's Rules requirement (however it's set) proves wrong in practice -- too strict (blocks reasonable profiles) or too loose (allows a near-empty Rules list to pass)
- Voice profiles start accumulating meaningful Rules content, blurring the intended 'Style's primary field, Voice's optional one' asymmetry into something that needs its own examination
- A genuine third profile kind emerges whose content doesn't fit Rules either, suggesting the schema needs a different kind of extension entirely
Steps:
1. If Rules/Goldens boundary blurs: tighten /ps-style's and /ps-voice's own conversational guidance on when to use which, before touching the schema again
2. If the validator's Rules requirement is wrong: adjust the specific threshold (min count, or optional-vs-required by Kind) rather than removing the field
3. If Voice's use of Rules grows unexpectedly: treat that as new evidence worth its own haft_note or ProblemCard, not an automatic reason to revisit this decision
4. If a third kind doesn't fit: reopen via a new /h-frame scoped to that kind's actual content, reusing this decision's reasoning as precedent rather than assuming Rules must also serve it
Blast radius: internal/onboarding/profile.go (Profile struct + Render/Validate), internal/mcpserver/tools_voice.go (save_voice_profile/save_voice_template schemas gain an optional rules field for symmetry), the not-yet-built internal/mcpserver/tools_style.go and cmd/pysar/assets/claude/skills/ps-style/SKILL.md and cmd/pysar/assets/templates/style/ (this decision's schema choice is a precondition for building all three)
