# Shared skill core + hostAdapter registry (V3 trigger)

## 1. Problem Frame

**Signal:** Operator wants Pysar usable inside Cursor IDE as the next AI-editor host after Claude Code. Today: pysar init --cursor is intentionally stubbed (dec-20260718-8278c494) with 'not yet supported'; all ps-* skill bodies, permission pre-approvals, and MCP launch config ship only under assets/claude/ into ~/.claude/skills + project .claude/settings.json + .mcp.json. A Cursor author who installs the pysar binary still has no host-native way to invoke the pipeline (equivalent of /ps, /ps-intake, …) or to get pysar serve wired with the same mechanical-I/O contract. Prior problem prob-20260718-35d97dc6 only covered flag/dispatch shape, not real Cursor scaffold content. 'Support Cursor' is the proposed solution label — the broken condition is missing Cursor-host scaffolding for the already-shipped agentic surface.

**Constraints:**
- Preserve dec-20260718-8278c494 flag surface (--cursor stays a boolean; mutual exclusivity with --claude/--codex)
- Do not weaken host-agnostic skill content invariants (skills must not become Claude-only prose; Cursor packaging may differ, editorial rules must not)
- Piece I/O remains via pysar MCP (dec-20260719-fa0366dd class of decision) — no regression to agent Write/Bash for .pysar/**
- Implementing a second real host is the recorded trigger to migrate to V3 hostAdapter+registry from sol-20260718-9dc51a75 / dec-20260718-8278c494 consequences — do not invent a third dispatch shape without revisiting that decision
- Codex remains out of scope for this problem unless it falls out of a shared adapter with zero extra product commitment
- No Medium/haft copy-paste of host conventions beyond CL1 inspiration

**Acceptance:** From a clean scratch directory, `pysar init --cursor` exits 0 and writes a Cursor-host project such that: (1) Cursor can launch `pysar serve` as an MCP server for that project without hand-editing config; (2) the operator can invoke an agentic entry equivalent to the Claude /ps orchestrator (and at least the stage skills /ps-intake through /ps-humanize + onboarding) with instructions that match the host-agnostic skill bodies already shipped; (3) piece persistence still goes through pysar MCP tools (not raw Write/Bash for .pysar/**); (4) `pysar init --claude` behavior is unchanged; (5) a short smoke: open the project in Cursor, run the entry command with a one-sentence idea, and observe a provisional piece directory under .pysar/pieces/ with brief.md written via MCP.

## 2. Decision

**Selected:** Shared skill core + hostAdapter registry (V3 trigger)

**Selection policy:** After CL1 inspection of Me/haft init (Cursor/Codex packaging), maximize skill_body_reuse and minimize init_structure_debt while still meeting full Cursor pipeline parity acceptance. Claude regression risk is mitigated by golden Claude init tests before --cursor goes live — not treated as a hard eliminate. Supersedes dec-20260808-a0e5e82f, which was bound before Haft host-init precedent was available. false_support_risk remains observation-only.

**Why selected:** Operator required full Cursor pipeline parity, then discovered haft already ships the cleaner shape: one skill corpus + per-host install paths/MCP dialects (Cursor: .cursor/mcp.json + ~/.cursor/skills; Codex: separate TOML/dialect later). V3 is that shape for Pysar and matches dec-20260718-8278c494's recorded 'second real host → registry' trigger. The earlier V1 bind was under incomplete evidence and is superseded.


**Invariants:**
- One host-neutral skill corpus is the source of truth for ps-* editorial instructions
- hostAdapter (or equivalent registry) owns only install paths, MCP JSON/TOML dialect, and host permission/settings files
- Flag surface remains --claude/--cursor/--codex booleans with mutual exclusivity (dec-20260718-8278c494)
- pysar init --cursor exits 0 with real Cursor scaffold (not not-yet-supported)
- pysar init --claude behavior for authors remains equivalent (golden tests)
- Piece I/O stays on pysar MCP tools
- Cursor packaging follows haft CL1 targets: .cursor/mcp.json with ${workspaceFolder}, skills under ~/.cursor/skills (or --local project .cursor/skills if Pysar adds local later)
- Codex remains stubbed this cycle unless zero-extra-commitment fallout
- Supersedes dec-20260808-a0e5e82f (Mirror Claude scaffold)
