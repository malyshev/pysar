# Structured per-piece run-log -- append-only record of every pass that touched a piece

## 1. Problem Frame

**Signal:** Pysar's editorial engine (per ES.enabling.architecture.001's skills/routing layer and ES.enabling.work_methods.001's actor/trigger/closing-check table) is currently specified but not enforced -- as designed today, it would rely on an LLM reading Markdown skill files and 'understanding' which pass to apply, the same shape as the operator's own Medium prototype, which the operator just identified as lacking any structural backstop: nothing prevents silently skipping a step, misrouting intent to the wrong pass, or completing a piece with no queryable record of what actually happened to it. This gap is real today, before any code exists, because it is baked into the current architecture decision's assumptions, not something introduced by a bug.

**Constraints:**
- Must be Pysar-original in mechanism -- haft's own typed-graph/carrier model is inspiration only (CL1 max per dec-20260718-eafefad2), not something Pysar imports or depends on at runtime; haft governs Pysar's own engineering decisions, it is not a runtime dependency of the shipped product
- Must fit inside the already-decided 5-layer architecture (ES.enabling.architecture.001) -- this is naturally an Artifact/state-layer concern, alongside the draft/ship-ready/checklist artifacts already specified in ES.enabling.work_methods.001
- Must not require the non-technical author to do anything manual -- no tagging, no explicit logging commands, consistent with the already-recorded author-surface promise
- Must be complementary to, not overlapping with, the memory engine just decided (dec-20260718-404573a2) -- that governs cross-piece repetition; this governs within-piece/per-session pass accountability

**Acceptance:** Given a piece that moves through Pysar's editorial engine (idea -> draft -> edit passes -> ship-ready), there is an observable, queryable record of which passes actually ran, in what order, with what relevant inputs (e.g. which voice/persona config was active, whether voice-lock ran before or after packaging as TS.target.boundary.001 requires) -- checkable after the fact without re-reading an AI chat transcript, and at least one known bad sequence (voice-lock before packaging) is either prevented outright or reliably detectable, not merely hoped against.

## 2. Decision

**Selected:** Structured per-piece run-log -- append-only record of every pass that touched a piece

**Selection policy:** Pareto front, all four variants non-dominated. Operator chose to combine V1 (best queryability and creative_flexibility, moderate build_cost) as the primary mechanism with a single targeted enforcement check drawn from V2's shape, rather than picking one point on the front wholesale -- a deliberate hybrid rather than a pure single-variant selection.

**Why selected:** V1 directly satisfies the acceptance criterion (a queryable record of what actually happened to a piece, checkable without re-reading a chat transcript) at moderate build cost, and does not risk fighting non-linear authoring the way V3's full state machine could. Layered with one specific, already-named enforcement check borrowed from V2's pattern -- voice-lock must not fire before packaging (per TS.target.boundary.001's deontics perspective) -- rather than adopting V2's general invariant-checking layer wholesale or committing to V3's complete state machine. A deliberate hybrid: observability everywhere, real prevention for the one concrete bad sequence already identified.


**Invariants:**
- Voice-lock must never execute against a piece before that piece has reached a 'packaged' state -- enforced as a real code check in the routing layer, not merely a documented rule
- Every pass that runs against a piece (scaffolding, draft edit, research opt-in, voice-lock, packaging) appends a structured, timestamped entry to that piece's run-log in the Artifact/state layer -- the author never has to do this manually
- The run-log is purely additive/observational for every pass except the one voice-lock/packaging check -- this decision does not silently expand into full invariant-checking for every pass without a future explicit decision
- This mechanism is complementary to, not a replacement for, dec-20260718-404573a2's cross-piece memory engine -- the run-log tracks within-piece pass history, the memory engine tracks cross-piece repetition
- V3 (formal state machine) and V2's fuller invariant-checking pattern remain documented escalation paths if real usage shows this hybrid is insufficient, per the rollback plan

## 3. Rationale

**Counterargument:** V3 (formal state machine) would give a much stronger guarantee across the piece's entire lifecycle, not just one hand-picked invariant. The strongest case against this hybrid is that it only fully solves the one case everyone already worried about -- the broader problem that motivated this ADR (Medium's gap: ANY silently skipped step, not just voice-lock ordering) is only addressed at the observability level by this decision, not prevented. Future misrouting beyond voice-lock/packaging remains detection-only.

**Selected variant weakest link:** V1's own weakest link carries forward for every pass except the one enforced check: any other, not-yet-named bad sequence (e.g. research opt-in being silently skipped) is still only detectable via the log after the fact, not prevented. Real prevention under this decision is limited to voice-lock/packaging ordering specifically.

## 4. Consequences

**Rollback plan:**
Triggers:
- The run-log reveals (or fails to reveal, due to missing entries) that bad sequences beyond voice-lock/packaging are recurring -- signal that more invariants need real enforcement, not just logging
- The voice-lock/packaging check itself proves too rigid -- a legitimate creative reason to allow voice-lock before packaging emerges that the check currently blocks, echoing V3's flagged flexibility risk on a smaller scale
Steps:
1. If more bad sequences recur: add additional named invariants one at a time, escalating toward V2's general pattern, reusing SolutionPortfolio sol-20260718-c931fd4a via a new /h-decide rather than re-exploring from scratch
2. If the voice-lock check is too rigid: relax or parameterize it (e.g. require explicit author confirmation to bypass) rather than removing structural enforcement entirely
3. If neither is sufficient and full lifecycle prevention becomes necessary: escalate to V3 (formal state machine), reusing the same portfolio
Blast radius: Pre-implementation -- no editorial-engine code exists yet, so refining or escalating this mechanism later costs re-engineering the routing/logging layer, not migrating real piece data. Once real pieces have run-logs, a future state-machine migration would need to backfill/interpret those logs into formal states.
