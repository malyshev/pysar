# internal/cli command registry that renders usage from registered cmds

## 1. Problem Frame

**Signal:** Running `pysar` with no args currently prints `pysar: hello world` (cmd/pysar/main.go). That was enough to prove the build/install loop (dec-20260718-817bfb74) but is not a usable product surface: a newly installed or returning user gets no statement of what Pysar is, what surfaces it has (console CLI vs agentic /ps), what to try next (e.g. init), or how to get help/version. Operator wants a meaningful intro comparable in job-to-be-done to the dogfood CLI's bare-invoke output (purpose blurb + surfaces + examples + usage) — haft is inspiration only (CL1 max per dec-20260718-eafefad2), not a template to copy. Subcommands already exist (init, --version) but are undiscoverable from the default path.

**Constraints:**
- Must not copy-paste haft's blurb or command list; any dogfood citation is CL1 inspiration with explicit Pysar-original divergence (dec-20260718-eafefad2)
- Console binary remains `pysar`; agentic `ps-*`/`/ps` naming (dec-20260718-a2a24f32) must not be conflated as if bare `pysar` were the slash-command surface
- Must not invent or imply subcommands that do not exist yet — only document real commands (today: init, --version) plus honest pointers for deferred surfaces
- Plain Go toolchain only (dec-20260718-817bfb74) — no new CLI framework required by this problem unless a variant explicitly accepts that cost
- Intro text must respect author-surface/harness-surface term map: no intake/staff-edit/sharpen/SEO vocabulary forced onto users

**Acceptance:** Invoking `pysar` with no arguments (and ideally `pysar --help` / `pysar help` if chosen) prints a short, accurate product intro that: (1) states what Pysar is in author-facing or clear console language without leaking internal phase names; (2) names at least the console entry actions that exist today (e.g. init, --version) with one-line purpose each; (3) gives at least one copy-pastable example; (4) exits 0 (or a documented help exit code) without side effects. Observable: `pysar` output no longer contains `hello world` and a cold reader can answer 'what is this and what do I run next?' from stdout alone.

## 2. Decision

**Selected:** internal/cli command registry that renders usage from registered cmds

**Selection policy:** Prefer the variant that delivers a meaningful bare-invoke intro AND keeps the listed commands a single source of truth with the dispatcher, when incremental build cost is near-zero (~50–80 LOC, no new deps). Reject YAGNI/'premature abstraction' as a selection criterion when the structural alternative's cost is bounded and small (note-20260718-c1b9df53). Framework adoption (cobra) deferred until flag/subcommand complexity justifies a dependency.

**Why selected:** V4 removes V1's real failure mode (usage banner drifting from the switch) at near-zero cost: a thin name+summary+Run registry renders the command list for bare `pysar` / help while dispatch uses the same registration. Operator explicitly rejected rejecting this as premature. Product intro copy (header) stays hand-authored Pysar-original text; only the command catalog is generated from the registry. Stays dependency-free and compatible with plain Go toolchain (dec-20260718-817bfb74).


**Invariants:**
- Bare `pysar` (no args) renders usage via the registry — not a disconnected hello-world string
- Usage lists only registered console commands that actually exist; no invented subcommands
- Registry stays thin: name, summary, run (plus usage render) — not a general CLI framework
- No third-party CLI dependency required by this decision
- Intro header copy is Pysar-original; haft wording is CL1 inspiration only (dec-20260718-eafefad2)
- Console binary remains `pysar`; do not conflate with agentic ps-*/`/ps` surface (dec-20260718-a2a24f32)

**Spec sections:**
- TS.target.role.001

**Post-conditions:**
- [ ] `go install ./cmd/pysar` then `pysar` shows the intro
- [ ] `pysar init` and `pysar --version` still work

**Admissibility:**
- NOT: Copy-pasting haft's blurb as Pysar's identity
- NOT: Listing commands in usage that are not registered/runnable
- NOT: Introducing cobra/urfave solely to satisfy this intro decision
- NOT: Using 'premature abstraction' to revert to dual-maintained static banners without naming a concrete cost

## 3. Rationale

**Counterargument:** V1 ships the same user-visible intro faster with a single string in main, and with only init + --version today the dual-edit drift has not bitten yet — paying for a registry package before the third command lands may be pure ceremony if command growth stalls.

**Selected variant weakest link:** If the registry is overbuilt into a mini-framework (flags, aliases, middleware) before those needs exist, the API can be wrong once and require a rewrite — the thin table itself is cheap; scope creep is the break point.

**Rejected alternatives:**
| Variant | Verdict | Reason |
|---------|---------|--------|
| internal/cli command registry that renders usage from registered cmds | **Selected** | V4 removes V1's real failure mode (usage banner drifting ... |
| Hand-authored static usage block in main (no framework) | Rejected | Accepts ongoing dual maintenance (switch + banner) whose refactor often never happens; loses the single-source win that V4 buys for nearly the same spend. Rejected after operator correction that near-zero-cost structure is not 'premature'. |
| Bare invoke = one-line tip; full intro lives under `pysar help` | Rejected | Fails the problem acceptance criterion: bare `pysar` alone must answer what this is and what to run next. |
| Adopt a CLI framework (e.g. cobra) with Long/Examples as the intro | Rejected | Real dependency and refactor cost for a two-command surface; V4 delivers discoverability without that blast radius. Revisit when flag trees or many subcommands justify it. |

**Predictions:**
| Claim | Observable | Threshold |
|-------|------------|-----------|
| Bare `pysar` prints a meaningful product intro with product identity, real commands from the registry, and at least one example — no hello-world | Run `pysar` with no args after install | stdout has no 'hello world'; cold reader can answer what Pysar is and can copy an example; listed commands match registered ones |
| Adding a new console subcommand updates both dispatch and usage list from one registration site | When the next real subcommand after init is added, diff shows registration in one place driving both paths | No separate hand-edited command list string required for that command to appear in bare-invoke usage |

## 4. Consequences

**Rollback plan:**
Triggers:
- Registry grows past name/summary/Run into unused flag/middleware machinery that blocks adding a real command
- Bare-invoke intro becomes harder to keep accurate or on-voice than a static string would have been
Steps:
1. Revert to printing a static usage block in cmd/pysar (V1 shape) while keeping command handlers
2. Delete or gut internal/cli if unused
3. Supersede this decision via haft_refresh if a framework (V3) is later bound
Blast radius: cmd/pysar and internal/cli only; no user data; high reversibility

**Refresh triggers:**
- Third+ console subcommand lands
- Operator adopts a CLI framework
- Usage output found lying about available commands

**Affected files:** cmd/pysar/**, internal/cli/**
