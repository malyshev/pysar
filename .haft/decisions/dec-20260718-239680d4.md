# Go single static binary

## 1. Problem Frame

**Signal:** Pysar needs to ship as a binary the user installs once and invokes globally to init/onboard new writing projects in arbitrary directories. Each project has its own topic/area and voice/surface config; the tool must manage several such projects side by side without cross-contamination. No tech stack has been chosen yet — TS/ES specs from onboarding describe the 5-layer editorial-engine architecture but are language/runtime-agnostic.

**Constraints:**
- Must support calling external LLM APIs (the editorial engine core is LLM-orchestration-heavy)
- Must not require the end user to install a separate language runtime just to run the tool
- Should not preclude the 5-layer functional-core/imperative-shell architecture already recorded in ES.enabling.architecture.001

**Acceptance:** A stack is selected such that: (1) it produces a single installable binary per target OS (at minimum macOS + Linux) with a standard install path; (2) the binary is globally invokable after install (on PATH); (3) it exposes init/onboard subcommands that scaffold a new project rooted at an arbitrary target directory; (4) multiple independently-configured projects (different topic/area, voice, target surface) coexist on one machine without shared/leaking state; (5) it is realistically maintainable by a solo maintainer with no CI yet.

## 2. Decision

**Selected:** Go single static binary

**Selection policy:** Pareto front, not a scalar winner. binary_distribution_fit (constraint) takes tie-break priority over code_reuse_from_existing_work once the latter was correctly discounted as CL1/illustrative-only evidence (operator correction, 2026-07-18). dogfood_consistency_with_haft is an observation and was never used to break ties, in either round of scoring.

**Why selected:** Rock-solid native binary distribution is a stated goal, and Go's cross-compilation story (single `go build` per GOOS/GOARCH, no per-OS build runners) is the most mature of all four variants for reasons independent of dogfooding. Against that stated goal, V2's strongest argument (direct reuse of that prior POC code) does not hold up -- prior writing POC is an explicitly dirty/experimental reference, not validated code -- so the remaining case for V2 (richer LLM ecosystem, faster iteration) is a bounded convenience, not a hard requirement Go cannot meet.


**Invariants:**
- The distributed Pysar binary remains a single self-contained executable requiring no separate language runtime install by the end user
- Cross-compilation for supported OSes (macOS, Linux at minimum) never requires physical per-OS build machines
- This decision governs distribution/language choice only -- it does not override the 5-layer functional-core/imperative-shell architecture already recorded in ES.enabling.architecture.001
- If the rollback trigger fires, the editorial-engine core's LLM-orchestration logic may be reconsidered for extraction into a separate process/sidecar before abandoning Go entirely, per the rollback steps

**Spec sections:**
- ES.enabling.architecture.001

## 3. Rationale

**Counterargument:** The strongest case against this decision is V2 (Bun-compiled TypeScript): it wins both llm_orchestration_ecosystem_fit and solo_maintainer_iteration_velocity for genuine, reference-independent reasons -- TS/Node's LLM SDK ecosystem is materially richer, and dynamic typing plus that ecosystem is faster to iterate on for a solo maintainer whose product requirements are still being discovered. Choosing binary robustness now trades away velocity on the part of the product where velocity plausibly matters most in the early phase. This is a real values call, not a one-sided one.

**Selected variant weakest link:** Go's LLM-orchestration ecosystem (prompt templating, streaming, structured-output parsing) is thinner than Python/TS -- more boilerplate to hand-roll for the editorial-engine core, which is the actually novel and still-being-discovered part of the product. If that boilerplate cost turns out to be unbounded rather than bounded, the ecosystem gap could become the dominant cost rather than a tolerable one.

**Rejected alternatives:**
| Variant | Verdict | Reason |
|---------|---------|--------|
| Go single static binary | **Selected** | Rock-solid native binary distribution is a stated goal, a... |
| Bun-compiled TypeScript binary (reuses prior writing POC's proven content stack) | Rejected | Loses the tie-break once rock-solid native binary distribution is treated as a stated goal: its cross-platform binary story is less turnkey than Go's, and its main supporting argument (prior writing POC code reuse) was downgraded from 'validated' to 'dirty/experimental reference' by the operator. |
| Rust single static binary | Rejected | Strictly dominated by V1: matches Go on binary_distribution_fit and cross_platform_binary_ease but loses on solo_maintainer_iteration_velocity (borrow-checker tax) with no offsetting gain on any dimension. |
| Python + uv-based packaging, positioned as a deliberate stepping stone | Rejected | binary_distribution_fit=poor is directly disqualifying once native binary robustness is a stated goal, regardless of its tie with V2 on ecosystem fit and iteration velocity. |

**Predictions:**
| Claim | Observable | Threshold |
|-------|------------|-----------|
| Go's native cross-compilation produces working macOS + Linux binaries from a single dev machine with no per-OS build runner required | Run `GOOS=darwin GOARCH=arm64 go build` and `GOOS=linux GOARCH=amd64 go build` from one machine, then execute each resulting binary on its target OS (or a VM/container for Linux) | Both binaries build without error and execute their `--version`/`init --help` output correctly with zero additional toolchain installs beyond the Go compiler itself |
| The Go LLM-orchestration boilerplate cost is bounded, not unbounded -- a first working editorial pass (idea -> stake/outline via an LLM API call) can ship in Go without abandoning the language | Time-to-first-working-editorial-pass in Go, compared against the rough estimate for the same pass in TypeScript | First working pass ships in Go within roughly 1.5x the TS-equivalent estimated time (not 3x+, which would indicate the ecosystem gap is the dominant cost) |

## 4. Consequences

**Rollback plan:**
Triggers:
- Building the first end-to-end editorial pass (e.g. idea -> stake/outline scaffolding via an LLM call) in Go takes materially longer than a rough TS-equivalent estimate, indicating the ecosystem gap is unbounded rather than tolerable
- Go's LLM-orchestration boilerplate (streaming, structured-output parsing) blocks forward progress on the editorial-engine core for more than ~2-3 weeks of active solo development
Steps:
1. Discard the Go scaffold/prototype built to that point (pre-code today, so this is low-cost)
2. Re-open this SolutionPortfolio (sol-20260718-56062837) and bind V2 (Bun-compiled TypeScript) via a new /h-decide, reusing the same comparison rather than re-exploring from scratch
3. Re-baseline ES.enabling.architecture.001 and any Go-specific affected_files listed below
Blast radius: Pre-implementation -- no users, no production data, no committed source tree yet. Rollback cost is bounded to discarded scaffolding and dev time already spent, not to any live system or user-facing regression.
