## 2. Decision

**Selection policy:** Pareto front over target-role dimensions (manual_testability, decision_measure_progress, dependency_readiness, relies_on_at_risk_decision), declared before scoring; loc_estimate is observation-role, watched per the ProblemCard's own 'lines of code' indicator, never optimized (Anti-Goodhart). **Why selected:** Singleton Pareto front in the re-run comparison (sol-20260718-fcc29be3): dominates the other four variants on manual_testability, decision_measure_progress, dependency_readiness, and relies_on_at_risk_decision. Scope corrected before this decision to match the already-bound on-disk-structure decision (dec-20260718-4b222794): pysar init writes .pysar/project (schema_version + host), no author-prose stub files (no idea.md/draft.md); pysar init --claude additionally writes host-specific files (e.g. CLAUDE.md) as a separate host-scaffold concern, isolated in its own function per dec-20260718-8278c494's migrate-to-registry stepping stone. ## 3. Rationale

**Counterargument:** The strongest argument against implementing now is that "optional --claude host files" is still a placeholder for an undecided file set -- I could unintentionally invent a CLAUDE.md convention that becomes sticky simply because it shipped first, the same failure mode (undecided structure treated as done) that this project's own note-20260718-d8d2744b warns against. Mitigation: keep the --claude host-file content minimal and explicitly provisional in this decision's scope, not a second undecided structure smuggled in under a decided one.

**Selected variant weakest link:** The piece-manifest side is no longer under-specified (dec-20260718-4b222794 settled that), but the --claude host-file content (what exactly goes in CLAUDE.md, whether .mcp.json is written, etc.) is still undecided by any DRR. Writing something here without a dedicated frame risks becoming de-facto convention lock-in nobody explicitly chose -- this is the portfolio's own weakest_link, narrowed to the part that's still genuinely open.
