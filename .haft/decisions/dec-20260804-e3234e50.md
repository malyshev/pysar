# Mirror dogfood doctrine exactly (OPTIMIZE before HUMANIZE)

## 1. Problem Frame

**Signal:** Pysar's editorial pipeline (internal/editorial: draft, staffedit, sharpen, humanize, export) has no phase that resolves [^shortname] citations into links, tunes title/subtitle for CTR + read-completion, or fills publish metadata (tags, meta description, slug) -- despite the dogfood project (a prior writing POC) having a mature reference implementation of exactly this (.cursor/skills/seo-optimizer), sequenced strictly WRITE -> SHARPEN -> OPTIMIZE -> HUMANIZE with a documented "never reorder" rationale (HUMANIZE deliberately de-sterilizes what OPTIMIZE smooths; reversing the order lets the later pass undo the earlier one). Operator asked for a --seo capability positioned after HUMANIZE and described it as also reducing "AI-written" signals, using a technique set (deliberate grammar-breaking, incomplete thoughts, "embracing messiness") that matches what Pysar's own ps-humanize skill already documents as "a draft prompt this project considered and declined" for serving no reader and existing only to defeat AI-detection classifiers. Operator wants the ordering doctrine discussed/possibly overridden rather than followed silently, and wants an evidence-based analysis of whether a distinct SEO-tuned humanize variant would outperform the current default humanize for search-engine outcomes specifically.

**Constraints:**
- Must not reintroduce AI-detector-evasion techniques (deliberate grammar-breaking, incomplete thoughts, "embracing messiness") into any humanize path without an explicit new operator-approved DecisionRecord that supersedes ps-humanize/SKILL.md's existing declared policy -- no silent reinstatement
- New phase output must follow Pysar's existing per-stage file convention (draft.md/staff-edit.md/sharpen.md/humanize.md are never mutated by later stages) -- the pre-SEO article snapshot must be preserved on disk in .pysar/, not overwritten in place
- No fabricated SEO claims (ranking-factor claims, stats) without grounding, mirroring the dogfood optimizer's existing "no new claims" discipline
- Whatever pipeline order is chosen must have explicit documented rationale, not a silent default in either direction

**Acceptance:** A --seo capability design is decided (skill/phase shape + pipeline position + humanize-variant question) and bound via /h-decide, where: (a) it delivers the dogfood-equivalent legitimate SEO work (citation resolution, title/subtitle tuning, meta description/tags/slug, scannability, outbound-link authority) verified by running it end-to-end on one real Pysar piece; (b) the pipeline-order choice (before vs. after humanize, or a split design) carries documented rationale addressing the dogfood's stated reason for its order, not a silent default; (c) the AI-detection-evasion question is resolved on evidence -- either rejected with a documented reason grounded in actual search-ranking-factor guidance, or accepted via an explicit new DecisionRecord that supersedes ps-humanize's existing declared policy, never a silent reinstatement.

## 2. Decision

**Selected:** Mirror dogfood doctrine exactly (OPTIMIZE before HUMANIZE)

**Selection policy:** Declared before scoring (compare step, sol-20260804-34a5dd17): eliminate any variant reintroducing declined AI-detector-evasion techniques (none eliminated -- all scored 0 on that constraint). Among survivors, maximize seo_value_coverage subject to resterilization_risk remaining 'low'; among candidates clearing that bar, prefer higher placement_fidelity; implementation_cost and pattern_reuse used only as tie-breakers. Mechanical application of this policy already pointed to V1; operator's explicit choice confirms it.

**Why selected:** Operator reviewed the Pareto front (V1/V3/V4) and explicitly chose V1: highest seo_value_coverage (90%), lowest resterilization_risk (low), and direct reuse of the dogfood's already-proven, fully-specified seo-optimizer implementation rather than inventing new verification or guardrail machinery. Operator explicitly confirmed the SEO step runs before humanize, accepting that SEO finishes before humanize rather than literally running last.


**Invariants:**
- When --seo is not passed, pipeline behavior and output files are byte-identical to pre-change Pysar (sharpen.md -> humanize.md directly, no new files)
- The SEO phase never mutates an earlier stage's file (draft.md, staff-edit.md, sharpen.md) -- it only reads them and writes its own new file
- Default ps-humanize skill contract and behavior are never modified by this decision -- no SEO-awareness or detector-evasion techniques added to humanize
- Zero [^shortname] citation markers remain in the SEO phase's output file when the phase completes successfully

## 3. Rationale

**Counterargument:** The operator's first, explicit request was SEO-after-humanize. Choosing V1 fully inverts that rather than partially honoring it (unlike V3's read-only post-humanize check or V4's literal post-humanize edit). If the operator's underlying goal was "the very last thing that happens to this article is discovery-optimized," V1 does not deliver that -- it delivers "discovery-optimization happened, then a separate voice pass ran after it and is authoritative over the shipped text." The operator's follow-up message ("SEO step before Humanize") resolves this explicitly in favor of the dogfood doctrine, but the gap between the original ask and the bound decision is real, not cosmetic, and worth keeping visible for future readers of this record.

**Selected variant weakest link:** Does not satisfy the operator's original ask that SEO run as the literal final stage -- SEO finishes before humanize, so humanize (not SEO) is the last thing that touches the article. Also: seo_value_coverage of 90% is a design-time estimate against the dogfood's checklist, not yet a measured result -- the new phase hasn't been implemented or run on a real Pysar piece.

| Post-humanize, metadata-only SEO pass (body untouched) | Rejected | Dominated in compare by the split dual-pass variant on every dimension -- same low risk, same partial placement fidelity, but materially less SEO value (40% vs 70% coverage). No scenario where this beats a front member. |

## 4. Consequences

**Rollback plan:**
Triggers:
- Real usage shows the --seo phase materially degrades a shipped article's discoverability or requires heavy operator rework versus not running it
- Operator later decides literal 'SEO happens last' is a hard requirement after all, superseding this decision
- The dogfood's own OPTIMIZE-before-HUMANIZE doctrine changes or is retired upstream
Steps:
1. Remove --seo flag wiring from the /ps orchestrator -- single flag/wiring removal, no data migration needed
2. Leave any already-shipped seo.md files in existing piece folders untouched as harmless historical artifacts
3. If reopening placement, supersede this decision via haft_refresh(action='supersede') before framing a replacement -- no silent contradiction
Blast radius: Limited to the new --seo flag path and its new SEO phase/skill -- default pipeline (--seo unset) is provably unaffected by design (invariant below), so rollback touches no existing shipped behavior.

**Refresh triggers:**
- Any change to ps-humanize/SKILL.md's declared policy on AI-detector-evasion techniques
- Any change to the dogfood's (prior writing POC) OPTIMIZE-before-HUMANIZE doctrine that this decision mirrors
- Addition of a COVER phase or other post-humanize stage that could reopen the placement question

**Affected files:** cmd/pysar/main.go, internal/editorial/passes.go, internal/editorial/humanize_pass.go, internal/mcpserver/piece_pass.go, cmd/pysar/assets/claude/skills/ps-humanize/SKILL.md, cmd/pysar/assets/claude/skills/ps/SKILL.md
