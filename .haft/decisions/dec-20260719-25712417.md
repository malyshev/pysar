# Per-file content-hash auto-refresh

## 1. Problem Frame

**Signal:** pysar init --force (just implemented, evidence attached to dec-20260718-fe926229) requires the operator to know about and explicitly type a flag to refresh a stale global skill -- this already caused real, repeated confusion (four separate incidents in one session) before the flag existed to fix it. Operator observes these global files (~/.claude/skills/ps-*) are system-owned and never hand-edited by the author, and proposes purging/recreating them automatically on reinstall so updates land with zero manual step. Operator explicitly requests exploring the full option space, not adopting this one proposal directly.

**Constraints:**
- Scope is strictly the global ~/.claude/skills/ps-* tree, which the operator has now explicitly classified as system-owned -- must not extend this same mechanism to project-local files (CLAUDE.md, .pysar/**, project .claude/settings.json, .mcp.json), which stay governed by the existing never-clobber-without-force behavior
- Must not silently destroy a genuine future customization if one ever exists, even if today's real-world risk is near-zero -- name the risk explicitly rather than assume it away
- Must work within the single static binary distribution model (dec-20260718-239680d4) -- no separate updater process or daemon
- Should not require the operator to remember a flag for the common, correct outcome of always running the current shipped version

**Acceptance:** A mechanism is selected such that: (1) after a pysar binary upgrade, the very next pysar init (no special flag required) leaves the operator running the current shipped skill content; (2) nothing is rewritten when installed content already matches the current shipped version -- repeated init with no upgrade in between causes zero unnecessary writes; (3) the mechanism's risk to a genuine future customization is explicitly named, not silently ignored.

## 2. Decision

**Selected:** Per-file content-hash auto-refresh

**Selection policy:** Pareto front over target-role dimensions (auto_reliability, unnecessary_churn, customization_risk), declared before scoring; new_state_files observation-role, never optimized. Policy fixed at comparison time (sol-20260719-51167bab), unchanged for this decision.

**Why selected:** V3 is the only variant satisfying all three of the ProblemCard's acceptance criteria at once: automatic correctness on the very next init after a shipped-content change, zero unnecessary churn on the common no-change case (only rewrites files that actually changed, unlike V2's blanket version-triggered purge), and an explicit, non-blind answer to the customization-risk constraint via per-file hash comparison. This directly improves on the operator's own original proposal (V2, coarse version-marker purge), which is formally dominated by V3 on both churn and risk.


**Invariants:**
- This mechanism only ever compares and acts on content the tool itself owns (the global ps-* skill tree) -- it never touches project-local files (CLAUDE.md, .pysar/**, project .claude/settings.json, .mcp.json)
- The --force flag remains available as an explicit manual override layered on top of automatic refresh, not removed
- Staleness/customization detection tracks per-file shipped-content identity via a hash manifest, not a single global version marker

## 3. Rationale

**Counterargument:** V3 adds real complexity -- a hash manifest to design, store, and keep consistent -- for a distinction (customization vs. staleness) that may not matter yet at Pysar's current single-skill scale, where no real customization has ever occurred. V5 (keep --force, add a staleness nudge) would have delivered equal safety with far less machinery today; V3 is a bet that this complexity pays for itself as more ps-* skills ship, not a free win.

**Selected variant weakest link:** The fallback policy for an ambiguous hash -- one matching neither the previously-shipped nor the currently-shipped content, i.e. looking like a real edit -- is not yet decided. This is V3's own stated weakest_link: the mechanism can detect this case but what it should DO about it (overwrite anyway, refuse and nudge, something else) is still open.

**Rejected alternatives:**
| Variant | Verdict | Reason |
|---------|---------|--------|
| Per-file content-hash auto-refresh | **Selected** | V3 is the only variant satisfying all three of the Proble... |
| V1 (Manual --force flag, already implemented) | Rejected | Dominated by V5 -- strictly worse, no compensating advantage. Superseded by this decision's automatic mechanism; --force is retained as a manual override, not removed. |
| V2 (Version-marker auto-refresh -- the operator's own original proposal) | Rejected | Dominated by V3 -- ties on automatic reliability but loses on both remaining target dimensions: purges every global skill file on any version bump regardless of whether that file actually changed (more churn), and has no way to ever detect or spare a real customization (higher risk). V3 keeps the automation the proposal wanted while fixing both of its weaknesses. |

| V5 (Manual --force plus automatic staleness nudge) | Rejected | Non-dominated and legitimate -- the safer, simpler alternative -- but does not fully satisfy the acceptance criterion that the next init after an upgrade just works with no manual step. Rejected in favor of closing that gap now rather than deferring it, given four real incidents already occurred under the fully-manual predecessor. |

**Predictions:**

## 4. Consequences

**Rollback plan:**
Triggers:
- The hash manifest becomes corrupted, missing, or inconsistent, and the fallback policy for that state was not implemented correctly, causing either false refreshes or false staleness reports
- A real customization is destroyed despite the hash-mismatch detection because the chosen fallback policy overwrites ambiguous hashes rather than sparing them
- The added complexity does not pay for itself as more ps-* skills ship, becoming a maintenance burden disproportionate to the benefit over simply keeping V5's simpler nudge-based approach
Steps:
1. If the fallback policy proves wrong in practice: revisit specifically that policy in isolation, not the whole per-file hash mechanism
2. If a real customization is destroyed: escalate to a stricter fallback (never auto-overwrite an ambiguous hash, only nudge -- reusing V5's nudge concept as the fallback behavior for exactly this case)
3. If complexity outweighs benefit at current scale: reopen this decision and reconsider V5, reusing sol-20260719-51167bab via a new /h-decide rather than re-exploring from scratch
Blast radius: cmd/pysar/main.go's global skill scaffolding logic, a new hash-manifest file under ~/.claude/skills/, the existing --force flag's role (retained as an explicit manual override layered on top of automatic refresh, not removed)

**Affected files:** cmd/pysar/main.go, cmd/pysar/init_test.go
