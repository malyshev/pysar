# Do not reject near-zero-cost structure as 'premature abstraction'

## Observations

- Operator rejects using 'premature abstraction' as a reason to prefer hardcoding when the structural alternative's incremental cost is near zero.
- For the CLI intro portfolio (sol-20260718-06d87720), V4 (tiny internal/cli registry) must be scored on concrete deltas vs V1 — lines/packages of indirection, risk of wrong registry shape if flag trees grow, and win of single-source command list — not on YAGNI rhetoric.
- Hardcoding the usage banner (V1) trades a few minutes now for ongoing dual-edit drift (switch + banner) that often never gets refactored; that deferred cost is real and must appear in V1's weakest link, not be waved away as future-you.

## Rationale

Calling something premature without naming what is spent and what is gained is an epistemic cheat: it sounds like prudence but encodes 'sorry I dumb, let me hardcode' and assumes a refactor window that rarely arrives. When cost ≈ nothing, structure that removes a named failure mode (banner lies by omission) is the default, not the luxury.
