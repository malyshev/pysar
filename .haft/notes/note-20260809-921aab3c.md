# Cursor cold-path failure is discoverability, not author inability to toggle

## Observations

- Operator clarification on prob-20260809-5a4334ac: the blocker is not that enabling project MCP is hard once found — it is that Cursor 3.x Customize → MCPs no longer surfaces project .cursor/mcp.json servers in the place authors expect after a year of the old Settings → MCP flow.
- Customize 'Connected' shows marketplace Plugin MCPs (e.g. Cloudflare) and does not guide the author to a workspace project server that is configured but disconnected.
- Pysar init --cursor currently assumes authors will find/enable project MCP; that assumption is false for the current Cursor product UX.

## Rationale

If Pysar's Cursor cold path depends on authors knowing where Cursor buried workspace MCPs, we are shipping against a host UX regression we do not control. Product variants must make Pysar appear where Cursor already shows Connected things (marketplace/deeplink) and/or remove the need to hunt, not teach PATH archaeology or Customize filter lore.

## Source

Operator message 2026-08-09: problem is not inability to enable — do not know where to look; Cursor does not help; year-old Cursor MCP settings flow broken by Cursor UI change. Prior logs: project-0-test-cursor-pysar stuck disconnected while Connected UI lists only Cloudflare plugins.
