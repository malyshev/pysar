# Message-noise gate: prevent verbosity/noise recurrence across CLI and agentic (ps-*) output

## Signal

This session repeatedly shipped noisy or pointless output from two surfaces Pysar itself produces for its own end users -- not Claude's own chat replies to the operator during development, which CLAUDE.md's existing Communication style section already governs. (1) CLI messages in cmd/pysar/main.go: fixed 3 times (raw path leakage, "already exists" read as an error, "differs" messages with no actionable info -- note-20260719-d883dd47, note-20260719-82ea61c0). (2) ps-voice/ps-style skill conversational output: fixed 3 times this session (dumping all Step 2 questions as one numbered list despite an explicit written prohibition, Step 6 firing a pointless "save a template of the template you didn't change" question, and after fixing that, Step 6 explaining its own skip instead of staying silent -- note-20260719-4638efd7, note-20260719-7ca22cda). Each fix was reactive, caught only via live operator testing, never proactively. Operator wants a structural gate against this recurring, not another one-off reactive patch.

## Problem Type

synthesis

## Constraints

- Must be distinct in scope from CLAUDE.md's existing Communication style section, which governs Claude's own chat replies to the operator during development, not what Pysar itself ships to its own end users via CLI or ps-* skills
- Must address both surfaces Pysar produces: static CLI output (directly testable) and agentic skill-prompt-governed live conversational output (not directly testable pre-runtime, since it is LLM-generated at conversation time, not static text in the repo)
- Must not be purely aspirational documentation alone -- already effectively tried once via existing prose guidance on an adjacent surface, already shown insufficient
- Reversible, low blast radius -- process/documentation plus at most a small test addition, not a schema or architecture change

## Acceptance

A concrete, reusable mechanism exists that: (1) is checked before any new/changed CLI message or skill conversational instruction is considered complete; (2) names the specific noise patterns already caught this session as concrete negative examples; (3) is a single source of truth that ps-* skills and future CLI message work reference, rather than each surface re-deriving its own rules ad hoc (as has happened 3 times, inconsistently, this session); (4) includes at least one genuinely testable/checkable component, not purely aspirational prose alone -- since CLAUDE.md's existing prose guidance for a related surface (Claude's own chat replies) already did not prevent 3 recurrences on these two adjacent surfaces this session.

## Blast Radius

CLAUDE.md (new dedicated section), cmd/pysar/assets/claude/skills/ps-voice/SKILL.md and ps-style/SKILL.md (reference the shared principle rather than re-deriving), cmd/pysar/init_test.go (possible regression tests), possibly a new .haft/specs/ file
