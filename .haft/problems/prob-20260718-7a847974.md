# Structural backstop for Pysar's editorial-engine orchestration: making pass-routing verifiable, not just prose-followed

## Signal

Pysar's editorial engine (per ES.enabling.architecture.001's skills/routing layer and ES.enabling.work_methods.001's actor/trigger/closing-check table) is currently specified but not enforced -- as designed today, it would rely on an LLM reading Markdown skill files and 'understanding' which pass to apply, the same shape as the operator's own Medium prototype, which the operator just identified as lacking any structural backstop: nothing prevents silently skipping a step, misrouting intent to the wrong pass, or completing a piece with no queryable record of what actually happened to it. This gap is real today, before any code exists, because it is baked into the current architecture decision's assumptions, not something introduced by a bug.

## Problem Type

synthesis

## Constraints

- Must be Pysar-original in mechanism -- haft's own typed-graph/carrier model is inspiration only (CL1 max per dec-20260718-eafefad2), not something Pysar imports or depends on at runtime; haft governs Pysar's own engineering decisions, it is not a runtime dependency of the shipped product
- Must fit inside the already-decided 5-layer architecture (ES.enabling.architecture.001) -- this is naturally an Artifact/state-layer concern, alongside the draft/ship-ready/checklist artifacts already specified in ES.enabling.work_methods.001
- Must not require the non-technical author to do anything manual -- no tagging, no explicit logging commands, consistent with the already-recorded author-surface promise
- Must be complementary to, not overlapping with, the memory engine just decided (dec-20260718-404573a2) -- that governs cross-piece repetition; this governs within-piece/per-session pass accountability

## Acceptance

Given a piece that moves through Pysar's editorial engine (idea -> draft -> edit passes -> ship-ready), there is an observable, queryable record of which passes actually ran, in what order, with what relevant inputs (e.g. which voice/persona config was active, whether voice-lock ran before or after packaging as TS.target.boundary.001 requires) -- checkable after the fact without re-reading an AI chat transcript, and at least one known bad sequence (voice-lock before packaging) is either prevented outright or reliably detectable, not merely hoped against.

## Blast Radius

Every piece that moves through Pysar's editorial engine once built; touches ES.enabling.work_methods.001's closing-check column directly and ES.enabling.architecture.001's Artifact/state layer
