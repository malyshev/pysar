# pysar init host-selection mechanism: --claude default, extensible to --cursor/--codex later

## Signal

dec-20260718-239680d4 already committed to init/onboard subcommands scaffolding a new project in an arbitrary directory; ES.enabling.agent_policy.001 already named Claude Code as the currently-supported host, Cursor/Codex experimental/deferred. Not yet decided: how pysar init selects and applies host-specific scaffolding -- operator wants --claude as the explicit flag (default when omitted), with a genuine extension point for --cursor/--codex to be added later without restructuring the command.

## Problem Type

synthesis

## Constraints

- Must not build a general-purpose plugin/registry system for 3 hosts, 2 of which don't exist yet -- match CLAUDE.md's own stated discipline against designing for hypothetical requirements, while still satisfying the operator's explicit 'window for extension' ask
- Must be consistent with dec-20260718-a2a24f32: init is a pysar console subcommand, not part of the ps-*/`/ps` agentic-tool surface
- Must build on the greenfield Go foundation already established (dec-20260718-817bfb74) -- plain go build/go install, no wrapper tool yet

## Acceptance

pysar init [--claude|--cursor|--codex] [dir] is implemented such that: (1) omitting the flag defaults to Claude Code scaffolding; (2) --claude explicitly requests the same; (3) --cursor/--codex are recognized as valid flag values at the CLI-parsing level today, even though their scaffolding logic isn't implemented yet -- invoking them yields a clear 'not yet supported' message, not a parse error or silent no-op; (4) adding real Cursor/Codex support later touches only host-specific scaffold logic, not the flag-parsing/dispatch shape.

## Blast Radius

Shape of the first real, user-facing pysar subcommand -- sets the pattern future subcommands (onboard, etc.) will likely follow
