# Close the distributed-guard gap: structurally force every pass to declare its own precondition check

## Signal

dec-20260718-20a08f83 bound the distributed precondition-guard mechanism for Pysar's editorial pipeline, with an explicitly named weakest_link: nothing structurally forces a future pass to declare its own precondition check -- a careless pass could omit one and nothing catches it before shipping. That decision's own rollback plan named a review-discipline mitigation as a 'cheap stopgap, not a fix.' Operator wants a real structural fix adopted now, while no real passes exist yet and the cost of fixing this is lowest, rather than waiting for the rollback plan's named trigger (a real pass shipping without a check, or auditability becoming a practical problem).

## Problem Type

synthesis

## Constraints

- Must not reintroduce a central phase-transition table (re-adopting the rejected FSM variant from dec-20260718-20a08f83's own comparison) unless explicitly chosen as the answer, with that reopening named plainly
- Should compose with, not duplicate, dec-20260718-6ba897d4's run-log
- Pure Go / stdlib-preferred, consistent with the project's established minimal-new-tooling preference (dec-20260718-817bfb74) unless a real gap forces otherwise

## Acceptance

A concrete mechanism (or composed set of mechanisms) is selected such that: (1) a pass registered without a precondition check either fails to compile, or fails loudly at a well-defined point before it can ever run against a real piece -- never silently; (2) the mechanism does not require abandoning dec-20260718-20a08f83's chosen approach (distributed guards) unless the comparison concludes that is genuinely warranted, in which case that must be named explicitly as reopening the prior decision, not smuggled in as a cleanup.

## Blast Radius

How every future pass declares and gets checked for its precondition -- touches the same surface as dec-20260718-20a08f83 itself
