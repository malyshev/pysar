# SEO/publish-packaging phase for Pysar's editorial pipeline, and its relationship to HUMANIZE

## Signal

Pysar's editorial pipeline (internal/editorial: draft, staffedit, sharpen, humanize, export) has no phase that resolves [^shortname] citations into links, tunes title/subtitle for CTR + read-completion, or fills publish metadata (tags, meta description, slug) -- despite the dogfood project (a prior writing POC) having a mature reference implementation of exactly this (.cursor/skills/seo-optimizer), sequenced strictly WRITE -> SHARPEN -> OPTIMIZE -> HUMANIZE with a documented "never reorder" rationale (HUMANIZE deliberately de-sterilizes what OPTIMIZE smooths; reversing the order lets the later pass undo the earlier one). Operator asked for a --seo capability positioned after HUMANIZE and described it as also reducing "AI-written" signals, using a technique set (deliberate grammar-breaking, incomplete thoughts, "embracing messiness") that matches what Pysar's own ps-humanize skill already documents as "a draft prompt this project considered and declined" for serving no reader and existing only to defeat AI-detection classifiers. Operator wants the ordering doctrine discussed/possibly overridden rather than followed silently, and wants an evidence-based analysis of whether a distinct SEO-tuned humanize variant would outperform the current default humanize for search-engine outcomes specifically.

## Problem Type

synthesis

## Constraints

- Must not reintroduce AI-detector-evasion techniques (deliberate grammar-breaking, incomplete thoughts, "embracing messiness") into any humanize path without an explicit new operator-approved DecisionRecord that supersedes ps-humanize/SKILL.md's existing declared policy -- no silent reinstatement
- New phase output must follow Pysar's existing per-stage file convention (draft.md/staff-edit.md/sharpen.md/humanize.md are never mutated by later stages) -- the pre-SEO article snapshot must be preserved on disk in .pysar/, not overwritten in place
- No fabricated SEO claims (ranking-factor claims, stats) without grounding, mirroring the dogfood optimizer's existing "no new claims" discipline
- Whatever pipeline order is chosen must have explicit documented rationale, not a silent default in either direction

## Optimization Targets

- Real search-engine discoverability/quality of shipped articles (title/meta/tags/citations/scannability, grounded in actual documented ranking-factor guidance)
- Coherence with Pysar's existing pipeline conventions and prior decisions (per-stage files, MCP-mediated writes, host-agnostic skills)

## Observation Indicators

- AI-detection-evasion score / ability to fool a classifier -- explicitly not an optimization target; optimizing directly for this is the failure mode the prior declined prompt exhibited

## Acceptance

A --seo capability design is decided (skill/phase shape + pipeline position + humanize-variant question) and bound via /h-decide, where: (a) it delivers the dogfood-equivalent legitimate SEO work (citation resolution, title/subtitle tuning, meta description/tags/slug, scannability, outbound-link authority) verified by running it end-to-end on one real Pysar piece; (b) the pipeline-order choice (before vs. after humanize, or a split design) carries documented rationale addressing the dogfood's stated reason for its order, not a silent default; (c) the AI-detection-evasion question is resolved on evidence -- either rejected with a documented reason grounded in actual search-ranking-factor guidance, or accepted via an explicit new DecisionRecord that supersedes ps-humanize's existing declared policy, never a silent reinstatement.

## Blast Radius

Pysar CLI surface (new --seo flag), internal/editorial pipeline architecture, ps-humanize skill contract (cmd/pysar/assets/claude/skills/ps-humanize/SKILL.md), any new ps-seo/ps-optimize skill, pipeline doctrine documentation
