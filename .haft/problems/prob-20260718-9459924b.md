# Onboarding command architecture: orchestrator vs standalone vs precondition-driven

## Signal

Operator proposes /ps-onboard as an orchestrator command invoking /ps-voice and /ps-style separately, motivated by wanting voice/style independently re-tunable later, not just once at init. This is the first concrete command-surface design for the schema-only onboarding engine (dec-20260718-5570376d) and must use the ps-* naming convention (dec-20260718-a2a24f32, which explicitly left the actual command list open -- "No command list is being decided here"). Must also consider whether a bespoke orchestrator duplicates the Pass/Precondition pipeline mechanism currently being rebuilt (dec-20260718-20a08f83, dec-20260718-ffbfb04b) for tracking "what's done, what's needed" rather than reusing it.

## Problem Type

synthesis

## Constraints

- Must use ps-* subcommand / /ps auto-mode naming convention (dec-20260718-a2a24f32); this stays on the agentic surface, no console pysar binary involvement, per dec-20260718-5570376d
- Go engine layer stays schema+validation only -- these are skill/prompt-level commands, not new Go engine code, per dec-20260718-5570376d's own invariant
- Should not duplicate the Pass/Precondition mechanism (dec-20260718-20a08f83, dec-20260718-ffbfb04b) with a parallel bespoke 'is onboarding done' tracker if that mechanism can express it directly
- One voice/style profile per project, no cross-project registry (dec-20260718-e84221af)

## Optimization Targets

- ease of re-invoking voice or style tuning independently after initial onboarding
- how much new orchestration logic/state must be hand-built vs reused from the already-decided precondition mechanism

## Observation Indicators

- number of distinct command/skill files needed
- whether onboarding completeness state duplicates or reuses Pass/Precondition tracking

## Acceptance

A command architecture is selected such that: (1) an author can run one command to complete first-time onboarding (voice + style) in one go; (2) an author can also independently re-invoke voice tuning or style tuning alone at any later time, without re-running the other; (3) the mechanism for knowing "what's already set up" does not duplicate the Pass/Precondition tracking mechanism if that mechanism can express it directly.

## Blast Radius

New skill/slash-command files scaffolded by pysar init --claude, the internal/onboarding schema package (dec-20260718-5570376d), possibly the internal/editorial Pass registry if reused

## Reversibility
