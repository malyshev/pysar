# Local dev/build loop for Pysar's greenfield Go skeleton: build, install, iterate

## Signal

The tech stack (Go, dec-20260718-239680d4) and 5-layer architecture (ES.enabling.architecture.001) are decided, but no code or build tooling exists yet, and there is no established local development loop -- build, install a runnable pysar binary, verify, repeat -- comparable to what the dogfood haft project has (Taskfile.yaml, install.sh, goreleaser). Operator wants a genuine greenfield hello-world Go project rooted at this directory that builds, installs locally (on PATH or via an alias) so each implementation step can be verified end-to-end as it's built, and eventually produces the cross-compiled installable artifacts already decided. Haft may be consulted for code-standard/design inspiration, capped per the reference-agnosticism gate (dec-20260718-eafefad2) -- never copied, never sole justification.

## Problem Type

synthesis

## Constraints

- Must not depend on haft's own build scripts, config, or code at runtime or build time -- may consult them for structure/naming inspiration only (CL1 max, explicit Pysar-original divergence stated), per dec-20260718-eafefad2
- Must respect dec-20260718-239680d4's invariants: single self-contained executable, no separate runtime for the END USER, native cross-compilation without per-OS build machines
- Must be realistically maintainable by a solo maintainer with no CI yet, echoing the original tech-stack acceptance criterion

## Acceptance

A local dev/build loop is chosen such that: (1) one command from the project root builds a pysar binary; (2) one command installs/updates that binary on the operator's PATH (or an explicit alias) so invoking pysar picks up the latest local build; (3) the first working version proves the whole loop end-to-end via real observable output (e.g. pysar --version or pysar hello actually runs after build+install); (4) the project layout matches what dec-20260718-239680d4 already named as affected_files (cmd/pysar/**, internal/**).

## Blast Radius

Establishes the actual first real source tree; every subsequent implementation step builds on this foundation. Cheap to get wrong now (no real code depends on it yet), more annoying to change once real commands exist.
