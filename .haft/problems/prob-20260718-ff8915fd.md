# CLI framework for Pysar: adopt Cobra vs. keep the existing hand-rolled internal/cli registry

## Signal

The requested rich root-command intro (product header, examples, available-commands list on bare invoke or --help, matching haft's own cobra-rendered root command) has already been implemented via a small, tested, stdlib-only internal/cli registry (internal/cli/registry.go, ~90 lines, passing tests) -- not via Cobra. Operator explicitly asked to run /h-reason on 'adopt Cobra', so the open question is whether Cobra should replace this already-working, already-tested implementation, or whether it should remain and Cobra should not be adopted.

## Problem Type

synthesis

## Constraints

- Cobra is the library haft happens to use -- if named as inspiration, that stays capped and scored on its own merits, never sole justification for adopting it here, per the same evidence-congruence discipline as dec-20260718-eafefad2
- Must not leave two competing CLI-dispatch mechanisms coexisting in the codebase after this decision -- pick one
- Must respect dec-20260718-817bfb74's build-loop decision (plain go build/install) -- adding Cobra doesn't change the build mechanism itself, but does add go.sum dependency entries a stdlib-only philosophy should be aware of

## Acceptance

A CLI-framework approach is selected such that: (1) it delivers the rich root-command intro already validated by registry_test.go's expectations (header, examples, available-commands list); (2) it's evaluated against dec-20260718-817bfb74's no-wrapper-tool build philosophy (new external dependency vs. staying stdlib-only) without silently contradicting it; (3) the decision states plainly whether internal/cli/registry.go and its tests are kept, replaced, or wrapped -- not left in an ambiguous, half-migrated state.

## Blast Radius

Every future subcommand's flag-parsing and help-text shape
