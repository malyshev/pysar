# Distribution/install mechanism so end users can install pysar locally without building from Go source

## Signal

Verified on disk: Pysar has no git remote at all (git remote -v returns empty -- purely local repo, never pushed anywhere), no README.md, no GitHub Actions workflows, no GoReleaser config, and no install script. The only distribution artifact is .pysar-repo-root/dist/ containing 3 manually-built binaries (linux-amd64, windows-amd64, windows-arm64, last built 2026-07-18/19) that are gitignored and NOT git-tracked -- purely local build leftovers, no macOS build despite the operator's own machine being macOS, no checksums, no version tagging. Operator wants an install experience for end users similar to /Users/malyshev/Projects/Me/haft's: verified haft ships install.sh (curl -fsSL <url>/install.sh | bash, OS/arch detection, downloads from GitHub Releases API, installs to ~/.local/bin or /usr/local/bin), backed by .goreleaser.yaml (cross-platform build + archive + checksum config) and .github/workflows/release.yml + install-test.yml (CI that builds and publishes releases on tag push, and tests the install script itself). None of this scaffolding exists for Pysar today -- this is a build-from-scratch synthesis problem, not a tweak.

## Problem Type

synthesis

## Constraints

- Must not push this local-only repo to any remote, or make any repo public, without a separate, explicit operator confirmation at that specific step -- creating a public release pipeline is a one-way-ish door (once released, hard to fully unpublish) distinct from and downstream of choosing HOW to distribute
- Must produce genuine working builds for the operator's own platform (macOS) at minimum -- current dist/ artifacts don't even cover it
- Must not require the end user to have Go toolchain installed -- a `go install` instruction alone does not satisfy "similar to haft", which explicitly targets people without a Go dev environment
- Whatever CI/release mechanism is chosen must be maintainable by this project's actual scale (single maintainer, no existing CI history) -- do not port haft's full pipeline complexity (goreleaser + multi-workflow CI + sidecar-runtime installs) uncritically when Pysar has no equivalent sidecar/runtime dependency to install

## Optimization Targets

- Genuine one-command install experience for a non-Go-developer end user, matching the ease of haft's install.sh
- Low ongoing maintenance burden proportionate to this project's actual size/team (currently one operator, no existing release history)

## Observation Indicators

- Feature/scope parity with haft's full release pipeline -- watch, don't chase; haft's pipeline serves a different-shaped project (sidecar runtimes, 15 skills, longer history) and copying its full shape uncritically would be scope-mirroring, not need-driven design

## Acceptance

An end user on macOS, Linux, and Windows can install a working pysar binary onto their machine via one documented command, without having Go installed or building from source themselves, and pysar init works immediately after -- verified by actually running the chosen install method on a clean machine/container per platform (or at minimum macOS + Linux, given no Windows test environment is readily available this session) and confirming `pysar --version` and `pysar init` both work post-install.

## Blast Radius

New: README.md, install.sh (or equivalent), .goreleaser.yaml or hand-rolled build scripts, .github/workflows/ (if GitHub is the chosen host) -- and, gated separately, the repo's remote/visibility status itself (currently none)
