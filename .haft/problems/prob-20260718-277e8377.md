# Reusable questionnaire engine for onboarding (voice + writing-style capture), not hardcoded scripts

## Signal

After pysar init, an author needs onboarding to establish at least two things: voice (how they want to sound) and writing style. Operator wants this built as a general-purpose questionnaire engine/mechanism -- an enabling-system architecture decision -- rather than a heap of hardcoded per-questionnaire scripts, so future questionnaires beyond these first two can be added without engine-level rework. This is developer-facing framing ("as a developer I want...") -- the question is HOW the engine is built, not WHETHER onboarding needs a questionnaire (operator has already decided that).

## Problem Type

synthesis

## Constraints

- Must fit the already-decided 5-layer architecture and the Go/Cobra stack -- no new language/runtime (dec-20260718-239680d4, dec-20260718-fd782668, dec-20260718-817bfb74)
- Must not force pipeline/phase vocabulary or a rigid-form feel onto the author surface -- answers should read as conversational (TS.environment-change.001 author-surface principle)
- Must compose with the already-decided on-disk manifest (dec-20260718-4b222794) for persistence -- no separate ad hoc storage format
- external POCs/haft citations CL1 max, never sole justification, must name Pysar-original divergence (dec-20260718-eafefad2)
- One voice/style profile per project, no cross-project persona registry (dec-20260718-e84221af)

## Optimization Targets

- ease of adding a new questionnaire later without touching engine code
- how naturally the interaction reads on the author surface, not form-like

## Observation Indicators

- lines of new code
- number of files needed to add one new questionnaire

## Acceptance

A mechanism is selected such that: (1) adding a new questionnaire (a third one, hypothetically) requires adding declarative content/data or a schema, not new engine code; (2) captured answers persist into the already-decided on-disk manifest structure (dec-20260718-4b222794), structured and queryable, not just prose notes; (3) the interaction can read as natural conversation on the author surface, not a rigid form, even though the underlying data model is structured.

## Blast Radius

A new internal package (questionnaire/onboarding engine), the .pysar/project manifest schema (new fields for captured profiles), and any future CLI or agentic (ps-*/  /ps) entry point that triggers onboarding
