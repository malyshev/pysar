# Tech stack for Pysar as an installable, globally-accessible multi-project CLI

## Signal

Pysar needs to ship as a binary the user installs once and invokes globally to init/onboard new writing projects in arbitrary directories. Each project has its own topic/area and voice/surface config; the tool must manage several such projects side by side without cross-contamination. No tech stack has been chosen yet — TS/ES specs from onboarding describe the 5-layer editorial-engine architecture but are language/runtime-agnostic.

## Problem Type

synthesis

## Constraints

- Must support calling external LLM APIs (the editorial engine core is LLM-orchestration-heavy)
- Must not require the end user to install a separate language runtime just to run the tool
- Should not preclude the 5-layer functional-core/imperative-shell architecture already recorded in ES.enabling.architecture.001

## Acceptance

A stack is selected such that: (1) it produces a single installable binary per target OS (at minimum macOS + Linux) with a standard install path; (2) the binary is globally invokable after install (on PATH); (3) it exposes init/onboard subcommands that scaffold a new project rooted at an arbitrary target directory; (4) multiple independently-configured projects (different topic/area, voice, target surface) coexist on one machine without shared/leaking state; (5) it is realistically maintainable by a solo maintainer with no CI yet.

## Blast Radius

Whole enabling system — this is the foundational language/runtime/packaging choice everything else (skills, MCP-equivalent surface, multi-project state) gets built on top of

## Reversibility

low
