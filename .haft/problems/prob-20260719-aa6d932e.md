# Style profile content fit: does Style's structural/mechanical content have a genuine home in the shared Profile schema?

## Signal

dec-20260718-ab150a73 already decided VoiceProfile and StyleProfile share exactly one Go struct type (Tone, Formality, SentenceLength, Register, BannedPhrases, Notes, Goldens) with "no divergent format" as an explicit invariant. That schema's field names and the MCP tool descriptions built on it (save_voice_profile's "tone": "How the author wants to come across, e.g. warm, direct, a little dry") were authored with voice/personality content specifically in mind. Operator now wants a /ps-style command and has explicitly distinguished the two: "Style is not personality... the shared rules for structure, sentences, word choice, and formatting... put the main point first, keep sentences short, use active voice, prefer everyday words, be specific, cut what doesn't earn its place." Several of the operator's own example style rules (main-point-first ordering, active voice, cut-what-doesn't-earn-its-place) have no clean home in the current four structured fields -- Tone in particular reads as purely voice-specific. Need to decide how Style's actual content populates (or extends) the shared schema before building /ps-style, rather than forcing a mismatch or silently diverging from the already-decided invariant.

## Problem Type

synthesis

## Constraints

- Any change must not silently contradict dec-20260718-ab150a73's "no divergent format" invariant without an explicit supersede -- if the answer requires diverging, that must be examined and decided, not assumed
- Whatever schema shape wins must still satisfy dec-20260718-5570376d's completeness-validator requirement (structured fields + goldens both checkable)
- Must not require internal/onboarding's already-shipped generic machinery (Render, Validate, TemplatesDir, Slug, WrapTemplate/UnwrapTemplate) to be duplicated per-Kind unless the chosen variant explicitly justifies that cost
- The /ps-style skill's questions to the author must read naturally as style questions, not voice questions wearing a style disguise
- Must not disturb the already-shipped, already-dogfooded VoiceProfile behavior or its saved .pysar/voice.md format

## Acceptance

A schema shape is chosen such that Style's actual content (main-point-first structure, short sentences, active voice, everyday words, specificity, editorial cutting) has a genuinely fitting structured home -- not force-fit into voice-flavored field names or dumped entirely into free text -- while /ps-style and /ps-voice both remain built on dec-20260718-5570376d's schema-only, completeness-validated architecture. Verified by actually authoring a real style profile against the chosen shape and confirming it reads as genuine style guidance, not repurposed voice fields.

## Blast Radius

internal/onboarding/profile.go (Profile struct, possibly a new field), internal/mcpserver (new save_style_profile/save_style_template tools mirroring voice's), cmd/pysar/assets/claude/skills/ps-style/SKILL.md (new), cmd/pysar/assets/templates/style/ (new built-in generic default)
