# Persistence delivery for ps-* skill outputs: avoid raw file-write permission prompts for non-technical authors

## Signal

/ps-voice persists via the skill's own Write tool call directly to .pysar/voice.md, which triggers Claude Code's per-write permission prompt -- confirmed by operator's real test ("claude code asked me for permissions write JSON"). Operator contrasts this with haft's own MCP-tool-based persistence (haft_note, haft_decision, etc.), which never prompts in this repo. Investigation of .claude/settings.local.json shows that's because this repo explicitly allowlists those specific MCP tool names in permissions.allow -- not because MCP calls are inherently prompt-free. A parallel mechanism exists for direct file writes: Claude Code's own docs confirm a committed .claude/settings.json can pre-approve Write(pattern) for specific paths, applying to any user who opens the project, the same allow-rule mechanism haft already relies on. Target audience is explicitly a "wide non-tech target group" (dec-20260718-ab150a73's own framing) -- a raw permission prompt naming a file path and requiring the author to understand "write" access is real friction for that audience.

## Problem Type

synthesis

## Constraints

- Must not violate dec-20260718-5570376d's schema-only invariant -- the Go engine layer defines schema+validation only, never conducts the questionnaire; a persistence mechanism is a different concern but must not smuggle in orchestration logic
- If a server component is introduced, it must ship inside the same pysar binary (e.g. a subcommand), not a separate install -- single static binary constraint (dec-20260718-239680d4)
- Pre-approving Write access is a trust decision, not just a UX one -- scope must be demonstrably narrow (only Pysar-managed paths under .pysar/**), never broad or arbitrary
- Must work for the same non-technical target audience dec-20260718-ab150a73 was framed around

## Optimization Targets

- how much permission-prompt friction a first-time non-technical author experiences during /ps-voice
- new component/maintenance cost introduced

## Observation Indicators

- new files/processes/binaries introduced
- whether the mechanism has been directly verified to suppress prompts, not just assumed

## Acceptance

A persistence mechanism is selected such that: (1) a first-time author using /ps-voice in a fresh pysar init'd project experiences zero, or clearly pre-explained, permission prompts for saving their own voice profile; (2) the mechanism's security scope is demonstrably narrow (limited to Pysar-managed paths, never arbitrary filesystem access); (3) the author never needs to understand implementation terms (JSON, MCP, permission scopes) to complete the flow.

## Blast Radius

pysar init scaffold output (may add .claude/settings.json), possibly a new pysar serve subcommand and MCP tool surface if that path is chosen, ps-voice (and future ps-*) skill content
