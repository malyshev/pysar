# Pipeline/orchestration mechanism: shared execution model every future Pysar command plugs into

## Signal

Pysar's editorial engine needs a shared execution model that every future author-facing command (idea scaffolding, draft intake, editing passes, voice-lock, research, packaging) plugs into as an entry point to a single, orchestrated flow -- analogous to how haft's own note/decide commands share one underlying kernel. Nothing defines this today: ES.enabling.architecture.001 names the layers and ES.enabling.work_methods.001 names the artifact-per-pass table, and dec-20260718-6ba897d4 established a per-piece run-log, but nothing defines HOW a pass is actually invoked, sequenced, gated by preconditions, or composed into a full end-to-end flow. Medium's own AGENTS.md (operator's prior prototype) already has a complete, battle-tested prose design for exactly this: a canonical phase order (INTAKE -> RESEARCH? -> WRITE -> STAFF-EDIT -> SHARPEN -> OPTIMIZE -> HUMANIZE -> COVER), a Status enum persisted per-piece gating what can run next, an artifact-per-phase convention, hard non-reorderable doctrine (HUMANIZE must follow OPTIMIZE), a skill-picker table mapping author intent to command, and pre/post-flight discipline every skill follows -- all of it prose an LLM reads and follows each session, none of it code-enforced.

## Problem Type

synthesis

## Constraints

- Scoped to the MECHANISM (how passes are invoked/sequenced/gated), not the actual phase list/names -- Pysar's own pass vocabulary is separate future work, consistent with TS.environment-change.001 keeping harness-internal phase names off the author surface
- Medium's AGENTS.md is real, battle-tested prior art from the operator's own prototype -- citing its structural pattern (status enum, phase order, skill picker, pre/post-flight discipline) is legitimate CL1-capped inspiration per dec-20260718-eafefad2, never sole justification, and Pysar's own pass content/names must be original
- Must fit inside the already-decided 5-layer architecture (ES.enabling.architecture.001) and compose with, not duplicate, the already-decided run-log (dec-20260718-6ba897d4) and memory engine (dec-20260718-404573a2)
- Must respect the Go/Cobra stack already decided (dec-20260718-239680d4, dec-20260718-fd782668) -- no new language/runtime

## Acceptance

A pipeline/orchestration mechanism is selected such that: (1) it defines a concrete, nameable way to add a new author-facing command as 'an entry point to a single pipe' -- not a vague aspiration; (2) it states plainly whether hard-ordering rules (the equivalent of Medium's 'HUMANIZE must follow OPTIMIZE') are enforced in code or remain documentation-only, and if documentation-only, that is named as a real weakest_link, not glossed over; (3) it states whether 'what state is this piece in, what can run next' is answerable by a structured query/type, or only by reading files by hand.

## Blast Radius

The execution model for every future Pysar editorial command -- the largest-blast-radius architectural decision in the project so far, since every command built after this inherits its shape
